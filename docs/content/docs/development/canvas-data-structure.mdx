# Canvas Data Structure

This document describes where canvas data lives and how it is shaped. After the resource migration, canvases, assets, generation records, and media are all server-authoritative; the browser keeps only UI state, Agent sessions, and the prompt cache.

## Storage

Server side (authoritative):

- Canvas projects, assets, and generation records live in MySQL behind `/api/canvases`, `/api/assets`, and `/api/generations`.
- Media binaries (images, videos, audio) are stored under the api's `MEDIA_ROOT` with the `local` driver (the `data/media` bind mount in compose) or in a private S3-compatible bucket with the `s3` driver; they are always served through `/api/media/{storageKey}`.
- Canvas export and import: exporting a canvas downloads each media file from `/api/media` by `storageKey`; importing uploads media first and then creates the canvas or asset.

Browser side (non-authoritative only; clearing it loses no business data):

- UI and preference state: the `app_state` store of the `infinite-canvas` localForage database, keyed entries such as theme, locale, config preferences, the plugin list, and prompt-source switches (keys like `infinite-canvas:theme_store`).
- Agent sessions: Canvas Agent chat messages and local thumbnail references, stored with the session independently of canvas project data.
- Prompt cache: the `prompt_cache` store of the same localForage database, caching the last successful fetch of third-party prompt sources.

The browser no longer stores canvases, assets, generation records, or media binaries. The legacy localForage `image_files` / `media_files` stores are obsolete; existing local data is not uploaded automatically — export with the old version first and import in the new version if you need to keep it.

## The canvas data payload

Canvas content is persisted as the `data` field on the server (2 MB limit per canvas). The canvas `id`, `title`, and `revision` are managed as server-side record fields, not part of `data`.

```ts
type CanvasData = {
  nodes: CanvasNodeData[];
  connections: CanvasConnection[];
  chatSessions: CanvasAssistantSession[];
  activeChatId: string | null;
  backgroundMode: "lines" | "dots" | "blank";
  showImageInfo: boolean;
  viewport: { x: number; y: number; k: number };
};
```

- `nodes`: canvas nodes.
- `connections`: edges store only node IDs; paths are calculated while rendering.
- `chatSessions` / `activeChatId`: in-canvas assistant sessions.
- `backgroundMode`: canvas background.
- `showImageInfo`: whether image info is displayed.
- `viewport`: screen translation in `x`/`y` and scale in `k`.

## Nodes

Each node is a `CanvasNodeData`:

```ts
type CanvasNodeData = {
  id: string;
  type: CanvasNodeTypeId;
  title: string;
  position: { x: number; y: number };
  width: number;
  height: number;
  metadata?: CanvasNodeMetadata;
};
```

- `type`: six built-ins (`image` / `text` / `config` / `video` / `audio` / `group`); plugin nodes use open strings of the form `"<pluginId>:<name>"`.
- `position` / `width` / `height`: canvas-world coordinates, not screen coordinates.
- `metadata`: per-type content and business state. Common fields include `content`, `prompt`, `status`, `fontSize`, `generationMode`, `model`, `size`, `count`, `naturalWidth/naturalHeight`, `freeResize`, `images` (multi-image slots), `primaryImageId`, `inputOrder`, `storageKey`, `mimeType`, `bytes`, and `videoTaskId`.
- Image and video nodes keep a display URL plus a `storageKey`; the actual media is served by the backend from that key. Deleting nodes, canvases, or assets cleans up their exclusive media on the server by reference.

## Assistant sessions

Assistant sessions are stored inside the canvas `data`:

```ts
type CanvasAssistantSession = {
  id: string;
  title: string;
  messages: CanvasAssistantMessage[];
  createdAt: string;
  updatedAt: string;
};
```

Canvas Agent (Codex) conversations are not part of this structure: Agent messages are owned by `threadId` / `turnId` / `itemId` and stored with the Agent's local storage independently; once a history snapshot becomes authoritative, live events are not merged twice.
