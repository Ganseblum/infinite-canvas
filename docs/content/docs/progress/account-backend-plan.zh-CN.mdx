# 账号体系与后端服务规划

本文档规划把无限画布从「纯前端本地应用」改造为「前后端分离的多用户系统」：新增一个 Go 后端服务，提供登录注册、数据云端同步和用户权益，通过 Docker 部署在自有服务器上。

本文档只描述方案，不包含实现代码。

## 现状

当前项目**没有任何后端服务**。

- `web/` 是 Vite + React 19 + Ant Design + Tailwind + Zustand 的纯静态 SPA，构建产物 `web/dist` 由 nginx 托管。
- `Dockerfile` 是两阶段构建，运行镜像只有 nginx，没有服务端进程。`vercel.json` 是静态 SPA 部署，`render.yaml` 复用同一个镜像。
- 业务数据全部在浏览器：画布、素材、插件走 IndexedDB（localforage），AI 配置、WebDAV 凭据、主题走 localStorage。
- AI 请求由浏览器直连用户自己配置的 OpenAI 兼容接口，中间不经过任何服务器。
- 跨设备同步依赖用户自备的 WebDAV 服务器。
- `canvas-agent/` 是运行在**用户本机**的 Express + MCP 桥接进程，监听 `127.0.0.1:17371`，用于连接 Codex / Claude Code 操作画布。它是单人本机工具，不是后端服务，也没有数据库。

登录注册功能**完全不存在**。`web/src/stores/use-user-store.ts` 只是一个空壳，`user` 恒为 `null`，仅有一个 `clearSession`。`web/src/router.tsx` 中八条业务路由全部无鉴权守卫。

## 目标

- 用户必须注册登录后才能使用画布、生图、素材等全部功能。
- 用户的画布、素材、生图记录、视频记录在服务端持久化，换设备登录后自动恢复，包含图片与视频原文件。
- 用户配置的第三方 AI 凭据由服务端加密托管，换设备免重填。
- 提供档位与配额体系，按存储容量、单文件大小与媒体保留期限制资源占用。
- 平台预设模型的 AI 请求经后端转发，用户通过在线支付购买点数，生成在服务端按点数计量扣减。
- 全套服务通过 Docker Compose 部署在自有服务器上。

## 已确认的关键决策

| 决策项 | 结论 | 影响 |
| --- | --- | --- |
| 第三方 AI API Key | 存服务端，AES-GCM 加密，主密钥走环境变量 | 换设备免重填；服务端需承担密钥保管责任，`SECURITY.md` 必须同步说明 |
| 是否保留免登录模式 | 不保留，全站强制登录 | 前端无需双模式兼容，代码更简单；Vercel 静态部署废弃 |
| 媒体文件同步范围 | 全量上云，图片与视频原文件都同步 | 体验最完整；服务器磁盘与带宽成本自行承担，需要配额兜底 |
| WebDAV 同步 | 直接移除 | 只保留云端同步一条路径，删除 `webdav-sync.ts` 及配置页 UI、国际化文案与配置导出字段 |
| 注册策略 | 完全开放注册 | 任何人都能注册，必须配合注册限流、邮箱验证与免费档配额共同兜底 |
| 邮箱验证与找回密码 | 两者都做 | 需要接入 SMTP，新增邮件令牌表与两个落地页 |
| 管理后台 | 第三期实现轻量版 | 在本项目内新增 `/admin` 路由，覆盖用户列表、点数增减、用量查看与封禁，第四期补上模型目录与充值档位配置 |
| 档位配额 | 免费与付费两档 | 免费 500 MB 存储、单文件 50 MB、媒体保留 7 天；付费 1 GB 存储、单文件 200 MB、媒体保留 14 天 |
| 付费形态 | 只卖点数，不做订阅制 VIP | 用户在线购买点数，有剩余点数即视为付费档；点数耗尽自动回落免费档，VIP 概念留到以后再引入 |
| AI 请求链路 | 平台预设模型经后端转发，用户自配渠道仍走浏览器直连 | 平台 Key 只存服务端，点数在服务端扣减；用户自己的 Key 不扣点数，但仍受存储配额与保留期约束 |
| 模型目录 | 由后台维护，前端按目录动态渲染参数表单 | 前端不再靠关键词猜能力、不再硬编码分辨率与时长；用户自定义渠道与模型继续保留 |
| 媒体保留期 | 全部媒体按最后触达时间计时，超期清理 | 活跃项目不会被回收，长期无人问津的媒体到期释放磁盘；到期前 2 天预警并提供导出入口 |
| 支付渠道 | 支付宝、微信、Stripe | 需要商户资质与公网可达的回调地址，回调必须验签且幂等 |

### 配额的能力边界

存储配额是**硬约束**，媒体必须经过后端才能落盘，服务端在写入前校验，无法绕过。

生成消耗同样是**硬约束**。点数是用户花真金白银买的，扣不准就等于卖了一个算不清账的东西，因此平台预设模型的 AI 请求全部改为经 Go 后端转发：平台的第三方 Key 只存在服务端，浏览器根本拿不到，实际调用了几次、用了什么参数完全由服务端掌握，扣点在转发链路里同步完成。这条链路就是第四期要做的事。

需要划清的边界是用户自己配置的渠道。那些请求用的是用户自己的 Key，仍然走浏览器直连，不扣点数，服务端也不统计次数。这不是漏洞而是刻意的设计——用户烧的是自己的额度，平台没有理由收费。但这些请求产出的图片和视频一旦上传，同样占用存储配额、同样受媒体保留期约束，服务器侧的成本敞口依旧被硬约束兜住。

因此产品文案可以把平台模型的点数消耗描述成确定的、不可绕过的计量，这是收费成立的前提。

### 点数与付费身份

「有剩余点数即付费用户」是这套模型里最需要说清楚的一条。它把付费身份从「买了哪个套餐、还剩多少天」简化成「余额是否大于零」：服务端判定档位时只查一次 `credits.balance`，不需要维护订阅状态机，也不需要处理续费、宽限续订、试用转正这些订阅制才有的边界情况。

代价是身份会随着使用自然翻转。用户充值后升到付费档，点数用完的那一刻自动回落免费档。回落本身不删任何数据，但已用存储很可能已经超过免费档的 500 MB，此时账号进入**只读模式**：可以浏览、导出、删除，不能再上传新媒体。同时开始 **30 天宽限期**，期间发邮件提醒，用户可以选择充值恢复付费档，也可以自行清理到 500 MB 以下。宽限期结束仍然超额的，从最旧的媒体开始清理，直到回到配额之内。

VIP 这类按月付费、附带专属权益的形态暂不引入。点数模型已经能覆盖当前需要的全部收费场景，而订阅制会额外带来账期、发票、批量续费失败这些问题，等有明确需求时再单独规划。

### 媒体保留期与到期清理

清理范围是**全部媒体，包括画布正在引用的**。这一点和常见做法不同，值得先解释：如果只清理孤儿文件，那么用户只要把图片挂在某张画布上就能永久占用磁盘，保留期形同虚设。

但「画布里的图片会被删掉」听起来像是会毁掉用户的项目，所以计时方式必须配套。一个媒体文件的**最后触达时间**取所有引用它的画布 `updated_at`、素材 `updated_at`、生成记录 `created_at` 里的最大值，只要有任何一处被动过，计时就重新开始；超过所属档位的 `retention_days` 才进入清理。结果是活跃项目永远不会被回收，只有真正放着不管、既没打开过画布也没碰过素材的媒体才会到期。

实现上不新增 `expires_at` 列。到期时间是一个会被多张表的写入不断刷新的派生值，落成列就得在每次画布保存、素材更新、生成写入时同步维护，写放大且极容易漏掉一处。改为清理任务扫描时现算，并**与第三期的孤儿文件回收合并成同一个扫描任务**——两者都要遍历三张业务表的 jsonb 字段解析引用关系，扫一遍就能同时算出「谁没人引用」和「谁最后一次被触达是什么时候」。

到期前必须预警：到期前 2 天发邮件，同时在站内给出提示，并提供一键导出入口，让用户能把要留的东西先拿走。没有预警的自动删除等同于事故。

### 开放注册与全量媒体同步的成本风险

这两个决策叠加后仍然存在成本敞口，但配额调整之后量级已经完全不同：免费档 500 MB 存储，100 个注册用户的理论峰值是 50 GB 磁盘，而不是原先的 500 GB。这个数字落进了单台服务器可以从容承受的范围，开放注册不再是一个需要靠运气的赌注。

量级下降不等于防线可以撤。以下几条全部保留：

- 注册接口按 IP 与邮箱域名维度限流，避免脚本批量注册。
- **邮箱验证通过前不允许上传媒体文件**，把未验证账号的存储占用压到零。
- 存储配额与单文件上限在文件写入前校验，超额直接拒绝而不是先写后算。
- 提供长期不活跃账号的清理策略，作为磁盘兜底手段。

在此之上新增一条防线：媒体按档位的保留期到期清理。它把「注册后传满 500 MB 就再也不管」这种静态占用变成了有期限的占用，磁盘用量不再随注册量单调累加，而是会随不活跃账号的到期自然回落。

服务器磁盘容量仍应按「预期注册量 × 免费配额」的一定比例预留，并配置磁盘水位告警，只是基数小了一个量级。

## 仓库形态：留在本仓库，新增 `server/` 顶层目录

**结论：不新开仓库，在当前仓库新增 `server/` 目录。**

本仓库已经是多包结构，`web/`（前端）、`canvas-agent/`（本机 Node 服务）、`plugins/`（画布插件）、`docs/`（文档站）各自独立，新增 `server/` 与既有组织方式完全一致。

选择单仓库的三个理由：

1. **前后端契约耦合紧。** 画布、素材、生成记录的字段结构由前端类型定义（`CanvasProject`、`Asset` 等）与后端表结构共同承担，改一个字段两侧都要跟着动。同一个仓库里一次改动就能同时更新两侧，拆成两个仓库需要额外的版本协调和契约同步机制，成本远大于收益。
2. **部署编排需要放在一起。** Docker Compose 要同时编排前端、后端、数据库三个服务，`nginx.conf` 要反代 `/api`，这些配置天然属于同一份部署描述。
3. **强制登录已经与上游定位分叉。** 上游 `basketikun/infinite-canvas` 是 MIT 开源的纯本地工具，本次改造是强制登录 + 服务端凭据托管的私有化版本，本就不打算再向上游合并。因此「拆仓库便于同步上游」这个理由不成立。

需要配套注意的是：`server/` 里不要提交任何真实密钥或生产配置，全部走环境变量与 `.env`（已在 `.dockerignore` 忽略）；README 中标注本仓库为私有化分叉版本，说明与上游的差异。

如果后续确实需要保留向上游合并的能力，替代方案是后端独立成仓、前端改动收敛到少数文件——但强制登录会侵入路由、请求层、配置页、顶栏等多处，很难收敛，不推荐。

`internal/storage` 抽象成接口 + 本地磁盘实现，后续需要换 MinIO 或 S3 时只替换实现，不改调用方。

`internal/payment` 按渠道拆成支付宝、微信、Stripe 三个实现，共用同一套下单与回调接口，验签一律交给各渠道官方 SDK，不自己拼签名字符串。`internal/provider` 按上游协议格式拆成 OpenAI、Gemini、Ark 三个实现，只把统一的请求翻译成各家的调用、再把响应解析回统一形状，不解析业务语义；渠道选择、故障转移与超时配置由 `internal/service/upstream.go` 承担；扣点、计量、余额校验由 `handler/ai.go` 在转发前后完成。三者职责分开，换一个上游厂商才不会牵动计费代码。

## 技术选型

| 用途 | 选型 | 理由 |
| --- | --- | --- |
| HTTP 框架 | Gin | 生态成熟、文档充足，路由与中间件写法简洁 |
| ORM | GORM + AutoMigrate | 项目尚未上线，不需要迁移脚本，AutoMigrate 建表最省代码 |
| 数据库 | PostgreSQL | 画布与素材是大块 JSON，直接用 JSONB 字段存储并可索引 |
| 鉴权 | golang-jwt/jwt v5 | access token + refresh token 双令牌 |
| 密码哈希 | golang.org/x/crypto/bcrypt | 标准做法，无需自行设计 |
| 凭据加密 | 标准库 crypto/aes + cipher.GCM | 无需引入第三方加密库 |
| 对象存储 | 本地磁盘卷 | 私有化部署最简单，接口留好扩展位 |
| 支付渠道 | 各渠道官方 Go SDK | 下单参数与回调验签由 SDK 处理，签名逻辑绝不手写 |
| AI 转发 | 标准库 net/http | 上游调用与 SSE 逐块刷出靠 `http.Flusher` 就够，各家协议的差异交给 `internal/provider` 里的适配实现，不需要额外框架 |

遵循项目规范：通用能力一律使用成熟稳定的库，不手写协议、加密、日期等底层实现。

## 数据模型

### 账号相关

**users** — 用户主表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `email` | varchar | 唯一，登录标识 |
| `username` | varchar | 唯一，登录标识 |
| `password_hash` | varchar | bcrypt 哈希 |
| `display_name` | varchar | 展示名 |
| `avatar_url` | varchar | 头像 |
| `role` | varchar | `user` / `admin`，管理后台鉴权依据 |
| `status` | varchar | `active` / `disabled`，封禁用 |
| `email_verified_at` | timestamptz | 邮箱验证时间，为空表示未验证 |
| `created_at` / `updated_at` | timestamptz | |

未验证邮箱的账号可以登录并浏览，但**不允许上传媒体文件**，这是开放注册下控制存储成本的关键约束。

**email_tokens** — 邮箱验证与密码重置共用一张表，按 `purpose` 区分

| 字段 | 类型 | 说明 |

| `id` | uuid | 主键 |
| `user_id` | uuid | 外键 |

| `used_at` | timestamptz | 已使用时间，保证一次性 |
| `created_at` | timestamptz | 用于发信频率限制 |

**refresh_tokens** — 刷新令牌，支持多设备登录与主动踢下线

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `user_id` | uuid | 外键 |
| `token_hash` | varchar | 只存哈希，不存明文 |
| `expires_at` | timestamptz | 过期时间 |
| `revoked_at` | timestamptz | 撤销时间，可空 |
| `user_agent` / `ip` | varchar | 设备溯源 |

**user_credentials** — 加密托管的第三方凭据

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `user_id` | uuid | 外键，唯一 |

| `key_version` | int | 主密钥版本，供后续轮换 |

### 业务数据

画布、素材、生成记录各自独立成表，一行一个业务对象，而不是把一整个域打包成一个 JSON 大对象存进去。这样列表页能分页、能按标题搜索、能交给数据库排序，乐观锁也只锁到单条记录。每张业务表都带 `deleted_at` 做软删除，因此不需要单独的删除标记表。

**canvases** — 画布

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `user_id` | uuid | 外键，索引 |
| `title` | varchar | 画布标题，支持模糊搜索 |
| `data` | jsonb | 完整画布内容：`nodes`、`connections`、`viewport`、`chatSessions`、`backgroundMode` 等 |
| `revision` | bigint | 乐观锁，每次写入递增 |
| `node_count` | int | 冗余字段，列表页展示用，避免解析 `data` |
| `connection_count` | int | 同上，列表卡片要显示「N 个节点 · N 条连线」 |
| `cover_key` | varchar | 封面图的 `storage_key`，可空 |
| `created_at` / `updated_at` | timestamptz | |
| `deleted_at` | timestamptz | 软删除，可空 |

索引 `(user_id, deleted_at, updated_at desc)` 正好覆盖列表页的默认查询：当前用户、未删除、按更新时间倒序。`node_count` 与 `connection_count` 是刻意做的冗余，让列表接口完全不用碰 `data` 这个可能有几 MB 的字段。

`cover_key` 需要单独说明：**当前列表页根本没有封面图**，卡片是纯色块加标题和统计文字。第二期把这个字段一次做到位——取值由服务端从 `data.nodes` 里取第一个图片节点的 `storageKey` 算出，客户端传了也忽略，列表卡片直接 `<img src={"/api/media/" + coverKey}>`，`coverKey` 为空时保持现有的纯色块样式。但排期时要提醒一句：卡片展示封面是一项全新的 UI 工作，不是把现有功能搬过来，它的工时要单独算，别默认跟着数据层改造顺手就完成了。

### 权益相关

**plans** — 档位定义

| 字段 | 类型 | 说明 |

| --- | --- | --- | --- | --- |
| `free` | 免费 | 500 MB | 50 MB | 7 天 |

| `amount` | bigint | 正数为增、负数为减 |

**orders** — 支付订单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `user_id` | uuid | 外键 |
| `provider` | varchar | `alipay` / `wechat` / `stripe` |
| `provider_order_id` | varchar | 渠道侧订单号，唯一 |
| `package_id` | varchar | 外键，指向 credit_packages |
| `amount_cents` | bigint | 实付金额 |
| `currency` | varchar | 币种 |
| `credits` | bigint | 本单到账点数 |
| `status` | varchar | `pending` / `paid` / `failed` / `refunded` |
| `paid_at` | timestamptz | 支付完成时间，可空 |
| `created_at` / `updated_at` | timestamptz | |

`orders.credits` 在下单时就把档位的 `credits + bonus_credits` 快照进来，回调时直接用这个值，不反查 credit_packages。档位随时可能调价或下架，而回调可能在几分钟甚至几小时后才到，只有快照才能保证用户拿到的是他下单时看到的数量。

`provider_order_id` 唯一是回调幂等的地基：同一笔支付重复回调时，第二次会被唯一索引直接挡住，不可能重复加点。渠道普遍会重试回调，这是常态而不是异常路径。

**usage_records** — 用量计数，按 `(user_id, metric, period)` 唯一。它**只服务 `storage_bytes` 一个 metric**，`period` 只有 `total`：存储要在每次上传前校验，而 `SUM(bytes)` 会随文件数增长逐渐变慢，放在上传热路径上不合适，计数器是这里的必要妥协。生成次数不进这张表，「今天生成了多少张」这类展示数字直接从 `generations` 数出来，扣费以点数流水为准。

### 模型目录

**model_catalog** — 平台模型目录

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `name` | varchar | 模型标识，调用上游接口时实际传的值 |
| `display_name` | varchar | 展示名 |
| `capability` | varchar | `image` / `video` / `text` / `audio` |
| `provider` | varchar | 归属渠道 |
| `constraints` | jsonb | 参数约束，形如 `{ sizes: [], aspectRatios: [], durations: [], qualities: [], maxReferenceImages: n }` |
| `credit_cost` | jsonb | 按参数计费的规则 |
| `enabled` | bool | 是否对用户可见 |
| `sort` | int | 排序 |
| `created_at` / `updated_at` | timestamptz | |

这张表要解决的是当前前端的三处硬伤：模型能力靠 `use-config-store` 里的 `guessCapability` 按名字关键词猜；分辨率与最大边长这类参数是 `image.ts` 里的 `QUALITY_BASE`、`IMAGE_MAX_EDGE` 等全局硬编码，对所有模型一视同仁；系统压根不知道某个具体模型支持哪些尺寸、比例或时长，用户只能试——选了不支持的组合，要等上游接口报错才知道。

`constraints` 落成 jsonb 而不是拆成多列，是因为不同能力的约束维度本来就不一样：图片模型关心尺寸与比例，视频模型关心时长，语音模型两者都不关心。拆成列会得到一张大部分字段为空的宽表，而这些约束只被前端表单读取和渲染，从来不需要按字段查询。`credit_cost` 同理，计费规则天然和参数绑定——同一个模型出 1024×1024 和出 4K 的成本不同，视频按时长计费，这些只能按模型逐个配。

必须强调的是：**模型目录是平台预设，不是强制白名单。** 用户自己配置的渠道与模型继续保留，前端把两者合并展示，区别只在于自定义模型没有 `constraints` 可用，参数表单退回当前的通用形态，也不消耗点数。

### 生成记录

历史流只增不改，因此用游标分页而不是页码分页：游标由 `created_at desc` 加 `id` 组成，即使拉取期间又产生了新记录，翻页也不会错位或重复。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/generations?kind=&status=&cursor=&size=` | 游标分页，返回 `{ items, nextCursor }`；`status=pending` 不分页，一次返回全部 |
| POST | `/api/generations` | 记录一次生成 |
| GET | `/api/generations/{id}` | 详情 |
| PATCH | `/api/generations/{id}` | 只接受 `status`、`result`、`durationMs`，且仅在记录仍为 `pending` 时可用 |
| DELETE | `/api/generations/{id}` | 软删除 |

`PATCH` 是视频异步任务逼出来的：视频生成先落一条 `pending` 记录，轮询拿到结果后要把它改成 `success` 或 `failed` 并写回产物。刻意把它做窄——只允许改这三个字段、只在 `pending` 时可用——是为了保住「历史流只增不改」这个前提，避免它退化成一个可以随意改写历史的通用更新接口。`status=pending` 之所以不分页，是因为刷新页面后要恢复轮询的那些记录未必落在第一页，分页会让恢复逻辑静默失效。

### 媒体文件

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| HEAD | `/api/media/{storageKey}` | 查询是否存在及大小、校验和 |
| GET | `/api/media/{storageKey}` | 下载二进制 |
| PUT | `/api/media/{storageKey}` | 上传，写入前校验配额与邮箱验证状态 |
| DELETE | `/api/media/{storageKey}` | 删除 |

媒体走独立的二进制接口，业务对象里只存 `storageKey`。前端拿到画布或素材后按需取文件，不与 JSON 主体一起传输。

**`GET /api/media/{storageKey}` 要设计成能直接塞进 `<img src>` 的普通 URL**，而不是让前端下载 Blob 再转 ObjectURL。这一点值得强调，因为它能直接删掉前端现有的一整套机制：目前 `image-storage.ts` 和 `file-storage.ts` 各维护一个模块级的 `storageKey → ObjectURL` Map，打开画布时批量把所有图片解成 ObjectURL，而这个 Map 永不驱逐，用户在画布间来回切换内存就一直涨。改成直连 URL 之后，浏览器 HTTP 缓存接管一切，那两个 Map、批量 hydration 的异步逻辑、以及随之而来的泄漏问题全部消失。

这里有一个必须解决的冲突：第一期把 access token 定为只存内存、refresh token 放在 `Path=/api/auth` 的 httpOnly cookie 里，而 `<img src>` 发出的请求既带不上内存里的 token，也够不到那个受限路径的 cookie。

解法是**登录与刷新时额外下发一个只读媒体 cookie**，属性为 `HttpOnly; Secure; SameSite=Lax; Path=/api/media`，与 refresh token 同周期轮换。它的权限被刻意限制到最小：只能读当前用户自己的媒体文件，不能调任何业务接口，更不能读凭据。即使被窃取，损失也远小于 access token 泄漏——后者能直接读走用户的全部第三方 API Key。

上传仍然走带 `Authorization` 头的正常请求，这个 cookie 只对 `GET` 和 `HEAD` 生效。不要为了省事把它做成通用会话 cookie，那等于把第一期的令牌设计推翻。

### 权益

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/plans` | 档位列表，返回两档的存储配额、单文件上限与保留期 |

`/api/plans` 由第三期实现，同样要求登录，返回两档的全部字段：`id`、`name`、`storageBytes`、`maxFileBytes`、`retentionDays`。它和 `/api/me` 不重复——后者只给当前档位，而充值页要向用户说清「付费档能多拿到什么」，这需要两档并排对照。

档位不需要分配接口——用户属于哪一档由点数余额推导，`/api/me` 直接返回当前档位、存储用量、点数余额与最近的媒体到期时间即可。存储用量读 `usage_records` 里的 `storage_bytes` 计数器，不在请求里现算 `SUM(media_files.bytes)`；点数消耗从 `credit_transactions` 查，两者都不需要单独的用量记账接口。

### 点数

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/credits` | 余额与最近流水摘要 |
| GET | `/api/credits/transactions?cursor=` | 流水游标分页 |

流水和生成记录一样是只增的历史流，因此同样用游标分页而不是页码分页。余额单独开一个 `/api/credits` 而不是并进 `/api/me`，是因为它在生成过程中会实时变化，前端需要能高频单独刷新；`/api/me` 还带着用户资料与档位信息，没必要跟着一起重取。

### 支付与订单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/credit-packages` | 充值档位列表，只返回已上架的 |
| POST | `/api/orders` | 创建订单，请求体 `{ packageId, provider }`，返回对应渠道的支付参数 |
| GET | `/api/orders?cursor=` | 订单列表，游标分页 |
| POST | `/api/orders/{id}/cancel` | 取消待支付订单 |
| POST | `/api/payments/webhook/{provider}` | 支付回调，公开访问但必须验签且幂等 |

`POST /api/orders` 只创建本地订单并返回支付参数，点数不在这一步到账。到账只发生在回调确认支付成功之后，且写订单状态、加点数余额、写点数流水这三件事必须在同一个事务里完成。

回调接口是整个后端唯一一个不带 `Authorization` 的写接口，它的两道防线要写死在实现里。**验签**交给各渠道官方 SDK，签名不通过直接拒绝，绝不能因为「订单号看起来像是我们的」就放行。**幂等**由 `orders.provider_order_id` 唯一索引加订单状态机保证，只允许 `pending → paid` 这一次跃迁，重复回调返回成功但不做任何写入。

### 模型目录

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/models` | 平台模型目录，含 `constraints` 与计费规则 |

前端在生成页初始化时拉一次，之后按用户选中的模型动态渲染参数表单：该模型不支持的尺寸、比例、时长直接禁用，而不是让用户选完再等上游报错。返回体里带上每个模型的 `credit_cost`，前端就能在用户点下生成之前把「这次大约要花多少点」显示出来，这对一个按次计费的产品来说是必需的，不是锦上添花。

| POST | `/api/ai/videos/generations` | 视频生成，只创建异步任务并返回 `taskId` |
| GET | `/api/ai/videos/tasks/{id}` | 查询视频任务的状态与产物 |
| POST | `/api/ai/audio/speech` | 语音合成 |
| POST | `/api/ai/chat/completions` | 对话补全，SSE 流式 |

路径贴着 OpenAI 兼容协议的形状，但**请求体与响应体都不是上游的原样透传**。请求按能力定义自己的字段，参考图传 `storageKey` 而不是 base64；响应固定给出 `credits` 与 `storageKey` 形式的产物，各家上游那些字段名、信封、`b64_json` 与 `url` 的差异全部收敛在服务端。`/api/ai/chat/completions` 同理，它是一套自有事件流而不是上游 SSE 的透传，后端逐块 flush，不能等上游返回完再一次性吐出来，否则画布里的助手对话会从流式变成整段弹出，体验直接倒退。

因此前端不是换个 baseUrl 就完事：要新增 `web/src/services/api/ai.ts` 承载这五个接口，再在 `image.ts`、`video.ts`、`audio.ts` 的生成入口按模型标识分流——裸模型名是平台目录里的模型，走 `ai.ts`；含 `::` 的是用户渠道的模型，继续走现有的浏览器直连实现。视频还要从「本地轮询上游」改成「轮询本站的任务查询接口」。

扣点顺序是**先扣后生成、失败退还**：转发前按模型的 `credit_cost` 与本次参数算出点数，在一个事务里校验余额、扣减、写一条消费流水，余额不足直接返回 402；上游失败或超时按被扣金额整笔退还，并写一条 `type = refund` 流水。不做「按实际结果补差」——第三期只暴露 `Reserve` 与 `Refund` 两个方法，本来就没有补差能力，多一条结算路径也就多一种对不上账的可能。这条链路的一致性是第四期最需要反复测的地方。

| GET | `/api/admin/users` | 用户列表，支持分页、关键字搜索与状态筛选 |

## 数据方案：服务端权威的资源化模型

最初的方案打算直接复用现有 WebDAV 同步的 domain manifest 契约：把 canvas、assets、image-workbench、video-workbench 四个域各自打包成一个 JSON 整体上传下载，客户端用 `mergeById` 合并，再补一张删除标记表填上缺失的删除语义。它的吸引力完全在于工作量——`web/src/services/app-sync.ts` 里真正与 WebDAV 绑定的只有上传下载两个函数，换掉传输层就能跑起来。

**这个方案已经被否决。** 它把「省下一部分前端工作量」排在了「架构长期可用」之前，而省下的工作量很快会以更贵的形式还回来：

1. **整域一坨 JSONB 无法查询。** 列表页想拿到画布列表，就必须把整个域拉下来，动辄几 MB，翻页、按标题搜索、按更新时间排序只能在前端内存里做。
2. **生成记录本质是只增的历史流。** 用「合并」去处理一条只追加不修改的日志流本来就别扭，而且用户攒到几千条之后每次打开工作台都要全量拉取，这个代价不可接受。
3. **revision 锁的粒度太粗。** 乐观锁加在整个域上，意味着两台设备改的是**不同**的画布也会撞车，用户无法理解为什么编辑 A 画布会被提示与 B 画布冲突。
4. **删除需要额外机制。** manifest 模型下必须专门建一张 tombstone 表记录删除，并在每次合并时按它过滤；资源化之后每行一个 `deleted_at` 就解决了。
5. **数据对外不可查。** 管理后台想看某个用户有多少画布、占了多少空间，未来任何一个 API 客户端想读一条记录，都得先把整域 JSON 拉下来自己解析。

因此数据层改为**服务端权威的资源化 REST 模型**：每张画布、每个素材、每条生成记录都是数据库里的一行，前端不再持有全量副本，而是按需向服务端请求。

**服务端是唯一权威。** 客户端不再做合并。写入直接落到服务端，读取以服务端返回为准。前端内存里的数据是服务端数据的一份视图，而不是需要与之对账的另一份副本。

**按需加载，列表与详情分离。** 列表接口只返回摘要字段，不含 `data`；打开某张画布时才请求详情。生成记录用游标分页，只拉当前这一页。用户攒多少数据，与首屏加载多少数据不再挂钩。

**乐观锁下放到单条记录。** `revision` 存在每一行画布上，`PUT /api/canvases/{id}` 必须带上客户端读到的 `revision`，服务端比对不一致就返回 409 `REVISION_CONFLICT`。改不同画布的两台设备互不干扰，只有真正同时编辑同一张画布才会冲突，冲突提示也能明确指到具体是哪一张。

**软删除替代删除标记。** 删除就是写 `deleted_at`，列表查询默认过滤掉。没有 tombstone 表，也不存在「本地删了远端又带回来」这个合并 bug——在这个模型里它根本不会发生。

代价要说清楚：**前端数据层的改动比原方案大得多。** 现有 store 是「启动时把整个域从 IndexedDB 读进内存」的模式，要改成「列表按页拉、详情按需拉、编辑后防抖回写」。`app-sync.ts` 那套合并逻辑不再复用，直接删除。这部分工作量是实打实增加的，换来的是一个能分页、能搜索、能被管理后台和未来任何客户端直接查询的数据层。

## 部署编排

`docker-compose.yml` 从单容器改为三服务：

```txt
app   nginx + 前端静态产物，对外暴露 3000
api   Go 后端，仅内网暴露 8080
db    PostgreSQL 17（`postgres:17-alpine`），仅内网暴露 5432
```

数据卷：`pgdata` 持久化数据库，`media` 持久化用户上传的图片与视频。`db` 的初始账号、密码与库名由 `POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_DB` 提供，健康检查用 `pg_isready -U $POSTGRES_USER`，`api` 要等它通过之后再启动。

`nginx.conf` 增加反代，前端与后端同源，无需处理 CORS：

```txt
location /api/media/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    client_max_body_size 200m;
}

location /api/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    client_max_body_size 2m;
}
```

**`proxy_pass` 不能带任何 URI 部分**，这是这份配置里最容易踩的坑。写成 `http://api:8080/` 时，nginx 会把 location 匹配到的 `/api/` 剥掉再转发，`/api/auth/login` 到后端就成了 `/auth/login`；而本文档所有接口都写作 `/api/...`，后端也统一注册在 `r.Group("/api")` 下，照字面实现会全线 404。不带尾斜杠则路径原样透传，和后端的路由前缀严格对齐。

体积上限必须拆成两档。200MB 是付费档的单文件上限，默认的 1MB 会直接导致上传失败，但这个额度只应该给 `/api/media/`：它对 `/api/` 下所有接口一视同仁的话，画布保存接口也跟着放开，而画布 `data` 存的是 jsonb、不计入任何存储配额，用户反复提交 200 MB 的画布 JSON 就能把数据库撑爆。所以媒体接口放到 200m，其余接口收到 2m，nginx 的前缀匹配是最长优先，两个 location 的书写顺序不影响结果。免费档 50 MB 的更严格限制由后端按用户档位校验，nginx 层不做区分——档位是会随点数余额翻转的动态属性，放在网关上判断既拿不到用户身份也没法实时跟随。

后端所需环境变量写入 `server/.env.example`：

| 变量 | 说明 |
| --- | --- |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `db` 服务的初始账号、密码与库名，同时供 compose 的 `pg_isready -U $POSTGRES_USER` 健康检查使用 |
| `DATABASE_URL` | PostgreSQL 连接串，取值必须与上面三个变量一致 |
| `PORT` | 后端监听端口，缺省 8080，改了要同步 nginx 的 `proxy_pass` 与 compose 的健康检查 |
| `JWT_SECRET` | 访问令牌签名密钥 |
| `CREDENTIAL_MASTER_KEY` | 凭据 AES-GCM 主密钥，32 字节；第四期的平台渠道 Key 复用同一把，不再引入第二把密钥 |
| `MEDIA_ROOT` | 媒体文件落盘路径，对应 `media` 卷 |
| `APP_BASE_URL` | 站点外网地址，用于拼接邮件里的验证与重置链接 |
| `SMTP_HOST` / `SMTP_PORT` | 邮件服务器地址与端口 |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | 邮件服务账号 |
| `SMTP_FROM` | 发件人地址 |
| `REGISTRATION_ENABLED` | 注册总开关，默认开启，出问题时可紧急关闭 |
| `ALIPAY_*` / `WECHATPAY_*` / `STRIPE_*` | 各支付渠道的商户号、密钥与回调地址，未配置的渠道自动不上架 |

平台预设模型的上游地址与 Key **不走环境变量**。第四期新建 `platform_channels` 表存放每个渠道的 `BaseURL`、AES-GCM 加密后的 `Payload`（明文是上游 API Key）、`Priority` 与 `Enabled`，加解密复用 `CREDENTIAL_MASTER_KEY`，管理入口是 `/api/admin/channels`，请求按 `Priority` 顺序取第一个可用渠道并在失败时切到下一个。之所以放表里，是因为换 Key、加备用渠道、临时停用某个上游都不该需要改配置重启容器，而多渠道故障转移本来就不是一对环境变量能表达的。

媒体保留期也没有单独的开关变量。清不清理由所属档位的 `retention_days` 决定，验证期间想先只扫描不删除，用第三期「先做成管理后台按需触发，在单个用户上验证正确后再挂定时任务」的做法即可，不需要再加一个全局总开关。

`APP_BASE_URL` 配错会直接导致验证邮件里的链接不可用，部署时需要重点核对。SMTP 全部变量为空时后端应启动失败并给出明确报错，而不是静默地发不出邮件。

支付回调地址必须公网可达，且要能被各渠道的服务器直接访问——纯内网部署无法完成支付闭环，这一点要在部署文档里写明。三个支付渠道相互独立，只配其中一个也能跑，未配置的渠道在 `/api/credit-packages` 与下单接口里自动不可选，而不是让用户点进去才失败。

`render.yaml` 目前是单镜像静态部署，改造后不再适用，需一并调整或移除。

## 安全设计

- 密码用 bcrypt 哈希存储，不可逆。
- refresh token 只存哈希，泄露数据库也无法直接使用；改密码时撤销该用户全部其他令牌。
- 第三方 AI 凭据用 AES-GCM 加密，主密钥从环境变量读取，不进数据库、不进仓库。表结构预留 `key_version` 支持后续轮换。
- 上传接口必须校验 `storage_key` 格式并限定在当前用户命名空间下，防止路径穿越与越权读取他人文件。
- 邮件令牌只存哈希，明文仅出现在邮件链接中，且必须一次性使用并设置较短有效期。
- 找回密码接口无论邮箱是否存在都返回成功，避免通过响应差异枚举已注册账号。
- 管理接口由独立的 `role = admin` 中间件校验，绝不能只靠前端隐藏入口。首个管理员通过环境变量或初始化命令创建，不开放自助提权。
- 平台自己的第三方 Key 加密存放在 `platform_channels` 表里，解密只发生在发起上游请求的那一刻，明文只在 `internal/service/upstream.go` 与 `internal/provider` 内部停留，不进缓存，任何情况下不出现在响应体、错误信息或日志里；转发响应还要过滤掉上游可能回显的鉴权头。
- 支付回调是唯一的公开写接口，必须先验签再处理，同时限制请求体大小与处理频率，避免它成为压垮后端或伪造订单的入口。
- AI 转发接口按用户维度限流。拿到一个已鉴权身份就能驱动平台的 Key 打上游，余额校验管的是花多少钱，限流管的是打多快，两者缺一不可。
- 服务端持有用户第三方厂商密钥属于重大责任变更，`SECURITY.md` 与 `docs/content/docs/support/security.mdx` 必须说明存储方式、加密算法与风险边界，并补充平台 Key 与支付密钥的保管方式。

### 开放注册带来的额外攻击面

公开注册意味着任何人都能拿到一个已鉴权身份，防护重点从「拦住陌生人」变成「限制单个账号能消耗多少资源」：

- 注册与发信接口按 IP 和邮箱维度双重限流，防止批量注册与邮件轰炸。
- 邮箱验证通过前禁止上传媒体，未验证账号无法占用磁盘。
- 存储配额、单文件上限与点数余额在操作前校验，超额或余额不足直接拒绝。
- 平台模型的转发接口按用户限流，新注册账号不因为「已登录」就能无限制驱动平台 Key。
- `REGISTRATION_ENABLED` 作为紧急开关，被刷时可立即关闭注册。

## 分期实施计划

每期都有独立的开发底稿，精确到文件职责、接口出入参、错误码与验收清单：[第一期](/zh-CN/docs/progress/account-backend-phase1)、[第二期](/zh-CN/docs/progress/account-backend-phase2)、[第三期](/zh-CN/docs/progress/account-backend-phase3)、[第四期](/zh-CN/docs/progress/account-backend-phase4)。

### 第一期：账号体系与邮件链路

后端搭建 `server/` 骨架，实现 users、refresh_tokens、email_tokens 三张表，注册登录登出刷新改密码、`/api/me`、鉴权中间件，接入 SMTP 完成邮箱验证与找回密码，并给注册和发信接口加上限流。

前端新增统一 client、`use-auth-store`、登录注册页、邮件验证与密码重置两个落地页、路由守卫、顶栏用户菜单与国际化文案。

部署上完成三服务编排、`/api` 反代与 `client_max_body_size` 放开。

因为选择了开放注册，邮箱验证不能推迟到后面的阶段——它是限制未验证账号占用磁盘的前提，必须和账号体系一起交付。

验收标准：全新环境起容器后可注册并收到验证邮件，点击链接完成验证；可登录、刷新令牌、登出；忘记密码能收到重置邮件并成功改密；未登录访问任意业务页面自动跳转登录页。

### 第二期：凭据托管与数据资源化

实现凭据加解密接口，前端配置页接入。后端实现 canvases、assets、generations、media_files 四张表与对应的资源接口，含分页列表、游标分页、单条乐观锁与软删除。前端新增四个资源客户端，把画布、素材、生成历史三处 store 从全量进内存改为按需加载与防抖回写，并删除 `app-sync.ts`。上传接口加上「未验证邮箱禁止上传」的约束。

数据资源化验收通过后，再执行 WebDAV 的整体移除。

这一期是三期里前端改动最重的一期，重点不在接口本身，而在数据层的加载时机改造，排期时要留出余量。

验收标准：A 设备创建画布并生成图片，B 设备登录同一账号后能看到完整画布与图片原文件；A 设备删除画布后 B 设备刷新列表不会再看到它；画布列表能分页、能按标题搜索，且列表响应体不含 `data`；两台设备同时编辑同一张画布时，后保存的一方收到 409 而不是静默覆盖；未验证邮箱的账号上传被拒绝。

### 第三期：档位、点数账本与管理后台

实现 plans、usage_records 与配额校验，写入免费与付费两档默认数据，`/api/me` 返回当前档位、存储用量与点数余额，前端个人中心展示，上传前做存储配额与单文件上限拦截。

同期实现点数与支付的账本侧：credits、credit_transactions、credit_packages、orders 四张表，充值档位、下单、订单列表与取消，以及三个渠道的回调验签与幂等处理，前端新增 `/billing` 充值与流水页。

同期实现媒体保留期清理：按最后触达时间现算过期，与孤儿文件回收合并成同一个扫描任务，到期前 2 天发预警邮件、站内提示并提供一键导出入口。

同期实现管理后台：`/admin` 路由与 `RequireAdmin` 守卫，用户列表、封禁解封、点数增减、订单查询、充值档位配置、用量查看与总览统计。

需要清醒认识的是，这一期结束时点数只是一个能充值、能查账的余额，还没有任何东西会消耗它。因此在第四期上线之前不要对外开放充值入口，否则等于卖一个暂时兑现不了的东西。

验收标准：超出存储配额或单文件上限时上传被拒绝并给出明确提示；用户能完成一次真实支付并看到余额与流水正确增加，同一笔支付重复回调不会重复加点，取消后的订单再回调也不会加点；超过保留期且长期未触达的媒体被清理，而近期编辑过的画布所引用的媒体不受影响，清理前 2 天能收到预警邮件；管理员能在后台查到任意用户的存储占用与点数余额并手工增减点数，非管理员访问 `/admin` 与管理接口均被拒绝。

### 第四期：AI 请求后端转发与点数计量

新增 model_catalog 表与 `/api/models`，把模型能力、参数约束与计费规则从前端硬编码搬到后台配置，管理后台补上模型目录的增删改查。后端新增 `internal/provider` 与 `internal/service/upstream.go`，以及 `/api/ai/*` 五个转发接口（视频改为异步任务，创建与查询各占一个），实现三种上游协议的适配与 SSE 流式转发；平台渠道的 Key 加密存在 `platform_channels` 表里，由 `/api/admin/channels` 管理并支持按优先级故障转移。前端新增 `web/src/services/api/ai.ts`，在 `image.ts`、`video.ts`、`audio.ts` 的生成入口按模型标识分流，平台模型的参数表单按 `constraints` 动态渲染，用户自定义渠道保持浏览器直连不变，`model-plugin.ts` 一行都不改。扣点在转发链路里完成：先扣后生成，失败整笔退还。

这一期和第三期的点数体系是同一件事的两面。第三期解决「怎么把点数卖出去」，第四期解决「点数怎么被消耗掉」；缺了后者，前者卖的就是一个无法计量、也无法兑现的东西。这也是它必须紧接着第三期做、不能无限期后排的原因。

它同时是整个收费模型的技术地基。平台 Key 只有放在服务端，扣点才可能准确；只有扣点准确，点数才敢作为商品出售。「平台预设模型扣点、用户自配渠道不扣点」这条商业规则也在这一期落地，判定依据是这次生成选中的是模型目录里的记录还是用户自己的渠道配置，而不是模型名字。

验收标准：使用平台预设模型生成图片、视频与语音都能成功，点数按模型的计费规则正确扣减并留下流水；画布里的助手对话是逐字流式输出而不是整段返回；余额不足时生成入口被拦截并提示充值；上游报错或超时时点数不被扣掉，已预扣的能退回并留下退还流水；用户自己配置的渠道仍然直连、不消耗点数；浏览器网络面板里看不到平台的第三方 Key；模型参数表单只展示该模型 `constraints` 支持的选项，不支持的组合直接禁用。

## 影响与破坏性变更

- **全站强制登录**，未登录无法使用任何功能。
- **WebDAV 同步整体移除**，原先依赖 WebDAV 做跨设备同步的用法不再支持，改由服务端统一存储。
- **前端数据层改动大于原方案**，画布、素材、生成记录全部改为按需加载，store 不再持有全量数据，依赖这些 store 直接读全量列表的组件都要跟着调整；`app-sync.ts` 的合并逻辑整体废弃，不再复用。
- **离线能力彻底丧失**，数据以服务端为准，断网后既读不到未缓存的画布，也保存不了修改。强制登录本就放弃了离线使用，资源化只是把这个结论落到了数据层。
- **Vercel 静态部署废弃**，只支持 Docker 自部署。
- **新增 SMTP 依赖**，没有可用邮件服务时注册流程无法完成。
- **新增支付渠道依赖**，需要支付宝、微信或 Stripe 的商户资质与密钥，且回调地址必须公网可达，纯内网部署无法完成支付闭环。
- **AI 请求链路一分为二**，平台预设模型经后端转发、用户自配渠道仍走浏览器直连，前端在发起生成前必须先判断走哪条路，不再是单一的直连模型。
- **平台承担第三方调用成本**，平台预设模型烧的是平台自己的 Key，用户每次生成都直接产生真金白银的成本。计费规则配错或扣点链路有洞，亏的是平台的钱。
- **点数耗尽会自动降档**，付费用户点数用完后回落免费档，已用存储超过 500 MB 时进入只读模式，30 天宽限期后从最旧的媒体开始清理。这是产品行为而不是故障，必须在界面和邮件里说清楚。
- **媒体不再永久保留**，所有媒体按档位的保留期计时，长期未触达的会被清理。这与「上传即永久保存」的直觉相反，是本次改动里最需要提前告知用户的一条。
- **项目定位从纯本地工具变为多用户服务**，`AGENTS.md` 中「外部服务请求统一放在 `web/src/services/api/`，由浏览器前端直连，不假设存在项目后端」这条规则必须修订，第四期之后 AI 请求也不再全部直连。
- 项目尚未上线，不做旧数据迁移，本地已有数据在首次登录后按新结构重新同步。
- `canvas-agent` 不受影响，仍然是连接 `127.0.0.1:17371` 的本机工具，与多用户后端是两条独立链路。

## 实施时需要重点盯的风险

方案层面的决策已经全部敲定，以下是落地过程中最容易出问题的地方。

**客户端垃圾回收会删掉仍在使用的文件，这是本方案唯一可能直接造成数据丢失的地方。** 现有的 `cleanupImages` 与 `cleanupUnusedMedia` 通过扫描「全部素材加全部画布」来判断哪些媒体没人引用，然后删掉孤儿文件。这套逻辑成立的前提是前端手里有全量数据——而按需加载恰好推翻了这个前提。改造后前端只持有当前打开的那一张画布，任何客户端 GC 都会把其它画布正在引用的图片当成孤儿删除。

这件事要拆成两半看，两半的紧急程度完全不同。

**删除客户端 GC 必须和按需加载改造同期完成**，也就是放在第二期，一天都不能拖。少删文件只是浪费磁盘，删错文件是丢用户数据，中间态一旦上线就开始出事故。

**服务端的孤儿文件回收则可以留到第三期。** 在它上线之前，用户删掉画布后其引用的媒体会暂时留在磁盘上，代价只是占空间，不影响任何人的数据。这块工作要扫三张业务表的 jsonb 字段判断引用关系，和第三期的存储用量重算、媒体保留期的到期判定是同一类活——三者共用同一次扫描，放一起做省下的不只是工作量，还有反复遍历大表的开销。

顺带一提，现有的 `cleanupUnusedMedia` 还有个既存缺陷：它绕过 `deleteStoredMedia` 直接删记录，既不释放 ObjectURL 也不清缓存 Map，图片侧的同名函数则处理正确。改造时这个不一致会自然消失。

**支付回调的幂等与时序。** 渠道会重试回调，也可能乱序到达，甚至可能在用户已经手动取消订单之后才到。加点必须以 `orders.provider_order_id` 唯一索引加订单状态机为准，只允许 `pending → paid` 这一次跃迁，重复回调返回成功但不做任何写入。订单状态、点数余额、点数流水三处写入必须在同一个事务里，任何一处失败都整体回滚——回调半成功比回调完全失败难查得多，而且用户会直接感知为「钱付了点没到」。还要处理「回调先于下单响应到达」这种情况：下单事务尚未提交时回调查不到订单，需要有重试或延迟处理机制，不能直接当成非法请求丢掉。

**点数扣减与生成结果的一致性。** 这是第四期最容易出事的地方，两个方向都会出问题：扣了点但生成失败，用户会认为平台在骗钱；生成成功但没扣到点，亏的是平台。可靠的做法是转发前按 `credit_cost` 扣减并记一条消费流水，失败时整笔退还，退还同样写一条 `type = refund` 的流水，而不是直接改余额——余额可以对不上账，流水不行。不要做「按实际结果补差」：第三期只提供 `Reserve` 与 `Refund` 两个方法，一次生成要么扣成、要么整笔退回，多一条结算路径只会多一种对不上账的可能。视频生成这类耗时长、可能异步出结果的场景要特别小心：请求已经发出但连接断了，点数到底扣不扣，必须有明确结论并在实现里写死，而不是听天由命。

**模型目录与用户自定义模型的优先级冲突。** 用户完全可能在自己的渠道里配一个和平台目录同名的模型。这时必须能明确区分本次生成走的是平台 Key 扣点数、还是用户 Key 不扣点数，判定依据只能是用户选中的是哪一条记录，绝不能靠模型名字匹配。选择器里两类模型要有可见的区分，生成前也要让用户知道这一次会不会花点。另一个边界是平台下架了某个模型，而用户的历史生成记录甚至画布节点里还引用着它——读取历史时不能因为目录里查不到就报错或渲染成空白。

**存储成本失控。** 开放注册叠加全量媒体上云仍是本方案的主要成本敞口，只是配额降到 500 MB 后量级可控了。配额校验必须在文件写入前完成，不能先落盘再统计；邮箱验证前禁止上传这条约束不能省略；磁盘水位告警要在第一期上线前就配好。

**保留期清理的误删风险。** 清理范围包含画布正在引用的媒体，这意味着最后触达时间一旦算错就是直接删用户的图。上线前必须先跑一段只扫描不删除的观察期，把「将被清理」的清单打出来人工核对；预警邮件和站内提示要确认真的发得出去；清理动作本身建议先软删除再延迟物理删除，留出可恢复的窗口。

**邮件送达率。** 自建 SMTP 很容易被判为垃圾邮件，导致用户收不到验证邮件而无法完成注册。建议使用成熟的邮件服务商，并在注册后的界面上明确提示「没收到可以重发」，同时提供重发入口。

**前端按需加载的改造深度。** 这是本方案里最容易被低估的一块。现有代码默认「数据已经全在内存里」，很多地方直接遍历全量列表；改成按需加载后，加载态、空态、分页边界、详情未就绪时的渲染都要逐处处理。建议先把画布跑通形成范式，再套用到素材与生成记录，不要三块并行改。

**乐观锁的冲突体验。** 单条记录级的 `revision` 把冲突范围缩到了最小，但同一张画布在两台设备上同时编辑仍会产生 409。前端必须给出明确的处理路径——提示冲突、拉取最新版本、让用户决定，而不是静默覆盖或直接丢弃用户当前的编辑。

**防抖保存的边界情况。** 画布编辑靠防抖回写，要处理好关闭页面、切换画布、网络失败这几种情况下的未保存内容，否则用户会遇到「改了但没存上」。保存失败必须有可见反馈和重试入口。

**WebDAV 移除的牵连范围。** 它同时涉及 store 字段、配置导出、配置页 UI 和两个语言包，删除时容易漏掉一处导致类型报错或界面残留。务必等第二期数据资源化验收通过后再动手。

**首个管理员的创建方式。** 需要在部署文档里写清楚，否则会出现「后台建好了但没人能登进去」的情况。
