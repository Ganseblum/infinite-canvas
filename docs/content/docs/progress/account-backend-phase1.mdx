# Phase 1 Implementation Checklist: Account System and Email Pipeline

This document is the development baseline for phase 1 of the [Account System and Backend Service Plan](/docs/progress/account-backend-plan) and is meant to guide coding directly. Plan-level trade-offs and rationale live in the plan document; this one covers only what to build and how.

## Scope

### In Scope

Backend account system (registration, login, logout, token refresh, password change, current user info), the SMTP email pipeline (email verification, password recovery), rate limiting, the frontend login and registration flow with route guards, and the three-service Docker orchestration.

### Out of Scope

Credential custody, data sync, media upload, tier entitlements, quota enforcement and the admin console. Those belong to phases 2 and 3.

However, **the data model must be built correctly from the start**: the `role` and `email_verified_at` columns on `users`, plus the `plans` table, are created in this phase and seeded with the `free` and `paid` tiers. The reason is that once registration ships it continuously produces users, and retrofitting columns later requires backfilling historical rows. Quota **enforcement** waits for phase 3, but the tier definitions have to be right now.

**No `subscriptions` table is created.** Billing is credit-based rather than subscription-based, paid status is derived directly from the credit balance in phase 3, and there is no subscription lifecycle for a table to maintain; anything built here would be dropped as the first act of phase 3. For the same reason there is no "assign a plan at registration" step. Neither this phase nor phase 2 has a `credits` table, so no tier can be determined, and **every user is therefore checked against the `free` tier for the per-file ceiling** — phase 2's `FILE_TOO_LARGE` reads `max_file_bytes` straight off the `plans` row where `id = free`. Only once phase 3 ships the credit system does that become "look up the tier by whether `credits.balance` is above zero, then read that row's ceilings". The `paid` row is seeded now anyway so phase 3 only has to wire up the decision logic instead of going back to fix the seed.

## Shared Conventions

### Response Format

Success returns the data object directly; failures wrap an `error`:

```json
{
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "Incorrect email or password"
  }
}
```

`message` is a user-facing fallback. The frontend matches localized copy by `code` first and only falls back to `message` when there is no match.

### Time Format

Every timestamp the API returns is RFC3339, in UTC, with milliseconds, for example `2026-08-13T04:15:30.123Z`. The backend serializes exactly one way — no Unix epochs, no local timezone offsets — and the frontend performs no conversion of its own, handing the string straight to dayjs for display in the user's local zone. The `"..."` placeholders in the endpoint examples below follow the same convention.

### Error Codes

| HTTP | code | Meaning |
| --- | --- | --- |
| 400 | `VALIDATION_FAILED` | Validation error, with a `fields` detail of which field failed |
| 400 | `INVALID_SIGNATURE` | Payment callback signature verification failed (activated in phase 3) |
| 400 | `MODEL_NOT_SUPPORTED` | The model is neither in the platform catalog nor backed by a channel the user configured (activated in phase 4) |
| 400 | `PARAM_NOT_SUPPORTED` | A parameter falls outside the model's `constraints`, carrying `param` and `allowed` (activated in phase 4) |
| 401 | `UNAUTHORIZED` | Missing or invalid credentials |
| 401 | `INVALID_CREDENTIALS` | Wrong account or password |
| 401 | `TOKEN_EXPIRED` | Access token expired; the frontend uses this to trigger a silent refresh |
| 402 | `INSUFFICIENT_CREDITS` | Credit balance too low, or a media upload attempted while read-only (activated in phase 3) |
| 403 | `ACCOUNT_DISABLED` | Account suspended |
| 403 | `EMAIL_NOT_VERIFIED` | Email not verified (reserved here, first used by phase 2 upload endpoints) |
| 403 | `FORBIDDEN` | Authenticated but not allowed to touch this resource, used by admin endpoints |
| 404 | `NOT_FOUND` | Resource does not exist |
| 409 | `EMAIL_TAKEN` | Email already registered |
| 409 | `USERNAME_TAKEN` | Username already in use |
| 409 | `REVISION_CONFLICT` | Canvas optimistic lock conflict, carrying the server's current `revision` (activated in phase 2) |
| 409 | `CHECKSUM_MISMATCH` | The uploaded `X-Checksum` differs from the server-computed value (activated in phase 2) |
| 409 | `ORDER_ALREADY_PAID` | Cancelling an order that has already been paid (activated in phase 3) |
| 410 | `TOKEN_INVALID` | Email token invalid, expired or already used |
| 413 | `FILE_TOO_LARGE` | Upload exceeds the tier's `max_file_bytes` (activated in phase 2) |
| 429 | `RATE_LIMITED` | Rate limit hit, response carries `Retry-After` |
| 429 | `CONCURRENCY_LIMITED` | Too many generation requests in flight for one user (activated in phase 4) |

| 500 | `INTERNAL_ERROR` | Server error, internal details never exposed |

This table is the single error-code registry for the whole project, and any code a later phase introduces must be registered back here. The reason is that the frontend builds localization keys from error codes (see "Localization" below); once the registry is scattered across per-phase documents, some code inevitably ends up with no copy and the user sees nothing but the backend's fallback `message`.

### Token Strategy

| Item | Design |
| --- | --- |
| Access token | JWT, HS256, 15-minute lifetime, claims carry `sub` (user id), `role`, `iat`, `exp` |
| Refresh token | Not a JWT; 32 random bytes base64url-encoded, stored in the database as a sha256 hash only, 30-day lifetime |
| Refresh behavior | Rotating; every refresh issues a new refresh token and immediately revokes the previous one |
| Reuse detection | Presenting an already-revoked refresh token revokes every token for that user and forces re-login |

### Token Storage: Refresh in an httpOnly Cookie, Access in Memory Only

This is the most important security decision in this phase.

**The refresh token is delivered via `Set-Cookie`** under the name `ic_refresh`, with `HttpOnly; Secure; SameSite=Lax; Path=/api/auth`. **The access token lives only in frontend memory** (a field on the Zustand store) and is never written to localStorage or sessionStorage.

The rationale: starting in phase 2 the project holds users' third-party AI API keys server-side, so a stolen session would let an attacker read every vendor key that user owns. Keeping the long-lived credential in a cookie that JavaScript cannot read reduces the blast radius of XSS from "permanent account takeover" to "the current page session". Since frontend and backend are same-origin behind the proxy, the cookie approach requires no cross-origin handling.

The cost is that the in-memory access token is lost on page reload, so the application must perform a silent refresh at startup. That flow is detailed under "Frontend Startup Flow" below.

`SameSite=Lax` combined with a refresh endpoint that only accepts POST is sufficient against CSRF, so no CSRF token is introduced in this phase.

The `Secure` attribute is controlled by the `COOKIE_SECURE` environment variable and defaults to `true`, but it has to be switchable. Browsers silently discard `Secure` cookies over plaintext connections, so on a deployment without TLS — acceptance testing against `http://ip:3000`, for instance — the refresh cookie is never stored, `bootstrap()` returns 401 forever and nothing stays logged in. Set `COOKIE_SECURE=false` there, and only there: internal networks and local development. Anything reachable from the public internet must terminate TLS and keep the value at `true`, otherwise the refresh token travels in the clear.

Phase 2 issues a second, read-only media cookie from the same code path: `ic_media` on `Path=/api/media`, also `HttpOnly; Secure; SameSite=Lax`, whose value is a short-lived JWT with `sub` and `scope: "media"` in its claims. It rotates on the same cycle as the refresh token and is honored only for `GET` and `HEAD`. This phase does not implement it, but the issuing and rotation code should leave room for it so phase 2 does not have to rewrite the issuing path.

### Rate Limits

| Endpoint | Dimension and threshold |
| --- | --- |
| Register | 10 per hour per IP |
| Login | 20 per 10 minutes per IP; 15-minute lockout after 5 consecutive failures per account |
| Send verification email | 3 per hour per email, 10 per hour per IP |
| Send reset email | 3 per hour per email, 10 per hour per IP |

In-process memory counters are sufficient for this phase and a single-instance deployment; switch to Redis when scaling horizontally.

## Backend File List

### `server/cmd/server/main.go`

The wiring entry point, in order: load configuration, connect to the database, run AutoMigrate, seed the default tiers, create the initial administrator, initialize the mail client, register routes, and start the HTTP server with graceful shutdown.

Every business route is registered under a single `r.Group("/api")`, so no handler prepends `/api` on its own; only the `/healthz` and `/readyz` health checks sit at the root outside that group, because they are probed exclusively from inside the compose network. This prefix must line up exactly with how nginx writes `proxy_pass` — see the `nginx.conf` section below.

### `server/internal/config/config.go`

Reads configuration from environment variables into a struct and validates required values at startup. `CREDENTIAL_MASTER_KEY` is unused this phase but validated anyway so its absence is not discovered in phase 2. Under the default `MAIL_DRIVER=smtp`, any empty SMTP variable causes startup to fail with a clear error; `MAIL_DRIVER=log` skips that group of checks and is meant for local development only.

### `server/internal/db/db.go`

Connects GORM to PostgreSQL, runs `AutoMigrate` for all models, provides `SeedPlans` to write the `free` and `paid` defaults, and provides `EnsureAdmin` to create or promote the first administrator from `ADMIN_EMAIL` and `ADMIN_PASSWORD`.

`SeedPlans` and `EnsureAdmin` run on every container start, so their idempotency semantics must be pinned down rather than left at "must be idempotent". `SeedPlans` is insert-if-missing: it writes a default row only when no plan carries that `id` and never touches an existing row. Quota values an operator adjusted through the admin console or by hand in SQL therefore survive a restart. The trade-off is that editing quotas in `.env` no longer takes effect after the first boot — later tier changes go through the admin console or straight to the database, deliberately.

`EnsureAdmin` follows the same rule: it creates the administrator only when no user matches `ADMIN_EMAIL`, promotes that user when it exists with a non-`admin` role, and **never resets the password of an existing administrator**. Otherwise the password the administrator was told to change would be overwritten by the initial value from `.env` on the next restart.

### `server/internal/model/model.go`

```go
type User struct {
    ID              uuid.UUID  `gorm:"type:uuid;primaryKey"`
    Email           string     `gorm:"uniqueIndex;not null"`
    Username        string     `gorm:"uniqueIndex;not null"`
    PasswordHash    string     `gorm:"not null"`
    DisplayName     string
    AvatarURL       string
    Role            string     `gorm:"not null;default:user"`
    Status          string     `gorm:"not null;default:active"`
    EmailVerifiedAt *time.Time
    LastLoginAt     *time.Time
    CreatedAt       time.Time
    UpdatedAt       time.Time
}

type RefreshToken struct {
    ID        uuid.UUID `gorm:"type:uuid;primaryKey"`
    UserID    uuid.UUID `gorm:"type:uuid;index;not null"`
    TokenHash string    `gorm:"uniqueIndex;not null"`
    ExpiresAt time.Time `gorm:"not null"`
    RevokedAt *time.Time
    UserAgent string
    IP        string
    CreatedAt time.Time
}

type EmailToken struct {
    ID        uuid.UUID `gorm:"type:uuid;primaryKey"`
    UserID    uuid.UUID `gorm:"type:uuid;index;not null"`
    TokenHash string    `gorm:"uniqueIndex;not null"`
    Purpose   string    `gorm:"not null"` // verify_email | reset_password
    ExpiresAt time.Time `gorm:"not null"`
    UsedAt    *time.Time
    CreatedAt time.Time
}

type Plan struct {
    ID            string `gorm:"primaryKey"` // free | paid
    Name          string
    StorageBytes  int64
    MaxFileBytes  int64
    RetentionDays int
}
```

`plans` holds tier definitions rather than subscription packages, describing only the three storage-side ceilings. The two rows `SeedPlans` writes must match phase 3 exactly: the `free` tier gets `storage_bytes` 500 MB (524288000), `max_file_bytes` 50 MB (52428800) and `retention_days` 7; the `paid` tier gets 1 GB (1073741824), 200 MB (209715200) and 14. Phase 2's per-file check and phase 3's storage quota check both read this table directly, so a wrong seed value is inherited verbatim downstream and nothing else corrects it.

There is no `subscriptions` table and no `plan_id` on `users`: paid status is a function of `credits.balance > 0`, computable at any moment, so no table has to maintain its lifecycle and none of the expiry, renewal and grace-period state machine is needed. Nothing in this phase reads `retention_days`; it is modeled now because it is an intrinsic property of a tier definition and phase 3's media retention cleanup uses it directly, without another schema change at that point.

`users.last_login_at` feeds the "last login" column of the phase 3 admin console and is updated both on successful login and on successful token refresh. Updating it only on login is not enough: a user who keeps the page open and rides on silent refresh would look permanently inactive.

GORM fills `created_at` on `refresh_tokens` and `email_tokens` automatically. The former orders the session list by issue time; the latter is kept for auditing and for multi-instance rate limiting later. Email send limits in this phase are counted in process memory and never read that table, so do not implement a second, table-backed limiter for it.

### `server/internal/auth/auth.go`

Password hashing (bcrypt, cost 12), JWT issuing and parsing, refresh token generation and hashing, email token generation and hashing. All token hashing uses sha256 uniformly, and plaintext exists only at the moment of delivery.

### `server/internal/mail/mail.go`

SMTP client wrapper and the two email templates. Sending must be asynchronous and non-blocking — registration must not fail because the mail service is flaky, and the user can resend later. Failures are logged at error level.

Links are built from `APP_BASE_URL`: verification is `{APP_BASE_URL}/verify-email?token=xxx` and reset is `{APP_BASE_URL}/reset-password?token=xxx`.

### `server/internal/middleware/`

| File | Responsibility |
| --- | --- |
| `auth.go` | Parses `Authorization: Bearer`, validates the JWT, puts user id and role into the context; returns `TOKEN_EXPIRED` rather than a generic `UNAUTHORIZED` on expiry |
| `ratelimit.go` | Sliding-window counting keyed by IP or email |
| `logger.go` | Request logging and request ids, with password and token fields redacted; see "Logging and Observability" below |
| `recovery.go` | Panic backstop returning a uniform `INTERNAL_ERROR` |

### Logging and Observability

Logging uses the standard library `log/slog`, emitting JSON to stdout for docker to collect; no third-party logging library is introduced in this phase. The level comes from the `LOG_LEVEL` environment variable — `debug`, `info`, `warn` or `error` — defaulting to `info`.

Every request gets an `X-Request-Id` generated at the edge (reusing the inbound header when one is present), echoed back on the response and attached as a fixed field to every log line that request produces, so a request id from a user's screenshot is enough to pull the whole trace. Request logs always carry method, path, status, duration, client IP and request id, with passwords, tokens and cookies redacted. Error-level logs additionally carry `user_id` whenever the context has one, which makes per-user investigation possible. Requests taking longer than one second are logged separately at warn level, so slow endpoints surface before users report them.

### `server/internal/handler/auth.go` and `account.go`

Implemented against the endpoint definitions below. All writes use transactions; registration creates exactly two rows in one transaction, the user and the email token. The `credits` table arrives in phase 3, which backfills a zero-balance row for existing users and folds that insert into the registration transaction from then on; do not reserve an empty table or a placeholder row for it here.

## Endpoint Definitions

### POST `/api/auth/register`

Request:

```json
{ "email": "a@b.com", "username": "alice", "password": "at least 8 chars" }
```

Validation: valid email format; username 3 to 32 characters limited to letters, digits, underscore and hyphen; password 8 to 72 characters (bcrypt's 72-byte ceiling).

Success returns 201 and sets the refresh cookie:

```json
{
  "user": { "id": "...", "email": "a@b.com", "username": "alice", "displayName": "alice", "avatarUrl": "", "role": "user", "emailVerified": false },
  "accessToken": "eyJ...",
  "plan": { "id": "free", "name": "Free" }
}
```

Successful registration counts as login, and the verification email is sent asynchronously.

Errors: `VALIDATION_FAILED`, `EMAIL_TAKEN`, `USERNAME_TAKEN`, `RATE_LIMITED`, `REGISTRATION_DISABLED`.

### POST `/api/auth/login`

Request `{ "account": "email or username", "password": "..." }`. Response matches registration, with status 200.

Errors: `INVALID_CREDENTIALS`, `ACCOUNT_DISABLED`, `RATE_LIMITED`.

### POST `/api/auth/refresh`

No request body; the refresh token is read from the cookie. Success returns 200 with `{ "user": {...}, "accessToken": "...", "plan": {...} }` and sets a new refresh cookie.

Failure returns 401 `UNAUTHORIZED` and clears the cookie. Detecting reuse of a revoked token revokes all tokens for that user.

### POST `/api/auth/logout`

Revokes the current refresh token and clears the cookie, returning 204. It returns 204 even when the cookie is already invalid so the frontend logout flow never gets stuck.

### POST `/api/auth/verify-email/send`

Requires login. Resends the verification email for the current user and returns 204. Already-verified accounts also return 204 but no mail is sent.

Errors: `UNAUTHORIZED`, `RATE_LIMITED`.

### POST `/api/auth/verify-email`

Request `{ "token": "token from the email link" }`, no login required. Success returns 200 with the updated `{ "user": {...} }`.

Logic: look up by token hash, verify `purpose = verify_email`, not expired and unused; set `used_at` and write `users.email_verified_at`.

Errors: `TOKEN_INVALID`.

### POST `/api/auth/password/forgot`

Request `{ "email": "a@b.com" }`, no login required. **Always returns 204 regardless of whether the address exists**, sending the reset email asynchronously when it does.

Errors: `RATE_LIMITED`. Rate limiting needs care here too: differing limit behavior between existing and non-existing addresses would leak account existence, so counting treats IP and requested email uniformly.

### POST `/api/auth/password/reset`

Request `{ "token": "...", "password": "new password" }`, no login required. Success returns 204.

Logic: validate the token, update the password hash, mark the token used, and **revoke every refresh token for that user**, forcing all devices to log in again.

Errors: `TOKEN_INVALID`, `VALIDATION_FAILED`.

### GET `/api/me`

Requires login. Returns:

```json
{
  "user": { "id": "...", "email": "...", "username": "...", "displayName": "...", "avatarUrl": "", "role": "user", "emailVerified": true, "createdAt": "..." },
  "plan": { "id": "free", "name": "Free", "storageBytes": 524288000, "maxFileBytes": 52428800, "retentionDays": 7 }
}
```

The `usage` field arrives in phase 3.

### PATCH `/api/me`

Request `{ "displayName": "...", "avatarUrl": "..." }`, both optional. Returns the updated `{ "user": {...} }`.

### POST `/api/me/password`

Request `{ "oldPassword": "...", "newPassword": "..." }`. Success returns 204, revokes every refresh token **except the current session**, and sets a new refresh cookie.

Errors: `INVALID_CREDENTIALS` (wrong old password), `VALIDATION_FAILED`.

### GET `/healthz` and GET `/readyz`

Neither health endpoint sits under the `/api` group, neither requires authentication, and neither is exposed through nginx — they are probed only from inside the compose network. `/healthz` is the liveness probe: it returns 200 with `{ "status": "ok" }` immediately, touching no database and performing no I/O, so it passes as long as the process is alive. `/readyz` is the readiness probe: it runs a single `SELECT 1` against the database, returning 200 on success and 503 with `{ "status": "unavailable" }` on failure. Splitting them apart separates "the process died" from "the process is alive but cannot reach the database" — the first calls for restarting the container, the second is not fixed by a restart at all.

The `api` healthcheck in `docker-compose.yml` probes `/readyz`, so `app`'s `depends_on` waits until the backend can genuinely serve requests instead of releasing as soon as the port opens.

## Frontend File List

### `web/src/services/api/client.ts`

The unified request client. Responsibilities:

- Prefix `API_BASE_URL`, defaulting to an empty string for same-origin `/api`.
- Inject `Authorization: Bearer` automatically, reading the token from the in-memory auth store.
- Set `credentials: "include"` so the refresh cookie accompanies requests.
- On `TOKEN_EXPIRED`, call refresh automatically and replay the original request, allowing **only one refresh in flight at a time** while other requests queue for its result. Without this, concurrent 401s trigger multiple refreshes whose token rotation invalidates one another.
- On refresh failure, clear the session and redirect to the login page.
- Convert the backend `error.code` into a typed error object.

This "single-flight refresh with request queueing" is the easiest place to introduce a bug and deserves focused concurrency testing.

Do not touch the existing direct-to-provider AI code under `web/src/services/api/`; it targets the user's own third-party channels and is unrelated to this client.

### `web/src/services/api/auth.ts`

`register`, `login`, `logout`, `refresh`, `sendVerifyEmail`, `verifyEmail`, `forgotPassword`, `resetPassword`.

### `web/src/services/api/account.ts`

`getMe`, `updateProfile`, `changePassword`.

### `web/src/stores/use-auth-store.ts`

```ts
type AuthStatus = "booting" | "authenticated" | "unauthenticated";

type AuthStore = {
    status: AuthStatus;
    user: AuthUser | null;
    plan: Plan | null;
    accessToken: string | null; // memory only, never persisted
    bootstrap: () => Promise<void>;
    login: (account: string, password: string) => Promise<void>;
    register: (input: RegisterInput) => Promise<void>;
    logout: () => Promise<void>;
    setSession: (session: SessionPayload) => void;
    clearSession: () => void;
};
```

**Do not add `persist` to this store**; the access token must be lost on page reload.

Delete `web/src/stores/use-user-store.ts`, which is a stub.

### Frontend Startup Flow

`status` starts as `booting`. Immediately after mount the app calls `bootstrap()`, which issues one refresh request: if the cookie is present it receives a new access token and user info and becomes `authenticated`; a 401 makes it `unauthenticated`.

While `booting`, the route guard neither admits nor redirects and renders a full-screen loading state. This step cannot be skipped, otherwise every page reload flashes the login page for an already-authenticated user.

Per the project's existing convention, application initialization that must run exactly once should be guarded by a module-level flag so that repeated effect execution in development does not call refresh twice and invalidate the rotated tokens.

## Deployment Orchestration

### `docker-compose.yml`

Three services. `app` is nginx plus the frontend build, publishing 3000; `api` is the Go backend exposed only on the internal network at 8080; `db` runs the `postgres:17-alpine` image, exposed only internally at 5432. `api` waits for the `db` health check before starting, and `app` depends on `api`.

Volumes: `pgdata` for the database and `media` for the media directory (unused this phase but created up front).

The `api` healthcheck probes `/readyz` with `wget -qO- http://127.0.0.1:8080/readyz` (alpine ships wget; on a `scratch` runtime image use a health-check subcommand built into the binary instead), with `interval` 10s, `timeout` 3s, `retries` 5 and `start_period` 15s so AutoMigrate and seeding have room to finish — without the grace period the first boot is marked unhealthy and restarts in a loop. `db` uses `pg_isready -U $POSTGRES_USER`. `app` only needs `depends_on: api: condition: service_healthy`; nginx itself needs no healthcheck.

### `nginx.conf`

Add two locations to the existing server block, raising the body-size ceiling for media endpoints only:

```txt
location /api/media/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 200m;
}

location /api/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 2m;
}
```

`proxy_pass` **must not carry a trailing slash**, the easiest trap in this file. Written as `http://api:8080/`, nginx strips the `/api/` prefix the location matched before forwarding, so `/api/auth/login` reaches the backend as `/auth/login`; every endpoint in this document is written as `/api/...` and the backend registers everything under `r.Group("/api")`, so a literal implementation would 404 across the board. Without the trailing slash the path passes through untouched and lines up exactly with the backend prefix. Any future change here must be confirmed against the prefix the backend registers.

Splitting the body-size ceiling in two is equally necessary. `client_max_body_size 200m` exists for phase 2's 200 MiB video uploads, but it applies uniformly to everything under `/api/`, including the canvas save endpoint `PUT /api/canvases/{id}` — canvas `data` is stored as jsonb and counts against no storage quota, so a user can bloat the database by repeatedly submitting a 200 MB canvas JSON. Only `/api/media/` is therefore raised to 200m while everything else is capped at 2m. nginx prefix matching is longest-first, so the order of the two locations does not matter. The backend must additionally enforce a byte ceiling on canvas `data` (2 MB is a reasonable value) and return `VALIDATION_FAILED` beyond it: requests that bypass nginx and hit 8080 directly have to be rejected too, and the reverse proxy cannot be the only line of defense.

`X-Real-IP` and `X-Forwarded-For` are mandatory: without them the backend attributes every request to the nginx container's single IP and rate limiting stops working entirely. The backend must read the client address from `X-Real-IP` and trust that header only from the internal network.

### `server/Dockerfile`

Multi-stage: compile a static binary with `golang:1.26-alpine`, then run on `alpine` or `scratch`. `ca-certificates` is required for SMTP over TLS.

### Environment Variables

Base variables live in the deployment section of the plan document; this phase adds the following on top:

| Variable | Default | Purpose |
| --- | --- | --- |
| `ADMIN_EMAIL` | none | Email of the first administrator, used by `EnsureAdmin` to create or promote the account |
| `ADMIN_PASSWORD` | none | Initial password for that administrator; the documentation should prompt the user to change it immediately, and an existing administrator is never reset by it |
| `COOKIE_SECURE` | `true` | Whether cookies carry the `Secure` attribute; must be `false` on internal or local environments without TLS and must stay `true` on anything public |
| `LOG_LEVEL` | `info` | Log level, one of `debug`, `info`, `warn`, `error` |
| `MAIL_DRIVER` | `smtp` | How mail is delivered: `smtp` uses a real mail service, `log` only prints the message and its link to the log for local development |
| `PORT` | `8080` | The backend HTTP listen port, which must not be hardcoded; changing it requires updating the `api` healthcheck and the `proxy_pass` in `nginx.conf` too |
| `POSTGRES_DB` | none | Name of the database the `db` container creates on initialization |
| `POSTGRES_PASSWORD` | none | Initial database password for the `db` container |
| `POSTGRES_USER` | none | Initial database user for the `db` container, also read by its healthcheck `pg_isready -U $POSTGRES_USER` |

With `MAIL_DRIVER=log` the SMTP variables are excluded from required-value validation; otherwise an empty one still fails startup.

The three `POSTGRES_*` variables belong to the `db` container and are read by the postgres image itself — the backend process reads none of them — but they must match the user, password and database name inside `DATABASE_URL` exactly, otherwise the database starts and the backend cannot connect. They take effect only when the data volume is first initialized: once `pgdata` exists, changing them does not alter the real credentials in the database and only breaks `DATABASE_URL`, so changing the values means dropping the volume first.

## Local Development

Writing code does not require the whole compose stack; starting the database alone is enough:

```bash
docker compose up -d db
cd server && go run ./cmd/server
```

When the backend runs outside a container, `DATABASE_URL` must point at `localhost:5432` rather than the compose-internal `db:5432`. Local values for `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `JWT_SECRET` and friends live in `server/.env`, which is not committed.

### Vite Proxy

The frontend `bun run dev` server listens on 3000 (see `vite --host 0.0.0.0 --port 3000` in `web/package.json`, not Vite's default 5173) while the backend listens on 8080, which are two different origins. A `SameSite=Lax` cookie is not attached to cross-origin XHR, so the refresh flow breaks outright. Locally you **must** proxy `/api` to the backend in `web/vite.config.ts` so the browser still sees a same-origin request:

```ts
export default defineConfig({
    // ...existing config
    server: {
        proxy: {
            "/api": {
                target: "http://localhost:8080",
                changeOrigin: true,
            },
        },
    },
});
```

That file has no `server.proxy` block today, so this is a net addition. With it in place, leave `VITE_API_BASE_URL` empty in development: requests go to same-origin `/api` and vite forwards them, matching what nginx does in production. Because the dev server also speaks plain `http://`, `COOKIE_SECURE` must be `false` locally, otherwise the session cannot be kept either.

### Running Without SMTP

Development machines rarely have a usable SMTP server, so registration stalls where the verification email never arrives and the flow cannot be completed. The fix is `MAIL_DRIVER=log`: nothing is delivered, and the mailer instead logs the recipient, subject and the full verification or reset link at info level, so pasting that link from the terminal into the browser finishes the flow. Configuration validation skips the SMTP variables in this mode, so there is no need to invent fake SMTP settings just to boot the service.

## Testing Strategy

The backend uses the standard library `net/http/httptest` for test servers and introduces no additional test framework. Three paths must be covered: the auth middleware (missing, invalid and expired tokens return `UNAUTHORIZED` and `TOKEN_EXPIRED` respectively, and a valid token puts the user id into the context), the full registration-to-login flow (register, send verification, verify, log in, refresh, log out, with the mailer in `log` mode so the plaintext token can be recovered for assertions), and rate limiting (consecutive failures trigger the lockout, `Retry-After` carries the right value, and the window recovers on its own). Cases that need a database run as integration tests against a temporary PostgreSQL started by testcontainers, or against the instance from `docker compose up -d db` locally, using a separate test database name so development data stays clean.

The frontend uses Vitest, focused on the "single-flight refresh with request queueing" in `client.ts`: with a stubbed fetch, fire several concurrent requests that all return `TOKEN_EXPIRED` and assert that refresh is called exactly once, that every request receives the replayed success result, and that a failed refresh rejects all of them with the same error while clearing the session. This document already calls that logic the easiest place to introduce a bug, and concurrency problems cannot be found by clicking through the UI, so the automated test is mandatory.

`web/package.json` currently has neither a `vitest` dependency nor a `test` script — the existing scripts are only `dev`, `build`, `typecheck`, `start`, `format` and `format:check` — so this phase must run `bun add -d vitest` and add `"test": "vitest run"` under `scripts`. Without that step there is no entry point to run the tests above.

Localization gets a key-symmetry check script: flatten the nested keys of `zh-CN.ts` and `en-US.ts`, compare the two sets, and fail with a non-zero exit code when either side is missing one. Wire it into CI or run it ahead of `bun run typecheck`. Error-code copy is the most likely thing to drift, because the code table lives in the backend while the copy lives in the frontend and the two rarely change in the same commit.

## Acceptance Checklist

Deployment:

- On a clean environment, `docker compose up -d` brings all three services up healthy, `/` serves the frontend and `/api/me` returns 401 when logged out.
- With SMTP variables missing under the default `MAIL_DRIVER=smtp`, the backend fails to start and the log states why.
- Restarting the database does not duplicate the default tiers or the administrator account.
- With `COOKIE_SECURE=false` on a TLS-less environment, logging in over `http://ip:3000` works, a page reload keeps the session, and the `ic_refresh` cookie is visible in the browser.
- Inside the compose network `/healthz` returns 200 and `/readyz` returns 200 while the database is up; stopping the `db` container makes `/readyz` return 503 and turns the `api` healthcheck unhealthy.
- After adjusting quotas in `plans` and changing the administrator password by hand, restarting the containers preserves both instead of letting `SeedPlans` and `EnsureAdmin` reset them.
- Endpoints such as `/api/auth/login` are reached correctly through nginx, with no 404 caused by a trailing slash stripping the `/api` prefix.
- Submitting a canvas JSON larger than 2 MB to `PUT /api/canvases/{id}` is rejected: 413 through nginx, `VALIDATION_FAILED` from the backend when hitting 8080 directly.

Local development:

- Following the "Local Development" section with only the `db` container plus `go run`, and the frontend on `bun run dev` reaching `/api` through the vite proxy, the full flow works: register, take the verification link from the log, verify, log in, and stay logged in across a reload.
- With `MAIL_DRIVER=log`, startup skips SMTP validation and the full verification link appears in the log after registration.

Registration and verification:

- A new account can be registered, the verification email arrives, and clicking the link completes verification with a success page.
- A duplicate email returns `EMAIL_TAKEN` and a duplicate username returns `USERNAME_TAKEN`, each surfaced with the matching localized message.
- Clicking a verification link twice returns `TOKEN_INVALID` without taking effect again.
- Unverified accounts can still log in and browse.

Login and session:

- Login and logout work, and the cookie is cleared on logout.
- Reloading the page keeps the session without flashing the login page.
- After the access token expires, the next request refreshes silently with no user-visible effect.
- When several concurrent requests hit 401 at once, exactly one refresh occurs and every request eventually succeeds.
- **No token can be found** in localStorage or sessionStorage via the browser console.

Passwords:

- Forgot password delivers a reset email; after reset the old password fails and other devices are signed out.
- A non-existent address produces the same success message, leaking nothing about account existence.
- Changing the password while logged in signs out other devices while keeping the current one.

Guards and rate limiting:

- Visiting any business page while logged out redirects to login and returns to the original page afterwards.
- Five consecutive wrong passwords temporarily locks the account, returning `RATE_LIMITED` with `Retry-After`.
- Rapidly repeated verification email requests are rate limited.
