# Account System and Backend Service Plan

This document plans a multi-user system layered onto Infinite Canvas: a new Go backend service providing registration and login, cloud data synchronization, media object storage and user entitlements, deployed on a self-hosted server with Docker.

**The login-free mode is kept.** Anonymous users keep their data in the browser, signed-in users get cloud storage, and both paths are dispatched by one shared data layer in the frontend so pages never fork on it.

This document describes the plan only and contains no implementation code.

## Current State

The project currently has **no backend service at all**.

- `web/` is a pure static SPA built with Vite + React 19 + Ant Design + Tailwind + Zustand. The build output `web/dist` is served by nginx.
- `Dockerfile` is a two-stage build whose runtime image contains only nginx, with no server-side process. `vercel.json` is a static SPA deployment and `render.yaml` reuses the same image.
- All business data lives in the browser: canvases, assets and plugins go through IndexedDB (localforage), while AI configuration, WebDAV credentials and theme go through localStorage.
- AI requests go directly from the browser to the OpenAI-compatible endpoint configured by the user, without passing through any server.
- Cross-device sync relies on a WebDAV server supplied by the user.
- `canvas-agent/` is an Express + MCP bridge process running on the **user's own machine**, listening on `127.0.0.1:17371`, used to connect Codex / Claude Code to the canvas. It is a single-user local tool, not a backend service, and has no database.

Authentication **does not exist at all**. `web/src/stores/use-user-store.ts` is only a stub where `user` is permanently `null` with a single `clearSession`. All eight business routes in `web/src/router.tsx` have no auth guard.

## Goals

- Offer registration and login. Signing in unlocks cloud storage, platform-preset models and credit billing; staying signed out still allows full canvas use with data kept on the local machine.
- Canvases, assets, image logs and video logs of signed-in users are persisted server-side and restored automatically after logging in on another device, including the original image and video files.
- Third-party AI credentials configured by the user are stored encrypted on the server so they do not need to be re-entered on a new device.
- Provide a tier and quota system that limits resource usage by storage capacity, per-file size and media retention period.
- AI requests for platform-preset models are forwarded through the backend, users buy credits through online payment, and generation is metered and deducted server-side.
- Inputs and artifacts on the platform path pass content moderation, meeting the compliance requirements of operating in mainland China.
- The full stack is deployed on a self-hosted server through Docker Compose, with media on S3-compatible object storage.

### What Quotas Can and Cannot Enforce

The storage quota is a **hard constraint**: media must pass through the backend to reach disk, the server validates before writing, and there is no way around it.

Generation is a **hard constraint** as well. Credits are bought with real money, and failing to deduct them accurately means selling something whose books cannot be balanced. AI requests for platform-preset models therefore all move behind the Go backend: the platform's third-party key exists only on the server and never reaches the browser, the server knows exactly how many calls were made with which parameters, and deduction happens inline in the forwarding path. Building that path is what phase 4 is for.

The boundary to draw is around channels the user configures themselves. Those requests use the user's own key, still go directly from the browser, cost no credits, and are not counted server-side. This is deliberate rather than a hole — the user is burning their own allowance and the platform has no grounds to charge for it. But the images and videos those requests produce still consume the storage quota and are still subject to media retention once uploaded, so the server-side cost exposure remains covered by hard constraints.

One more boundary sits outside the signed-in state entirely: **the anonymous mode is subject to no platform quota at all.** Its data lives in browser IndexedDB, never passes through the backend and occupies not one byte of the server, so there is no storage quota, no per-file limit and no retention cleanup. The only ceiling is whatever storage the browser grants the site — an allowance the browser sizes from free disk space and the user can wipe with one click, which is neither under our control nor something we should promise. Anonymous users also cannot use platform-preset models: they are visible in the selector, but clicking one only leads to a signup prompt, because that path spends the platform's key and the user's credits and both require a meterable identity.

Product copy can therefore describe credit consumption on platform models as definite, unavoidable metering. That is the precondition for charging at all.

### Credits and Paid Status

Fix the unit first: **1 credit = 1 micro-yuan = 0.000001 CNY, and top-ups convert 1:1**, so paying 10 CNY yields 10,000,000 credits. Every amount and every credit figure is an `int64` and floating point is not allowed anywhere in the math — 0.1 + 0.2 does not equal 0.3 in floating point, and in a billing system every rounding error eventually becomes an entry the books cannot explain. Micro-yuan rather than cents, because a single generation may well cost a fraction of a cent, and a cent-based ledger forces the crude "anything less than a cent rounds up to a cent" pricing. The interface always shows money in yuan; "credits" is an internal accounting unit and users should never have to learn the conversion.

**The ledger has two buckets.** `purchased` holds only credits the user paid for; `granted` holds gifts — check-ins, the bonus portion of a top-up package, and administrative compensation. Deduction always draws from `granted` first and `purchased` second, so users spend the free part before the part they paid for.

The split exists to answer a question a single bucket cannot: **has this user ever actually paid?** "Any balance above zero means paid" breaks the instant grants exist — hand a new user a small trial allowance and they immediately become a "paid user" entitled to 1 GB of storage and 15-day retention while the platform has collected nothing. Paid status is therefore redefined as **`purchased_micros > 0 OR paid_until > now()`**, and no amount of granted credit confers it.

`paid_until` handles the other half: whether a user who did pay drops back to free the moment their credits run out. With only `purchased_micros > 0`, the tier flips at the instant of exhaustion, so topping up in the morning and running out by the afternoon triggers a downgrade and cleanup — which reads as bad faith. Every top-up therefore pushes `paid_until` forward from the current moment by `entitlement_days` (30 by default, overridable per package), and the paid tier holds for that window regardless of whether the balance hits zero.

**This is still not a subscription.** `paid_until` is only an expiry timestamp, and its passing triggers nothing: no scheduled job, no auto-renewal, no billing cycles or dunning, no failed-charge retries, and no `subscriptions` table. Tier resolution is one comparison computed on the spot, and an expired user simply lands on the free tier at their next request. What makes subscriptions expensive was never the table; it is the state machine around it, and none of that is introduced here.

The consequences of a tier flip match the original plan, with one buffer added. A downgrade deletes nothing, but storage in use has very likely already passed the new tier's ceiling, at which point the account enters **read-only mode**: browsing, exporting and deleting still work, uploading new media does not. Users who have paid before land first on the **`sunset` tier** (200 MB storage, 200 MB per file, 7-day retention) with a 60-day grace period, and only then fall to the free tier's 50 MB. This tier is forced by dropping the free quota from 500 MB to 50 MB: paid users routinely accumulate a few hundred megabytes, so dropping them straight to 50 MB turns "running out of credits deletes most of my work" from an edge case into the guaranteed path of every churned subscriber — that is not quota design, that is converting churned users into complaints at scale. Reminder emails go out during the grace period, the user can top up to restore or trim their own data, and accounts still over quota after 60 days are cleaned up starting from the oldest media until they fit.

**v1 does not support refunds**, and this belongs in the terms of service: credits are non-refundable once purchased, and the `refunded` value of `orders.status` is reserved but never used. The reason is that consumed credits have already incurred real upstream cost, and refunding a partially consumed balance requires a whole apparatus of pro-rata settlement, clawing back grants and rolling back paid status — complexity and reconciliation risk that the current scale does not justify. Note this differs from the full refund on a failed generation: that is a reversal inside one transaction, written as a `type = refund` ledger row, and involves no real money.

### Free Generation Allowance

The free tier gets two **independent** one-time counters: 3 images **and** 1 video, neither drawing from the other. Once spent they are gone, and **there is no daily reset**.

Skipping the daily reset is a calculation, not caution. Under open registration a daily reset makes a single account's annualized exposure 365 times that of a one-time allowance while the cost of registering approaches zero — effectively building a reliable pipe for "a new inbox buys another round forever". A one-time allowance is bounded by "signups × once", an order of magnitude smaller, and abuse costs a one-off rather than a continuous bleed. Two counters instead of one generic count, because upstream costs for images and video differ by one to two orders of magnitude: a shared counter would either let one video swallow everything or squeeze the image allowance down to no experiential value.

The allowance only covers a **locked, cheapest parameter combination**: images are limited to `n = 1` plus the model's smallest size and default quality; video is limited to 480p, the smallest positive value in the model's `constraints.duration`, no audio track and no reference images. When parameters fall outside that combination the request **does not error, it simply switches to the credit path** — the point of a trial is to let people see the result, not to hand them a feature they must first study the rules to use, and an error reading "the free allowance does not support this size" only loses the new user on their very first generation. All the frontend has to do is show in advance whether this run uses the allowance or credits, with the server as the authority on that judgment.

A `model_catalog.free_trial_eligible` column is also required to bound the model scope. Locking parameters caps only part of the per-run cost; the spread between models is larger, and without this column new users are free to spend their trial on the most expensive model in the catalog — which is precisely what everyone would choose. It defaults to false, so newly listed models do not enter the trial scope automatically; otherwise every listing of a pricier model silently widens the exposure.

The paid side remains purely credit-based and the two systems never mix: there is no "convert runs into credits" middle ground, and no single generation is ever half allowance and half balance. The order of evaluation is model `free_trial_eligible` and parameters inside the locked combination first, remaining counter second; only when both hold does the run use the allowance, and otherwise it always uses credits.

### Media Retention and Expiry Cleanup

Cleanup covers **all media, including media a canvas currently references**. This differs from the common approach and deserves explaining up front: if only orphans were cleaned up, a user could occupy storage forever simply by keeping an image attached to some canvas, and retention would mean nothing.

But "images inside my canvas get deleted" sounds like it destroys people's projects, so the timing rule has to compensate. A media file's **last touch time** is the maximum of `updated_at` across every canvas referencing it, `updated_at` across every asset referencing it, and `created_at` of every generation record referencing it. Touching any one of them restarts the clock, and only exceeding the tier's `retention_days` (7 days on free and sunset, 15 days on paid) moves the file into cleanup. The result is that active projects are never reclaimed and only genuinely abandoned media — canvases never opened, assets never touched — ever expires.

No `expires_at` column is added. Expiry is a derived value continuously refreshed by writes to several tables, so materializing it as a column means maintaining it on every canvas save, asset update and generation write: write amplification, and very easy to miss one path. It is computed on the fly when the cleanup job scans instead, and that job is **merged with the phase 3 orphan reclamation into a single scan** — both have to walk the jsonb columns of three business tables to resolve references, and one pass yields both "who is unreferenced" and "when was this last touched".

Warning before expiry is mandatory: an email 2 days ahead plus an in-app notice, together with a one-click export entry so users can take out whatever they want to keep. Automatic deletion without warning is an incident, not a feature.

### Cost Risk of Open Registration Combined with Full Media Sync

These two decisions still create a cost exposure, but the quota change puts it in an entirely different bracket: with a 50 MB free tier, the theoretical peak for 100 registered users is 5 GB rather than the earlier 500 GB. That number is effectively free on any object storage provider, so **capacity is no longer something to worry about in advance**.

The cost focus therefore moves from disk to **egress**. Canvas applications have high read amplification: opening one canvas pulls dozens of images, and every switch between canvases, every device syncing, every shared link someone else opens is another egress. Capacity is paid once, traffic accumulates per request, and a few hundred gigabytes of monthly egress on metered object storage can exceed the storage bill by an order of magnitude. That is exactly why Cloudflare R2 is the first choice in the cloud — its egress is free, which zeroes out the dominant cost line. R2's real-world speed in mainland China has to be measured, and if it proves unacceptable the fallback is Alibaba Cloud OSS + CDN, where traffic becomes the largest cost line again and traffic alerting plus a budget ceiling become mandatory.

A smaller magnitude does not mean the defenses can go. All of the following stay:

- Rate-limit the registration endpoint by IP and by email domain to prevent scripted bulk signups.
- **Disallow media uploads until email verification passes**, keeping unverified accounts at zero storage.
- Check the storage quota and the per-file limit before writing a file rather than writing first and accounting afterwards.
- Provide a cleanup policy for long-inactive accounts as a backstop.
- Clean up media per tier on expiry, turning "sign up, fill the quota, never come back" from a permanent occupation into a time-limited one, so usage no longer accumulates monotonically with signups but falls back as inactive accounts expire.

One exposure is added on top, pointing the opposite way: **the free generation allowance is real money spent upstream.** Storage merely occupies space; a free generation is something the platform has already paid an upstream vendor for. Three images plus one video multiplied by the signup count is the ceiling on that spend, so it has to be considered together with registration rate limiting and email verification — containing signups is what contains this bill. `FREE_TRIAL_ENABLED` is the emergency valve under abuse, and like `REGISTRATION_ENABLED` it must be wired up in advance.

Storage capacity should still be provisioned as a proportion of "expected signups multiplied by the free quota" with watermark alerting configured, just with a base an order of magnitude smaller; the alerts that actually matter now are egress volume and daily free-allowance consumption.

## Repository Layout: Stay in This Repository, Add a Top-Level `server/`

**Conclusion: do not create a new repository. Add a `server/` directory in the current repository.**

This repository is already a multi-package structure where `web/` (frontend), `canvas-agent/` (local Node service), `plugins/` (canvas plugins) and `docs/` (documentation site) are independent. Adding `server/` is fully consistent with the existing organization.

Three reasons for the single-repository choice:

1. **The frontend-backend contract is tightly coupled.** The field shapes of canvases, assets and generation records are carried jointly by frontend type definitions such as `CanvasProject` and `Asset` and by backend table schemas, so changing one field means touching both sides. A single repository lets one change update both sides at once, whereas two repositories require extra version coordination and contract synchronization at a cost far exceeding the benefit.
2. **Deployment orchestration belongs together.** Docker Compose must orchestrate frontend, backend and database simultaneously, and `nginx.conf` must proxy `/api`. These configurations naturally belong to the same deployment description.
3. **Server-side credential custody and billing have already diverged from upstream.** Upstream `basketikun/infinite-canvas` is an MIT-licensed pure local tool, whereas this work keeps the anonymous local mode while adding accounts, server-side credential custody, object storage and credit billing, and is not intended to be merged back. The argument that separate repositories ease upstream syncing therefore does not apply.

Related precautions: never commit real keys or production configuration under `server/` — use environment variables and `.env` (already ignored in `.dockerignore`). Mark this repository as a private fork in the README and describe the differences from upstream.

If the ability to merge upstream must be preserved, the alternative is a separate backend repository with frontend changes confined to a few files. However, the auth state and the data dispatch layer intrude into routing, the request layer, the config page and the top navigation, making such confinement impractical. Not recommended.

`internal/storage` is one interface with two implementations: `local` writes to a disk volume and `s3` speaks the S3-compatible protocol, selected by `STORAGE_DRIVER`, with callers seeing only the interface. Presigned URL generation for the read path lives in this layer too — the local driver returns the backend's own direct-read address while the S3 driver returns a presigned URL aligned to the hour, so nothing above needs to know which one is mounted.

`internal/payment` splits into Alipay and WeChat Pay implementations behind one shared order-creation and webhook interface, with signature verification always delegated to each provider's official SDK rather than assembling signature strings by hand. `internal/provider` splits by upstream protocol into OpenAI, Gemini and Ark implementations that only translate a unified request into each vendor's call and parse the response back into one shape, never touching business semantics; channel selection, failover and timeout configuration live in `internal/service/upstream.go`; deduction, metering and balance checks live in `handler/ai.go` around the forwarding call. Keeping the three apart is what lets a vendor swap leave the billing code untouched.

## Technology Choices

| Purpose | Choice | Rationale |
| --- | --- | --- |
| HTTP framework | Gin | Mature ecosystem, plenty of documentation, concise routing and middleware |
| ORM | GORM + AutoMigrate | The project is not yet released, so no migration scripts are needed and AutoMigrate is the least code |
| Database | PostgreSQL | Canvases and assets are large JSON blobs that fit JSONB columns directly and can be indexed |
| Authentication | golang-jwt/jwt v5 | Access token plus refresh token |
| Password hashing | golang.org/x/crypto/bcrypt | Standard practice, no custom design needed |
| Credential encryption | Standard library crypto/aes and cipher.GCM | No third-party crypto library required |
| Object storage | S3-compatible (Cloudflare R2 in the cloud, Alibaba Cloud OSS as fallback), local disk driver retained | The dominant cost of a canvas application is egress rather than capacity, and R2's free egress zeroes that line out; `aws-sdk-go-v2` covers every S3-compatible service with one implementation, and private deployments can still switch back to a disk volume |
| Content moderation | Alibaba Cloud Content Moderation Enhanced | Operating in mainland China calls for a service usable as compliance evidence rather than a self-built model; text and images go through the same vendor, integrated in phase 5 |
| Payment providers | Each provider's official Go SDK | Order parameters and webhook signature verification come from the SDK; signature logic is never hand-written |
| AI forwarding | Standard library net/http | Upstream calls and chunk-by-chunk SSE flushing need nothing beyond `http.Flusher`, and per-vendor protocol differences live in the adapters under `internal/provider`, so no extra framework is needed |

This follows the project convention that general-purpose capabilities always use mature, stable libraries rather than hand-written protocol, crypto or date implementations.

### Business Data

Canvases, assets and generation records each get their own table with one row per business object, rather than packing an entire domain into a single large JSON blob. That way the list view can paginate, search by title and let the database sort, and optimistic locking narrows down to a single row. Every business table carries `deleted_at` for soft deletion, which removes the need for a separate deletion-marker table.

**canvases** — canvases

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid | Primary key |
| `user_id` | uuid | Foreign key, indexed |
| `title` | varchar | Canvas title, supports fuzzy search |
| `data` | jsonb | Full canvas content: `nodes`, `connections`, `viewport`, `chatSessions`, `backgroundMode` and so on |
| `revision` | bigint | Optimistic lock, incremented on every write |
| `node_count` | int | Denormalized for the list view so `data` never has to be parsed |
| `connection_count` | int | Same purpose; list cards display "N nodes · N connections" |
| `cover_key` | varchar | `storage_key` of the cover image, nullable |
| `created_at` / `updated_at` | timestamptz | |
| `deleted_at` | timestamptz | Soft deletion, nullable |

The index `(user_id, deleted_at, updated_at desc)` covers exactly the default list query: current user, not deleted, newest first. `node_count` and `connection_count` are deliberate denormalizations that let the list endpoint avoid touching `data`, a column that can run to several megabytes.

`cover_key` deserves a separate note: **the list view has no cover image today**, its cards being a flat color block with a title and some statistics. Phase 2 implements the column outright — the server derives the value from `data.nodes` as the `storageKey` of the first image node and ignores whatever the client sends, and the list card renders a plain `<img src={"/api/media/" + coverKey}>`, keeping the existing solid color block when `coverKey` is empty. One scheduling caveat stands: rendering a cover on the card is new UI work rather than a port of something that already exists, so budget it separately instead of assuming it falls out of the data layer rework for free.

**generations** — generation records, replacing the former image-workbench and video-workbench domains

| Column | Type | Notes |

### Entitlements

**plans** — tier definitions

| Column | Type | Notes |
| --- | --- | --- |
| `id` | varchar | `free` / `paid` / `sunset` |
| `name` | varchar | Display name |
| `storage_bytes` | bigint | Total storage quota |
| `max_file_bytes` | bigint | Per-file limit |
| `retention_days` | int | Media retention in days |
| `free_image_trials` | int | One-time free image generations |
| `free_video_trials` | int | One-time free video generations |

Three default rows are seeded on initialization:

| id | Name | Storage quota | Per-file limit | Media retention | Free images | Free videos |
| --- | --- | --- | --- | --- | --- | --- |
| `free` | Free | 50 MB | 20 MB | 7 days | 3 | 1 |
| `paid` | Paid | 1 GB | 200 MB | 15 days | 0 | 0 |
| `sunset` | Sunset | 200 MB | 200 MB | 7 days | 0 | 0 |

The allowance lands as two columns, `free_image_trials` and `free_video_trials`, rather than a `trial_units` jsonb or one generic count: they are two unrelated counters to begin with, structured fields can participate directly in SQL checks, and this avoids reserving an extension point for a hypothetical third capability nobody needs yet. These columns define only the **ceiling**; how much a user has spent lives in `usage_records` keyed by `(user_id, metric)`, so adjusting an allowance means editing one tier row and touching no user data.

`sunset` is not a tier sold to anyone. It appears only on the downgrade path, so it is excluded from the public `/api/plans` list and cannot be purchased. Making it a tier row instead of a hardcoded set of downgrade parameters keeps "how much can be stored during the sunset period, and for how long" as configurable, inspectable and admin-editable as the other two.

This table no longer records daily generation limits — generation consumes credits, and the free allowance is a one-time trial rather than a recurring quota. Nor does it represent "which plan the user bought"; the user-tier relationship is derived from paid status on the spot:

- `purchased_micros > 0 OR paid_until > now()` → `paid`
- otherwise, `paid_until` is non-null and `paid_until + 60 days > now()` → `sunset`
- otherwise → `free`

The sunset tier therefore needs no new column and no "downgraded at" field: `paid_until` already records exactly when the paid entitlement ended, and the grace period counts 60 days from there. It also means a downgrade is not an event that has to be triggered — no scheduled job, no state transition, just the same expression yielding a different answer at a different moment. There is still no subscriptions table and no subscription relation to maintain.

**credits** — credit balance, two buckets

| Column | Type | Notes |
| --- | --- | --- |
| `user_id` | uuid | Primary key and foreign key, one row per user |
| `purchased_micros` | bigint | Balance bought with money, never negative |
| `granted_micros` | bigint | Balance received as a grant, never negative |
| `paid_until` | timestamptz | Expiry of the paid entitlement, nullable |
| `updated_at` | timestamptz | |

**No separate `balance` total column**: it equals the sum of the two buckets, and storing it again only creates a second "truth" that can disagree with them, while adding two numbers at display time costs nothing. Deduction always draws `granted` first and `purchased` second, and when it spans both buckets the two updates must happen in the same transaction.

**credit_transactions** — credit ledger

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid | Primary key |
| `user_id` | uuid | Foreign key, indexed |
| `type` | varchar | `purchase` / `consume` / `refund` / `grant` / `expire` |
| `bucket` | varchar | `purchased` / `granted`, the bucket this entry moves |
| `amount_micros` | bigint | Positive to add, negative to deduct, in micro-yuan |
| `balance_after_micros` | bigint | Balance of **that bucket** after this movement |
| `ref_type` | varchar | `order` / `generation` / `admin` / `checkin` |
| `ref_id` | varchar | Id of the related object |
| `note` | varchar | Free-form note |
| `created_at` | timestamptz | Indexed, used for cursor pagination |

The ledger is a table of its own rather than just a balance column because a paid system has to be auditable: when a user asks "why did my credits go down", the product must be able to itemize the answer. `balance_after_micros` is a deliberate denormalization so that diagnosing a discrepancy does not require replaying the whole ledger to find the entry that went wrong. Balance and ledger writes must happen in one transaction, otherwise "balance deducted but no ledger row" — or the reverse — will eventually occur, and that class of damage cannot be repaired automatically.

`bucket` is what makes the reconciliation identity hold per bucket: `credits.purchased_micros` equals the sum of `amount_micros` over all `bucket = purchased` rows, and the same for `granted`. Without it, a deduction spanning both buckets could only be recorded as one combined amount, leaving no way to reconstruct which bucket the money came from, and the two buckets would degenerate into a split that exists in the balance but cannot be explained in the ledger. **A cross-bucket deduction is therefore written as two rows**, in the same transaction and sharing one `ref_id`.

`ref_type` reserves the `checkin` value now. Check-ins do not ship in this round, but their destination must be the `granted` bucket, and pinning that down structurally beforehand avoids the tempting shortcut of dropping them into `purchased` later — which would turn every user who checks in into a paying customer.

**credit_packages** — top-up packages

| Column | Type | Notes |
| --- | --- | --- |
| `id` | varchar | Primary key |
| `name` | varchar | Display name |
| `price_micros` | bigint | Price in micro-yuan; credits landing in `purchased` equal it 1:1 |
| `bonus_micros` | bigint | Bonus credits, landing in the `granted` bucket |
| `entitlement_days` | int | Days of paid entitlement this package grants; falls back to `ENTITLEMENT_DAYS` when null |
| `currency` | varchar | Currency, currently `CNY` only |
| `enabled` | bool | Whether it is listed |
| `sort` | int | Ordering |

The old `credits` column is gone: top-ups convert 1:1, so credits landing in `purchased` always equal `price_micros`, and storing it twice only creates a chance for two numbers to disagree. `price_cents` also becomes `price_micros` so the whole schema shares one unit; conversion to cents happens when submitting to the payment provider, which is why the admin form must validate that a price is a whole multiple of 10,000 micro-yuan (a whole cent) and leave no room for an uncollectable price. `entitlement_days` sits on the package rather than relying solely on a global constant so larger packages can grant a longer window — that is a promotional lever, and hardcoding it globally throws it away.

**orders** — payment orders

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid | Primary key |
| `user_id` | uuid | Foreign key |
| `provider` | varchar | `alipay` / `wechat` |
| `provider_order_id` | varchar | Provider-side order number, unique |
| `package_id` | varchar | Foreign key into credit_packages |
| `amount_cents` | bigint | Amount actually paid, in cents, used for provider reconciliation |
| `currency` | varchar | Currency, currently `CNY` only |
| `purchased_micros` | bigint | Snapshot of credits this order adds to the `purchased` bucket |
| `granted_micros` | bigint | Snapshot of bonus credits this order adds to the `granted` bucket |
| `entitlement_days` | int | Snapshot of the paid entitlement days this order grants |
| `status` | varchar | `pending` / `paid` / `failed` / `refunded` (value reserved, unused in v1) |
| `paid_at` | timestamptz | Payment completion time, nullable |
| `created_at` / `updated_at` | timestamptz | |

The single former `credits` field now splits into three snapshots. Splitting is necessary rather than cosmetic: at settlement these three values go into two different buckets and one expiry timestamp, and a single combined number cannot be decomposed back. All three can also be changed in the admin console after the user places an order — repricing, adjusting the bonus ratio, shortening a promotional window — and only a snapshot at order creation guarantees the user receives what they were shown. The webhook uses these three values directly and never re-reads credit_packages, since packages can be repriced or delisted at any time while a callback may arrive minutes or hours later. `amount_cents` stays in cents because it exists for provider and finance reconciliation and takes no part in internal accounting.

The uniqueness of `provider_order_id` is the foundation of webhook idempotency: a repeated callback for the same payment is stopped by the unique index, making double-crediting impossible. Providers retry callbacks as a matter of course, so this is the normal path and not an exceptional one.

**usage_records** — usage counters, unique by `(user_id, metric, period)`, with `period` only ever `total`. It serves three metrics: `storage_bytes`, `free_image_trials` and `free_video_trials`. Storage has to be validated before every upload and `SUM(bytes)` degrades as the file count grows, which does not belong on the upload hot path, so a counter is the necessary compromise; the two allowances are the same case — the check runs before every generation, and because they are one-time, a counter is both more direct and less exposed to later data changes than recomputing from `generations` (deleting a generation record must not refund a free trial, but a recomputation would). Other generation counts still stay out of this table: display figures such as "images generated today" are counted straight from `generations`, and billing is settled from the credit ledger.

### Model Catalog

**model_catalog** — platform model catalog

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid | Primary key |
| `name` | varchar | Model identifier actually sent upstream |
| `display_name` | varchar | Display name |
| `capability` | varchar | `image` / `video` / `text` / `audio` |
| `provider` | varchar | Owning channel |
| `constraints` | jsonb | Parameter constraints, shaped like `{ sizes: [], aspectRatios: [], durations: [], qualities: [], maxReferenceImages: n }` |
| `credit_cost` | jsonb | Pricing rules keyed by parameters, in micro-yuan |
| `free_trial_eligible` | bool | Whether the free generation allowance may use it, false by default |
| `enabled` | bool | Whether it is visible to users |
| `sort` | int | Ordering |
| `created_at` / `updated_at` | timestamptz | |

This table exists to fix three defects in the current frontend: model capability is guessed from name keywords by `guessCapability` in `use-config-store`; resolution and maximum edge length are global hardcoded constants such as `QUALITY_BASE` and `IMAGE_MAX_EDGE` in `image.ts`, applied identically to every model; and the system has no idea which sizes, aspect ratios or durations a specific model actually supports, so users have to find out by trial — pick an unsupported combination and the only feedback is an upstream error.

`constraints` is jsonb rather than a set of columns because different capabilities constrain different dimensions in the first place: image models care about sizes and aspect ratios, video models care about durations, speech models care about neither. Splitting them into columns produces a wide table that is mostly null, and these constraints are only ever read and rendered by frontend forms, never queried by field. `credit_cost` is the same: pricing is naturally bound to parameters — the same model costs differently at 1024×1024 and at 4K, video is priced by duration — so it can only be configured model by model.

`free_trial_eligible`, conversely, has to be a queryable boolean column rather than a key inside `constraints`: the allowance check sits on the generation hot path and needs it in SQL and index conditions, and the admin console needs to list "which models are currently in the trial scope" at a glance. Defaulting to false is deliberate — newly listed models do not enter the trial scope automatically, otherwise every listing of a pricier model silently widens the free exposure.

One point deserves emphasis: **the model catalog is a platform preset, not a mandatory allowlist.** Channels and models the user configures themselves are kept, the frontend merges both sources into one list, and the only difference is that custom models have no `constraints` to work from, so their parameter form falls back to today's generic shape and they consume no credits.

### Generations

History is append-only, so it uses cursor pagination rather than page numbers. The cursor is `created_at desc` plus `id`, which keeps paging stable and duplicate-free even when new records arrive mid-scroll.

| Method | Path | Notes |
| --- | --- | --- |

### Media Files

| Method | Path | Notes |
| --- | --- | --- |
| HEAD | `/api/media/{storageKey}` | Check existence, size and checksum |
| GET | `/api/media/{storageKey}` | 302 redirect to a presigned URL; streams the binary directly under the local disk driver |
| PUT | `/api/media/{storageKey}` | Upload, proxied and streamed to object storage by the backend, with quota and email-verification checks before writing |
| DELETE | `/api/media/{storageKey}` | Delete |

Media travels over dedicated binary endpoints and business objects reference only a `storageKey`. Once the frontend has a canvas or an asset it fetches files on demand rather than carrying them inside the JSON body.

**`GET /api/media/{storageKey}` must be designed as an ordinary URL that can go straight into `<img src>`**, not something the frontend downloads as a Blob and converts to an ObjectURL. This is worth emphasizing because it deletes an entire existing mechanism: today `image-storage.ts` and `file-storage.ts` each maintain a module-level `storageKey → ObjectURL` map, opening a canvas resolves every image into an ObjectURL in bulk, and that map is never evicted, so memory grows steadily as the user moves between canvases. With direct URLs the browser HTTP cache takes over and both maps, the asynchronous bulk hydration and the leak that comes with them all disappear.

There is a conflict to resolve here: phase 1 keeps the access token in memory only and scopes the refresh cookie to `Path=/api/auth`, so an `<img src>` request can reach neither the in-memory token nor that path-restricted cookie.

The resolution is to **issue an additional read-only media cookie at login and refresh**, with `HttpOnly; Secure; SameSite=Lax; Path=/api/media`, rotated on the same cycle as the refresh token. Its authority is deliberately minimal: it can read only the owning user's media and cannot call any business endpoint, let alone read credentials. Even if stolen, the loss is far smaller than a leaked access token, which would expose every third-party API key the user owns.

Uploads still travel as ordinary requests carrying an `Authorization` header; this cookie applies only to `GET` and `HEAD`. Do not turn it into a general session cookie for convenience, which would undo the phase 1 token design.

#### Read path: a 302 to a presigned URL

`GET /api/media/{storageKey}` is implemented as **verify identity and ownership, then 302 to a presigned URL on the object store**, so the binary never passes through the backend and one round of egress bandwidth plus one memory copy disappear. The two presigning parameters have to be designed as a pair: **the issue time is aligned to the hour and the lifetime equals 2 × the alignment window** (1-hour alignment and a 2-hour lifetime by default). Alignment is what makes every request within the same hour receive **the identical URL**, giving browsers and CDNs a shared cache key to hit — without it every request signs a fresh URL, cache hit rate drops to zero and the redirect buys nothing. The lifetime is twice the alignment window so that every URL still has a full window of headroom when the next alignment point arrives, avoiding "a URL signed one second before the hour expires one second later".

**The `Cache-Control` of the 302 response itself can only be `private, max-age={presign seconds remaining - 60}`.** This is the most dangerous spot on the whole read path, worth hardcoding with a test to match. Following the intuition that "media is immutable content" and attaching `immutable` or a one-year `max-age` to this redirect makes the browser cache the redirect together with the signature inside it; two hours later the signature expires, the request never returns to the server to be re-signed, and the result is every image on the site breaking at once, immune to refreshes, fixable only by clearing the cache. The one-year `immutable` policy belongs on **the object's own metadata** — that caching policy applies to the object the presigned URL points at, not to the redirect pointing at it. The 60 seconds subtracted are the safety margin for clock skew and in-flight requests.

The presigned URL itself carries no cookie and cannot carry one to the object storage domain, which is exactly what we want: the media cookie's authority ends at "exchange this for one redirect", the actual read authority rests with that short-lived URL, and both windows are narrow.

**Writes keep going through the backend as a proxied stream; v1 does not do presigned direct upload.** Direct upload would save one hop, but the quota check and the sha256 both have to happen on the write path: uploading directly and reconciling through a callback afterwards leaves a window where the file is already in the bucket but not yet accounted for, and that window is the easiest possible way to blow past a quota. Revisit it when proxying actually becomes the bottleneck; v1 does not trade away a hard constraint for a performance gain that does not exist yet.

The local disk driver does not redirect and streams the binary from the backend, so development environments and private deployments can exercise the whole path without any S3 service at all.

### Payments and Orders

| Method | Path | Notes |
| --- | --- | --- |
| GET | `/api/credit-packages` | Top-up package list, listed packages only |
| POST | `/api/orders` | Create an order with body `{ packageId, provider }`, returning the provider's payment parameters |
| GET | `/api/orders?cursor=` | Cursor-paginated order list |
| POST | `/api/orders/{id}/cancel` | Cancel a pending order |
| POST | `/api/payments/webhook/{provider}` | Payment webhook, publicly reachable but must verify signatures and be idempotent |

`POST /api/orders` only creates a local order and returns payment parameters; credits do not land at this step. They land only after a webhook confirms payment, and writing the order status, crediting both buckets, pushing `paid_until` and appending the ledger rows must all happen inside one transaction. Settlement writes two ledger rows: `purchased_micros` into the `purchased` bucket and `granted_micros` into the `granted` bucket, both carrying the same `ref_id` pointing at the order. `paid_until` becomes `max(current value, now()) + entitlement_days` — extending from the current value is what keeps a user still inside their entitlement window from *shortening* their expiry by topping up again.

There are only two providers, Alipay and WeChat Pay, and only one currency, CNY; v1 integrates neither Stripe nor any foreign currency. Orders are non-refundable, and the `refunded` status is reserved but written by no code path.

The webhook is the only write endpoint in the entire backend without an `Authorization` header, so its two defenses have to be built into the implementation. **Signature verification** is delegated to each provider's official SDK and a failed signature is rejected outright — never waved through because "the order number looks like ours". **Idempotency** comes from the `orders.provider_order_id` unique index plus the order state machine, which permits the `pending → paid` transition exactly once and answers repeated callbacks with success while writing nothing.

### AI Request Forwarding

Added in phase 4 and requiring login throughout. Only platform-preset models take this path; user-configured channels still go directly from the browser.

| Method | Path | Notes |
| --- | --- | --- |
| POST | `/api/ai/images/generations` | Image generation, one entry point for both text-to-image and image editing |
| POST | `/api/ai/videos/generations` | Video generation, creates an asynchronous task and returns a `taskId` |
| GET | `/api/ai/videos/tasks/{id}` | Look up a video task's status and artifact |
| POST | `/api/ai/audio/speech` | Speech synthesis |
| POST | `/api/ai/chat/completions` | Chat completion, SSE streaming |

The paths mirror the shape of the OpenAI-compatible protocol, but **neither request nor response bodies pass through verbatim**. Requests define their own fields per capability and reference images travel as a `storageKey` rather than base64; responses always carry `credits` plus artifacts as `storageKey`s, with every upstream difference in field naming, envelopes and `b64_json` versus `url` collapsed server-side. `/api/ai/chat/completions` is the same story: it emits our own event stream rather than relaying the upstream SSE, with the backend flushing chunk by chunk instead of waiting for the upstream to finish and emitting everything at once, otherwise assistant conversations in the canvas regress from streaming to a single block appearing at the end.

The frontend therefore cannot get away with swapping a baseUrl. It gains a new `web/src/services/api/ai.ts` covering these five endpoints, and each generation entry point in `image.ts`, `video.ts` and `audio.ts` splits on the model identifier — a bare model name is a catalog model and goes through `ai.ts`, while an identifier containing `::` is a user channel model and keeps the existing browser-direct implementation. Video also moves from polling the upstream locally to polling this site's task endpoint.

Deduction happens **before generation, with a refund on failure**: before forwarding, the credits are computed from the model's `credit_cost` and the current parameters, then one transaction checks the balance, deducts it and appends a consumption ledger row, returning 402 outright when the balance is insufficient; an upstream failure or timeout refunds the full deducted amount and appends a `type = refund` row. There is no "settle the difference against the actual result" — phase 3 exposes only `Reserve` and `Refund` and has no settlement capability, and a second settlement path is just one more way for the books to disagree. The consistency of this path is what phase 4 needs to test hardest.

## Data Approach: A Server-Authoritative Resource Model

The original plan was to reuse the domain manifest contract from the existing WebDAV sync: pack each of the four domains — canvas, assets, image-workbench, video-workbench — into a single JSON blob to upload and download, merge it client-side with `mergeById`, and bolt on a deletion-marker table to supply the missing delete semantics. Its entire appeal was effort: the only parts of `web/src/services/app-sync.ts` genuinely bound to WebDAV are two upload and download functions, so swapping the transport layer would have been enough to get it running.

**That plan has been rejected.** It put "save some frontend work" ahead of "an architecture that holds up", and the saved work would come back quickly in more expensive forms:

1. **A whole domain in one JSONB blob cannot be queried.** To show a canvas list the client must pull the entire domain, easily several megabytes, and paging, title search and sorting by update time can only happen in frontend memory.
2. **Generation records are an append-only history stream.** Treating a log that is only ever appended to as something to "merge" is awkward to begin with, and once a user accumulates a few thousand entries, fetching all of them every time the workbench opens is simply unacceptable.
3. **The revision lock is far too coarse.** With optimistic locking applied to an entire domain, two devices editing **different** canvases still collide, and no user can be expected to understand why editing canvas A reports a conflict with canvas B.
4. **Deletion needs a separate mechanism.** The manifest model requires a dedicated tombstone table plus filtering on every merge, whereas a per-row `deleted_at` handles it once the data is resource-shaped.
5. **The data is opaque to everything else.** An admin console wanting to know how many canvases a user has, or any future API client wanting to read a single record, would first have to pull the whole domain blob and parse it.

The data layer therefore moves to a **server-authoritative resource-oriented REST model**: every canvas, asset and generation record is one row in the database, and the frontend no longer holds a full copy but requests what it needs on demand.

**The server is the single source of truth.** The client no longer merges. Writes go straight to the server and reads take the server response as authoritative. In-memory frontend data is a view of server data, not a second copy that has to be reconciled with it.

**On-demand loading, with list and detail separated.** List endpoints return summary fields only, never `data`; detail is fetched when a canvas is opened. Generation records use cursor pagination and only the current page is fetched. How much data a user has accumulated no longer determines how much is loaded on first paint.

**Optimistic locking pushed down to the individual record.** `revision` lives on each canvas row, `PUT /api/canvases/{id}` must carry the `revision` the client read, and a mismatch returns 409 `REVISION_CONFLICT`. Two devices editing different canvases never interfere, only genuine concurrent edits to the same canvas conflict, and the conflict message can name exactly which canvas is affected.

**Soft deletion instead of deletion markers.** Deleting writes `deleted_at`, and list queries filter it out by default. There is no tombstone table and no "deleted locally, resurrected from the remote" merge bug — in this model it cannot happen.

The cost has to be stated plainly: **the frontend data layer changes far more than under the original plan.** Today's stores read an entire domain from IndexedDB into memory at startup; they must become "fetch the list page by page, fetch detail on demand, write back on a debounce after edits". The merge logic in `app-sync.ts` is not reused — it is deleted. That is a real increase in work, and what it buys is a data layer that can paginate, can be searched, and can be queried directly by the admin console and by any future client.

## Deployment Orchestration

`docker-compose.yml` changes from a single container to three services:

```txt
app   nginx plus the frontend static build, exposes 3000 publicly
api   Go backend, exposes 8080 on the internal network only
db    PostgreSQL 17 (`postgres:17-alpine`), exposes 5432 on the internal network only
```

Volumes: `pgdata` persists the database and `media` persists user-uploaded images and videos. The `db` service takes its initial account, password and database name from `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB`, its healthcheck runs `pg_isready -U $POSTGRES_USER`, and `api` starts only once that check passes.

`nginx.conf` gains a reverse proxy so frontend and backend are same-origin and CORS is unnecessary:

```txt
location /api/media/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    client_max_body_size 200m;
}

location /api/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    client_max_body_size 2m;
}
```

**`proxy_pass` must carry no URI part at all**, the easiest trap in this file. Written as `http://api:8080/`, nginx strips the `/api/` prefix the location matched before forwarding, so `/api/auth/login` reaches the backend as `/auth/login`; every endpoint in this document is written as `/api/...` and the backend registers everything under `r.Group("/api")`, so a literal implementation would 404 across the board. Without the trailing slash the path passes through untouched and lines up exactly with the backend's route prefix.

The body-size ceiling has to be split in two. 200MB is the per-file limit of the paid tier and the 1MB default would fail uploads outright, but that allowance belongs to `/api/media/` alone: applied uniformly to everything under `/api/` it also opens up the canvas save endpoint, and canvas `data` is stored as jsonb and counts against no storage quota, so a user could bloat the database by repeatedly submitting a 200 MB canvas JSON. Media is therefore raised to 200m while everything else is capped at 2m; nginx prefix matching is longest-first, so the order of the two locations does not matter. The stricter 50 MB limit of the free tier is enforced by the backend against the user's tier and is not distinguished at the nginx layer — a tier flips with the credit balance, and a gateway can neither see the user's identity nor track that in real time.

Backend environment variables go into `server/.env.example`:

| Variable | Notes |
| --- | --- |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | Initial account, password and database name for the `db` service, also used by the compose healthcheck `pg_isready -U $POSTGRES_USER` |
| `DATABASE_URL` | PostgreSQL connection string, which must agree with the three variables above |
| `PORT` | Backend listening port, 8080 by default; changing it means updating the nginx `proxy_pass` and the compose healthcheck too |
| `JWT_SECRET` | Access token signing secret |
| `CREDENTIAL_MASTER_KEY` | AES-GCM master key for credentials, 32 bytes; the phase 4 platform channel keys reuse this same key rather than introducing a second one |
| `MEDIA_ROOT` | On-disk path for media files, backed by the `media` volume |
| `APP_BASE_URL` | Public site address, used to build verification and reset links in emails |
| `SMTP_HOST` / `SMTP_PORT` | Mail server address and port |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | Mail service account |
| `SMTP_FROM` | Sender address |
| `REGISTRATION_ENABLED` | Master switch for registration, enabled by default, can be shut off in an emergency |
| `ALIPAY_*` / `WECHATPAY_*` / `STRIPE_*` | Merchant ids, secrets and callback URLs per payment provider; unconfigured providers are automatically not listed |

The upstream address and key for platform-preset models **do not travel through environment variables**. Phase 4 adds a `platform_channels` table holding each channel's `BaseURL`, an AES-GCM encrypted `Payload` (the upstream API key in plaintext), `Priority` and `Enabled`, encrypted with the same `CREDENTIAL_MASTER_KEY`, managed through `/api/admin/channels`, with requests taking the first usable channel by `Priority` and moving to the next one on failure. A table rather than variables because rotating a key, adding a standby channel or disabling an upstream temporarily should never require editing config and restarting the container — and multi-channel failover was never something a pair of environment variables could express.

Media retention has no switch variable either. Whether a file is cleaned up is decided by its tier's `retention_days`, and running scan-only during validation is covered by the phase 3 approach of triggering the job on demand from the admin console and verifying it on a single user before attaching a schedule. No global master switch is needed.

A misconfigured `APP_BASE_URL` makes every link in verification emails unusable, so it deserves careful review at deploy time. When the SMTP variables are all empty the backend should fail to start with a clear error rather than silently failing to send mail.

Payment callback URLs must be publicly reachable and directly accessible by each provider's servers. A purely internal deployment cannot complete the payment loop, and the deployment documentation has to say so. The three providers are independent and configuring just one is enough to run; unconfigured providers become unselectable in `/api/credit-packages` and the order endpoint rather than failing only after the user commits to them.

`render.yaml` is currently a single-image static deployment and no longer applies after this migration; it must be adjusted or removed.

## Security Design

- Passwords are stored as irreversible bcrypt hashes.
- Refresh tokens are stored as hashes only, so a database leak does not yield usable tokens; changing the password revokes all other tokens for that user.
- Third-party AI credentials are AES-GCM encrypted with a master key read from an environment variable, never stored in the database or committed to the repository. The schema reserves `key_version` for future rotation.
- Upload endpoints must validate the `storage_key` format and confine it to the current user's namespace to prevent path traversal and cross-user reads.
- Email tokens are stored as hashes with the plaintext appearing only in the email link; they must be single-use with a short expiry.
- The password recovery endpoint always returns success regardless of whether the address exists, so response differences cannot be used to enumerate registered accounts.
- Admin endpoints are guarded by dedicated `role = admin` middleware and never by frontend entry-point hiding alone. The first administrator is created through an environment variable or an initialization command; self-service privilege escalation is not offered.
- The platform's own third-party key is stored encrypted in the `platform_channels` table and decrypted only at the moment an upstream request is made, with the plaintext living only inside `internal/service/upstream.go` and `internal/provider`, never cached, and never appearing in a response body, an error message or a log line. Forwarded responses must also strip any authentication headers the upstream might echo back.
- The payment webhook is the only public write endpoint. It must verify signatures before doing anything, and cap request body size and processing rate so it cannot become a way to overload the backend or forge orders.
- AI forwarding endpoints are rate-limited per user. Any authenticated identity can drive the platform's key upstream; the balance check governs how much can be spent and the rate limit governs how fast, and neither alone is sufficient.
- Holding users' third-party vendor keys server-side is a significant change in responsibility. `SECURITY.md` and `docs/content/docs/support/security.mdx` must document the storage method, encryption algorithm and risk boundary, and additionally cover custody of the platform key and the payment secrets.

### Additional Attack Surface from Open Registration

Public registration means anyone can obtain an authenticated identity, shifting the focus from "keep strangers out" to "limit how many resources one account can consume":

- Rate-limit registration and mail-sending endpoints by both IP and email address to prevent bulk signups and mail bombing.
- Block media uploads until email verification passes, so unverified accounts occupy no disk.
- Check the storage quota, the per-file limit and the credit balance before the operation, rejecting outright when exceeded or insufficient.
- Rate-limit the forwarding endpoints for platform models per user, so a freshly registered account cannot drive the platform key without limit merely by being logged in.
- Use `REGISTRATION_ENABLED` as an emergency switch to close registration immediately under abuse.

## Phased Implementation

Each phase has its own development baseline covering file responsibilities, endpoint payloads, error codes and an acceptance checklist: [phase 1](/docs/progress/account-backend-phase1), [phase 2](/docs/progress/account-backend-phase2), [phase 3](/docs/progress/account-backend-phase3), [phase 4](/docs/progress/account-backend-phase4).

### Phase 1: Account System and Email Pipeline

On the backend, build the `server/` skeleton and implement the users, refresh_tokens and email_tokens tables, registration, login, logout, refresh, password change, `/api/me` and the auth middleware, then integrate SMTP for email verification and password recovery and add rate limiting to the registration and mail endpoints.

On the frontend, add the unified client, `use-auth-store`, the login and registration page, the verification and password reset landing pages, the route guard, the top navigation user menu and localized strings.

For deployment, complete the three-service orchestration, the `/api` reverse proxy and the raised `client_max_body_size`.

Because registration is open, email verification cannot be deferred to a later phase — it is the precondition for keeping unverified accounts off the disk and must ship together with the account system.

Acceptance: on a clean environment, bringing up the containers allows registration with a verification email received and the link completing verification; login, token refresh and logout work; password recovery delivers a reset email and the password change succeeds; visiting any business page while logged out redirects to the login page.

### Phase 2: Credential Custody and the Data Resource Model

Implement the credential encryption endpoints and wire them into the frontend config page. On the backend, implement the canvases, assets, generations and media_files tables with their resource endpoints, covering paginated lists, cursor pagination, per-record optimistic locking and soft deletion. On the frontend, add the four resource clients, convert the canvas, asset and generation-history stores from full in-memory loading to on-demand loading with debounced write-back, and delete `app-sync.ts`. Add the "unverified email cannot upload" constraint to the upload endpoint.

Remove WebDAV entirely only after the resource model passes acceptance.

This is the heaviest phase for the frontend. The difficulty is not the endpoints themselves but reworking when data is loaded, so the schedule needs slack for it.

Acceptance: create a canvas and generate an image on device A, then log into the same account on device B and see the complete canvas along with the original image files; after deleting the canvas on device A, refreshing the list on device B no longer shows it; the canvas list paginates and can be searched by title, and its response body contains no `data`; when two devices edit the same canvas concurrently, the later save receives a 409 instead of silently overwriting; an account with an unverified email is rejected on upload.

### Phase 3: Tiers, the Credit Ledger and the Admin Console

Implement plans, usage_records and quota checks, seed the free and paid tiers, have `/api/me` return the current tier, storage usage and credit balance, display them in the frontend profile center, and block uploads that exceed the storage quota or the per-file limit.

In the same phase, implement the ledger side of credits and payments: the credits, credit_transactions, credit_packages and orders tables, top-up packages, order creation, order listing and cancellation, and signature verification plus idempotent webhook handling for all three providers, with a new `/billing` page for top-up and ledger on the frontend.

In the same phase, implement media retention cleanup: expiry computed on the fly from the last touch time, merged with orphan reclamation into a single scan, with a warning email, an in-app notice and a one-click export entry 2 days before expiry.

In the same phase, implement the admin console: the `/admin` route with a `RequireAdmin` guard, user list, suspend and restore, credit adjustment, order lookup, top-up package configuration, usage inspection and overview statistics.

It is worth being clear-eyed about the end state of this phase: credits are a balance that can be topped up and audited, but nothing consumes them yet. Do not open the top-up entry point to users before phase 4 ships, or the product is selling something it cannot yet redeem.

Acceptance: uploads exceeding the storage quota or the per-file limit are rejected with a clear message; a user can complete a real payment and see the balance and ledger increase correctly, a repeated callback for the same payment does not credit twice, and a callback arriving after cancellation credits nothing; media past its retention period and untouched for a long time is cleaned up while media referenced by a recently edited canvas is untouched, with a warning email arriving 2 days before; an administrator can look up any user's storage footprint and credit balance and adjust credits manually, while non-administrators are rejected from both `/admin` and the admin endpoints.

### Phase 4: Backend AI Forwarding and Credit Metering

Add the model_catalog table and `/api/models`, moving model capability, parameter constraints and pricing rules out of frontend hardcoding into admin configuration, and add model catalog CRUD to the admin console. On the backend, add `internal/provider` and `internal/service/upstream.go` plus the five `/api/ai/*` forwarding endpoints (video becomes an asynchronous task, so creation and lookup take one endpoint each), implementing the three upstream protocol adaptations and SSE streaming; platform channel keys live encrypted in the `platform_channels` table, managed through `/api/admin/channels` with failover by priority. On the frontend, add `web/src/services/api/ai.ts` and split on the model identifier at each generation entry point in `image.ts`, `video.ts` and `audio.ts`, render platform model parameter forms from `constraints`, leave user-configured channels going directly from the browser, and do not touch `model-plugin.ts` at all. Deduction happens inside the forwarding path: deduct before generating, refund in full on failure.

This phase and the phase 3 credit system are two sides of one thing. Phase 3 answers "how do credits get sold" and phase 4 answers "how do credits get consumed"; without the latter, the former is selling something that can be neither metered nor redeemed. That is why it must follow phase 3 closely rather than being deferred indefinitely.

It is also the technical foundation of the whole monetization model. Only with the platform key on the server can deduction be accurate, and only with accurate deduction can credits be sold at all. The commercial rule that platform-preset models cost credits while user-configured channels do not also lands in this phase, decided by whether the selected model is a catalog record or the user's own channel configuration — never by model name.

Acceptance: generating images, videos and speech with platform-preset models all succeed, with credits deducted according to the model's pricing rules and a ledger row left behind; assistant conversations in the canvas stream token by token rather than arriving as one block; an insufficient balance blocks the generation entry point and prompts a top-up; an upstream error or timeout deducts nothing and refunds anything already held with a refund ledger row; user-configured channels still go direct and consume no credits; the platform's third-party key never appears in the browser network panel; the parameter form offers only the options the model's `constraints` support and disables unsupported combinations.

## Impact and Breaking Changes

- **Login becomes mandatory site-wide**; nothing is usable while logged out.
- **WebDAV sync is removed entirely**; workflows that relied on WebDAV for cross-device sync are no longer supported and move to server-side storage.
- **The frontend data layer changes more than under the original plan.** Canvases, assets and generation records all become on-demand, stores no longer hold full datasets, and every component that iterated a complete in-memory list must be adjusted. The merge logic in `app-sync.ts` is dropped entirely rather than reused.
- **Offline capability is gone completely.** The server is authoritative, so once the network drops, uncached canvases cannot be read and edits cannot be saved. Mandatory login already gave up offline use; the resource model simply carries that decision into the data layer.
- **Vercel static deployment is dropped**; only self-hosted Docker is supported.
- **A new SMTP dependency is introduced**; registration cannot complete without a working mail service.
- **A new payment provider dependency is introduced**; Alipay, WeChat Pay or Stripe merchant credentials are required and the callback URL must be publicly reachable, so a purely internal deployment cannot complete the payment loop.
- **The AI request path splits in two.** Platform-preset models go through the backend while user-configured channels stay direct from the browser, so the frontend must decide which path applies before starting a generation instead of always going direct.
- **The platform absorbs third-party call costs.** Platform-preset models burn the platform's own key, so every generation a user runs costs real money. A misconfigured pricing rule or a hole in the deduction path costs the platform directly.
- **Running out of credits downgrades the tier automatically.** A paid user who exhausts their credits falls back to free, enters read-only mode when storage exceeds 500 MB, and after a 30-day grace period has media cleaned up starting from the oldest. This is product behaviour rather than a fault and must be stated plainly in the UI and in emails.
- **Media is no longer kept forever.** All media is timed against its tier's retention period and anything untouched for long enough is cleaned up. This runs against the intuition that uploading means permanent storage, and it is the single change users most need to be told about in advance.
- **The project changes from a pure local tool to a multi-user service.** The rule in `AGENTS.md` stating that external service requests live in `web/src/services/api/`, go directly from the browser and must not assume a project backend has to be revised; after phase 4 even AI requests are no longer all direct.
- The project is not yet released, so no legacy data migration is performed; existing local data is re-synced under the new structure after first login.
- `canvas-agent` is unaffected and remains a local tool talking to `127.0.0.1:17371`, an independent path from the multi-user backend.

## Risks to Watch During Implementation

All plan-level decisions are settled. The following are the areas most likely to cause trouble during delivery.

**Client-side garbage collection will delete files that are still in use, the one place in this plan that can directly lose user data.** The existing `cleanupImages` and `cleanupUnusedMedia` decide which media are unreferenced by scanning "all assets plus all canvases" and then delete the orphans. That logic holds only because the frontend has the complete dataset in hand — and on-demand loading is precisely what invalidates that premise. After the change the frontend holds only the canvas currently open, so any client-side GC will treat images referenced by other canvases as orphans and delete them.

This splits into two halves whose urgency differs completely.

**Removing the client-side GC must land alongside the on-demand loading work**, meaning in phase 2, with no delay whatsoever. Deleting too few files merely wastes disk; deleting the wrong files loses user data, and shipping the intermediate state starts causing incidents immediately.

**Server-side orphan reclamation, by contrast, can wait for phase 3.** Until it exists, media referenced by a deleted canvas simply lingers on disk at the cost of space and nobody's data is at risk. That work has to scan the jsonb columns of three business tables to determine references, which is the same class of job as the phase 3 storage usage recomputation and the media retention expiry check — all three share a single scan, and building them together saves not just effort but the cost of walking large tables repeatedly.

Incidentally, the current `cleanupUnusedMedia` also carries a pre-existing defect: it bypasses `deleteStoredMedia` and removes records directly, releasing neither the ObjectURL nor the cache map entry, while its image-side counterpart handles this correctly. The inconsistency disappears naturally during this refactor.

**Webhook idempotency and ordering.** Providers retry callbacks, callbacks can arrive out of order, and one can even land after the user has already cancelled the order manually. Crediting must be governed by the `orders.provider_order_id` unique index plus the order state machine, permitting the `pending → paid` transition exactly once and answering repeated callbacks with success while writing nothing. The order status, the credit balance and the ledger row must be written in one transaction with a full rollback if any part fails — a half-succeeded callback is far harder to diagnose than one that fails outright, and the user experiences it directly as "I paid and got nothing". The case of a callback arriving before the order-creation response also needs handling: the order is invisible while its transaction is uncommitted, so there must be a retry or delayed-processing mechanism rather than discarding it as an invalid request.

**Consistency between credit deduction and generation results.** This is the most failure-prone part of phase 4, and it hurts in both directions: deducting credits for a failed generation makes users believe the platform is cheating them, while a successful generation that goes undeducted costs the platform money. The reliable approach is to deduct the credits from `credit_cost` before forwarding with a consumption ledger row, then refund the whole amount on failure, writing the refund as a `type = refund` ledger row rather than editing the balance directly — a balance can be reconciled later, a ledger cannot. Do not settle a difference against the actual result: phase 3 offers only `Reserve` and `Refund`, so a generation is either charged in full or refunded in full, and a second settlement path is just one more way for the books to disagree. Long-running cases such as video generation, where the result may arrive asynchronously, need particular care: when the request has gone out but the connection drops, whether credits are charged must be a decision written into the implementation rather than left to chance.

**Priority conflicts between the model catalog and user-defined models.** A user can perfectly well configure a model in their own channel with the same name as one in the platform catalog. The system must then be able to say unambiguously whether this generation uses the platform key and costs credits or uses the user's key and costs nothing, and that decision can only come from which record the user selected, never from matching model names. The two kinds of model need a visible distinction in the selector, and the user should know before generating whether this run will spend credits. The other edge case is a model the platform has delisted while the user's generation history, or even a canvas node, still references it — reading that history must not error out or render blank just because the catalog lookup fails.

**Runaway storage cost.** Open registration combined with full media upload remains the main cost exposure in this plan, though dropping the quota to 500 MB brings the magnitude under control. Quota checks must complete before a file is written rather than accounting after it lands; the "no upload before email verification" constraint must not be skipped; disk watermark alerting must be configured before phase 1 goes live.

**Accidental deletion by retention cleanup.** Cleanup covers media a canvas currently references, which means a miscalculated last touch time deletes a user's images outright. Before it goes live, run an observation period that scans without deleting and have the "would be cleaned up" list reviewed by hand; confirm that warning emails and in-app notices actually get delivered; and prefer soft-deleting first with physical deletion delayed, leaving a window in which the operation can be undone.

**Email deliverability.** Self-hosted SMTP is easily classified as spam, leaving users unable to complete registration because the verification email never arrives. Prefer an established mail provider, state clearly on the post-registration screen that the email can be resent, and provide a resend entry point.

**Depth of the on-demand loading rework.** This is the most easily underestimated part of the plan. Existing code assumes the data is already in memory and iterates complete lists in many places; once loading becomes on-demand, loading states, empty states, pagination edges and rendering before detail arrives all have to be handled one by one. Get canvases working first to establish the pattern, then apply it to assets and generation records — do not rework all three in parallel.

**Conflict experience under optimistic locking.** Per-record `revision` shrinks the conflict window to the minimum, but the same canvas edited on two devices at once still produces a 409. The frontend needs an explicit path for it — surface the conflict, fetch the latest version, let the user decide — instead of silently overwriting or discarding what the user just did.

**Edge cases in debounced saving.** Canvas edits are written back on a debounce, so closing the page, switching canvases and network failures all need to account for unsaved content, otherwise users hit the "I changed it but it never saved" trap. Failed saves must produce visible feedback and a retry path.

**Ripple effects of removing WebDAV.** It touches store fields, config export, config page UI and both locale files, and it is easy to miss one spot and end up with type errors or leftover UI. Do it only after the phase 2 resource model passes acceptance.

**How the first administrator is created.** This must be spelled out in the deployment documentation, otherwise the console ships with nobody able to log into it.
