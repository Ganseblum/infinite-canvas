# 第三期实施清单：点数计费与管理后台

本文档是[账号体系与后端服务规划](/zh-CN/docs/progress/account-backend-plan)第三期的开发底稿。前置条件是[第一期](/zh-CN/docs/progress/account-backend-phase1)与[第二期](/zh-CN/docs/progress/account-backend-phase2)已交付并通过验收。

## 范围界定

### 本期要做

点数账本（余额、流水、退还机制与对账不变量）、充值档位与支付订单、支付回调、档位定义与存储配额校验、`usage_records` 存储计量、平台模型目录、媒体保留期清理与孤儿文件回收、`/api/me` 返回点数与档位、前端个人中心与充值页、`/admin` 管理后台。

### 本期不做

**实际的扣点动作。** 扣点发生在第四期的 AI 请求转发接口里，本期只把账本、余额、流水、退还机制建好，并暴露一个供第四期调用的内部方法。本期部署上线后点数不会自己减少，唯一的余额变化来源是充值与管理员手工增减。

订阅制、自动续费、发票、退款自助申请。原方案里的两档订阅套餐已经整体作废，`subscriptions` 表在本期删除。

## 先说清楚：存储与生成次数都是硬约束

原方案在这里写的是「存储是硬约束、生成次数是软约束」，理由是 AI 请求由浏览器直连用户自己配置的第三方渠道、完全不经过本项目后端，服务端无法感知用户实际生成了多少次，只能依赖前端上报，技术上可以绕过。**这个结论现在全部不再成立**，因为规划已经新增第四期，把 AI 请求改成由 Go 后端转发。

**存储是硬约束。** 所有媒体文件必须经过 `PUT /api/media/{storageKey}` 才能落盘，服务端在写入前校验总量与余额状态，超额直接拒绝。这条路径没有绕过的可能。

**生成次数同样是硬约束。** 第四期之后密钥只存在于服务端、浏览器完全接触不到，用户想生成就必须走后端转发，而转发接口在发出请求前先扣点。没有点数就没有请求，不存在「改前端代码绕过计费」这条路。

所以本期的点数余额可以在产品文案里当成真实限制来描述，不需要再加「技术上可被绕过」这类免责说明。代价是**生成的计量能力依赖第四期的转发接口**：本期把账本、余额、流水和退还机制建好，但没有任何地方会调用扣点，实际消耗要等第四期上线才会发生。这个先后关系在下面的「点数扣减的一致性」里还会再讲一遍，因为它是本期最容易被误读的地方。

## 档位与点数模型

### 档位定义取代订阅套餐

`plans` 表的语义从「订阅套餐」变成「档位定义」，只描述存储侧的三个上限，不再带任何生成次数字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | varchar 主键 | `free` 或 `paid` |
| `name` | varchar | 展示名 |
| `storage_bytes` | bigint | 存储总量上限 |
| `max_file_bytes` | bigint | 单文件大小上限，第二期已在用 |
| `retention_days` | int | 媒体保留天数，见下面的保留期一节 |

两档的取值：

| 档位 | storage_bytes | max_file_bytes | retention_days |
| --- | --- | --- | --- |
| `free` | 500 MB（524288000） | 50 MB（52428800） | 7 |
| `paid` | 1 GB（1073741824） | 200 MB（209715200） | 14 |

第一期的 `SeedPlans` 写入的是 `free` 与 `pro` 两档并带 `daily_images`、`daily_videos` 字段，本期改写成 `free` 与 `paid` 并删掉这两列。项目尚未上线，直接改模型与 seed 即可，不写迁移脚本，不做旧字段兼容。

`daily_images` 与 `daily_videos` 之所以删掉，是因为「每天多少张」这种一刀切的计数根本描述不了真实成本：同样是一次图片生成，不同模型、不同尺寸、不同质量之间的成本能差几十倍，视频更是按秒计价。这些差异用点数表达是自然的，用张数表达只能取一个所有人都不满意的折中值。

`subscriptions` 表整个删除。订阅表存在的意义是记录「谁在什么时间段内享有什么套餐」，而点数制下不存在时间段——付费身份是余额的函数，随时可以算出来，不需要一张表去维护它的生命周期，也不需要处理到期、续费、宽限这一整套状态机。

### 付费身份由剩余点数决定

判定规则只有一条：**`credits.balance > 0` 就是付费用户，走 `paid` 档；余额为 0 就回落 `free` 档。**

不需要 `is_vip` 字段，不需要有效期，也不需要定时任务去改谁的状态。查一次余额就得到当前档位，任何时刻都是准的，不存在「状态没跑到位」的窗口。代价是每次取档位都要读一次 `credits` 表，但那是主键查询，可以忽略。

用户视角上这意味着**充值同时买到了点数和更宽的存储**，点数用完存储也会回到免费档。这个耦合关系必须在充值页明确写出来，否则用户会以为存储上限是一次性永久获得的，等到降档清理时才发现不是。

### 点数耗尽后的降档与宽限期

余额归零时档位立刻回落 `free`。如果该用户此时的 `storage_bytes` 已经超过 `free` 档上限，账号进入**只读模式**，同时起算 **30 天宽限期**并发一封邮件说明后果。

只读的准确含义要写清楚，它比字面意思窄：**只读只作用于媒体上传**。用户仍然可以浏览全部内容、编辑画布结构、重命名、删除数据、导出 zip，只是不能再往服务端写入新的媒体文件。这样设计是因为限制的目标是磁盘占用，而画布结构、素材元数据、生成记录这些 jsonb 的体量以 KB 计，拦它们既省不下空间又会让账号变成一块砖。删除必须放行则是显然的——不让用户删东西，他就没有自救的手段。

从未充值过的新用户不会被误判成只读：他们余额确实是 0，但用量远在 `free` 上限之内，触发条件的第二个分句不成立。**只读态是「余额为 0」与「用量超出 `free` 上限」同时成立的派生结果，不是余额为 0 本身的效果。**

宽限期的起算时刻**不需要新增列**，从流水里现算：取该用户最近一条 `balance_after = 0` 的 `credit_transactions.created_at`。余额一旦回正就会产生更新的正余额流水，所以最新的那条归零记录必然就是当前这一轮的归零时刻。没有任何流水的用户（从未充值）自然也就没有归零时刻，不进入这套流程。

宽限期满后从**最旧的媒体开始清理，删到 `storage_bytes` 落回 `free` 档上限以内为止**，不是删光。「最旧」按下面保留期一节定义的最后触达时间排序，而不是上传时间，避免删掉用户上周还在编辑的项目里的图。

任何一笔充值都会立刻解除只读、恢复 `paid` 档并让宽限期计时归零，因为归零时刻是从流水现算的，充值写入的正余额流水天然覆盖了它。

## 数据模型

本期新增四组表，全部按第一二期的写法用 GORM 模型定义、`AutoMigrate` 建表。

### 点数余额与流水

```go
type Credit struct {
    UserID    uuid.UUID `gorm:"type:uuid;primaryKey"` // 同时是 users 的外键
    Balance   int64     `gorm:"not null;default:0"`
    UpdatedAt time.Time
}

type CreditTransaction struct {
    ID           uuid.UUID `gorm:"type:uuid;primaryKey"`
    UserID       uuid.UUID `gorm:"type:uuid;index;not null"`
    Type         string    `gorm:"type:varchar(16);not null;index:idx_credit_tx_refund,unique,priority:1,where:type = 'refund'"` // purchase | consume | refund | grant | expire
    Amount       int64     `gorm:"not null"`                  // 正数为增、负数为减
    BalanceAfter int64     `gorm:"not null"`
    RefType      string    `gorm:"type:varchar(16)"`          // order | generation | admin
    RefID        string    `gorm:"type:varchar(64);index:idx_credit_tx_refund,unique,priority:2"` // refund 时指向被退的那条 consume 流水
    Note         string    `gorm:"type:varchar(200)"`
    CreatedAt    time.Time `gorm:"index"`
}
```

`idx_credit_tx_refund` 是一个**部分唯一索引**，只约束 `type = 'refund'` 的行，让 `(type, ref_id)` 在退还流水里唯一。它是退还幂等的唯一机制，具体怎么用见下面的「点数扣减的一致性」。**只能建成部分索引**：管理员增减点数写的是 `type=grant`、`ref_id` 为操作管理员 id，同一个管理员必然要发很多次点，全量唯一索引会从第二次开始直接拒绝；消费流水同样允许同一个请求产生多条。GORM 的 `index` 标签支持 `where` 选项，上面的写法能让 `AutoMigrate` 直接建出部分索引；如果所用 GORM 版本不支持，就在 `AutoMigrate` 之后补一句 `CREATE UNIQUE INDEX IF NOT EXISTS idx_credit_tx_refund ON credit_transactions (type, ref_id) WHERE type = 'refund'`，与第一期建索引的代码放在一起，不要散到 service 里。

`credits` 一个用户一行，注册时随 user 在同一事务里创建余额为 0 的行，不要等到第一次充值才建，否则每个读余额的地方都要处理「行不存在」的分支。

整套账本只有一条不变量，但它必须永远成立：**`credits.balance` 等于该用户全部 `credit_transactions.amount` 的和。** `balance_after` 是写入那一刻的余额快照，用于事后逐条核对是哪一笔开始对不上。任何改余额的代码路径都必须在同一事务里同时写流水，**禁止出现只 UPDATE `credits` 不写流水的地方**，那会让这条不变量失去意义，也就失去了唯一的对账手段。

扣减用带条件的单条 UPDATE 完成，不要先读后写：

```sql
UPDATE credits SET balance = balance - $1, updated_at = now()
WHERE user_id = $2 AND balance >= $1
```

影响行数为 1 表示扣减成功，为 0 表示余额不足，直接返回 402 `INSUFFICIENT_CREDITS`。这样不需要显式行锁，也不存在「读到余额够、写的时候已经不够」的竞态窗口。

`expire`（点数过期）本期不启用，先把枚举值留好，避免以后加类型时又要动一遍校验白名单和前端文案表。

### 充值档位与订单

```go
type CreditPackage struct {
    ID           string `gorm:"primaryKey;type:varchar(32)"`
    Name         string `gorm:"type:varchar(80);not null"`
    Credits      int64  `gorm:"not null"`
    BonusCredits int64  `gorm:"not null;default:0"`
    PriceCents   int64  `gorm:"not null"`
    Currency     string `gorm:"type:varchar(8);not null;default:CNY"`
    Enabled      bool   `gorm:"not null;default:true"`
    Sort         int    `gorm:"not null;default:0"`
}

type Order struct {
    ID              uuid.UUID  `gorm:"type:uuid;primaryKey"`
    UserID          uuid.UUID  `gorm:"type:uuid;index;not null"`
    Provider        string     `gorm:"type:varchar(16);not null"` // alipay | wechat | stripe
    ProviderOrderID *string    `gorm:"type:varchar(128);uniqueIndex"`
    PackageID       string     `gorm:"type:varchar(32);not null"`
    AmountCents     int64      `gorm:"not null"`
    Currency        string     `gorm:"type:varchar(8);not null"`
    Credits         int64      `gorm:"not null"`
    Status          string     `gorm:"type:varchar(16);not null;default:pending"` // pending | paid | failed | refunded
    PaidAt          *time.Time
    CreatedAt       time.Time
    UpdatedAt       time.Time
}
```

`amount_cents` 与 `credits` 在建单时从 `credit_packages` **快照**到订单行，到账时不回查档位表。档位的价格和赠送点数随时可能被管理员调整，回查会让「用户下单时看到的」和「实际到账的」对不上，而这种差错在支付场景里是没法解释的。

`provider_order_id` 的唯一索引是回调幂等的基础设施。建单时若第三方还没返回单号，字段留 `NULL`——唯一索引对 `NULL` 不生效，但**空串会互相冲突**，第二个待支付订单会直接插不进去。因此字段类型必须是 `*string` 而不是 `string`，GORM 下用零值字符串是很容易踩进去的坑。

索引：`(user_id, created_at desc)` 服务用户侧订单列表，`(status, created_at)` 服务超时订单的扫描清理。

### 平台模型目录

```go
type ModelCatalog struct {
    ID          uuid.UUID      `gorm:"type:uuid;primaryKey"`
    Name        string         `gorm:"type:varchar(120);not null"`
    DisplayName string         `gorm:"type:varchar(120);not null"`
    Capability  string         `gorm:"type:varchar(16);not null"` // image | video | text | audio
    Provider    string         `gorm:"type:varchar(60);not null"`
    Constraints datatypes.JSON `gorm:"type:jsonb"`
    CreditCost  datatypes.JSON `gorm:"type:jsonb"`
    Enabled     bool           `gorm:"not null;default:true"`
    Sort        int            `gorm:"not null;default:0"`
    CreatedAt   time.Time
    UpdatedAt   time.Time
}
```

`name` 是发给第三方接口的模型标识，`display_name` 是给用户看的名字，两者必须分开：渠道换了模型 id 而产品名不变的情况很常见，混成一个字段就得改用户可见的文案。

`constraints` 描述这个模型接受哪些参数。这份键集由本期定义，第四期的转发接口拿同一份键做服务端白名单校验，**两边必须逐字一致**，任何一侧改键名都会让另一侧读不到：

```json
{
  "size": ["1024x1024", "1536x1024", "1024x1536"],
  "quality": ["low", "medium", "high"],
  "n": { "max": 4 },
  "duration": [4, 6, 8],
  "resolution": ["480p", "720p", "1080p"],
  "ratio": ["16:9", "9:16", "1:1"],
  "features": ["mask", "referenceImage"]
}
```

键名一律用单数，与请求体里的参数名逐个对应，服务端校验时就不需要再维护一张「参数名到约束键名」的映射表。数组型的键是取值白名单，做精确匹配；对象型的键是范围约束，目前只有 `n` 一个，`max` 给出单次最多生成几个产物；`features` 是能力开关的字符串数组，`mask` 表示支持蒙版、`referenceImage` 表示支持参考图，这类能力没有取值可枚举，塞进一个数组比给每种能力单开一个布尔键要省事得多。

不适用的键直接省略，前端按「键在不在」决定渲染哪些控件，不写模型名的硬编码分支。

`credit_cost` 描述按参数计费的规则：

```json
{
  "base": 10,
  "rules": [
    { "when": { "quality": "high" }, "multiplier": 2 },
    { "when": { "size": "1536x1024" }, "add": 5 },
    { "when": { "duration": 8 }, "multiplier": 2 }
  ]
}
```

求值顺序固定：从 `base` 起，按 `rules` 的数组顺序依次应用命中的 `add` 与 `multiplier`，结果向上取整。顺序写死在规则数组里而不是靠优先级字段，是为了让管理员在后台看到的顺序就是实际生效的顺序。

两个 jsonb 之所以不拆成列，是因为不同能力的参数维度完全不同——图片按尺寸和质量，视频按时长和分辨率，音频按字数——拆列会拆出一堆常年为空的字段，而且每加一种计费维度都要改表结构。代价是不能用 SQL 直接算价，但计价本来就发生在应用层。

这张表只描述「平台侧提供哪些模型、怎么计价」，与第二期用户自带渠道里的模型列表是两回事：前者花点数，后者花用户自己的第三方额度。两者在前端必须分开展示，不要混进同一个下拉。

## 点数扣减的一致性

扣点和生成结果必须一致，这是本期最容易写错的地方，单独讲清楚。

顺序只有两种选择。**先生成后扣**看起来对用户更友好，只在成功后收费，但失败率一高就会漏扣：转发超时、流式中断、进程重启，任何一处丢掉扣点动作，这次生成的成本就白付了，而这类失败在 AI 接口上并不罕见。**先扣后生成**则可能多扣，但多扣是可以退的。

本期采用**先扣后生成、失败自动退还**。判断依据是两类错误的可恢复性不同：漏扣不可恢复，算力已经消耗掉了，事后没有任何办法追回；多扣可恢复，退一笔就行。宁可走多扣退还的路径，也不要走漏扣的路径。

**退还必须走流水**，写一条 `type=refund`、`amount` 为正数、`ref_type=generation`、**`ref_id` 指向被退的那条 `type=consume` 流水的 id** 的记录，不能直接把 `balance` 加回去。指向消费流水而不是指向转发请求或生成记录，是因为退还的对象本来就是那一笔扣款：一次生成可能因为重试产生多条消费流水，只有流水 id 能唯一确定这次退的是哪一笔，而且它同时是下面那个唯一索引的去重键。这条规则的全部价值在于让 `balance = SUM(amount)` 这条等式永远成立：一旦不等，就说明有代码绕过了账本，可以立刻定位到是哪一笔、哪个路径写的。任何时候都能对账，是财务类数据唯一可接受的状态。

供第四期调用的内部方法就两个：

```go
// 扣减，余额不足返回 ErrInsufficientCredits
func (s *CreditService) Reserve(ctx context.Context, userID uuid.UUID, amount int64, refID string) error

// 退还，refID 是被退的那条 consume 流水 id，靠部分唯一索引保证幂等
func (s *CreditService) Refund(ctx context.Context, userID uuid.UUID, amount int64, refID, note string) error
```

`Reserve` 用上面那条带条件的 UPDATE 扣减并在同一事务里写 `type=consume` 流水，余额不足时返回 `ErrInsufficientCredits`，由 handler 转成 402。`Refund` 的幂等**完全依赖 `idx_credit_tx_refund` 这个部分唯一索引**：直接插入退还流水，撞上唯一冲突就把它当成「已经退过了」返回成功。不要在写入前先查一遍有没有同一条退还记录再决定写不写，查与写之间有竞态窗口，两个并发的退还都会查到「没有」然后各写一条，而这正是唯一索引存在的理由。转发接口重试时会重复触发退还，没有这个索引就会退两次。

**本期不会产生任何 `type=consume` 的流水**，因为没有任何地方调用 `Reserve`——实际扣减发生在第四期的转发接口里。本期只把这两个方法、账本表和对账不变量建好，并用管理后台的手工增减点数（`type=grant`）验证账本正确。读到这里不要以为本期上线后点数就会自动消耗。

## 用量统计

### 只有存储需要计数器

`usage_records` 只服务一个 metric，按 `(user_id, metric, period)` 唯一。

| metric | period 形态 | 更新时机 |
| --- | --- | --- |
| `storage_bytes` | `total` | 文件上传成功时增加，删除时减少 |

之所以存储不像生成次数那样实时 `SUM`，是因为它要在**每次上传前**校验，而 `SUM(bytes)` 会随文件数增长逐渐变慢，放在上传热路径上不合适。计数器是这里的必要妥协。

`storage_bytes` 由服务端自己维护，不接受客户端上报。增减必须与 `media_files` 的写入放在同一个事务里，否则并发上传会导致计数漂移。

### 生成次数从生成记录统计，扣费以点数流水为准

这一节要说清楚两套数字的关系，否则很容易在前端把它们混用。

`generations` 表仍然是生成历史的权威来源，「今日生成了多少张」这类**展示用**的数字直接从表里数出来，不需要独立计数器：

```sql
SELECT count(*) FROM generations
WHERE user_id = ? AND kind = ? AND deleted_at IS NULL
  AND created_at >= date_trunc('day', now() AT TIME ZONE 'UTC')
```

`(user_id, kind, created_at desc)` 索引第二期已经建好，这个查询很便宜。日期按 UTC 算，避免跨时区用户看到的「今日」和服务端不一致。

但**扣费依据不是这张表，而是 `credit_transactions`**。两者记录的是不同性质的事实：`generations` 记录「生成了什么」，是业务历史，用户可以软删除；`credit_transactions` 记录「花了多少点」，是财务事实，永不删除。用户删掉一条生成记录，历史里少一条，已经花掉的点数不会退回来。

因此不要试图用「生成条数 × 单价」反推消耗，也不要在对账时拿两张表的行数比大小。两者行数天然不相等：一次生成可能只扣一次点却产出多张图；失败的生成会留下一条 `consume` 加一条 `refund`，却没有对应的成功生成记录；用户软删除生成记录时流水也不会跟着少。**唯一的对账等式是 `credits.balance = SUM(credit_transactions.amount)`**，除此之外的任何交叉验算都会得出错误结论。

### 存储用量的自愈

计数与实际占用长期运行后可能出现偏差，例如异常中断的上传。提供一个重算入口：管理后台的用户详情页放一个「重算存储用量」按钮，触发对该用户 `media_files` 的 `SUM(bytes)` 全量统计并覆盖计数。不做定时任务，按需触发即可。

## 媒体保留期与孤儿文件回收

### 保留期按最后触达时间续期

清理范围是**全部媒体，包括画布正在引用的**。这一点必须在产品文案和充值页写清楚，否则用户会以为「只要还挂在画布上就永远不会被删」，等到文件消失才发现不是。

计时方式是这里的关键设计：不是从上传时间起算固定寿命，而是**按最后触达时间续期**。一个媒体的最后触达时间等于所有引用它的画布 `updated_at`、素材 `updated_at`、生成记录 `created_at` 里的最大值；没有任何引用时退化为 `media_files.created_at`。超过所属档位的 `retention_days` 才进入清理范围。

这样设计的效果是：用户还在用的项目，每次自动保存都会把它引用的全部媒体的寿命续上；只有真正被冷落了几周、一次都没打开过的项目才会被清理。按上传时间算固定寿命则会把用户天天在编辑的老项目误删，那是不可接受的。

**不新增 `expires_at` 列。** 加一列意味着每次画布保存、素材更新、生成记录写入都要回头更新它引用的全部媒体行，写放大严重，而且一旦某条路径漏更新就会误删用户还在用的文件。清理任务扫描时现算即可——扫描是低频后台作业，多几个 join 完全无所谓，而误删是不可逆的。

到期前 2 天发邮件加站内预警，列出将被清理的媒体数量与总大小，并提供一键导出入口（复用现有的画布导出）。预警按用户维度发送而不是按文件维度，同一用户 7 天内不重复发，用第一期发信限流那套计数器控制即可，不需要为此新增表。

### 保留期清理与孤儿回收合并为一个扫描任务

孤儿文件回收是第二期遗留给本期的工作。第二期删掉了客户端的垃圾回收（它依赖「前端持有全量数据」这个已经不成立的前提，留着会误删其它画布正在引用的图片），但没有实现服务端的替代品，所以在本期之前，用户删掉画布后其引用的媒体会一直留在磁盘上。这不影响任何人的数据，只是占空间，因此推迟是安全的。

它和保留期清理的输入完全一样——都要扫 `canvases`、`assets`、`generations` 三张表的 jsonb 字段收集还被引用的 `storage_key`——因此**合并成同一个扫描任务**，扫一遍出两个结果集：

1. 在 `media_files` 里存在但没有任何引用的 `storage_key`，即孤儿，直接删。
2. 有引用但最后触达时间已超过 `retention_days` 的，即过期媒体，删。

分两次扫是纯粹的浪费，更重要的是两套引用收集逻辑早晚会不一致，届时同一个文件在一个任务里算孤儿、在另一个任务里算有效，排查起来非常痛苦。

两个必须注意的点。**判断引用时不能漏掉软删除的记录**——`deleted_at` 不为空的画布仍可能是用户想恢复的，它引用的文件不该被当成孤儿删掉；软删除记录的 `updated_at` 同样参与最后触达时间的计算，所以一张软删除后再没动过的画布，其独占的媒体会在保留期后随过期清理一起消失，不需要为软删除单独定义一套保留期。**回收要按用户隔离**，绝不能做成全局扫描后统一删除，一旦引用收集逻辑有 bug，影响面就是全部用户而不是一个。

宽限期满的降档清理复用同一个任务，只是排序和终止条件不同：按最后触达时间从旧到新删，删到该用户 `storage_bytes` 落回 `free` 档上限以内即停止，不是删光。

建议先做成管理后台按需触发的动作，在单个用户上验证正确后再挂定时任务。清理完成后顺带重算一次该用户的存储用量。

## 接口

### 错误码补充

沿用第一期的错误码表，本期新增三个：

| HTTP | code | 触发场景 |
| --- | --- | --- |
| 402 | `INSUFFICIENT_CREDITS` | 余额不足以支付本次请求；只读态下调用媒体上传、管理员把余额扣成负数同样返回此码 |
| 409 | `ORDER_ALREADY_PAID` | 取消一个已支付的订单 |
| 400 | `INVALID_SIGNATURE` | 支付回调验签失败 |

第二期的 507 `STORAGE_QUOTA_EXCEEDED` 继续沿用。上传接口的判断顺序是**先余额后总量**：先判只读态返回 402，不是只读态再判总量返回 507。顺序反过来会让只读用户看到「存储超限，请清理文件」的提示，而对他们正确的引导是充值。

### 用量、档位与点数

**GET `/api/me`** 在第一期的基础上增加 `credits` 与 `usage`，`plan` 换成新的档位结构：

```json
{
  "user": { "...": "..." },
  "plan": { "id": "paid", "name": "付费档", "storageBytes": 1073741824, "maxFileBytes": 209715200, "retentionDays": 14 },
  "credits": { "balance": 1280 },
  "usage": { "storageBytes": 1234567, "imageGenerateToday": 12, "videoGenerateToday": 2 },
  "readOnly": false,
  "graceEndsAt": null
}
```

`plan` 里不再有 `dailyImages` 与 `dailyVideos`，前端所有读这两个字段的地方都要删掉，不要留成「两套配额判断并存」。`plan.id` 由余额实时判定，不查任何订阅表。

`readOnly` 与 `graceEndsAt` 是服务端算好的派生字段。判定规则虽然只有两个条件，但让前端各自实现一遍必然出现口径不一致，而这个口径直接决定用户看到的是「充值」还是「清理文件」。

`usage` 里的生成次数只用于展示，不参与任何拦截判断。

### 点数与流水

**GET `/api/credits`** 需登录，返回余额与最近流水摘要：

```json
{
  "balance": 1280,
  "recent": [
    { "id": "t1...", "type": "purchase", "amount": 1100, "balanceAfter": 1280, "refType": "order", "refId": "o1...", "note": "标准包", "createdAt": "..." }
  ]
}
```

`recent` 固定返回最近 5 条，供个人中心的余额卡片直接渲染，省掉一次分页请求。

错误：`UNAUTHORIZED`。

**GET `/api/credits/transactions?cursor=&size=&type=`** 游标分页，形状与第二期的生成记录一致：

```json
{
  "items": [
    { "id": "t2...", "type": "consume", "amount": -20, "balanceAfter": 1260, "refType": "generation", "refId": "g1...", "note": "GPT Image · hd", "createdAt": "..." }
  ],
  "nextCursor": "eyJ0..."
}
```

`cursor` 是 `base64url(created_at 的 RFC3339Nano 形式 + "|" + id)`，对客户端不透明，解不出来返回 `VALIDATION_FAILED`。`size` 缺省 20、上限 100。`type` 可选，按流水类型筛选，不在枚举内返回 `VALIDATION_FAILED`。

用游标而不是页码的理由与生成记录相同：流水是只增历史流，`COUNT(*)` 会随时间线性变慢，而新流水插在头部会让 offset 分页出现重复项和漏项。

流水**只读，没有任何写接口**。所有写入都由服务端在业务事务里完成，前端没有任何途径能伪造一条记录。

错误：`UNAUTHORIZED`、`VALIDATION_FAILED`。

### 充值档位与订单

**GET `/api/credit-packages`** 需登录，返回 `enabled = true` 的档位，按 `sort` 升序：

```json
{
  "items": [
    { "id": "standard", "name": "标准包", "credits": 1000, "bonusCredits": 100, "priceCents": 3000, "currency": "CNY" }
  ]
}
```

错误：`UNAUTHORIZED`。

**POST `/api/orders`** 请求 `{ "packageId": "standard", "provider": "alipay" }`，成功 201：

```json
{
  "order": { "id": "o1...", "packageId": "standard", "amountCents": 3000, "currency": "CNY", "credits": 1100, "status": "pending", "createdAt": "..." },
  "payment": { "type": "qrcode", "payload": "https://qr.alipay.com/..." }
}
```

`order.credits` 是 `credits + bonusCredits` 的和，建单时算好写进订单行。

`payment.type` 取 `qrcode`、`redirect`、`clientSecret`，前端据此决定渲染二维码、跳转还是拉起渠道 SDK。三个渠道的形态差异全部收敛在这一个字段里，前端不写 `if (provider === "alipay")` 这类分支。

错误：`VALIDATION_FAILED`（档位不存在或已下架、`provider` 不在枚举内）、`UNAUTHORIZED`、`RATE_LIMITED`（同用户 10 单/小时，防止刷出大量垃圾待支付订单）。

**GET `/api/orders?cursor=&size=&status=`** 游标分页返回当前用户的订单，形状与流水列表一致，`items` 里是订单对象。错误：`UNAUTHORIZED`、`VALIDATION_FAILED`（游标无法解码或 `status` 不在枚举内）。

**POST `/api/orders/{id}/cancel`** 取消待支付订单，成功 200 返回更新后的订单。只有 `pending` 状态能取消。

错误：`NOT_FOUND`（订单不存在，**或订单不属于当前用户**——与第二期一致，跨用户访问返回 404 而不是 403）、`ORDER_ALREADY_PAID`。

### 支付回调

**POST `/api/payments/webhook/{provider}`** 公开路由，不走 `RequireAuth`，但**必须验签**。

请求体是各渠道自己的格式，不做统一约定。每个渠道一个适配函数，把原始报文验签并解析成统一的 `{ providerOrderID, outTradeNo, amountCents, status }` 再进入同一套处理流程。

响应格式**按渠道要求返回**，支付宝要 `success` 纯文本，微信要固定结构的 JSON，Stripe 只看 2xx。这一处不能套用项目统一的错误响应格式，否则渠道会判定回调失败并持续重试。

错误：`INVALID_SIGNATURE`（400）、`NOT_FOUND`（本地找不到对应订单）。**验签失败一律拒绝**，不提供任何跳过验签的开关或环境变量，调试用渠道自己的沙箱环境。

到账的具体处理逻辑与幂等保证见下面的「支付实现要点」，那一节的五条都是硬性要求。

### 模型目录

**GET `/api/models?capability=`** 需登录，返回 `enabled = true` 的模型，按 `sort` 升序，`capability` 可选：

```json
{
  "items": [
    {
      "id": "m1...",
      "name": "gpt-image-1",
      "displayName": "GPT Image",
      "capability": "image",
      "provider": "openai",
      "constraints": { "size": ["1024x1024", "1536x1024"], "quality": ["low", "medium", "high"], "n": { "max": 4 }, "features": ["referenceImage"] },
      "creditCost": { "base": 10, "rules": [ { "when": { "quality": "high" }, "multiplier": 2 } ] }
    }
  ]
}
```

`creditCost` 要原样下发给前端，用于在生成按钮旁实时显示「本次消耗 N 点」。但**前端算出来的价只用于展示**：第四期扣点时服务端用同一份规则重新算一遍，不接受客户端传来的价格。前端能改的数字不能成为收费依据。

错误：`UNAUTHORIZED`、`VALIDATION_FAILED`（`capability` 不在枚举内）。

### 上传接口增加总量校验

第二期已有的 `PUT /api/media/{storageKey}` 增加两条校验，顺序不能颠倒：

1. 只读态（余额为 0 且 `storage_bytes` 已超 `free` 档上限）返回 402 `INSUFFICIENT_CREDITS`，响应体带 `{ "graceEndsAt": "..." }`。
2. 当前 `storage_bytes` 加上本次文件大小超过所属档位的 `storage_bytes`，返回 507 `STORAGE_QUOTA_EXCEEDED`，响应体带 `{ "used": ..., "limit": ... }`。

校验与写入必须在同一事务内，先占用后写盘，失败则回滚计数。

### 管理后台

全部路由挂在 `/api/admin` 下，由独立的 `RequireAdmin` 中间件校验 `role = admin`。中间件要在 `RequireAuth` 之后执行，非管理员返回 403 `FORBIDDEN`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/users` | 分页列表，支持 `page`、`size`、`sort`、`q`（匹配邮箱或用户名）、`status`、`planId` |
| GET | `/api/admin/users/{id}` | 用户详情，含档位、点数余额、用量、注册时间、最近登录 |
| PATCH | `/api/admin/users/{id}` | 修改 `status`（`active`/`disabled`） |
| POST | `/api/admin/users/{id}/password` | 重置密码，并撤销该用户全部 refresh token |
| POST | `/api/admin/users/{id}/credits` | 增减点数，见下 |
| POST | `/api/admin/users/{id}/usage/recalculate` | 重算存储用量 |
| POST | `/api/admin/users/{id}/media/reclaim` | 触发该用户的清理扫描（孤儿加过期），完成后自动重算存储用量 |
| GET | `/api/admin/stats` | 总览：用户总数、今日新增、存储总占用、今日生成量、今日充值金额、全站点数余额总量 |
| GET/POST | `/api/admin/models` | 模型目录列表与新增 |
| PATCH/DELETE | `/api/admin/models/{id}` | 单个模型的修改与删除 |
| GET/POST | `/api/admin/credit-packages` | 充值档位列表与新增 |
| PATCH | `/api/admin/credit-packages/{id}` | 单个充值档位的修改 |
| GET | `/api/admin/orders` | 全站订单列表，支持 `page`、`size`、`sort`，以及按 `status`、`provider`、`userId` 筛选 |

用户列表响应：

```json
{ "items": [ { "id": "...", "email": "...", "username": "...", "role": "user", "status": "active", "emailVerified": true, "planId": "paid", "balance": 1280, "storageBytes": 123, "createdAt": "..." } ], "total": 128, "page": 1, "size": 20 }
```

两个列表接口的分页参数直接沿用第二期给业务资源定的那套约定，不另立一份：`page` 从 1 开始、缺省 1，`size` 缺省 20、上限 100，越界返回 `VALIDATION_FAILED`；`sort` 走白名单枚举再映射到列名，不能把参数拼进 SQL，前缀 `-` 表示倒序，两个接口都缺省 `-createdAt`，不在白名单内返回 `VALIDATION_FAILED`。`/api/admin/users` 的白名单是 `createdAt`、`balance`、`storageBytes`，`/api/admin/orders` 的白名单是 `createdAt`、`amountCents`。管理后台的列表页天然要在注册时间、余额、订单金额之间来回排序，沿用同一套参数名前端还能直接复用第二期已有的分页写法。

`planId` 不是 `users` 表上的列，而是余额的派生值，按它筛选必须 join `credits` 判余额：`planId=paid` 对应 `credits.balance > 0`，`planId=free` 对应余额为 0。列表里的 `balance` 与 `storageBytes` 同样来自 join `credits` 与 `usage_records`，一次查询取齐，不要渲染每一行时再各查一次。

全部管理接口的公共错误：`UNAUTHORIZED`（未登录）、`FORBIDDEN`（非管理员）、`NOT_FOUND`（用户或资源不存在）、`VALIDATION_FAILED`（参数不合法），下面只列各接口特有的部分。

`PATCH /api/admin/users/{id}` **不再能改 `planId`**。档位由余额决定，管理员想给某个用户升档就发点数，让判定路径保持唯一。留一个能直接改档位的后门，等于允许出现「档位是 paid 但余额为 0」这种账本解释不了的状态。

**POST `/api/admin/users/{id}/credits`** 请求 `{ "amount": 500, "note": "客服补偿" }`，`amount` 正增负减，成功 200 返回 `{ "balance": 1780 }`。

必须写入一条 `type=grant`、`ref_type=admin`、`ref_id` 为操作管理员 id 的流水，`note` 一并落库。**不允许直接改 `credits.balance`**，否则对账等式立刻失效，而这是本期唯一一个由人手工触发的余额变更入口，最容易被图省事写成裸 UPDATE。扣减到负数直接拒绝，返回 402 `INSUFFICIENT_CREDITS`。

**DELETE `/api/admin/models/{id}`** 是硬删除，但只允许删从未被使用过的模型；已经产生过流水的模型只能置 `enabled = false`。流水的 `note` 里存了模型名，删掉目录行不会让历史流水失去可读性，但把用户正在用的模型删掉，会让前端下拉里的选中项凭空消失。

`credit_packages` 只提供 GET、POST、PATCH，**没有 DELETE**：订单行引用了 `package_id`，删掉档位会让历史订单查不到来源。下架用 `enabled = false`。

### 封禁的即时生效

把用户改成 `disabled` 后，其已签发的 access token 在 15 分钟内仍然有效。必须同时**撤销该用户全部 refresh token**，这样最多 15 分钟后就会因无法刷新而彻底掉线。

如果要求立即生效，需要在鉴权中间件里每次查库确认用户状态，代价是每个请求多一次查询。本期采用撤销令牌的方案，在管理后台的操作提示里说明「最多 15 分钟后完全生效」。

## 支付实现要点

支付是本期唯一一处「出错会直接造成资金差错」的地方，下面五条都不是可选项。

**回调必须幂等。** 同一个 `provider_order_id` 重复回调只能到账一次。渠道会因为超时、网络抖动、主动重推等原因重复发送同一个回调，这是常态而不是异常。保证方式是订单表的唯一约束加状态机：到账时用一条带条件的 UPDATE 完成状态跃迁。

```sql
UPDATE orders SET status = 'paid', paid_at = now(), updated_at = now()
WHERE id = $1 AND status = 'pending'
```

影响行数为 1 才继续加点数，为 0 说明这一单已经处理过，**直接返回成功响应给渠道，不要报错**——返回错误会让渠道认为回调失败并无限重试。

**到账必须是一个事务。** 更新订单状态、增加 `credits.balance`、写 `credit_transactions` 三件事在同一个数据库事务里完成，任何一步失败整体回滚。分开做的后果是两种都很难收场的差错：加了点数但订单还是 `pending`，下次回调再加一次；或者订单标记成已付但点数没加，用户付了钱拿不到东西。

**不要信任回调里的金额。** 到账点数一律取本地订单行的 `credits`，金额校验取本地 `amount_cents`。回调里的金额只用于比对，不一致时**拒绝到账并记 error 级日志**，因为这意味着要么订单被篡改，要么对接了错误的渠道账号，两种情况都不该靠自动逻辑兜过去。绝不能用回调里的数字覆盖本地记录。

**验签失败一律拒绝。** 不提供 `SKIP_SIGNATURE_VERIFY` 之类的开关，也不因为「本地调试不方便」临时放宽——伪造回调等于凭空造钱，这是整条支付链路上唯一一个能被外部直接攻击的入口。各渠道的公钥或密钥从环境变量读取，缺失时启动失败并明确报错，写法与第一期校验 SMTP 变量一致。

**超时订单要清理。** `pending` 订单超过 30 分钟未支付即置为 `failed`，用一个每 5 分钟跑一次的后台任务扫描 `(status, created_at)` 索引。置失败前必须先向渠道**主动查一次真实状态**，不能只看本地时间就判失败：用户可能在最后一秒付款而回调还在路上，直接置失败就会出现「钱付了、订单是 failed、点数没到」的差错。查到已支付的走正常到账流程，这条主动查询同时也是回调整体丢失时的兜底。

```go
type Provider interface {

```

## 前端改造

### 个人中心 `web/src/pages/profile/index.tsx`

在第一期的资料与改密码基础上，增加当前档位、点数余额、存储用量进度条与最近 5 条流水。存储用量用 Ant Design 的 `Progress`，接近上限时变色提示。

处于只读态时在页面顶部放一条 Alert，写明宽限期截止时间、到期后会清理什么、以及充值和导出两个入口。这条提示不能用 `message` 弹一下就消失，它需要一直在——用户很可能是几天后才回来看的。

### 充值与订单 `web/src/pages/billing/`

档位卡片列表加订单历史两块。点击档位调 `POST /api/orders`，按 `payment.type` 渲染：`qrcode` 弹二维码 Modal，`redirect` 跳转，`clientSecret` 拉起渠道 SDK。

支付完成的感知**不能只靠回调**，因为回调打到的是服务端，前端并不知道。二维码 Modal 打开期间轮询订单详情，直到状态变成 `paid` 或用户关闭弹窗，轮询间隔 3 秒、最多 10 分钟。到账后让 `/api/me` 与 `/api/credits` 的 react-query 查询失效，余额和档位自动刷新，不要手写同步逻辑。按项目既有约定，轮询定时器要在 effect 的 cleanup 里清理干净。

订单列表用 `useInfiniteQuery` 配 `nextCursor`，与生成记录同一套写法。

### 生成入口的点数拦截

生成前用 `/api/me` 的 `credits.balance` 与模型目录算出的预估消耗做本地比较，不足则禁用按钮并提示充值，不需要额外请求。

但要写清楚：**本期的前端拦截只是体验优化，真正的扣点在第四期的转发接口里。** 前端算出的预估价只用于展示「本次消耗 N 点」，不要据此在本地扣减任何数字，也不要在生成后自己往流水里写东西——流水根本没有写接口。

原来读 `plan.dailyImages` 与 `usage.imageGenerateToday` 做拦截的代码要整块删除，不要留成两套配额判断并存。

涉及位置是 `web/src/pages/image/index.tsx`、`web/src/pages/video/index.tsx`，以及画布内的生成逻辑 `web/src/components/canvas/canvas-node-generation.ts`。三处都要接，不要漏掉画布内生成。

### 模型选择与动态表单

模型下拉的数据源改为 `GET /api/models`，参数表单**按 `constraints` 动态渲染**，不在前端硬编码每个模型支持哪些尺寸。

渲染规则就是看键在不在：有 `size` 或 `ratio` 就渲染对应选择器，有 `duration` 就渲染时长选择，有 `quality` 就渲染质量选择，有 `resolution` 就渲染分辨率选择，有 `n` 就渲染生成数量输入并把 `n.max` 作为上限，`features` 里含 `referenceImage` 才显示参考图上传、含 `mask` 才显示蒙版入口，键不存在就不渲染该控件。

切换模型时要校验当前已选参数在新模型的 `constraints` 里是否仍然合法，不合法就回落到第一个可选值。漏掉这一步会出现「换了模型但尺寸还是上一个模型独有的值」，一直到第四期的转发接口才报错，用户完全看不懂。

预估消耗跟着参数变化实时重算并显示在生成按钮附近，求值顺序与服务端的 `credit_cost` 规则保持一致。这段求值逻辑抽成 `web/src/lib/credit-cost.ts` 的纯函数，三个生成入口共用，不要在每个页面各写一份。

平台模型与第二期用户自带渠道的模型要在 UI 上分开，不要混进同一个下拉——两者的计费主体完全不同，一个花点数，一个花用户自己的第三方额度，混在一起用户根本不知道这一次生成花的是谁的钱。

### 上传超额与只读态的处理

媒体上传遇到 507 `STORAGE_QUOTA_EXCEEDED` 或 402 `INSUFFICIENT_CREDITS` 时，**不要让整个保存操作失败**。画布、素材、生成记录本身的元数据体量很小，应当照常写入服务端，只是其中引用的媒体文件缺失。

这个区分很重要：如果因为一张图超额就让整张画布保存失败，用户的编辑成果会直接丢掉。正确做法是元数据先落库，上传失败的 `storageKey` 收集起来统一提示。两个错误码的引导方向不同，文案要分开：507 引导去清理文件，402 引导去充值并说明宽限期还剩多久。

### 管理后台 `web/src/pages/admin/`

四个页面：`users/`、`models/`、`credit-packages/`、`orders/`。

按项目既有约定组织：页面私有组件放各自目录的 `components/` 下，不要放到共享目录；表格配色、卡片阴影、深浅主题分支统一在 `web/src/lib/app-theme.ts` 配置，页面组件里不写 `dark ? ... : ...` 这类判断。

列表统一用 Ant Design `Table` 配 `@ant-design/pro-components`（项目已有依赖），支持搜索、筛选、分页。用户页的行操作包含封禁解封、增减点数、重置密码、触发清理扫描、查看详情。

模型页支持新增、编辑、上下架，`constraints` 与 `credit_cost` 两个 jsonb 字段要用受控的表单控件编辑，**不要做成裸 JSON 文本框**：直接让管理员手写 JSON，拼错一个键就会让前端的动态表单渲染不出控件，而这个错误在保存时看不出来，要到用户打开生成页才暴露。`constraints` 的七个键各配一种控件：`size`、`quality`、`duration`、`resolution`、`ratio` 五个数组键用可增删的标签输入，`n` 用一个数字输入填 `max`，`features` 用固定选项的多选框（当前只有 `mask` 与 `referenceImage`），每个键都能整体启用或删除，删掉即表示该模型不支持这个参数。控件的键集与上面数据模型一节写死的那七个键一一对应，加新键要同时改后端校验、这里的表单和前端的动态渲染，三处缺一不可。

### 路由与守卫

`/admin` 下各页挂在 `RequireAuth` 内层再包一个 `RequireAdmin`，非管理员重定向到首页而不是登录页。`/billing` 只需要 `RequireAuth`。顶栏用户下拉在 `role === "admin"` 时多出「管理后台」入口，所有登录用户都多出「充值」入口并显示当前余额。

前端隐藏入口只是体验优化，**真正的权限判断在后端中间件**，两者都要做。

### 国际化

在 `zh-CN.ts` 与 `en-US.ts` 同步新增 `admin.*`、`billing.*`、`credits.*` 三段，保持两个文件对称。原有 `quota.*` 里关于每日生成次数的文案要删除，不要留着不用。

## 验收清单

点数账本：

- 管理后台给用户加 500 点后，`/api/credits` 的余额相应增加，流水里多一条 `type=grant`、`ref_type=admin` 的记录，`balanceAfter` 与新余额一致。
- 对任意用户执行 `SELECT SUM(amount) FROM credit_transactions WHERE user_id = ?`，结果等于 `credits.balance`；充值、增减、退还等任意操作之后重复验证，等式始终成立。
- 管理员把余额扣成负数被拒绝，返回 402 `INSUFFICIENT_CREDITS`，余额与流水都不变。
- 并发对同一用户发起多次扣减，最终余额正确，不出现超扣。
- 流水没有任何写接口，前端无法伪造记录。
- 本期部署上线后不会自动产生 `type=consume` 的流水，余额只随充值与管理员操作变化。

扣点失败退还：

- 用单元测试或临时调试入口调用 `Reserve` 后模拟生成失败再调 `Refund`，余额回到扣减前的值，流水里 `consume` 与 `refund` 成对出现，且 `refund` 的 `ref_id` 等于那条 `consume` 的 id。
- 用同一条消费流水的 id 连续调用两次 `Refund`，第二次撞上 `idx_credit_tx_refund` 唯一冲突后仍返回成功，只产生一条 `type=refund` 流水，余额只增加一次；同一个管理员连续给同一用户发两次点则两次都成功，不会被这个索引误伤。
- 余额不足时 `Reserve` 返回错误且不产生任何流水，上层接口返回 402 `INSUFFICIENT_CREDITS`。

支付与订单：

- 创建订单返回的 `credits` 等于档位的 `credits + bonusCredits`；管理员随后调整该档位的价格与赠送点数，已创建订单的金额与点数不变。
- 用同一个 `provider_order_id` 重复推送回调，只到账一次，余额只增加一次，流水只多一条，且第二次回调返回渠道要求的成功响应而不是错误。
- 伪造签名的回调返回 400 `INVALID_SIGNATURE`，订单状态与余额都不变。
- 回调里的金额与本地订单的 `amount_cents` 不一致时拒绝到账，日志里有 error 级记录。
- 在到账事务中人为让写流水失败，订单状态回滚为 `pending`、余额不变，重推回调能正常到账。
- 取消已支付的订单返回 409 `ORDER_ALREADY_PAID`；用另一个账号的订单 id 调取消返回 404。
- 待支付订单超过 30 分钟被置为 `failed`，且置失败前向渠道主动查过一次真实状态；把渠道状态构造成已支付时，该订单转为正常到账而不是 `failed`。

档位与只读：

- 新注册用户余额为 0、档位为 `free`，能正常上传媒体，不会被误判成只读。
- 充值后 `/api/me` 的 `plan.id` 立刻变成 `paid`，`storageBytes`、`maxFileBytes`、`retentionDays` 同步变大，全程不需要管理员操作。
- 付费用户点数耗尽且用量超过 `free` 上限后，`/api/me` 的 `readOnly` 为 true、`graceEndsAt` 有值，媒体上传返回 402 `INSUFFICIENT_CREDITS` 并带 `graceEndsAt`。
- 只读态下仍能浏览画布、编辑画布结构、重命名、删除数据、导出 zip。
- 只读用户充值任意金额后立刻恢复上传，`readOnly` 变回 false、`graceEndsAt` 变回 null。
- 存储接近上限时上传被拒绝，返回 507 `STORAGE_QUOTA_EXCEEDED` 且响应体含 `used` 与 `limit`。
- 并发上传多个文件后，`usage.storageBytes` 与 `media_files` 的 `SUM(bytes)` 一致。
- 「重算存储用量」能修正人为改坏的计数。
- 全库与全前端代码里都不再出现 `subscriptions`、`dailyImages`、`dailyVideos`。

保留期与清理：

- 删除一张画布后触发清理扫描，它独占的图片从磁盘消失、存储用量下降；被其它画布或素材共用的图片**不会**被删。
- 一个媒体只被一张画布引用时，把该画布的 `updated_at` 改到 `retention_days` 之前，扫描后该媒体被清理；重新编辑一次画布让 `updated_at` 刷新，同一个媒体不再被清理，验证按最后触达时间续期生效。
- 软删除但仍在保留期内的画布，其引用的媒体不会被清理。
- 同一次扫描同时产出孤儿与过期两个结果集，日志里能看到两者分别清理了多少个文件、多少字节。
- 宽限期满的降档清理按最后触达时间从旧到新删，删到 `storage_bytes` 落回 `free` 上限即停止，不会把用户媒体删光。
- 到期前 2 天收到预警邮件与站内提示，提示里有可用的一键导出入口，同一用户不会每天重复收到。

模型目录：

- 管理员新增一个模型后，前端生成页的下拉里立刻出现，参数表单按 `constraints` 渲染出对应控件。
- 从某个模型的 `constraints` 里去掉 `quality` 后，前端不再渲染质量选择器，其余控件不受影响。
- 切换模型时不合法的已选参数自动回落到第一个可选值，不会把上一个模型独有的取值带过去。
- 生成按钮旁的预估消耗随参数变化实时更新，与服务端按同一份 `credit_cost` 算出的结果一致。
- 已产生过流水的模型无法硬删除，只能下架；下架后前端下拉里消失，历史流水仍能读出模型名。
- 充值档位没有删除入口，下架后 `GET /api/credit-packages` 不再返回，但历史订单仍能查到来源档位。
- 平台模型与用户自带渠道的模型在界面上分开展示，能一眼看出这次生成花的是点数还是自己的第三方额度。

管理后台：

- 管理员能看到用户列表，能按邮箱搜索、按状态与 `planId` 筛选、按余额排序、翻页，列表里能看到点数余额与当前档位；`size` 传 500 或 `sort` 传白名单外的值都返回 `VALIDATION_FAILED`。
- 封禁用户后其 refresh token 全部失效，最多 15 分钟后完全掉线。
- 管理员重置用户密码后，该用户全部设备被踢下线。
- **非管理员账号直接请求 `/api/admin/users`、`/api/admin/models`、`/api/admin/credit-packages`、`/api/admin/orders` 一律返回 403**，即使前端入口被隐藏也拦得住。
- 非管理员访问 `/admin` 下任意路由被重定向到首页。
- 订单列表能按状态、渠道、用户筛选，能看到每单对应的点数与到账时间。
- 模型页的 `constraints` 与 `credit_cost` 用表单控件编辑，不是裸 JSON 文本框。

一致性：

- 管理后台与充值页在深色与浅色主题下配色正常，且没有在页面组件里写主题分支。
- `bun run typecheck` 通过，两个语言包 key 结构对称。
