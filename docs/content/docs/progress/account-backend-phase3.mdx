# Phase 3 Implementation Checklist: Credit Billing and Admin Console

This document is the development baseline for phase 3 of the [Account System and Backend Service Plan](/docs/progress/account-backend-plan). It assumes [phase 1](/docs/progress/account-backend-phase1) and [phase 2](/docs/progress/account-backend-phase2) have shipped and passed acceptance.

## Scope

### In Scope

The credit ledger (balance, transactions, the refund mechanism and the reconciliation invariant), top-up packages and payment orders, payment callbacks, tier definitions and storage quota enforcement, `usage_records` storage accounting, the platform model catalog, media retention cleanup and orphan file reclamation, credits and tier in the `/api/me` response, the frontend profile center and billing page, and the `/admin` console.

### Out of Scope

**The actual credit deduction.** Deduction happens in the phase 4 AI request proxy; this phase only builds the ledger, balance, transactions and refund mechanism, and exposes an internal method for phase 4 to call. After this phase ships, credits never decrease on their own — the only sources of balance change are top-ups and manual admin adjustments.

Subscriptions, auto-renewal, invoices and self-service refunds. The two-tier subscription model from the original design is scrapped entirely, and the `subscriptions` table is dropped in this phase.

## First: Both Storage and Generation Counts Are Hard Constraints

The original text said storage was a hard constraint while generation counts were soft, on the grounds that AI requests went from the browser straight to the user's own third-party channel, never traversing this project's backend, so the server could not observe how many generations happened and had to rely on frontend reporting that could be bypassed. **None of that holds any more**, because the plan now includes a phase 4 that routes AI requests through the Go backend.

**Storage is a hard constraint.** Every media file must pass through `PUT /api/media/{storageKey}` to reach disk, and the server validates the total and the balance state before writing, rejecting on overage. There is no way around that path.

**Generation counts are a hard constraint too.** After phase 4, keys live solely on the server and never reach the browser, so generating anything requires going through the backend proxy, and the proxy deducts credits before issuing the request. No credits means no request; there is no "edit the frontend to skip billing" route.

Credit balances can therefore be described in product copy as real limits, with no "technically bypassable" disclaimer. The cost is that **metering depends on the phase 4 proxy**: this phase builds the ledger, balance, transactions and refund mechanism, but nothing calls into deduction, so real consumption only begins once phase 4 ships. That ordering comes up again under "Consistency of Credit Deduction" below, because it is the single most misread point in this phase.

## Tiers and the Credit Model

### Tier Definitions Replace Subscription Plans

The `plans` table changes meaning from "subscription plan" to "tier definition", describing only the three storage-side limits and carrying no generation-count fields at all:

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | varchar primary key | `free` or `paid` |
| `name` | varchar | Display name |
| `storage_bytes` | bigint | Total storage cap |
| `max_file_bytes` | bigint | Per-file size cap, already used since phase 2 |
| `retention_days` | int | Media retention window, see the retention section below |

The two tiers:

| Tier | storage_bytes | max_file_bytes | retention_days |
| --- | --- | --- | --- |
| `free` | 500 MB (524288000) | 50 MB (52428800) | 7 |
| `paid` | 1 GB (1073741824) | 200 MB (209715200) | 14 |

Phase 1's `SeedPlans` writes `free` and `pro` with `daily_images` and `daily_videos` columns; this phase rewrites it to `free` and `paid` and drops those two columns. The project has not launched, so the model and the seed change directly — no migration script, no legacy field compatibility.

`daily_images` and `daily_videos` go away because a flat "N per day" count cannot describe real cost: for the same single image generation, different models, sizes and quality levels differ by tens of times, and video is priced per second. Credits express those differences naturally; a per-day count can only pick a compromise nobody is happy with.

The `subscriptions` table is deleted outright. A subscription table exists to record "who is entitled to which plan during which period", and under a credit model there is no period — paid status is a function of the balance, computable at any moment. There is no lifecycle to maintain and no expiry, renewal or grace state machine to implement.

### Paid Status Is Determined by Remaining Credits

There is exactly one rule: **`credits.balance > 0` means a paid user on the `paid` tier; a zero balance falls back to `free`.**

No `is_vip` field, no validity period, no scheduled job flipping anyone's status. One balance read yields the current tier, correct at any instant, with no window in which "the state has not caught up yet". The cost is a `credits` read on every tier lookup, but that is a primary-key query and can be ignored.

From the user's point of view this means **a top-up buys credits and wider storage at the same time**, and running out of credits also drops storage back to the free tier. That coupling must be stated explicitly on the billing page, otherwise users assume the storage cap was a one-time permanent upgrade and only discover otherwise when downgrade cleanup runs.

### Downgrade, Read-Only and the Grace Period After Credits Run Out

The tier falls back to `free` the moment the balance hits zero. If that user's `storage_bytes` already exceeds the `free` cap, the account enters **read-only mode**, a **30-day grace period** starts, and an email goes out explaining the consequences.

Read-only means something narrower than it sounds, and that must be spelled out: **read-only applies only to media uploads.** Users can still browse everything, edit canvas structure, rename, delete data and export zips; they simply cannot write new media files to the server. The reason is that the thing being limited is disk usage, and canvas structure, asset metadata and generation records are jsonb payloads measured in kilobytes — blocking them saves no space and turns the account into a brick. Allowing deletes is obvious: forbid deletion and the user has no way to rescue themselves.

Users who never topped up are not misclassified as read-only: their balance really is zero, but their usage sits far below the `free` cap, so the second clause of the condition fails. **Read-only is a derived state requiring both "zero balance" and "usage above the `free` cap", not an effect of a zero balance by itself.**

The grace period's start time **needs no new column** and is computed from the ledger: take `created_at` of that user's most recent `credit_transactions` row with `balance_after = 0`. Any top-up produces a newer row with a positive balance, so the latest zero row is necessarily the current exhaustion moment. A user with no transactions at all (never topped up) has no exhaustion moment and never enters this flow.

When the grace period expires, cleanup **starts from the oldest media and deletes until `storage_bytes` falls back under the `free` cap**, not until everything is gone. "Oldest" is ordered by the last-touch time defined in the retention section below rather than upload time, so images inside a project the user was editing last week do not get deleted.

Any top-up immediately lifts read-only, restores the `paid` tier and resets the grace clock — because the exhaustion moment is computed from the ledger, the positive-balance row written by the top-up supersedes it automatically.

## Data Model

This phase adds four groups of tables, all defined as GORM models and created by `AutoMigrate` in the style of phases 1 and 2.

### Credit Balance and Transactions

```go
type Credit struct {
    UserID    uuid.UUID `gorm:"type:uuid;primaryKey"` // also the foreign key to users
    Balance   int64     `gorm:"not null;default:0"`
    UpdatedAt time.Time
}

type CreditTransaction struct {
    ID           uuid.UUID `gorm:"type:uuid;primaryKey"`
    UserID       uuid.UUID `gorm:"type:uuid;index;not null"`
    Type         string    `gorm:"type:varchar(16);not null"` // purchase | consume | refund | grant | expire
    Amount       int64     `gorm:"not null"`                  // positive adds, negative subtracts
    BalanceAfter int64     `gorm:"not null"`
    RefType      string    `gorm:"type:varchar(16)"`          // order | generation | admin
    RefID        string    `gorm:"type:varchar(64)"`
    Note         string    `gorm:"type:varchar(200)"`
    CreatedAt    time.Time `gorm:"index"`
}
```

`credits` holds one row per user, created with a zero balance in the same transaction as the user at registration. Do not defer creation to the first top-up, or every balance read grows a "row does not exist" branch.

The whole ledger has exactly one invariant, and it must always hold: **`credits.balance` equals the sum of that user's `credit_transactions.amount`.** `balance_after` is a snapshot of the balance at write time, used to pinpoint which entry first diverged. Every code path that changes the balance must write a transaction row in the same database transaction, and **no path may UPDATE `credits` without writing one** — that would void the invariant and with it the only reconciliation tool available.

Deduction uses a single conditional UPDATE rather than read-then-write:

```sql
UPDATE credits SET balance = balance - $1, updated_at = now()
WHERE user_id = $2 AND balance >= $1
```

One row affected means the deduction succeeded; zero means insufficient balance and returns 402 `INSUFFICIENT_CREDITS`. This needs no explicit row lock and leaves no race window in which the balance was sufficient at read time but not at write time.

`expire` (credit expiry) is not enabled this phase; the enum value exists up front so that adding the behavior later does not require touching the validation whitelist and frontend copy tables again.

### Top-Up Packages and Orders

```go
type CreditPackage struct {
    ID           string `gorm:"primaryKey;type:varchar(32)"`
    Name         string `gorm:"type:varchar(80);not null"`
    Credits      int64  `gorm:"not null"`
    BonusCredits int64  `gorm:"not null;default:0"`
    PriceCents   int64  `gorm:"not null"`
    Currency     string `gorm:"type:varchar(8);not null;default:CNY"`
    Enabled      bool   `gorm:"not null;default:true"`
    Sort         int    `gorm:"not null;default:0"`
}

type Order struct {
    ID              uuid.UUID  `gorm:"type:uuid;primaryKey"`
    UserID          uuid.UUID  `gorm:"type:uuid;index;not null"`
    Provider        string     `gorm:"type:varchar(16);not null"` // alipay | wechat | stripe
    ProviderOrderID *string    `gorm:"type:varchar(128);uniqueIndex"`
    PackageID       string     `gorm:"type:varchar(32);not null"`
    AmountCents     int64      `gorm:"not null"`
    Currency        string     `gorm:"type:varchar(8);not null"`
    Credits         int64      `gorm:"not null"`
    Status          string     `gorm:"type:varchar(16);not null;default:pending"` // pending | paid | failed | refunded
    PaidAt          *time.Time
    CreatedAt       time.Time
    UpdatedAt       time.Time
}
```

`amount_cents` and `credits` are **snapshotted** from `credit_packages` onto the order row at creation time and never re-read from the package table at settlement. Package prices and bonus credits can be adjusted by an administrator at any time, and re-reading would make "what the user saw when ordering" differ from "what actually landed" — a discrepancy that is impossible to explain in a payment context.

The unique index on `provider_order_id` is the infrastructure behind callback idempotency. If the provider has not returned an order number at creation time, leave the field `NULL` — a unique index ignores `NULL`, but **empty strings collide with each other** and the second pending order simply fails to insert. The field must therefore be `*string` rather than `string`; zero-value strings are an easy trap under GORM.

Indexes: `(user_id, created_at desc)` serves the user-facing order list, `(status, created_at)` serves the timeout cleanup scan.

### Platform Model Catalog

```go
type ModelCatalog struct {
    ID          uuid.UUID      `gorm:"type:uuid;primaryKey"`
    Name        string         `gorm:"type:varchar(120);not null"`
    DisplayName string         `gorm:"type:varchar(120);not null"`
    Capability  string         `gorm:"type:varchar(16);not null"` // image | video | text | audio
    Provider    string         `gorm:"type:varchar(60);not null"`
    Constraints datatypes.JSON `gorm:"type:jsonb"`
    CreditCost  datatypes.JSON `gorm:"type:jsonb"`
    Enabled     bool           `gorm:"not null;default:true"`
    Sort        int            `gorm:"not null;default:0"`
    CreatedAt   time.Time
    UpdatedAt   time.Time
}
```

`name` is the model identifier sent to the third-party endpoint and `display_name` is the name shown to users; the two must stay separate, because a channel renaming its model id while the product name stays put is common, and a single field would force user-visible copy to change with it.

`constraints` describes which parameters the model accepts:

```json
{
  "sizes": ["1024x1024", "1536x1024", "1024x1536"],
  "aspectRatios": ["1:1", "3:2", "2:3"],
  "durations": [5, 10],
  "qualities": ["standard", "hd"],
  "maxReferenceImages": 4
}
```

Keys that do not apply are simply omitted, and the frontend decides which controls to render by key presence rather than hard-coded per-model branches.

`credit_cost` describes parameter-based pricing:

```json
{
  "base": 10,
  "rules": [
    { "when": { "quality": "hd" }, "multiplier": 2 },
    { "when": { "size": "1536x1024" }, "add": 5 },
    { "when": { "duration": 10 }, "multiplier": 2 }
  ]
}
```

Evaluation order is fixed: start from `base` and apply each matching `add` and `multiplier` in array order, rounding up at the end. Order lives in the array rather than a priority field so that the order an administrator sees in the console is the order that actually applies.

The two jsonb columns are not split into real columns because the parameter dimensions differ completely across capabilities — images by size and quality, video by duration and resolution, audio by character count — so splitting would produce a pile of perpetually empty fields, and every new pricing dimension would mean a schema change. The trade-off is that prices cannot be computed in SQL, but pricing belongs in the application layer anyway.

This table describes only "which models the platform offers and how they are priced". It is a different thing from the model list of a user's own channel from phase 2: the former spends credits, the latter spends the user's own third-party allowance. The two must be presented separately in the frontend and never merged into one dropdown.

## Consistency of Credit Deduction

Deduction and generation outcome must agree, and this is the easiest thing in the phase to get wrong, so it gets its own section.

There are only two possible orderings. **Generate then charge** looks friendlier since it only bills on success, but it under-charges as soon as the failure rate rises: a proxy timeout, an interrupted stream, a process restart — anywhere the deduction is dropped, the cost of that generation is simply eaten, and these failures are not rare on AI endpoints. **Charge then generate** can over-charge, but over-charging is refundable.

This phase takes **charge first, generate second, refund automatically on failure**. The deciding factor is that the two error classes differ in recoverability: an under-charge is unrecoverable because the compute has already been spent and there is no way to claw it back afterwards; an over-charge is recoverable with a single refund. Take the over-charge-and-refund path over the under-charge path.

**Refunds must go through the ledger**, writing a row with `type=refund`, a positive `amount`, `ref_type=generation` and a `ref_id` pointing at the corresponding proxy request or generation record — never by adding to `balance` directly. The entire value of this rule is keeping `balance = SUM(amount)` true forever: the moment it is not, some code has bypassed the ledger, and the offending entry and path can be located immediately. Being reconcilable at any time is the only acceptable state for financial data.

Phase 4 calls exactly two internal methods:

```go
// Deduct; returns ErrInsufficientCredits when the balance is too low
func (s *CreditService) Reserve(ctx context.Context, userID uuid.UUID, amount int64, refID string) error

// Refund; idempotent per refID
func (s *CreditService) Refund(ctx context.Context, userID uuid.UUID, amount int64, refID, note string) error
```

`Reserve` deducts with the conditional UPDATE above and writes a `type=consume` row in the same transaction, returning `ErrInsufficientCredits` on a low balance for the handler to translate into 402. `Refund` must be idempotent: before writing, check `credit_transactions` for an existing `(type=refund, ref_id)` row and return success if one exists. A retrying proxy request will trigger the refund more than once, and without idempotency it refunds twice.

**This phase produces no `type=consume` rows at all**, because nothing calls `Reserve` — the real deduction lives in the phase 4 proxy. This phase only builds those two methods, the ledger tables and the reconciliation invariant, verifying correctness through manual admin adjustments (`type=grant`). Do not read this section and conclude that credits start being consumed once this phase ships.

## Usage Accounting

### Only Storage Needs a Counter

`usage_records` serves a single metric, unique by `(user_id, metric, period)`.

| metric | period form | Update trigger |
| --- | --- | --- |
| `storage_bytes` | `total` | Incremented on successful upload, decremented on delete |

Storage is not summed live the way generation counts are because it must be validated **before every upload**, and `SUM(bytes)` degrades as the file count grows, which does not belong on the upload hot path. The counter is a necessary compromise here.

`storage_bytes` is maintained solely by the server and never accepted from clients. Increments and decrements must share a transaction with the `media_files` write, otherwise concurrent uploads drift the count.

### Generation Counts Come from Generation Records, Billing Comes from the Ledger

This section exists to make the relationship between the two numbers explicit, because they are otherwise easy to conflate in the frontend.

The `generations` table remains the authority on generation history, and **display** figures such as "how many images today" are counted straight from it with no dedicated counter:

```sql
SELECT count(*) FROM generations
WHERE user_id = ? AND kind = ? AND deleted_at IS NULL
  AND created_at >= date_trunc('day', now() AT TIME ZONE 'UTC')
```

The `(user_id, kind, created_at desc)` index already exists from phase 2, making this query cheap. Dates are computed in UTC so a user's notion of "today" matches the server's across time zones.

But **billing is based on `credit_transactions`, not on that table.** The two record different kinds of fact: `generations` records "what was generated", a business history the user may soft-delete; `credit_transactions` records "how many credits were spent", a financial fact that is never deleted. Deleting a generation record removes a row from the history and returns nothing to the balance.

Do not, therefore, try to derive consumption from "row count × unit price", and do not reconcile by comparing row counts across the two tables. They are naturally unequal: one generation may deduct once while producing several images; a failed generation leaves a `consume` plus a `refund` with no successful generation record; and soft-deleting a generation record does not remove any ledger row. **The one reconciliation equation is `credits.balance = SUM(credit_transactions.amount)`** — any other cross-check produces wrong conclusions.

### Self-Healing Storage Counts

Counts and actual usage can diverge over a long runtime, for instance after an aborted upload. Provide a recompute entry point: a "recalculate storage usage" button on the admin user detail page that runs a full `SUM(bytes)` over that user's `media_files` and overwrites the counter. No scheduled job is needed; on-demand is enough.

## Media Retention and Orphan Reclamation

### Retention Renews on Last Touch

Cleanup covers **all media, including files a canvas currently references.** This must be stated plainly in product copy and on the billing page, or users will assume "anything still on a canvas is safe forever" and only learn otherwise when files disappear.

How the clock works is the key design decision here: it is not a fixed lifetime from upload, it **renews on last touch**. A media file's last-touch time is the maximum of the `updated_at` of every canvas referencing it, the `updated_at` of every asset, and the `created_at` of every generation record; with no references at all it degrades to `media_files.created_at`. Only files past their tier's `retention_days` enter the cleanup set.

The effect is that a project still in use has the lifetime of every media file it references extended on each autosave, and only projects genuinely untouched for weeks get cleaned. A fixed lifetime from upload would delete images out of an old project the user edits daily, which is not acceptable.

**No `expires_at` column is added.** Such a column would mean that every canvas save, asset update and generation write has to go back and update every media row it references — heavy write amplification, and a single path forgetting to update it would delete files the user still uses. The cleanup task can compute it on the fly during its scan: scanning is a low-frequency background job where a few extra joins are irrelevant, whereas a wrongful delete is irreversible.

Two days before expiry, send an email plus an in-app warning listing the number and total size of the files about to be cleaned, with a one-click export entry (reusing the existing canvas export). Warnings are sent per user rather than per file, at most once per user per 7 days, controlled by the same counter mechanism as phase 1's mail rate limiting — no new table required.

### Retention Cleanup and Orphan Reclamation Share One Scan

Orphan file reclamation is work phase 2 handed to this phase. Phase 2 removed the client-side garbage collector, which relied on the frontend holding the complete dataset — a premise that no longer holds and that would cause it to delete images other canvases still reference — but it did not build a server-side replacement. Until this phase ships, media referenced by a canvas the user deleted simply stays on disk. Nobody's data is at risk, only space, which is why deferring it was safe.

Its input is identical to retention cleanup's — both scan the jsonb columns of `canvases`, `assets` and `generations` to collect every still-referenced `storage_key` — so the two **merge into a single scan task** producing two result sets in one pass:

1. `storage_key` values present in `media_files` with no references at all, the orphans, deleted outright.
2. Referenced files whose last-touch time is past `retention_days`, the expired media, deleted as well.

Two passes would be pure waste, and more importantly two copies of the reference-collection logic will eventually disagree, at which point the same file counts as an orphan in one task and as live in the other — a miserable thing to debug.

Two things demand care. **Reference collection must not skip soft-deleted rows** — a canvas with a non-null `deleted_at` may still be something the user wants to restore, so the files it references must not be treated as orphans; the `updated_at` of soft-deleted rows also feeds the last-touch computation, so a canvas soft-deleted and never touched again has its exclusive media removed by the expiry pass once retention lapses, with no separate retention rule for soft deletion. **Reclamation must be scoped per user** and never implemented as a global scan followed by a bulk delete, because a bug in reference collection would then affect every user instead of one.

The post-grace-period downgrade cleanup reuses the same task with a different ordering and stop condition: delete by last-touch time oldest first, stopping as soon as that user's `storage_bytes` falls under the `free` cap rather than deleting everything.

Make this an on-demand admin action first, proving it correct on a single user before attaching a scheduled job. Recompute that user's storage usage once cleanup finishes.

## Endpoints

### Additional Error Codes

Phase 1's error code table still applies; this phase adds three:

| HTTP | code | Trigger |
| --- | --- | --- |
| 402 | `INSUFFICIENT_CREDITS` | Balance too low for the request; also returned for media uploads in read-only mode and for admin adjustments that would push the balance negative |
| 409 | `ORDER_ALREADY_PAID` | Cancelling an order that is already paid |
| 400 | `INVALID_SIGNATURE` | Payment callback signature verification failed |

Phase 2's 507 `STORAGE_QUOTA_EXCEEDED` still applies. The upload endpoint checks **balance before total**: read-only mode returns 402 first, and only a non-read-only account proceeds to the total check that may return 507. Reversing the order would show read-only users "storage limit exceeded, please clean up files" when the correct guidance for them is to top up.

### Usage, Tier and Credits

**GET `/api/me`** gains `credits` and `usage` on top of the phase 1 shape, and `plan` switches to the new tier structure:

```json
{
  "user": { "...": "..." },
  "plan": { "id": "paid", "name": "Paid", "storageBytes": 1073741824, "maxFileBytes": 209715200, "retentionDays": 14 },
  "credits": { "balance": 1280 },
  "usage": { "storageBytes": 1234567, "imageGenerateToday": 12, "videoGenerateToday": 2 },
  "readOnly": false,
  "graceEndsAt": null
}
```

`plan` no longer carries `dailyImages` or `dailyVideos`, and every frontend read of those two fields must be deleted rather than left alongside a second quota check. `plan.id` is derived live from the balance and queries no subscription table.

`readOnly` and `graceEndsAt` are derived fields computed by the server. The rule has only two conditions, but letting each frontend call site implement it independently guarantees they will diverge, and that rule directly decides whether the user is shown "top up" or "clean up files".

The generation counts in `usage` are for display only and take no part in any gating decision.

### Credits and Transactions

**GET `/api/credits`** requires authentication and returns the balance plus a recent-transaction summary:

```json
{
  "balance": 1280,
  "recent": [
    { "id": "t1...", "type": "purchase", "amount": 1100, "balanceAfter": 1280, "refType": "order", "refId": "o1...", "note": "Standard pack", "createdAt": "..." }
  ]
}
```

`recent` always returns the latest 5 entries so the profile center's balance card renders directly, saving one paginated request.

Errors: `UNAUTHORIZED`.

**GET `/api/credits/transactions?cursor=&size=&type=`** is cursor-paginated with the same shape as phase 2's generation records:

```json
{
  "items": [
    { "id": "t2...", "type": "consume", "amount": -20, "balanceAfter": 1260, "refType": "generation", "refId": "g1...", "note": "GPT Image · hd", "createdAt": "..." }
  ],
  "nextCursor": "eyJ0..."
}
```

`cursor` is `base64url(RFC3339Nano created_at + "|" + id)`, opaque to the client, returning `VALIDATION_FAILED` when it cannot be decoded. `size` defaults to 20 and caps at 100. `type` is optional and filters by transaction type, returning `VALIDATION_FAILED` when outside the enum.

The reasoning for cursors over page numbers matches generation records: the ledger is an append-only history stream, `COUNT(*)` degrades linearly over time, and new rows inserted at the head make offset pagination duplicate and skip entries.

The ledger is **read-only, with no write endpoint whatsoever**. All writes happen server-side inside business transactions, and the frontend has no path to fabricate an entry.

Errors: `UNAUTHORIZED`, `VALIDATION_FAILED`.

### Top-Up Packages and Orders

**GET `/api/credit-packages`** requires authentication and returns packages with `enabled = true` ordered by `sort` ascending:

```json
{
  "items": [
    { "id": "standard", "name": "Standard pack", "credits": 1000, "bonusCredits": 100, "priceCents": 3000, "currency": "CNY" }
  ]
}
```

Errors: `UNAUTHORIZED`.

**POST `/api/orders`** takes `{ "packageId": "standard", "provider": "alipay" }` and returns 201:

```json
{
  "order": { "id": "o1...", "packageId": "standard", "amountCents": 3000, "currency": "CNY", "credits": 1100, "status": "pending", "createdAt": "..." },
  "payment": { "type": "qrcode", "payload": "https://qr.alipay.com/..." }
}
```

`order.credits` is the sum of `credits + bonusCredits`, computed and written onto the order row at creation.

`payment.type` is one of `qrcode`, `redirect` or `clientSecret`, telling the frontend whether to render a QR code, navigate away or launch the provider SDK. All three providers' shape differences collapse into this one field, so the frontend never writes `if (provider === "alipay")` branches.

Errors: `VALIDATION_FAILED` (unknown or delisted package, `provider` outside the enum), `UNAUTHORIZED`, `RATE_LIMITED` (10 orders per hour per user, to stop a pile of junk pending orders).

**GET `/api/orders?cursor=&size=&status=`** returns the current user's orders with cursor pagination, the same shape as the transaction list with order objects in `items`. Errors: `UNAUTHORIZED`, `VALIDATION_FAILED` (undecodable cursor or `status` outside the enum).

**POST `/api/orders/{id}/cancel`** cancels a pending order and returns 200 with the updated order. Only `pending` orders can be cancelled.

Errors: `NOT_FOUND` (the order does not exist, **or belongs to another user** — consistent with phase 2, cross-user access returns 404 rather than 403), `ORDER_ALREADY_PAID`.

### Payment Callbacks

**POST `/api/payments/webhook/{provider}`** is a public route outside `RequireAuth`, but **signature verification is mandatory**.

The request body follows each provider's own format with no unified contract. Each provider gets an adapter function that verifies the signature and parses the raw payload into a uniform `{ providerOrderID, outTradeNo, amountCents, status }` before entering the shared handling flow.

The response format **follows each provider's requirements**: Alipay wants the plain text `success`, WeChat wants a fixed JSON structure, Stripe only looks at 2xx. This is the one place that must not use the project's unified error response format, or the provider decides the callback failed and keeps retrying.

Errors: `INVALID_SIGNATURE` (400), `NOT_FOUND` (no matching local order). **Verification failures are always rejected**, with no switch or environment variable to skip verification; use the provider's own sandbox for debugging.

The settlement logic and idempotency guarantees are in "Payment Implementation Notes" below, where all five points are mandatory.

### Model Catalog

**GET `/api/models?capability=`** requires authentication and returns models with `enabled = true` ordered by `sort` ascending, with `capability` optional:

```json
{
  "items": [
    {
      "id": "m1...",
      "name": "gpt-image-1",
      "displayName": "GPT Image",
      "capability": "image",
      "provider": "openai",
      "constraints": { "sizes": ["1024x1024", "1536x1024"], "qualities": ["standard", "hd"], "maxReferenceImages": 4 },
      "creditCost": { "base": 10, "rules": [ { "when": { "quality": "hd" }, "multiplier": 2 } ] }
    }
  ]
}
```

`creditCost` is sent to the frontend verbatim so the generate button can show "costs N credits" live. But **the price the frontend computes is for display only**: phase 4 recomputes it server-side from the same rules at deduction time and never accepts a client-supplied price. A number the frontend can edit cannot be the basis for charging.

Errors: `UNAUTHORIZED`, `VALIDATION_FAILED` (`capability` outside the enum).

### Total Quota Check on Upload

The `PUT /api/media/{storageKey}` endpoint from phase 2 gains two checks, in this order:

1. Read-only mode (zero balance and `storage_bytes` already above the `free` cap) returns 402 `INSUFFICIENT_CREDITS` with `{ "graceEndsAt": "..." }` in the body.
2. Current `storage_bytes` plus the incoming file size exceeding the tier's `storage_bytes` returns 507 `STORAGE_QUOTA_EXCEEDED` with `{ "used": ..., "limit": ... }` in the body.

The check and the write must share a transaction, reserving before writing to disk and rolling the counter back on failure.

### Admin Console

All routes sit under `/api/admin` behind a dedicated `RequireAdmin` middleware validating `role = admin`. It runs after `RequireAuth` and returns 403 `FORBIDDEN` for non-administrators.

| Method | Path | Notes |
| --- | --- | --- |
| GET | `/api/admin/users` | Paginated list supporting `page`, `size`, `q` (email or username), `status` and `planId` |
| GET | `/api/admin/users/{id}` | User detail with tier, credit balance, usage, registration time and last login |
| PATCH | `/api/admin/users/{id}` | Change `status` (`active`/`disabled`) |
| POST | `/api/admin/users/{id}/password` | Reset the password and revoke all of that user's refresh tokens |
| POST | `/api/admin/users/{id}/credits` | Adjust credits, see below |
| POST | `/api/admin/users/{id}/usage/recalculate` | Recompute storage usage |
| POST | `/api/admin/users/{id}/media/reclaim` | Run the cleanup scan (orphans plus expired) for that user, recomputing storage usage afterwards |
| GET | `/api/admin/stats` | Overview: total users, new today, total storage, generations today, top-up revenue today, total outstanding credits |
| GET/POST/PATCH/DELETE | `/api/admin/models` | Model catalog CRUD |
| GET/POST/PATCH | `/api/admin/credit-packages` | Top-up package management |
| GET | `/api/admin/orders` | Site-wide order list filterable by `status`, `provider` and `userId` |

User list response:

```json
{ "items": [ { "id": "...", "email": "...", "username": "...", "role": "user", "status": "active", "emailVerified": true, "planId": "paid", "balance": 1280, "storageBytes": 123, "createdAt": "..." } ], "total": 128, "page": 1, "size": 20 }
```

Errors shared by every admin endpoint: `UNAUTHORIZED` (not signed in), `FORBIDDEN` (not an administrator), `NOT_FOUND` (user or resource missing) and `VALIDATION_FAILED` (bad parameters); only endpoint-specific errors are listed below.

`PATCH /api/admin/users/{id}` **can no longer change `planId`**. The tier is decided by the balance, so an administrator who wants to upgrade someone grants credits, keeping a single derivation path. Leaving a back door that sets the tier directly permits states like "tier is paid but balance is zero", which the ledger cannot explain.

**POST `/api/admin/users/{id}/credits`** takes `{ "amount": 500, "note": "Support compensation" }` where `amount` adds when positive and subtracts when negative, returning 200 with `{ "balance": 1780 }`.

It must write a `type=grant`, `ref_type=admin` row whose `ref_id` is the acting administrator's id, persisting `note` alongside. **Changing `credits.balance` directly is not allowed**, or the reconciliation equation breaks immediately — and since this is the only manually triggered balance change in the phase, it is the most tempting place to shortcut into a bare UPDATE. Adjustments that would go negative are rejected with 402 `INSUFFICIENT_CREDITS`.

**DELETE `/api/admin/models/{id}`** is a hard delete, but only for models that were never used; a model with ledger history can only be set to `enabled = false`. Ledger rows keep the model name in `note`, so deleting the catalog row does not make history unreadable, but deleting a model users are currently on makes the selected item in their dropdown vanish.

`credit_packages` offers only GET, POST and PATCH and has **no DELETE**: order rows reference `package_id`, and deleting a package makes historical orders untraceable. Delist with `enabled = false`.

### How Quickly Suspension Takes Effect

After switching a user to `disabled`, their already-issued access token stays valid for up to 15 minutes. Their refresh tokens must therefore **all be revoked at the same time**, so they drop off entirely within 15 minutes when refresh fails.

Immediate effect would require a database lookup of user status on every authenticated request, at the cost of one extra query per request. This phase takes the token revocation approach and states "fully effective within 15 minutes" in the admin console's confirmation copy.

## Payment Implementation Notes

Payments are the one place in this phase where a mistake causes an actual financial discrepancy. None of the five points below is optional.

**Callbacks must be idempotent.** The same `provider_order_id` may only settle once. Providers resend the same callback due to timeouts, network jitter and manual re-pushes; this is normal, not exceptional. The guarantee comes from the order table's unique constraint plus a state machine: settlement performs the state transition with a single conditional UPDATE.

```sql
UPDATE orders SET status = 'paid', paid_at = now(), updated_at = now()
WHERE id = $1 AND status = 'pending'
```

Only one row affected proceeds to grant credits; zero means this order was already processed, so **return a success response to the provider rather than an error** — an error makes the provider treat the callback as failed and retry forever.

**Settlement must be one transaction.** Updating the order status, incrementing `credits.balance` and writing `credit_transactions` all happen in a single database transaction, rolling back entirely if any step fails. Doing them separately produces two equally awkward failures: credits granted while the order stays `pending`, so the next callback grants them again; or the order marked paid without the credits, so the user paid and got nothing.

**Do not trust amounts in the callback.** Credits granted always come from the local order row's `credits`, and amount validation uses the local `amount_cents`. The callback's amount is used only for comparison, and a mismatch **rejects settlement and logs at error level**, because it means either the order was tampered with or the wrong provider account is wired up — neither should be papered over by automatic logic. Never overwrite local records with numbers from a callback.

**Verification failures are always rejected.** There is no `SKIP_SIGNATURE_VERIFY` switch and no temporary relaxation because "local debugging is inconvenient" — a forged callback creates money out of thin air, and this is the only externally attackable entry point on the whole payment path. Each provider's public key or secret is read from environment variables and a missing one fails startup with a clear error, in the same style as phase 1's SMTP validation.

**Timed-out orders need cleanup.** A `pending` order unpaid for more than 30 minutes becomes `failed`, driven by a background task scanning the `(status, created_at)` index every 5 minutes. Before marking it failed, the task must **actively query the provider for the real status** rather than judging by local time alone: the user may have paid at the last second with the callback still in flight, and failing the order outright produces "money paid, order failed, no credits". Orders found already paid go through the normal settlement flow, and this active query doubles as the fallback for callbacks lost entirely.

## Frontend Changes

### Profile Center `web/src/pages/profile/index.tsx`

On top of the phase 1 profile and password sections, add the current tier, the credit balance, a storage usage progress bar and the latest 5 ledger entries. Use the Ant Design `Progress` component, changing color as the limit approaches.

In read-only mode, put an Alert at the top of the page naming the grace period deadline, what will be cleaned when it expires, and entry points for both topping up and exporting. This notice must not be a `message` toast that disappears — it needs to persist, since the user may only come back days later.

### Billing and Orders `web/src/pages/billing/`

Two blocks: the package card list and order history. Clicking a package calls `POST /api/orders` and renders by `payment.type` — `qrcode` opens a QR Modal, `redirect` navigates, `clientSecret` launches the provider SDK.

Payment completion **cannot be detected from the callback alone**, because the callback reaches the server and the frontend never sees it. While the QR Modal is open, poll the order detail until the status becomes `paid` or the user closes the dialog, at a 3-second interval for at most 10 minutes. On settlement, invalidate the `/api/me` and `/api/credits` react-query entries so the balance and tier refresh themselves rather than being synchronized by hand. Per existing project conventions, the polling timer must be cleared in the effect's cleanup.

The order list uses `useInfiniteQuery` with `nextCursor`, the same pattern as generation records.

### Credit Gating at Generation Entry Points

Before generating, compare `credits.balance` from `/api/me` against the estimated cost derived from the model catalog locally, disabling the button and prompting a top-up when short — no extra request needed.

But state it clearly: **the frontend gate in this phase is a UX nicety; the real deduction lives in the phase 4 proxy.** The estimated price is only for displaying "costs N credits"; do not decrement any local number from it, and do not write ledger entries after generating — the ledger has no write endpoint at all.

The existing code that gates on `plan.dailyImages` and `usage.imageGenerateToday` must be deleted wholesale rather than left as a second, parallel quota check.

The affected locations are `web/src/pages/image/index.tsx`, `web/src/pages/video/index.tsx` and the in-canvas generation logic in `web/src/components/canvas/canvas-node-generation.ts`. All three need wiring; do not miss in-canvas generation.

### Model Selection and Dynamic Forms

The model dropdown's data source becomes `GET /api/models`, and the parameter form is **rendered dynamically from `constraints`** rather than hard-coding which model supports which sizes.

The rule is simply key presence: `sizes` or `aspectRatios` render the corresponding selector, `durations` renders a duration picker, `qualities` renders a quality picker, `maxReferenceImages` caps the reference image uploader, and an absent key renders no control.

When switching models, validate that the currently selected parameters are still legal under the new model's `constraints`, falling back to the first allowed value when they are not. Skipping this produces "switched model but the size is still the previous model's exclusive value", which only errors out at the phase 4 proxy where the user has no idea what went wrong.

The estimated cost recomputes live as parameters change and appears next to the generate button, following the same evaluation order as the server's `credit_cost` rules. Extract that evaluation into a pure function in `web/src/lib/credit-cost.ts` shared by all three generation entry points rather than reimplementing it per page.

Platform models and the user's own channel models from phase 2 must be visually separated and never merged into one dropdown — they bill against entirely different accounts, one spending credits and the other the user's own third-party allowance, and mixing them leaves the user unsure whose money a generation is spending.

### Handling Upload Overage and Read-Only Mode

When a media upload hits 507 `STORAGE_QUOTA_EXCEEDED` or 402 `INSUFFICIENT_CREDITS`, **do not fail the entire save**. The metadata for a canvas, asset or generation record is tiny and should still be written to the server; only the referenced media file is missing.

This distinction matters: failing an entire canvas save because one image exceeded quota throws away the user's editing work. The correct behavior is to persist the metadata first and collect the `storageKey` values that failed into a single message. The two error codes point in different directions and need separate copy: 507 directs the user to clean up files, 402 directs them to top up and states how much grace period remains.

### Admin Console `web/src/pages/admin/`

Four pages: `users/`, `models/`, `credit-packages/` and `orders/`.

Organized per existing project conventions: page-private components live in each page's own `components/` directory rather than a shared one, and table colors, card shadows and light/dark branching are configured centrally in `web/src/lib/app-theme.ts` instead of `dark ? ... : ...` checks inside page components.

Use the Ant Design `Table` with `@ant-design/pro-components` (already a dependency) for search, filtering and pagination. Row actions on the users page cover suspend and restore, adjust credits, reset password, trigger a cleanup scan and view detail.

The models page supports create, edit and delist, and the `constraints` and `credit_cost` jsonb fields must be edited through controlled form controls, **not a raw JSON textarea**: letting an administrator hand-write JSON means one misspelled key silently renders no control in the dynamic form, an error invisible at save time that only surfaces when a user opens the generation page.

### Routing and Guards

Nest the pages under `/admin` inside `RequireAuth` with an additional `RequireAdmin`, redirecting non-administrators to the home page rather than the login page. `/billing` only needs `RequireAuth`. The top navigation user dropdown gains an admin console entry when `role === "admin"`, and every signed-in user gains a top-up entry showing the current balance.

Hiding the frontend entry is only a UX nicety; **the real authorization decision lives in backend middleware**, and both are required.

### Localization

Add `admin.*`, `billing.*` and `credits.*` sections to both `zh-CN.ts` and `en-US.ts`, keeping the files symmetric. Existing `quota.*` copy about daily generation limits must be deleted rather than left unused.

## Acceptance Checklist

Credit ledger:

- Granting a user 500 credits from the admin console increases the balance in `/api/credits` and adds one `type=grant`, `ref_type=admin` row whose `balanceAfter` matches the new balance.
- `SELECT SUM(amount) FROM credit_transactions WHERE user_id = ?` equals `credits.balance` for any user, and the equation still holds after top-ups, adjustments, refunds or any other operation.
- An admin adjustment that would push the balance negative is rejected with 402 `INSUFFICIENT_CREDITS`, leaving both balance and ledger unchanged.
- Multiple concurrent deductions against the same user end with a correct balance and no over-deduction.
- The ledger exposes no write endpoint and the frontend cannot fabricate an entry.
- After this phase ships, no `type=consume` rows appear on their own; the balance changes only through top-ups and admin actions.

Deduction failure and refund:

- Calling `Reserve` from a unit test or temporary debug entry point, simulating a generation failure and then calling `Refund` returns the balance to its pre-deduction value, with `consume` and `refund` appearing as a pair sharing one `ref_id`.
- Calling `Refund` twice with the same `refID` produces a single `type=refund` row and increases the balance only once.
- `Reserve` on an insufficient balance returns an error, writes no ledger row, and the calling endpoint returns 402 `INSUFFICIENT_CREDITS`.

Payments and orders:

- The `credits` on a created order equals the package's `credits + bonusCredits`; changing that package's price and bonus afterwards leaves the existing order's amount and credits untouched.
- Pushing the same `provider_order_id` callback repeatedly settles once, increases the balance once and adds one ledger row, with the second callback returning the provider's expected success response rather than an error.
- A callback with a forged signature returns 400 `INVALID_SIGNATURE` and changes neither the order status nor the balance.
- A callback whose amount disagrees with the local order's `amount_cents` is rejected and logged at error level.
- Forcing the ledger write to fail mid-settlement rolls the order back to `pending` with an unchanged balance, and re-pushing the callback settles normally.
- Cancelling an already-paid order returns 409 `ORDER_ALREADY_PAID`; cancelling another account's order id returns 404.
- A pending order older than 30 minutes becomes `failed`, and the provider was actively queried for its real status first; with the provider status stubbed as paid, that order settles normally instead of failing.

Tier and read-only mode:

- A newly registered user has a zero balance on the `free` tier and can upload media normally, without being misclassified as read-only.
- After a top-up, `/api/me` immediately reports `plan.id` as `paid` with larger `storageBytes`, `maxFileBytes` and `retentionDays`, with no admin action anywhere in the flow.
- Once a paid user's credits run out while usage exceeds the `free` cap, `/api/me` reports `readOnly` true with a `graceEndsAt` value, and media uploads return 402 `INSUFFICIENT_CREDITS` carrying `graceEndsAt`.
- In read-only mode the user can still browse canvases, edit canvas structure, rename, delete data and export zips.
- A read-only user regains uploads immediately after any top-up, with `readOnly` back to false and `graceEndsAt` back to null.
- Uploads near the limit are rejected with 507 `STORAGE_QUOTA_EXCEEDED` and a body containing `used` and `limit`.
- After several concurrent uploads, `usage.storageBytes` matches `SUM(bytes)` over `media_files`.
- "Recalculate storage usage" corrects a deliberately corrupted counter.
- Neither the database nor the frontend codebase still mentions `subscriptions`, `dailyImages` or `dailyVideos`.

Retention and cleanup:

- Triggering the cleanup scan after deleting a canvas removes the images it exclusively owned from disk and lowers storage usage, while images shared with another canvas or asset are **not** deleted.
- For media referenced by exactly one canvas, backdating that canvas's `updated_at` beyond `retention_days` gets the file cleaned on the next scan; editing the canvas again to refresh `updated_at` leaves the same file untouched, proving last-touch renewal works.
- Media referenced by a soft-deleted canvas still inside its retention window is not cleaned.
- One scan produces both the orphan and the expired result sets, and the log shows how many files and bytes each removed.
- Post-grace downgrade cleanup deletes by last-touch time oldest first and stops as soon as `storage_bytes` falls under the `free` cap, never wiping the user's media entirely.
- A warning email and in-app notice arrive two days before expiry with a working one-click export entry, and the same user does not receive it again the next day.

Model catalog:

- A model created by an administrator appears immediately in the frontend generation dropdown, with the parameter form rendering the controls described by `constraints`.
- Removing `qualities` from a model's `constraints` stops the frontend rendering the quality selector while leaving the other controls intact.
- Switching models falls illegal selected parameters back to the first allowed value rather than carrying over the previous model's exclusive value.
- The estimated cost beside the generate button updates live with parameter changes and matches what the server computes from the same `credit_cost` rules.
- A model with ledger history cannot be hard-deleted, only delisted; after delisting it disappears from the dropdown while historical ledger rows still show its name.
- Top-up packages have no delete action; a delisted package stops appearing in `GET /api/credit-packages` while historical orders still resolve their source package.
- Platform models and the user's own channel models are displayed separately, making it obvious whether a generation spends credits or the user's own third-party allowance.

Admin console:

- An administrator sees the user list and can search by email, filter by status and paginate, with the credit balance and current tier visible in the list.
- Suspending a user invalidates all their refresh tokens and drops them entirely within 15 minutes.
- An admin password reset signs the user out on every device.
- **A non-administrator requesting `/api/admin/users`, `/api/admin/models`, `/api/admin/credit-packages` or `/api/admin/orders` directly receives 403**, holding even though the frontend entry is hidden.
- A non-administrator visiting any route under `/admin` is redirected to the home page.
- The order list filters by status, provider and user, and shows the credits and settlement time for each order.
- The models page edits `constraints` and `credit_cost` through form controls rather than a raw JSON textarea.

Consistency:

- The admin console and billing page render correctly in both light and dark themes without theme branching inside page components.
- `bun run typecheck` passes and both locale files have symmetric key structures.
