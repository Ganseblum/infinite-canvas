# Phase 2 Implementation Checklist: Credential Custody and Resource-Oriented Data

This document is the development baseline for phase 2 of the [Account System and Backend Service Plan](/docs/progress/account-backend-plan). It assumes [phase 1](/docs/progress/account-backend-phase1) has shipped and passed acceptance.

## Scope

### In Scope

AES-GCM credential custody, REST endpoints for the three business resources (canvases, assets and generations), media file object storage, per-record optimistic locking and soft deletes, per-file size validation, the "unverified email cannot upload" constraint, and the frontend rework from loading everything locally to loading on demand from the server.

### Out of Scope

Total storage quota, generation counting and the admin console, all deferred to phase 3.

Per-file size validation is included here because `plans.max_file_bytes` was created in phase 1 and the nginx `client_max_body_size` needs a backend backstop. **Total** storage validation depends on usage accounting and waits for phase 3.

Reclaiming orphaned media also waits for phase 3. Deciding whether a `storage_key` is still referenced means scanning the jsonb columns of three business tables, which is the same kind of work as phase 3's storage recount and belongs with it. This phase only guarantees that a file the user explicitly deletes disappears from disk immediately.

**Retention-based cleanup also lands in phase 3.** One thing to keep in mind: media uploaded in this phase is not kept forever as a product matter — seven days on the free tier and fourteen on the paid one, renewed by last-touch time, after which the phase 3 cleanup job removes it. This phase does not implement that, but frontend design should account for it and avoid assuming a file stays available once uploaded, particularly for export and sharing features.

## Why the Whole-Domain Sync Model Was Dropped

The original plan for this phase reused the sync model from the WebDAV era: pack each domain into a single `DomainManifest` JSON, upload and download it as a whole, merge local and remote with `mergeById` on the client, and handle deletions through a tombstone table plus a local snapshot diff. That model has been rejected, for the following reasons.

**A packed domain cannot be paginated, searched or sorted.** The canvas list wants to page through by update time and the assets page wants to filter by tag and keyword — exactly what a database is good at. Once a whole domain is squeezed into one JSON blob, every filter has to run on the client, which first requires downloading everything. The more a user accumulates, the slower the list page gets, and that curve never flattens.

**Generation history is an append-only stream, and pulling all of it is unacceptable.** A few months of normal use produces thousands of records, and the manifest model uploads and downloads all of them on every sync. Using "merge" on a log stream that is only ever appended to is a mismatch in the first place.

**A revision lock on an entire domain is far too coarse.** Two devices editing two completely different canvases still collide because they share one domain revision, which then triggers a re-pull, re-merge and rewrite. No user can be expected to understand why editing canvas A reports a conflict with canvas B.

**Deletion needs extra machinery that soft deletes provide for free.** The manifest model requires a dedicated tombstone table plus a client-side snapshot diff to infer which ids were deleted locally, and every merge has to filter against both. With resources, deletion is a `deleted_at` on one row, and the server already knows what was deleted.

**"Reuse the merge logic in `app-sync.ts`" was never a saving.** The original plan treated it as the main advantage of this phase, but it trades a worse architecture for short-term effort: putting conflict resolution on the client means any browser running an outdated frontend can corrupt data, and the server has no constraint that can stop it.

Moving to a **server-authoritative, resource-oriented REST model** removes all of this at once: pagination, search and sorting go back to SQL; writes target a single record, so the optimistic lock is scoped to one canvas; deletion is a `deleted_at`; and the client needs no merge logic at all. The cost is that the frontend must move from everything-in-memory to on-demand loading, which is where most of this phase's frontend effort goes. "Frontend Changes" below walks through it page by page.

## Credential Custody

### Encryption Scheme

AES-256-GCM. The master key comes from `CREDENTIAL_MASTER_KEY` as base64-encoded 32 bytes, decoded and length-checked at startup, failing to boot when invalid.

Every write generates a fresh 12-byte random nonce, stored separately from the ciphertext in `user_credentials.nonce` and `payload`. `key_version` is currently fixed at 1, reserved for future key rotation.

The plaintext is the serialized JSON of `AiConfig`, including `baseUrl`, `apiKey` and the `baseUrl` and `apiKey` of every entry in `channels[]`.

`user_credentials` is the one table out of this phase's nine that was previously only described in the plan document without a structure ready to implement, so here it is:

```go
type UserCredential struct {
    UserID     uuid.UUID `gorm:"type:uuid;primaryKey"`
    Payload    []byte    `gorm:"not null"`
    Nonce      []byte    `gorm:"not null"`
    KeyVersion int       `gorm:"not null;default:1"`
    CreatedAt  time.Time
    UpdatedAt  time.Time
}
```

`UserID` is the primary key directly: a user has exactly one credential record, so there is no need for a separate surrogate key, and the "one row per user" constraint ends up enforced by the database rather than by business code. `UpdatedAt` cannot be dropped: the `GET /api/credentials` response below carries `updatedAt`, which the config page uses to tell the user when the configuration was last synced, and without the column that field has no source. All timestamps serialize as RFC3339, UTC, with milliseconds.

### Endpoints

**GET `/api/credentials`** requires login and returns the decrypted configuration:

```json
{ "config": { "channelMode": "...", "baseUrl": "...", "apiKey": "...", "channels": [ ... ] }, "updatedAt": "..." }
```

When nothing has been saved yet it returns 200 with `config` set to `null` rather than 404, sparing the frontend an extra branch.

**PUT `/api/credentials`** takes `{ "config": { ... } }`, encrypts and persists it, and returns 204.

### A Risk That Must Be Documented

The `apiKey` in the response is **full plaintext** and cannot be masked, because the frontend needs it to call the third-party AI channel directly. This means anyone who obtains a user's access token can read every vendor key that user owns.

That is precisely why phase 1 put the refresh token in an httpOnly cookie and kept the access token in memory only. Do not move tokens into localStorage "for easier debugging" during this phase; doing so collapses the entire defense.

**This risk does not go away in phase 4 and must be treated as permanent.** Phase 4 only moves platform-catalog models behind the backend; channels the user configures themselves stay on the browser-direct path, and that path cannot issue a request without the plaintext key. `GET /api/credentials` therefore keeps returning plaintext and will not switch to masked values.

That makes the phase 1 defense a permanent requirement rather than a stopgap: the access token stays in memory, the refresh token stays in an httpOnly cookie, and neither ever touches localStorage. Equally, there is no point layering second-level encryption or temporary key-exchange tokens on top of this exposure — none of them stop an attacker who already holds an access token, and they only add complexity. Protecting the token itself is what actually works.

`SECURITY.md` and `docs/content/docs/support/security.mdx` must be updated in this phase to state that the server holds users' third-party keys, along with the encryption algorithm, master key custody and the risk boundary.

## Data as Resources

### Resource Breakdown

Three business resources, one table each, one row per business object:

| Resource | Frontend concept | Pagination |
| --- | --- | --- |
| `canvases` | Canvas projects | Page-based, list returns summaries only |
| `assets` | My assets | Page-based, list returns full objects |
| `generations` | Image and video workbench history | Cursor-based, append-only stream |

The single `generations` table replaces the former `image-workbench` and `video-workbench` domains. The only difference between them is whether `kind` is `image` or `video`; every other field is identical, so there is no reason for two tables.

Binary media never lands in a business table. Business rows carry a `storage_key`, while the bytes are indexed by `media_files` and held by object storage.

### Table Structures

Defined as GORM models in the phase 1 style and created by `AutoMigrate`. Field-level descriptions live in the data model section of the plan document; what follows is the structure and indexes to implement directly.

```go
type Canvas struct {
    ID              uuid.UUID      `gorm:"type:uuid;primaryKey"`
    UserID          uuid.UUID      `gorm:"type:uuid;not null"`
    Title           string         `gorm:"type:varchar(200);not null"`
    Data            datatypes.JSON `gorm:"type:jsonb;not null"`
    Revision        int64          `gorm:"not null;default:1"`
    NodeCount       int            `gorm:"not null;default:0"`
    ConnectionCount int            `gorm:"not null;default:0"`
    CoverKey        string         `gorm:"type:varchar(80)"`
    CreatedAt       time.Time
    UpdatedAt       time.Time
    DeletedAt       gorm.DeletedAt
}

type Asset struct {
    ID         uuid.UUID      `gorm:"type:uuid;primaryKey"`
    UserID     uuid.UUID      `gorm:"type:uuid;not null"`
    Kind       string         `gorm:"type:varchar(16);not null"` // text | image | video
    Title      string         `gorm:"type:varchar(200);not null"`
    Tags       pq.StringArray `gorm:"type:text[]"`
    Data       datatypes.JSON `gorm:"type:jsonb;not null"`
    StorageKey string         `gorm:"type:varchar(80)"`
    Bytes      int64          `gorm:"not null;default:0"`
    CreatedAt  time.Time
    UpdatedAt  time.Time
    DeletedAt  gorm.DeletedAt
}

type Generation struct {
    ID         uuid.UUID      `gorm:"type:uuid;primaryKey"`
    UserID     uuid.UUID      `gorm:"type:uuid;not null"`
    Kind       string         `gorm:"type:varchar(16);not null"` // image | video
    Status     string         `gorm:"type:varchar(16);not null"` // pending | success | failed
    Prompt     string         `gorm:"type:text"`
    Model      string         `gorm:"type:varchar(120)"`
    Config     datatypes.JSON `gorm:"type:jsonb"`
    Result     datatypes.JSON `gorm:"type:jsonb"`
    DurationMs int            `gorm:"not null;default:0"`
    CreatedAt  time.Time
    DeletedAt  gorm.DeletedAt
}

type MediaFile struct {
    ID         uuid.UUID `gorm:"type:uuid;primaryKey"`
    UserID     uuid.UUID `gorm:"type:uuid;not null"`
    StorageKey string    `gorm:"type:varchar(80);not null"`
    ObjectPath string    `gorm:"type:varchar(300);not null"`
    MimeType   string    `gorm:"type:varchar(120);not null"`
    Bytes      int64     `gorm:"not null"`
    Checksum   string    `gorm:"type:varchar(64);not null"`
    CreatedAt  time.Time
}
```

Indexes:

| Table | Index | Query it serves |
| --- | --- | --- |
| `canvases` | `(user_id, deleted_at, updated_at desc)` | The default list query: current user, not deleted, newest first |
| `assets` | `(user_id, deleted_at, updated_at desc)`, plus GIN on `tags` | The first for paging, the second for tag filtering |
| `generations` | `(user_id, kind, created_at desc)` | Cursor pagination over workbench history |
| `media_files` | Unique `(user_id, storage_key)` | Ownership checks and idempotent overwrite on re-upload |

Three details deserve their own note.

`Generation` deliberately has no `UpdatedAt`. Apart from the single terminal-state write that settles a pending record (see the generation endpoints below), it never changes after being written, and a column that almost always equals `CreatedAt` only suggests it can be edited freely. That one write needs no timestamp either: the exact moment a result settled means nothing to the user, and the list is always ordered by `CreatedAt`.

`MediaFile` deliberately has no `DeletedAt`. Deleting media also removes the object from disk, so a row saying "deleted, and the file is gone anyway" serves no purpose; media is hard-deleted.

`Tags` uses a native PostgreSQL array rather than jsonb so it can carry a GIN index, letting tag filtering hit an index instead of a sequential scan.

The `user_credentials` structure is given in the credential custody section above and is created by `AutoMigrate` alongside these. The previously designed `sync_domains` and tombstone tables are no longer needed, and `sync_files` is renamed to `media_files`.

### Optimistic Locking and Conflict Semantics

Only `canvases` carries a `revision`, because only a canvas is realistically edited on two devices at the same time for an extended period.

Writes are a single conditional UPDATE:

```sql
UPDATE canvases SET data = $1, revision = revision + 1, updated_at = now()
WHERE id = $2 AND user_id = $3 AND revision = $4 AND deleted_at IS NULL
```

One affected row means success and the new `revision` is returned. Zero rows means re-reading the record: if it exists, return 409 with the server's current `revision`; if not, return 404. No explicit transaction or row lock is needed, and there is no read-then-write race window.

Assets and generations get no optimistic lock. An asset is a small object edited one at a time, so collisions are rare and harmless and last-write-wins is enough; generations cannot be modified at all. Locking a concurrency scenario that does not exist would only force the frontend to write conflict branches it never hits.

### Soft Deletes Instead of a Tombstone Table

All three business tables carry `deleted_at`, and deleting means writing a timestamp. Every list and detail query filters on `deleted_at IS NULL`, so a soft-deleted record simply does not exist as far as the client is concerned.

Deleting the same id twice returns 204 for idempotency, and a `GET` after deletion returns 404.

This removes the need for a tombstone table and for a client-side snapshot diff. The old "a canvas deleted locally comes back on the next sync" bug is specific to the merge model and cannot occur here — the client never has the opportunity to write a full dataset containing deleted records back to the server.

## Endpoint Definitions

### Shared Conventions

Every resource endpoint requires login and forces `user_id = current user` into the query. **Cross-user access returns 404, never 403**, so status codes cannot be used to probe whether an id exists.

Page-based pagination uses one set of parameters and one response shape:

| Item | Convention |
| --- | --- |
| `page` | 1-based, defaults to 1 |
| `size` | Defaults to 20, capped at 100; beyond that returns `VALIDATION_FAILED` |
| `q` | Keyword, case-insensitive containment match on the title; an empty string means no filter |
| `sort` | One of `updatedAt`, `createdAt`, `title`, with a `-` prefix for descending; defaults to `-updatedAt`; anything off the allowlist returns `VALIDATION_FAILED` |
| Response | `{ "items": [ ... ], "total": 37, "page": 1, "size": 20 }` |

`sort` must go through an allowlist enum mapped to a column name; the parameter is never concatenated into SQL.

Error codes added or first used in this phase; everything else follows phase 1:

| HTTP | code | Trigger |
| --- | --- | --- |
| 403 | `EMAIL_NOT_VERIFIED` | An unverified account calls media upload; reserved in phase 1, first used here |
| 409 | `REVISION_CONFLICT` | The `revision` sent to a canvas `PUT` does not match the server, which returns its current `revision` inside `error` |
| 409 | `CHECKSUM_MISMATCH` | The client supplied `X-Checksum` and it differs from the sha256 the server computed |
| 413 | `FILE_TOO_LARGE` | The upload exceeds the plan's `max_file_bytes` |

`VALIDATION_FAILED` covers the following cases this phase: out-of-range pagination parameters, a `sort`, `kind` or `status` outside its enum, an undecodable cursor, a `storageKey` that fails the regex, and an attempt to settle a generation record that already reached a terminal state.

### Canvases

**GET `/api/canvases?page=&size=&q=&sort=`**

```json
{
  "items": [
    { "id": "8f...", "title": "Storyboard draft", "nodeCount": 12, "connectionCount": 8, "coverKey": "", "updatedAt": "..." }
  ],
  "total": 37,
  "page": 1,
  "size": 20
}
```

**There is no `data` in the response**, which is the entire reason the list page opens instantly. Page size depends only on the number of rows, never on how much content those canvases hold.

`connectionCount` cannot be dropped: a list card currently reads "N nodes · N connections", and shipping only `nodeCount` leaves half of that line with nothing to fill it.

`coverKey` needs one extra note: **the list page has no cover image at all today**, only a solid color block with a title and the stats line. The rule for deriving the value is defined below (the `storageKey` of the first image node), but rendering a cover on the card is new UI work rather than a port of something that already exists. Budget it as a new feature instead of assuming it falls out of the data layer rework for free.

**POST `/api/canvases`** takes `{ "title": "Untitled canvas", "data": { ... } }`, where `data` may be omitted for an empty canvas. Success returns 201:

```json
{ "id": "8f...", "title": "Untitled canvas", "revision": 1, "nodeCount": 0, "connectionCount": 0, "coverKey": "", "createdAt": "...", "updatedAt": "..." }
```

**GET `/api/canvases/{id}`** returns the full record:

```json
{
  "id": "8f...",
  "title": "Storyboard draft",
  "data": { "nodes": [], "connections": [], "viewport": { "x": 0, "y": 0, "k": 1 }, "chatSessions": [], "activeChatId": null, "backgroundMode": "lines", "showImageInfo": false },
  "revision": 12,
  "nodeCount": 12,
  "connectionCount": 8,
  "coverKey": "image:Ab3xY",
  "createdAt": "...",
  "updatedAt": "..."
}
```

Errors: `NOT_FOUND`.

**PUT `/api/canvases/{id}`** takes `{ "data": { ... }, "revision": 12 }` and replaces `data` wholesale. Success returns 200 with `{ "revision": 13, "updatedAt": "..." }`.

`title` **is not editable through this endpoint**. Autosave fires a PUT every few seconds, and if it also carried the title, an editor still holding the old one would quietly revert a rename another device just made through `PATCH`. Renaming is an infrequent, lightweight action; routing it through `PATCH` is both safer and far cheaper on bandwidth.

`nodeCount`, `connectionCount` and `coverKey` are derived server-side from the lengths of `data.nodes` and `data.connections` (the node count, the connection count, and the `storageKey` of the first image node); values sent by the client are ignored. Letting the client report them lets the list page show numbers that disagree with the actual content, and avoiding a parse of `data` is the whole reason those three columns exist.

On conflict, 409:

```json
{ "error": { "code": "REVISION_CONFLICT", "message": "This canvas was modified on another device", "revision": 15 } }
```

**PATCH `/api/canvases/{id}`** takes `{ "title": "New title" }` and touches metadata only. Success returns 200 with `{ "id": "...", "title": "...", "updatedAt": "..." }`.

**This endpoint does not bump `revision`**, since it never touches `data`. Renaming a canvas must not invalidate an edit in progress on another device.

**DELETE `/api/canvases/{id}`** soft-deletes and returns 204, and returns 204 again on repeat calls.

Deleting a canvas **does not cascade to the media it references**, because the same `storage_key` may also be referenced by an asset or a generation record. Reclamation is designed in phase 3 alongside usage accounting.

### Assets

**GET `/api/assets?page=&size=&kind=&q=&tag=`**

`kind` is one of `text`, `image` or `video` and is unfiltered when omitted. `q` matches exactly two places: the `title` column and `data->>'content'`. `tag` may be repeated, multiple tags mean "contains all of them", implemented as `tags @> ARRAY[...]` so the GIN index applies.

The scope of `q` must be pinned to those two columns rather than taking the shortcut of `data::text ILIKE`. `data` is jsonb, and only text assets carry prose in it — the `TextAsset.data` defined at `web/src/stores/use-asset-store.ts:10` is exactly `{ content: string }`. Image and video assets hold not one word of prose in `data`, only `storageKey`, `mimeType` and dimensions. Casting the whole column to text means searching "png" drags out every PNG asset and pasting a fragment of a `storageKey` finds something too, which is not what search is supposed to do.

One thing to record here: `ILIKE '%keyword%'` has a wildcard on both ends, so no B-tree index applies and both columns are scanned sequentially. Per-user asset counts this phase are in the low hundreds, where a sequential scan costs nothing, so no extra index is added yet. Once a single user holds tens of thousands of assets and search starts to drag, install the pg_trgm extension and add GIN indexes on `title` and `(data->>'content')`; the endpoint does not change at that point, only the indexes.

The response shape matches the canvas list, but `items` holds **complete asset objects**:

```json
{
  "items": [
    { "id": "a1...", "kind": "image", "title": "Reference", "tags": ["draft", "character"], "data": { "storageKey": "image:Ab3xY", "width": 1024, "height": 1024, "bytes": 812345, "mimeType": "image/png", "source": "Added manually", "note": "", "metadata": {} }, "storageKey": "image:Ab3xY", "bytes": 812345, "createdAt": "...", "updatedAt": "..." }
  ],
  "tags": ["draft", "character", "background"],
  "total": 128, "page": 1, "size": 20
}
```

Assets are not split into summaries the way canvases are, because their `data` holds only a few hundred bytes of dimensions, format and `storageKey` — the image itself lives behind the media endpoints. Designing a separate summary shape for that would be complexity with no payoff.

The top-level `tags` is **the user's complete tag set**, used to populate the tag selector in the filter bar. It is returned only when `page=1` and omitted on later pages, so the frontend simply keeps the set it got from the first page. Facets are the decision here rather than a separate `GET /api/assets/tags`: the tag selector and the list always appear together, so splitting them into two endpoints means one extra request every time the assets page opens. The project also already has the pattern — `web/src/components/prompts/use-prompt-list.ts:25` builds its candidate list from `tags` in the first-page response, and copying that needs no new loading state at all.

A server-side `assets` row cannot hold today's frontend `Asset` object, so the two sides have to be lined up field by field before anyone starts. The `AssetBase` defined at `web/src/stores/use-asset-store.ts:9-26` carries `coverUrl`, `source`, `note` and `metadata`, `ImageAsset.data` has a required `dataUrl` and `VideoAsset.data` a required `url` — none of which appear in the response above. Here is where each of them goes:

| Frontend field | Server destination | Notes |
| --- | --- | --- |
| `id` | `assets.id` | Generated by `nanoid()` on the client today; becomes a server-issued uuid |
| `kind` | `assets.kind` | One to one, same enum |
| `title` | `assets.title` | One to one |
| `tags` | `assets.tags` | One to one, stored as `text[]` |
| `createdAt`, `updatedAt` | `assets.created_at`, `assets.updated_at` | Server-generated; ignored if sent in the request body |
| `data.content` (text assets) | `data.content` | The prose body, and the key `q` searches |
| `data.storageKey` | `assets.storage_key` and `data.storageKey` | The column serves ownership checks and deletion; the copy in `data` lets the frontend build the URL directly |
| `data.width`, `data.height`, `data.mimeType` | Same keys inside `data` | Metadata kept as is |
| `data.bytes` | `assets.bytes` and `data.bytes` | Also stored as a column because phase 3 usage accounting sums it |
| `data.dataUrl` (images) | **Not stored** | Replaced by `/api/media/{storageKey}` |
| `data.url` (videos) | **Not stored** | Same |
| `coverUrl` | **Not stored** | Also derived from `storageKey` as `/api/media/{storageKey}` |
| `source` | `data.source` | Kept, under the same key inside `data` |
| `note` | `data.note` | Kept, under the same key inside `data` |
| `metadata` | `data.metadata` | Kept wholesale; the server never parses it |

The three "not stored" fields are the crux of this rework. `dataUrl`, `url` and `coverUrl` currently hold blob URLs or base64, artifacts of the local-storage era: the frontend pulls a Blob out of IndexedDB, calls `URL.createObjectURL` and writes the address back into the object. Once the media endpoints exist those addresses are fully determined by `storageKey`, so persisting them is both redundant and guaranteed to rot — a blob URL points at nothing outside the page that created it. The frontend `Asset` type changes accordingly: all three fields are removed, render sites build `/api/media/{storageKey}` inline, `data.storageKey` goes from optional to required, and the `asset.coverUrl || asset.data.dataUrl` fallback at `web/src/pages/assets/index.tsx:404` disappears with them.

`source`, `note` and `metadata` go into `data` instead of getting their own columns because they are only ever displayed and never filtered or sorted on. Giving a column to a field that surfaces once in a detail panel wastes the column, the index and every future migration that has to carry it.

**POST `/api/assets`** takes the complete object minus `id` and timestamps, returning 201 with the created record.

**GET `/api/assets/{id}`** returns one record; errors with `NOT_FOUND`.

**PATCH `/api/assets/{id}`** accepts any subset of `title`, `tags`, `data`, `storageKey` and `bytes`, returning 200 with the updated object. There is no optimistic lock; the later write wins.

**DELETE `/api/assets/{id}`** soft-deletes and returns 204.

### Generations

**GET `/api/generations?kind=&status=&cursor=&size=`**

| Parameter | Convention |
| --- | --- |
| `kind` | `image` or `video`, unfiltered when omitted, `VALIDATION_FAILED` outside the enum |
| `status` | `pending`, `success` or `failed`, unfiltered when omitted, `VALIDATION_FAILED` outside the enum |
| `cursor` | The `nextCursor` from the previous response; starts at the newest record when omitted |
| `size` | Defaults to 20, capped at 100; beyond that returns `VALIDATION_FAILED` |

Ordered by `(created_at desc, id desc)`. `cursor` is `base64url(RFC3339Nano created_at + "|" + id)`, opaque to the client, and returns `VALIDATION_FAILED` when it cannot be decoded.

```json
{
  "items": [
    { "id": "g1...", "kind": "image", "status": "success", "prompt": "...", "model": "gpt-image-1", "config": { ... }, "result": { "images": [ { "storageKey": "image:Ab3xY", "width": 1024, "height": 1024 } ] }, "durationMs": 8421, "createdAt": "..." }
  ],
  "nextCursor": "eyJ0..."
}
```

`nextCursor` is `null` when there is no further page.

**`status=pending` is the one value that is not paginated.** It returns every pending record the user has in a single response with `nextCursor` always `null`, subject to a safety cap of 100 rows. Resuming polling after a reload on the video page requires every record still being generated, and by creation time those can sit on any page at all; making the caller page through looking for them writes a guaranteed bug into the endpoint. The cap is 100 because pending is a transient state — a normal account never has more than a handful of videos in flight, and if 100 have piled up something is stuck, at which point truncating is the right answer. Any other `status` value, or none at all, still uses regular cursor pagination.

**No `total` is returned here**, and pagination is not page-based. Generation history is a continuously appended stream: with offset pagination, new records inserted at the head cause duplicates and gaps while the user pages, and `COUNT(*)` on an append-only table gets linearly slower while infinite scroll never needed a total anyway. Canvases and assets are collections rather than streams — the list stays stable while a user pages through it, so offset pagination is fine and buys a total count and jump-to-page.

**POST `/api/generations`** takes `{ "kind": "image", "status": "success", "prompt": "...", "model": "...", "config": { ... }, "result": { ... }, "durationMs": 8421 }` and returns 201 with the created record.

The `status` enum is exactly `pending`, `success` and `failed`, validated against that allowlist on both write and query. `pending` means the task was submitted and the result has not come back; `success` means the artifacts exist and are written into `result`; `failed` means the task ended and the reason is in `result`. Images generate synchronously, so the outcome is already known when the request returns and the record lands as `success` or `failed` with no `pending` stage. Videos are asynchronous, so a record lands as `pending` the moment the task is submitted — that is the only reason a reload can find it again through `status=pending` and resume polling — and settles into `success` or `failed` once polling reaches a terminal state. The frontend already uses these three values at `web/src/pages/video/index.tsx:40`; the server adopts the same enum so neither side has to translate.

**PATCH `/api/generations/{id}`** exists solely for that settling write. It accepts only `{ "status": "success" | "failed", "result": { ... }, "durationMs": 8421 }` and returns 200 with the updated record.

**GET `/api/generations/{id}`** returns one record; errors with `NOT_FOUND`.

**DELETE `/api/generations/{id}`** soft-deletes and returns 204.

That `PATCH` has to stay narrow: the server only allows it while the record's current `status` is `pending`, returns `VALIDATION_FAILED` for anything already in a terminal state, and never accepts changes to `kind`, `prompt`, `model` or `config`. A generation record is a historical fact once written, and the only part with any reason to change is a result that has not settled yet. Without this narrow opening, a video record could only be deleted and recreated, changing its `id` and `createdAt` and making it jump position in the history list.

### Media Files

`storageKey` appears in the path and must be validated strictly, with a regex aligned to the frontend `storageKeyPattern` and a tightened character set:

```txt
^(image|video|audio|file|video-reference|audio-reference):[A-Za-z0-9_-]{1,64}$
```

Anything else returns 400. **The `storageKey` must never be concatenated into a file path.** The server reassembles the on-disk path as `{MEDIA_ROOT}/{userID}/{prefix}/{id}`, where `prefix` is the segment before the colon and `id` the segment after it. The `userID` prefix naturally isolates users and eliminates path traversal.

| Method | Path | Notes |
| --- | --- | --- |
| HEAD | `/api/media/{storageKey}` | 200 when present with `Content-Length`, `Content-Type` and `X-Checksum` headers; 404 otherwise |
| GET | `/api/media/{storageKey}` | Streams the binary with `Content-Type`, an `ETag` derived from the checksum and `Cache-Control: private, max-age=31536000, immutable`; **must be usable directly as an `<img src>`** |
| PUT | `/api/media/{storageKey}` | Binary body, `Content-Type` required, `X-Checksum` optional; 201 with `{ storageKey, bytes, checksum, mimeType }` |
| DELETE | `/api/media/{storageKey}` | Deletes record and object, returns 204; also 204 when absent |

Upload errors: 403 `EMAIL_NOT_VERIFIED`, 409 `CHECKSUM_MISMATCH`, 413 `FILE_TOO_LARGE`.

The server **always computes sha256 itself** and never trusts the client-provided value; `X-Checksum` serves only as a cross-check, and a mismatch writes neither a row nor a file.

Repeating a PUT for the same `storageKey` means overwrite: the unique `(user_id, storage_key)` constraint makes `media_files` update the existing row rather than add one. This is what makes retrying an interrupted upload safe.

#### GET Must Be a Directly Referenceable URL

This constraint decides how much frontend code disappears, so it gets its own note. `GET /api/media/{storageKey}` has to be an ordinary URL the browser can request on its own, so the frontend writes `<img src="/api/media/image:Ab3xY">` and the image shows up — **not a Blob download turned into an ObjectURL**.

Today `image-storage.ts` and `file-storage.ts` each hold a module-level `storageKey → ObjectURL` Map and resolve every image in bulk when a canvas opens. Nothing ever evicts those Maps, so memory grows monotonically as the user moves between canvases. With direct URLs the browser's HTTP cache takes over, and both Maps, the async bulk hydration around them and the leak they cause all disappear.

There is one conflict to resolve first. Phase 1 keeps the access token in memory only and puts the refresh token in the `ic_refresh` cookie scoped to `Path=/api/auth`, and a request issued by `<img src>` can reach neither. The fix is to **issue an additional read-only media cookie on login and on refresh**, named `ic_media`, with `HttpOnly; Secure; SameSite=Lax; Path=/api/media`, where `Secure` is driven by the `COOKIE_SECURE` environment variable exactly as in phase 1 so local HTTP debugging still works. Its authority is the bare minimum: it reads the current user's own media, calls no business endpoint and cannot touch credentials. Even if it leaks, the damage is far smaller than a leaked access token, which hands over every third-party API key the user owns.

The value of `ic_media` is a separately issued short-lived JWT whose claims carry only `sub` (the user id) and `scope: "media"`. It lives for 30 days, the same cycle as the refresh token, and rotates together with it: whenever the refresh endpoint issues a new `ic_refresh` it must reissue `ic_media` as well. Skip that and a user who stays signed in past 30 days watches every image in their canvases turn into a broken thumbnail at once while the access token still works perfectly, which is a miserable thing to debug.

Server-side validation is three steps: verify the signature, confirm `scope` equals `media`, then take `sub` as the user id and check ownership in `media_files`. Any step that fails returns 401 — do not soften that to a placeholder image or wave it through because "it's only a picture". The `scope` check in particular cannot be skipped: without it an access token presented as a media cookie would also pass, which erases the boundary between the two credentials.

The auth middleware needs a rule written specifically for `/api/media/*`: `GET` and `HEAD` accept either the `ic_media` cookie or an `Authorization: Bearer` header, whichever is present, with Bearer taking precedence when both are; `PUT` and `DELETE` accept Bearer only and never the cookie. Accepting the cookie on writes turns a credential built for `<img src>` into a write endpoint reachable by cross-site requests, and `SameSite=Lax` only covers part of that surface, so it should not be the only line of defense.

Logging out must clear `ic_media` along with everything else. Phase 1's logout only clears `ic_refresh`; with a second cookie in play, logout has to emit two immediately expired cookies, each carrying its original `Path` (`/api/auth` for `ic_refresh`, `/api/media` for `ic_media`) — the browser will not overwrite the original if the path differs. Miss this and someone on a shared computer can keep pulling the previous user's images one by one with the leftover cookie.

Uploads still go through a normal request carrying an `Authorization` header. Do not take the shortcut of making `ic_media` a general session cookie, which would undo phase 1's token design.

### Unverified Email Cannot Upload

Apply this constraint only to `PUT /api/media/{storageKey}`, leaving canvas, asset and generation reads and writes unrestricted. Unverified users can still create canvases, write text assets and record generation history — they just cannot consume disk, which controls cost without making the account feel unusable.

The `EMAIL_NOT_VERIFIED` code reserved in phase 1 is first used here. On receiving it the frontend should guide the user to verify their email and offer a resend entry point, and **must not fail the whole save** — the canvas itself still gets persisted, only the referenced media is missing, and the message needs to name which files failed to upload.

| Path | Responsibility |

| `internal/crypto/crypto.go` | AES-GCM encryption and decryption, master key loading and length validation |
| `internal/storage/storage.go` | `Storage` interface definition |
| `internal/storage/local.go` | Local disk implementation handling path assembly, atomic writes and sha256 computation |

| `internal/handler/media.go` | Media HEAD, GET, PUT and DELETE, including `storageKey` validation, dual `ic_media` cookie / Bearer auth and the size check |

Keep the `Storage` interface minimal:

```go
type Storage interface {
    Put(ctx context.Context, path string, r io.Reader) (bytes int64, checksum string, err error)
    Get(ctx context.Context, path string) (io.ReadCloser, error)
    Delete(ctx context.Context, path string) error
    Stat(ctx context.Context, path string) (bytes int64, err error)
}
```

The local implementation writes to a temporary file and renames it, so an interrupted upload never leaves a partial file that a later request mistakes for a complete one. The `storageKey`-to-`objectPath` conversion happens exactly once, in `handler/media.go`; `Storage` receives an already-assembled safe path and knows nothing about key formats.

The four business handlers will inevitably repeat the same paging, sorting and soft-delete filtering code. Factor that into small shared helpers inside `internal/handler` rather than introducing a repository layer — every query this phase is a single-table operation, and another layer only lengthens the call chain.

### From Everything-in-Memory to On-Demand Loading

This is the core frontend change of the phase. The current situation:

- `web/src/stores/canvas/use-canvas-store.ts` uses zustand `persist` with a custom `PersistStorage` to write `projects: CanvasProject[]` into localforage as a whole, each project carrying its full `nodes`, `connections` and `chatSessions`.
- `web/src/stores/use-asset-store.ts` likewise persists the entire `assets: Asset[]`.
- `web/src/pages/image/index.tsx` and `web/src/pages/video/index.tsx` each create their own `image_generation_logs` / `video_generation_logs` localforage instance and `iterate` every record on mount before sorting.

All three share the same shape: opening a page means loading that domain's entire dataset into memory. After the rework:

**Drop `persist` from both stores**, deleting the custom `canvasStorage` and `assetStorage` `PersistStorage` implementations along with it. The server is authoritative, and localforage no longer persists business data.

**Keep the stores, but only for session-scoped in-memory state**: the canvas currently being edited, UI selection, save status. List data does not belong there — it is server state, and react-query owns it.

**The `hydrated` flag loses its meaning**, since it means "localforage finished reading". Everywhere it currently gates a loading state (the canvas list page and the canvas editor) switches to react-query's `isPending`.

**List and detail fetching, caching and invalidation all go through `@tanstack/react-query`**, which the project already depends on. Agreed query keys: `["canvases", params]`, `["canvas", id]`, `["assets", params]`, `["generations", kind]`. Invalidate the matching prefix after a successful write instead of hand-splicing the local list array. Do not build `loading` and `error` `useState` pairs driven by a `useEffect` fetch.

**The local media cache layer is deleted entirely; caching moves to the browser.** `web/src/services/image-storage.ts` and `file-storage.ts` currently store binaries in localforage and hand back blob URLs. That layer goes away along with both ObjectURL maps, and nodes render `<img src="/api/media/{storageKey}">` directly.

The obvious worry — "won't every canvas open re-download dozens of images?" — is answered by HTTP caching. Media is immutable: the content behind a given `storageKey` never changes, and a repeated PUT only happens when retrying an interrupted upload. So `GET /api/media/{storageKey}` can serve `Cache-Control: private, max-age=31536000, immutable` together with an `ETag`, and reopening the same canvas issues no request at all. This is less work than building a cache layer on IndexedDB and removes any need to worry about capacity limits, eviction policy or releasing ObjectURLs.

### Canvas List Page

`web/src/pages/canvas/index.tsx` becomes `useQuery(["canvases", { page, size, q, sort }], listCanvases)`, renders the summaries in `items`, and drives an Ant Design `Pagination` from the `total` in the response.

`CanvasProjectCard` in `web/src/components/canvas/canvas-project-card.tsx` currently takes a full `CanvasProject` and must take the summary type instead (`id`, `title`, `nodeCount`, `connectionCount`, `coverKey`, `updatedAt`). The "N nodes · N connections" line on the card (line 55) reads `project.nodes.length` and `project.connections.length` today and switches to the two count fields. The cover becomes a plain `<img src={"/api/media/" + coverKey}>`, keeping the existing solid color block when `coverKey` is empty.

The single-item export button on the card breaks. It hands the full `project` straight to `exportCanvasProjects` in `web/src/lib/canvas/canvas-export.ts`, and a summary has no `data`, so export has to fetch the detail with `GET /api/canvases/{id}` before packaging it. Bulk export on the list page needs the same treatment.

Add a search box and a sort selector to the header, both passed to the server as query parameters rather than filtering in the browser. Debounce the search box before firing a request.

The "delete all" button needs rethinking: it is implemented as `projects.map((project) => project.id)` over the full list, and after pagination the frontend simply does not hold every id. Either scope it to the current selection or drop the entry point.

The `mode=new` and `mode=recent` auto-entry paths change too: `new` calls `createCanvas` and navigates to the returned id, while `recent` takes the first row of the first page and falls back to creating one when the list is empty. The guard that depended on `hydrated` becomes a check on the query's `isSuccess`; the `autoOpenRef` run-once guard stays.

Zip import becomes two steps: `PUT /api/media/{storageKey}` for each binary in the archive first, then `POST /api/canvases`. The order cannot be reversed, or the canvas references images that have not been uploaded and opens as a wall of broken thumbnails on another device.

### Canvas Editor and Debounced Autosave

`web/src/pages/canvas/project.tsx` calls `useQuery(["canvas", id], getCanvas)` on entry and pushes the returned `data` into the page-local `nodes`, `connections` and `chatSessions` state, keeping `revision` in a ref.

`hydrateCanvasImages` and `hydrateAssistantImages` **go from async bulk resolution to building a string synchronously**. Their job today is to look each `storageKey` up in IndexedDB, pull out the Blob, create an ObjectURL and write it into `metadata.content`; with direct URLs that collapses into one line, `content = "/api/media/" + storageKey`, with no `Promise.all` and no `await` left. The async wait around `restore()` in `project.tsx` goes away with them.

**The loading state must distinguish three cases, and this is the easiest place to plant a bug.** The current logic has two states: once `hydrated` finishes, an `openProject` that finds nothing calls `navigate("/canvas", { replace: true })` and sends the user back to the list. Reading from local disk almost never fails, so "not found" really does mean "does not exist". Over the network, `isPending`, a 404 and a network error are three different things — **carrying the two-state logic over means a user who loses connectivity is treated as "this canvas does not exist", bounced out of the editor and stripped of unsaved edits on the way**. Only an explicit 404 may navigate away; a network error has to stay on the page and offer a retry.

Today two effects call `updateProject` as state changes — one for structure, one debouncing the viewport by 500 ms — and the store then debounces a localforage write by another 400 ms. Collapse all three into a single save pipeline:

1. Any state change that alters `data` (`nodes`, `connections`, `chatSessions`, `activeChatId`, `backgroundMode`, `showImageInfo`, `viewport`) marks the canvas dirty.
2. Two seconds of idle triggers `PUT /api/canvases/{id}`. If the user never pauses, force a save at least every 30 seconds so a long stretch of dragging is not left entirely unsaved.
3. **Serialize the requests**: never send a PUT while one is in flight, and fire immediately afterwards if the canvas went dirty again in the meantime. Concurrent PUTs manufacture revision conflicts against themselves.
4. Overwrite the local `revision` ref with the value from each successful response.
5. On unmount, route change and `visibilitychange` to hidden, flush a save if still dirty.
6. Show save status in the top bar: saving, saved, or failed with a retry. Failures must be visible and manually retryable, never silently dropped.

When switching canvases, make sure a pending save targets the right id — canvas A's content must never be PUT to canvas B. Per the project's existing convention, every timer and listener here is cleared in the effect's cleanup.

**Node resizing needs write suppression before any of this is wired up.** Dragging a node sets `historyPausedRef` to true in `handleNodeMouseDown`, so the entire drag writes to the store zero times and commits once on release. **Resizing has no such guard** — `handleResizeMove` calls `setNodes` on every mousemove, with neither rAF throttling nor a pause flag. That costs nothing today, because a store write is one array `map`. Once debounced saving is attached, the two-second debounce does hold the network requests back, but every mousemove still rebuilds the whole `nodes` array and re-renders the entire page, and the resize turns visibly janky. Set the pause flag when a resize starts, exactly as dragging does, and commit once when it ends.

Text node content, the prompt input and the config input have the same problem: all three **write state on every keystroke** today. Debounce those writes at the exit of the save pipeline instead of adding a separate debounce inside each handler.

Media upload is independent of canvas saving: upload with `PUT /api/media/{storageKey}` the moment generation or import produces a new image, rather than batching at save time. Canvas `data` stores only `storageKey`, so writing a reference before its bytes land produces a canvas that is guaranteed to render broken.

Renaming goes through `PATCH`, stays out of the autosave pipeline and does not change the local `revision`.

### Handling Revision Conflicts

A 409 `REVISION_CONFLICT` from PUT means another device or another tab saved in the meantime. **Do not silently overwrite, and do not silently discard local edits.**

Open a modal titled along the lines of "This canvas was modified on another device", with two options:

- **Overwrite with my version**: re-send the PUT using `error.revision` as the new base.
- **Reload**: discard unsaved local changes and re-fetch the detail.

Spell out the consequence in each button (overwriting loses the other side's changes, reloading loses your own unsaved ones) rather than offering a bare "OK / Cancel". Pause autosave while the modal is open, otherwise it reappears every two seconds.

No automatic merging. A canvas is a graph with coordinates and connections, and an automatic merge usually produces a canvas neither side recognizes. Let the user choose.

### Cursor Pagination for Generations

`web/src/pages/image/index.tsx` and `web/src/pages/video/index.tsx` currently read every local record on mount and sort it. Replace that with `useInfiniteQuery`, taking `nextCursor` from the response in `getNextPageParam`, and have `LogPanel` load the next page when scrolled to the bottom.

The `Tag` at the top of `LogPanel` showing `logs.length` becomes "N loaded" or goes away entirely, since the list endpoint no longer returns a total. For the same reason, "select all" now means "select everything loaded so far" and its label should say so.

After a generation finishes, call `createGeneration` and then `invalidateQueries(["generations", kind])` so the new record appears at the top. Upload the artifacts to media first and write the record second; the order matters.

Deleting the selection becomes one `deleteGeneration` per record. Remove the `LOG_STORE_KEY` constants and the `localforage.createInstance` calls from both pages.

The video page has one extra problem. `resumePendingLogs` currently picks the records whose `status` is pending out of the fully loaded history list and resumes polling them. After pagination the first page need not contain any of those records, so the whole recovery path fails silently and a video still being generated never updates its status once the user reloads. It switches to a single `GET /api/generations?kind=video&status=pending` on mount — that query is unpaginated and returns everything at once, and it is a separate query from the infinite-scroll history list, so the two must not share a key.

The write order around it needs straightening out too. On submitting a video task, call `createGeneration` first to persist a `status: "pending"` record and keep its `id`; when polling ends, upload the artifacts to media, then call `patchGeneration` to settle the record into `success` or `failed`, then `invalidateQueries(["generations", "video"])`. Do not wait for success before writing the record at all — that leaves nothing to recover from after a mid-generation reload, and nothing for `status=pending` to return.

### Server-Side Filtering on the Assets Page

`web/src/pages/assets/index.tsx` currently reads every asset into memory and then runs three layers of `useMemo` for keyword filtering, kind filtering and array slicing. All three become query parameters: `q`, `kind`, `tag`, `page` and `size` go straight to `GET /api/assets`, and `Pagination` is driven by the `total` in the response. Debounce keyword input by roughly 300 ms before requesting.

Tag filtering is new capability. The page currently offers only keyword and kind, so once the server supports `tag` the filter bar can gain a tag selector where multiple selections mean "contains all".

The candidate list behind that selector needs a data source of its own. The canvas side panel derives it live from every asset with `Array.from(new Set(assets.flatMap(a => a.tags)))`, and once the server paginates there is no full dataset left to derive it from. This phase settles on **facets** rather than a separate `GET /api/assets/tags`: the first page of `GET /api/assets` carries the user's full `tags` set (defined in the assets section above), the frontend takes it from that first response and reuses it while paging. All four entry points below share that one candidate list.

Note also that **the same in-memory filtering logic exists in four copies**, not just on the assets page: `CanvasAssetsTab` in `canvas-side-panel.tsx` (which additionally groups by kind and has no pagination whatsoever), `MyAssetsTab` in `asset-picker-modal.tsx`, and `assets_list` in `agent-site-tools.ts`. Reworking only the assets page leaves three call sites still reading the full dataset, and they break outright the moment the store drops its full array. All four need the change, and the search boxes in the three UI entry points all need the same 300 ms debounce.

Delete `cleanupImages` from `use-asset-store.ts` entirely, together with both cleanup functions it calls: `cleanupUnusedImages` in `web/src/services/image-storage.ts` and `cleanupUnusedMedia` at `web/src/services/file-storage.ts:52` (`use-asset-store.ts:91-92` invokes both in one go). Both implementations depend on holding every asset and every canvas at once to decide which files are unreferenced, and that premise disappears with on-demand loading — scanning the local store for "unreferenced" files while holding a single page of data deletes exactly the files other pages are still using.

**This is the only change in this phase that can destroy user data outright, and both functions must go — deleting just one is not enough.** They have two call sites, and removing the store action makes both fail to compile, which conveniently doubles as the checklist: `cleanupAssetImages` at `web/src/pages/canvas/project.tsx:188` (called when deleting the current project from inside a canvas) and `cleanupImages` at `web/src/components/canvas/canvas-delete-projects-dialog.tsx:14` (called when confirming deletion on the list page). Both have to be handled in the same batch of changes as the deletion itself; do not leave an intermediate state where local cleanup still runs against data that now lives on the server.

### Wiring Credentials and the Config Page

Remove the `webdav` field and `WebdavSyncConfig` type from `use-config-store`. AI configuration is fetched from `/api/credentials` after login and written back when the user edits it, with localStorage acting only as an offline cache. Debounce the write-back; firing a request on every keystroke in the config page is unacceptable.

Delete the WebDAV block in `web/src/pages/config/` outright. **Do not replace it with a "cloud sync" block.** With resources there is no such action as "sync once now" — every edit lands on the server automatically, save status lives in the canvas editor's top bar, and the config page needs no sync entry point at all. The `AppSyncProgress` callback the old plan intended to reuse goes away with `app-sync.ts`.

## Data Migration

There is no migration. The project has not launched, there is no production data to preserve, and the backend only needs `AutoMigrate` to create the tables.

Existing IndexedDB data in users' browsers — canvases, assets, generation history and media binaries — **is not uploaded automatically**. An automatic upload would need one-shot transfer logic that also handles partial failure, duplicate import and `storageKey` collisions, and all of that becomes dead code the moment it runs once. Users who want to keep older content can export a zip with the existing canvas export feature and import it after logging in.

Say this plainly in the release notes so nobody upgrades and concludes their data was lost.

## Acceptance Checklist

Credential custody:

- Configure an AI channel on device A and save; logging in on device B shows the configuration automatically and generation works.
- Inspecting the database directly, `user_credentials.payload` is unreadable binary with no plaintext API key discoverable.
- The `nonce` differs on every save.
- A misconfigured or wrong-length master key makes the backend fail to start with a clear error.

Canvas resources:

- Paging, keyword search and sorting by update time or title all happen on the server, and the browser network panel shows no request that pulls every canvas at once.
- The list response contains no `data`, and page size is independent of how much content the canvases hold.
- Both numbers in the "N nodes · N connections" line on a card are populated and correct, matching what the canvas actually contains when opened; adding a connection inside the canvas and returning to the list updates the connection count.
- Two seconds after the user stops editing, the canvas autosaves and the top bar reads "saved"; while dragging nodes continuously, a save still happens at least every 30 seconds.
- Editing while offline surfaces a clear failure with a manual retry, and the retry succeeds once the network returns.
- **Opening a canvas while offline leaves the page where it is with a retry on screen, rather than treating it as "this canvas does not exist" and bouncing back to the list.**
- Resizing a node keeps the UI smooth and fires exactly one save request on release; typing continuously likewise sends one request only after the user stops.
- With the same canvas open on two devices, saving on A and then on B gives B a 409 and a choice dialog; choosing "overwrite with mine" shows B's content on A after a reload, and choosing "reload" shows A's content on B with local changes discarded.
- Renaming a canvas does not cause a 409 for an edit in progress on another device.
- A deleted canvas disappears from the list, `GET /api/canvases/{id}` returns 404, and a repeat DELETE still returns 204.

Assets and generations:

- Keyword, kind and tag filters on the assets page all hit the server, and changing a filter visibly issues a new request.
- The first page of the asset list carries the full `tags` set and it drives the tag selector's options; page two does not repeat `tags` in its response, and the selector's options do not go empty as a result.
- Searching a keyword that appears only in the body of a text asset finds that asset; searching a fragment of a `storageKey`, or `png`, does not surface image assets.
- With thousands of assets, first paint on the list page is independent of the total.
- Generation history loads the next page on scroll to the bottom, and stops requesting without duplicate loads once `nextCursor` is `null`.
- A newly generated record appears at the top after the list refreshes, with no duplicate entries.
- Deleting several generation records and continuing to page produces neither gaps nor repeats.
- Reloading the page mid-generation still resumes polling for a pending video record and updates its status on completion, even when that record is no longer on the first page.
- With enough history to push the pending record past the third page, `GET /api/generations?kind=video&status=pending` still returns it in one shot and the response's `nextCursor` is `null`.
- The canvas side panel, the asset picker modal and the agent's `assets_list` all filter on the server, with no code left depending on a full in-memory array.

Media and security:

- An unverified account can create canvases and write text assets, but `PUT /api/media/{storageKey}` returns `EMAIL_NOT_VERIFIED` while the canvas itself still saves successfully.
- Uploading a file larger than the plan's `max_file_bytes` is rejected with `FILE_TOO_LARGE`.
- A client-supplied `X-Checksum` that disagrees with the server's returns `CHECKSUM_MISMATCH` and leaves no partial file on disk.
- Retrying an interrupted upload with the same `storageKey` leaves exactly one row in `media_files`.
- Deleting or corrupting the `ic_media` cookie by hand and then calling `GET /api/media/{storageKey}` returns 401, and forging the cookie with a JWT whose `scope` is not `media` returns 401 as well.
- Requesting the same media URL with only an `Authorization: Bearer` header and no `ic_media` cookie serves the file normally; conversely, `PUT` or `DELETE` with only the cookie returns 401.
- After logout both `ic_refresh` and `ic_media` are gone from the browser, and a media request at that point returns 401.
- Fetching a `storageKey` belonging to another user returns 404 rather than their file.
- A `storageKey` containing `../` or malformed colons returns 400.
- Using another account's canvas id for GET, PUT or DELETE returns 404 in every case, never 403.

Data layer and legacy removal:

- Neither store uses `persist`, and after logout the browser's IndexedDB holds no canvas, asset or generation data — only the media cache.
- Loading and error states for lists and details come from react-query, with no hand-written `loading` / `error` useState in the pages.
- Images in a canvas load straight from `<img src="/api/media/...">`, no address starting with `blob:` can be found in the DOM, and the ObjectURL cache Maps in `image-storage.ts` and `file-storage.ts` are gone.
- Browser memory falls back down after switching between a dozen or so image-heavy canvases repeatedly, instead of growing monotonically.
- Searching for `webdav` and `app-sync` finds nothing and `bun run typecheck` passes.
- Searching for `cleanupImages`, `cleanupUnusedImages` and `cleanupUnusedMedia` finds nothing, both call sites are cleaned up, and `bun run typecheck` passes.
- The config page shows no WebDAV form, no manual sync entry point and no leftover blank areas.
- The "local storage" panel on the config page no longer lists empty `image_generation_logs` and `video_generation_logs` entries, and the remaining entries match what is actually stored.
