失败分类（按「产品缺陷 / 用例或注册表漂移 / 环境或数据问题」三桶）：

- **F1（GR-SM-01，labels 形状）— 环境或数据问题（构建未同步），非产品缺陷。** Q2 修复已存在于工作区源码（`server/internal/canvas/feedback.go`、`server/internal/admin/admin_feedback.go`，mtime 20:15），但运行中 server 于 19:48 由 `go run` 构建，早于修改，故实测纯点赞仍返回 `labels:[""]`（admin 生成反馈列表同口径）。处置：重建并重启 server 后复测 GR-SM-01（及受同口径影响的 GR-BD-03 labels 展示），预期即可转绿；不入缺陷池。
- **F2（FB-API-06，support 角色权限越界）— 产品缺陷，走缺陷链。** 现象：support 角色用户 `GET /api/admin/users` → 200（预期 403 FORBIDDEN），响应含全平台用户邮箱、会员与点数信息；`/api/admin/roles`、`/api/admin/audit-logs`、`/api/admin/settings` 同样 200，即客服实际拥有整个 admin 面。根因（复现级定位）：`authz/sync.go` 把 support 作为系统角色播种并强制 `is_system=true`（L83–94），而 `middleware/authz.go` LoadAdminAccess 对 `IsSystem` 角色授予 `authz.Keys()` 全量权限，压过 `role_permissions` 中 feedback.read/write 的绑定——与 sync.go 自述「权限固定为反馈工单模块」自相矛盾。修复位置：产品代码（如 LoadAdminAccess 改按 `role_key==SystemRoleKey` 判定全量权限，或拆分「不可删除」与「全量权限」两个语义）。复现：以 role_key='support' 的账号登录，`curl -H "Authorization: Bearer <token>" http://127.0.0.1:8090/api/admin/users` → 200。
- **F4（FB-BD-05 step5，rating 非法值静默忽略）— 与修订口径不符的产品缺口。** 宣称的 Q4 修复在源码中不存在（`admin_feedback.go` L187 仍为「非 ±1 静默忽略」，且运行二进制同样不含）。实测 `?rating=0` → 200 未过滤。注意：按计划原口径该行为本属「通过」。需 supervisor 裁定：补实现后按修订口径复测，或撤销该修订口径并回写计划。在裁定前按修订口径记 fail。
- **F3（FB-BD-01 step6，`" 好 "` 期望 201）— 用例或注册表漂移，非缺陷。** 计划该步期望与自身矛盾：去空白后「好」仅 1 字，低于计划自己声明的 2 字下限（step1 对 1 字期望 400）。实现按「去空白后 2–1000 字」一致拒绝（400 + fields.content）。处置：修订用例（预期改 400，或输入改为去空白后 ≥2 字验证去空白计数语义），无需改代码。
