### 测试数据准备（执行前一次性完成）

1. **探活**：`curl -s {API}/healthz` 返回 2xx。
2. **自建账号（推荐注册 API 流程）**：对每个 `{U_*}` 执行 `POST {API}/api/v1/auth/register`（body `{"email","username","password"}`，邮箱用户名不得与已有重复）→ 201 后从 `/tmp/ic-acceptance/server.log` 末尾取 `MAIL_DRIVER=log` 打印的验证链接并访问（或按其 token 走验证接口）→ 登录取 token。备选：sqlite 向 `platform_users` 插入新行（列：`id` char36 uuid、`email`、`username`、`password_hash`、`status='active'`、`email_verified_at` 置当前时间）；bcrypt 哈希在 `server/` 目录下写临时 main 包调 `internal/auth.HashPassword(password string) (string, error)` 用 `go run` 打印，用完删除临时文件。
3. **support 任命**：`sqlite3 {DB} "UPDATE platform_users SET role_key='support' WHERE email='{U_SUP 邮箱}';"`（只改新建行，禁止改种子行）。环境未预置 support 账号，属造数缺口，见流程疑点 Q5。
4. **success 生成行造数**：为 `{U_GEN}`（2 行）、`{U_B}`（1 行）各插一条，并为 `{U_API}` 或 `{U_GEN}` 另插一条 `status='failed'` 行：
   ```sql
   INSERT INTO generations (id, user_id, kind, status, prompt, model, duration_ms, moderation_status, created_at)
   VALUES ('<uuid>', '<该账号 user id>', 'image', 'success', '测试提示词', 'test-model', 0, 'skipped', datetime('now'));
   ```
   备选：经 `{WEB}` 工作台走假上游 `127.0.0.1:8901` 真实生成（消耗点数、耗时不可控，仅在直插不可行时使用）。
5. **登录约束**：每个账号只调一次 `POST {API}/api/v1/auth/login`（body `{"account","password"}`）取 `accessToken`，全程复用；登录限流 20 次/10 分钟/IP，**禁止反复登录**。凭据由环境属主在会话外提供，不写入本文件与执行证据。

### 错误包络口径（断言统一参照）

- 业务错误响应体统一为 `{"error":{"code":"<UPPER_SNAKE>","message":"…","fields"?:{...}}}`；限流 429 额外带 `Retry-After` 响应头（正整数秒，随窗口剩余时间变化，断言只验证存在与格式，不断言具体值）。
- 归属/存在性错误一律 `404 NOT_FOUND`，不区分「不存在 / 他人资源 / 非成功记录」（防探测同口径）。

### 会话与执行顺序约束

- 无登出类用例，全部用例可在各自账号的共享会话中执行。
- **配额时序（硬约束）**：`{U_BD}` 的创建配额被 BD-01 + BD-02 恰好用满（10 次，含失败请求——限流中间件在参数校验之前计数），BD-01 必须先于 BD-02 执行，两用例须排在该账号所有创建类步骤的最后；重跑需等窗口过期或重建账号。`{U_RL}` 只服务 BD-03。`{U_UI}` 的创建类尝试仅限 UI-1（2 次成功 + 1 次失败）。
- E2E 顺序依赖：UI-2 依赖 UI-1 产生的工单；UI-4 依赖 UI-3 记录的 `{GEN_UI}`；UI-5 独立。

### 执行方式标注约定

- `curl`：按步骤给出的方法/路径/请求体直接执行；状态码用 `curl -s -o /dev/null -w "%{http_code}"` 或 `-i` 观察；响应体断言解析 JSON 字段。
- `sqlite3`：对 `{DB}` 只读查询核对行数与字段值；可插入新行，禁止删改已有行。
- `supervisor 浏览器执行`：由主 Agent 按「浏览器 UI 步骤脚本」节逐步执行并回填。

## 流程疑点

以下为规格/摘要未定义或实现口径两可的行为，编号提交评审裁定；用例侧不自行发明口径，仅按「可观察结果」记录。

1. **刷新后点赞/点踩高亮不回显**：`/image` 与 `/video` 页的点赞状态是组件本地 state，未用 `GET /api/v1/generations/:id/feedback` 回填；已反馈的结果卡在刷新后显示为未选中，此时「再点已选按钮撤销」的 UI 闭环只在同一会话内成立（刷新后点击会重新提交 upsert 覆盖而非撤销）。GET 接口本身可用（FB-API-04 覆盖）。需裁定：这是待修缺陷还是接受现状；若接受，UI 用例永久不把「刷新后保持高亮」当预期（当前 UI-4/UI-5 步骤 6 按此口径执行）。
2. **labels 空数组的序列化形状**：未选标签时（如纯点赞）payload 返回 `labels` 为 `[""]`（含一个空字符串的数组）而非 `[]`。admin 端 `filter(Boolean)` 后显示「—」不受影响，但 API 消费方会拿到非预期元素。需裁定是否应归一为 `[]`。
3. **超限标签静默丢弃而非报错**：labels 第 7 个起、单个超 20 字的实现是静默丢弃并 200（GR-BD-02 断言了该行为）。UI 预设只有 6 个标签不会触发，仅 API 直调可触发。需裁定：静默清洗是否符合「最多 6 个、单个 ≤20 字」的预期语义，还是应返回 400。
4. **admin 生成反馈列表 rating 参数非法时静默忽略**：`rating=0` 等非 ±1 值不过滤直接返回全量 200，与工单列表 `status`/`category` 非法值 400 的口径不一致（FB-BD-05 记录了这一差异）。需裁定是否统一为 400。
5. **support 角色账号环境未预置**：种子里只有普通用户与管理员，没有任何账号绑定 `support` 角色；测试需 sqlite 直改新建账号 `role_key='support'`（或经 admin 用户管理任命）。建议在测试环境准备脚本中固化 support 账号，避免每次手工造数；正式任命链路（admin 界面操作）可另补一条 UI 用例。
6. **重复关闭 409 的错误码复用校验码**：实现返回 `409 + code=VALIDATION_FAILED + message「工单已关闭」`（`errs.AddConflict`）。前端按 code 优先映射本地化文案时，用户可能看到通用校验文案而非「工单已关闭」；且 UI 正常路径下关闭按钮在 closed 后隐藏，普通用户难以触发。需裁定是否需要专门的冲突错误码。
7. **提交弹窗与后端长度口径不对称**：UI 提交弹窗只有 `maxLength=1000` 的上限约束，2 字下限无前端提示，1 字提交依赖后端 400 toast（UI-1 步骤 4 记录实际文案）。需裁定是否在前端补最小长度提示，避免消耗用户限流配额的无效提交。
