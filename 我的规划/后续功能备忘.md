# 后续功能备忘

本文档记录已经讨论、当前明确暂缓的功能。每项写清范围、前置依赖与决策状态，实施时从这里取需求，不再重新讨论一遍背景。

## 内容审核真实接入

- 目标：把 `MODERATION_PROVIDER` 从 `fake` 切到真实模型（NSFWJS + Detoxify）。
- 现状：Go 适配层与图片/上传/提示词链路已交付，sidecar 契约固定——NSFWJS `POST /classify {mimeType, data(base64)}` 返回 `predictions[]`，Detoxify `POST /classify {text}` 返回 `scores{}`。**视频链路有阻塞缺陷，见下**。
- 待定：三档方案二选一（A 完整 NSFWJS + Detoxify，B 文本换 ONNX 轻量模型，C 先只上图片审核）；需先确认服务器 CPU/内存资源。
- 附带项：api 容器加 `ffmpeg` 用于视频抽帧。
- 依赖：服务器部署完成。

### 开启审核之前必须先修（注意：`MODERATION_ENABLED=true` 就会触发，与 provider 是否真实无关）

> 触发条件是总开关而不是真实 provider：`ModerationService.Enabled()` 返回的是 `enabled && provider != nil`（`server/internal/service/moderation.go:69`），而 `MODERATION_ENABLED=true` 时即便 provider 仍是 `fake` 也会构造出 provider（`server/cmd/server/main.go:134-142`）。所以第 1 条在测试环境用 `fake` 打开审核的那一刻就会生效，不必等到切真实模型；第 2 条（视频不经隔离区）的代码路径同样自那时起生效，只是「原件丢失」的后果要等真的出现拒绝才显现。

1. **视频任务会永久卡在 `moderating`（阻塞级）**：`server/internal/service/aitask.go:139` 在审核开启时先把任务置为 `moderating`，但成功收敛（第 167 行）与 `failTask`（第 205 行）的更新条件都还是 `status = 'pending'`，此时库里已是 `moderating`，**匹配 0 行且 GORM 不报错**，事务照常提交。结果是生成记录 `success`、视频已落正式存储、点数已扣，而 `ai_tasks.status` 永远停在 `moderating`，`GET /api/ai/videos/tasks/{id}` 恒返回该状态；前端 `web/src/services/api/video.ts:87-94` 把非终态一律当 pending 且轮询无总超时，UI 上视频永远不会完成。被拒时同样卡住，且 `refundedMicros` 依 `task.Status == "failed"` 计算（第 320-325 行）会报成 0。24 小时后清理任务（`cleanupTerminal`，第 266-270 行）删行，查询变 404。
2. **视频产物不进隔离区**：`aitask.go:137-153` 直接在内存里抽帧送审，没有任何 `Quarantine().Put`；对比图片链路（`server/internal/handler/ai.go:381-429`）是「先隔离再送审」。后果是视频被拒后原件立即丢失，管理员复核即使改判也没有原件可释放（释放逻辑依赖 `record.QuarantineKey`），与第五期承诺的「隔离对象保留 24 小时供人工复核」不符。
3. **`MODERATION_PROVIDER` 缺省 `fake` 且启动无提示**：`server/internal/config/config.go:145` 默认 `fake`，`MODERATION_ENABLED=true` 时允许 `fake` 无条件通过（第 279-281 行），启动日志也不提示正在使用 fake。只开开关、忘切 provider，就是四类触发点全部「看着在审核、实际零拦截」——与 fail mode 要防的静默放行是同一类风险。建议启用审核时若 provider 仍为 `fake` 则启动告警（测试环境显式声明，正式环境拒绝启动）。
4. 两个次要项：`MODERATION_VIDEO_SAMPLE_FPS` 是死配置（`server/internal/service/video_moderation.go:20` 写死 1 fps，同处 `-frames:v 24` 使超过约 24 秒之后的画面完全不抽帧，长视频存在漏检窗口）；`quarantine.Stats` 的「字节数」用 `SUM(LENGTH(quarantine_key))` 统计（`server/internal/service/quarantine.go:150-153`），结果恒为「条数 × 约 38」，容量告警会失真。

## 验证码登录

- 目标：登录页增加邮箱验证码登录 tab（设计稿已有）。
- 方案：复用 `email_tokens` 表，新增 `purpose = login_code`；6 位码、10 分钟有效、一次性、最多 5 次尝试；限流 3 次/小时/邮箱、10 次/小时/IP。
- 前置改动（不是无依赖的纯新增）：`EmailToken` 目前只有 `token_hash` / `purpose` / `expires_at` / `used_at`，**没有尝试计数列**，「最多 5 次尝试」需要加列或另存计数；`Purpose` 的取值注释（`verify_email | reset_password`）也要一并扩。
- **实施时必须一并修掉的既有缺陷**：`server/internal/handler/auth.go` 的 Verify（第 476-495 行）与 Reset（第 547-575 行）都是「先读判断、后无条件 Update」，没有 `WHERE used_at IS NULL` 的条件更新，并发下同一令牌可以被消费两次——同一个包里的 refresh 轮换（第 332-348 行）已经是「条件更新 + 判 RowsAffected」的正确写法。验证码登录是**更短的凭据**（6 位数字、10 分钟），照抄现有非原子写法等于把这个洞放大，必须按 refresh 的原子模式实现。
- 顺带项（同一处改动）：发信限流目前 verify 与 forgot **共用**同一个邮箱桶与 IP 桶（`server/internal/handler/auth.go:61-63`、`server/cmd/server/main.go:232-245`），实际额度是两接口合计而不是文档写的各自独立；新增登录验证码短信/邮件时会挤占同一份额度，需要先决定是分桶还是接受合计。

## 社交登录（QQ / 微信）

- 决策：**不做**，只保留注册 + 邮箱验证。
- 原因：技术接入不难（OAuth2 授权码 + openid/unionid 绑定），门槛在资质——微信开放平台网站应用需要企业主体、认证费与已备案域名，QQ 互联同样要求备案域名；当前阶段不值得为此投入。
- 若未来重启：需先定 OAuth 用户是否视为邮箱已验证（影响上传与免费额度）以及同邮箱多登录方式的合并规则。

## 多产品共用 Admin

- 见[Admin 后台与多产品规划](Admin后台与多产品规划.md)，触发条件是第二个产品立项。
- **立项前必须先定的硬前置**：多产品能否共用一个 admin，取决于每个产品是否有一个实现了**同一套 `/api/admin/*` 契约**（相对各自 `apiBase` 的路径与响应形状一致）的后端。admin 前端只占两成工作量，八成在每个产品后端。纯静态站、或数据只存在浏览器里的产品接不进来，只能在产品切换器里做外链。
- **admin 不碰数据库**：改配置走「admin 前端 → 该产品后端 → 该产品自己的库」，admin 不持有也不需要任何数据库凭据。不同产品库不同这件事由此自然消解，不存在跨库操作。
- **跨域按「直接跨域」处理，不让 admin 域名反代各产品 API**：各产品接口留在自己域名下，session cookie 天然按 host 隔离，正好落实现有规划里的「每产品独立会话」；若改成同源反代，多个产品的 cookie 会挤在 `admin.youc.online` 一个 host 上，需要改 cookie 名或加路径前缀来防止串号。代价是**每个产品后端各实现一份 CORS 中间件**（精确 `Origin` + `Access-Control-Allow-Credentials` + 放行 `Authorization` 的 OPTIONS 预检，白名单走环境变量），后端若是不同语言，这份工作和契约一起重写。
- **接口差异分两层**：路径差异（如 `work/v1/api` 与 `blog/v1/api`）由注册表的 `apiBase` 吸收；**响应形状差异注册表解决不了**，只能统一契约，或在 admin 侧为每个产品写适配层（产品越多越厚，不推荐）。
- **模块按产品裁剪**：注册表用 `modules` 字段声明该产品支持哪些模块（如 blog 可能只要 `users` / `settings` / `audit`），菜单据此渲染，接口未实现的模块不出现。
- 立项时的第一步：定 blog / work 的后端技术栈，以及是否复用同一套管理契约——这个决定不做出，admin 拆了也接不上。
