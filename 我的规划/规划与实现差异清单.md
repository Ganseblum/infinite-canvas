# 规划与实现差异清单

本清单分三轮产出，编号连续不重叠：

- **第一轮（第 1-30 条）**：规划文档承诺 vs 实际代码实现的偏差。4 条并行只读调查线产出。
- **第二轮（第 31-82 条）**：规划文档**内部逻辑**、前后端**代码本身**、公开**技术文档**准确性、**安全边界**专项。6 条并行只读调查线产出。
- **第三轮（第 83 条起）**：换六个不同视角重审——架构决策、**对抗式证伪**、发布就绪度、端到端用户旅程、数据与运维、合规与隐私。

**验证状态**标注：

- **已复现**——主对话亲自核对过代码，行号与结论均已确认。**此标注只表示机制与行号经代码核对，不表示影响已量化。**
- **影响待评估**——机制成立，但可达性或影响面属推断，尚未验证（例如需要特定配置、真实环境或特定时序才触发）。
- **待复现**——调查线给出了 `文件:行号` 证据，但主对话未逐条复核，实施前请先确认。
- **经对抗式复核修正**——该条在第三轮被独立证伪线挑战过，表述或严重度已按证据调整。

第三轮的对抗式证伪未能推翻任何一条 P0，但修正了 8 条的表述/严重度（详见「第三轮」一节的说明）。

## P0 阻塞级

### 1. 注销冷静期不可撤销：用户申请注销后彻底登不进来【已复现】

- **文档**：《账号后端总规划》要求冷「申请注销后允许登录浏览和导出，7 天内可随时撤销」；《第三期》验收项「申请后…但能登录浏览和导出」「冷静期内撤销后账号恢复 active」。
- **代码**：`server/internal/handler/auth.go:272`（登录）与 `:327`（刷新）都是 `if user.Status != "active"` → 403 `ACCOUNT_DISABLED`。而 `server/internal/middleware/middleware.go:195` 的 `RequireActiveUser` **只拦 `disabled`**，明确放行 `pending_deletion`——证明设计意图就是让冷静期账号继续访问业务接口。
- **后果**：申请注销后 access token 最多 15 分钟失效，此后任何 401 触发的静默刷新都返回 403，前端 `web/src/services/api/client.ts:117-135` 对非 2xx 一律 `clearSession` → 跳登录页 → 登录也 403。`/api/me/deletion/cancel` 再也到不了，用户只能等 7 天后被匿名化。**误操作注销不可逆**。
- **测试盲区**：`server/internal/handler/billing_test.go:154-190` 的 `TestAccountDeletionLifecycle` 全程用固定 access token，不经过 refresh/login，测不出该缺陷。
- **建议**：登录与刷新改成只拦 `disabled`；补一条「申请注销 → refresh → login → cancel」的集成测试。

### 2. 冷静期只拦了下单，没拦生成【已复现】

- **文档**：《第一期》错误码表与《第三期》都写「注销冷静期内调用**生成或下单**」应被拦截。
- **代码**：`server/internal/middleware/middleware.go:204` 的注释自称「拦截注销冷静期内的写操作（生成、下单）」，但 `RequireNotPendingDeletion` 全仓只挂了一处——`server/cmd/server/main.go:347` 的 `POST /api/orders`。`main.go:316` 的 `/api/ai` 组只有 `Auth + active`，`handler/ai.go` 与 `service/quote.go` 内部也没有任何 status 判断。
- **后果**：冷静期账号在 access token 有效期内（≤15 分钟）仍可调生成接口并扣点，`/api/me/free-grant/claim` 也没拦。「导出不受限、生成受限」的语义被削平。
- **注意严重度与修复顺序（经对抗式复核修正）**：实际敞口是**申请注销后 ≤15 分钟**，不是整个 7 天——因为第 1 条会让刷新/登录都 403，token 一过期用户就进不来，也就无法再生成。**但这也意味着第 1 条与第 2 条必须同批修**：单独放行冷静期账号的登录与刷新，会把本条敞口从 15 分钟直接放大到 7 天。只修第 1 条不修第 2 条，等于把一个小窗口变成一个星期的窗口。
- **建议**：给 `/api/ai` 组补挂 `RequireNotPendingDeletion`（与 orders 一致），并同步检查 claim 入口；与第 1 条在同一次改动内完成。

### 3. 开启内容审核后，视频任务永久卡在 `moderating`【已复现】

- **代码**：`server/internal/service/aitask.go:139` 在审核开启时先把任务置为 `moderating`；但成功收敛（第 167 行）与 `failTask`（第 205 行）的更新条件都还是 `status = 'pending'`——此时库里已是 `moderating`，**匹配 0 行且 GORM 不报错**，事务照常提交。
- **后果**：生成记录 `success`、视频已落正式存储、点数已扣，但 `ai_tasks.status` 永远停在 `moderating`；`GET /api/ai/videos/tasks/{id}` 恒返回该状态，前端 `web/src/services/api/video.ts:87-94` 把非终态一律当 pending 且轮询无总超时 → **UI 上视频永远不会完成**。被拒时同样卡住，且 `refundedMicros` 依 `task.Status == "failed"` 计算（第 320-325 行）会报成 0。24 小时后 `cleanupTerminal`（第 266-270 行）删行，查询变 404。
- **触发条件**：`MODERATION_ENABLED=true` 即触发，**与 provider 是否真实无关**（`service/moderation.go:69` 的 `Enabled()` 只看开关与 provider 非空；`cmd/server/main.go:134-142` 在 fake 下同样构造 provider）。测试环境打开审核开关的那一刻就会命中。
- **建议**：收敛条件改为匹配 `pending` 或 `moderating`；或把状态跃迁与终态写入合并到一次条件更新里。

### 4. 免费额度不校验参数组合，也不按 `n` 计数【已复现】

- **文档**：《账号后端总规划》要求「额度只覆盖被锁定的最便宜参数组合：图片限 `n = 1` + 最小尺寸 + 默认质量；参数超出锁定组合时改走点数分支」。
- **代码**：`server/internal/service/quote.go:234` 的免费分支只看计费模式；`quote.go:389` 的 `FreeTrialFor(userID, catalogItem, capability)` 只判 `FreeTrialEligible` 与剩余次数，**根本不接收 `params` 与 `n`**；`handler/ai.go:1219-1239` 占用一次计数与 `n` 无关，而 `ai.go:213-227` 会把 `N: n` 原样发给上游。
- **后果**：任意参数组合、任意 `n`（种子模型 `n.max=4`，硬上限 15）都按 0 元报价，只消耗 1 次试用计数。按 `server/internal/db/seed_billing.go:53-80` 的价目，单次免费请求成本可达设计上限的约 13 倍，且随注册量线性放大——正是文档要压住的支出。
- **建议**：`FreeTrialFor` 接收并校验 `params`/`n`，命中锁定组合才走免费。

### 5. 免费生成资格不校验领取记录【已复现】

- **文档**：《第一期》要求「消费免费次数时以**已批准领取记录**和一次性用量计数共同判定」。
- **代码**：`service/quote.go:389-402` 无任何 claim 查询；全仓 `FreeGrantClaim` 只出现在 `handler/account.go:241-298`（写记录）与测试里，AI 链路从不读取。
- **后果**：无论领取是否成功（包括 `status=denied` 的风控拒绝记录），用户都直接拿到 3 图 + 1 视频的一次性免费额度。风控与 `FREE_GRANT_DAILY_BUDGET_MICROS` 只限制 claim 记录，不限制真实扣费。
- **建议**：免费判定前查 `FreeGrantClaim` 是否为 `granted`。

### 6. 文档化的 `docker compose up -d` 部署路径已不可用【已复现】

- **文档**：`README.md`、`docs/content/docs/overview/quick-start.mdx`、`docs/content/docs/overview/docker.mdx`、`docs/content/docs/progress/pending-test.mdx` 都写「`cp .env.example .env` → `docker compose up -d`」。
- **代码**：`docker-compose.yml:5` `${APP_IMAGE:?...}`、`:11` `${APP_PORT:?...}`、`:27` `${API_IMAGE:?...}` 三项都是无默认值的强制插值，而 `.env.example` 里**这三个变量一个都没有**。
- **后果**：compose 在解析阶段直接失败（`required variable ... is missing a value`）。即使补上，api 仍会因密钥长度与 `FREE_GRANT_*` 必填项校验 `os.Exit(1)`（`server/internal/config/config.go:216-221`、`:250-259`），app 因 `depends_on: api: service_healthy` 一起起不来。自部署用户 100% 卡在第一步。
- **成因**：仓库侧「compose 改为本地构建、镜像 tag 与端口环境化」只更新了 `deploy/env.*.example`，根 `.env.example` 与引用它的公开文档未同步。
- **建议**：给根 `.env.example` 补上三个变量（或给 compose 加默认值），并同步四份文档。

## P1 资金与安全边界

### 7. 回调金额为 0 时整个金额校验被跳过【机制已复现；影响经复核下调为加固项】

- **代码**：`server/internal/service/orders.go:197`（回调）与 `:269`（查单）都写 `PriceMicros != 0 && PriceMicros != order.PriceMicros`——**金额解析为 0 时判断短路，直接按本地快照到账**。机制成立。
- **可达性经对抗式复核下调**：这条**当前不可达**。支付宝 `payment/alipay.go:126-131` 的 `PaidAmountMicros` 在解析失败时返回的是 **error**（不是 0），调用方会拒绝；微信只在「验签通过但 `transaction.Amount` 为 nil」这种异常报文下才返回 0（`payment/wechat.go:108-111`）。所以它是防御缺口，不是现网资金漏洞。
- **为什么仍然要修**：新增渠道时最容易踩这个口子——易支付的 `money` 是字符串，只要实现方让解析失败返回 0 就会静默放行。《易支付接入规划》的安全节已经写明该要求，本条作为**加固项**保留，不作为上线阻塞。
- **建议**：让「解析不出金额」返回错误而不是 0，或把该处改成无条件比对。

### 8. 视频产物不进隔离区，被拒后原件丢失【已复现】

- **代码**：`service/aitask.go:137-153` 直接在内存里抽帧送审，全链路无 `Quarantine().Put`；对比图片链路 `handler/ai.go:381-429` 是「先隔离再送审」。
- **后果**：视频被拒后原件立即丢失，管理员复核即使改判也没有原件可释放——释放逻辑依赖 `record.QuarantineKey`（`handler/admin_moderation.go:188`），而视频记录的 key 是空串（`service/moderation.go:115`）。与第五期「隔离对象保留 24 小时供人工复核」的承诺不符。

### 9. `ic_media` 媒体令牌不可撤销【已复现】

- **代码**：`auth/auth.go:25` `MediaTokenTTL = 30 天`；`middleware/middleware.go:150-166` 只验签名 + `scope=media`，不查任何撤销表；`handler/auth.go:363-365` 的 `revokeAllUserTokens` 只更新 `refresh_tokens`。
- **后果**：改密码、重置密码、复用检测踢下线，都不会让已签发的 `ic_media` 失效。账号被盗后走「重置密码踢下线」这一标准恢复动作，攻击者仍可凭偷到的 cookie 读该用户全部媒体最长 30 天。文档承诺的是「与 refresh token 同周期轮换」「改密码撤销该用户全部其他令牌」。
- **建议**：媒体令牌改短 TTL，或引入会话版本号/jti 黑名单。

### 10. 邮件令牌消费非原子，并发下「一次性」失效【已复现】

- **代码**：`handler/auth.go:476-495`（Verify）与 `:547-575`（Reset）都是「先读判断、后无条件 `Update("used_at")`」，没有 `WHERE used_at IS NULL`。同一个包里的 refresh 轮换（第 332-348 行）已经是「条件更新 + 判 `RowsAffected`」的正确写法。
- **后果**：同一 reset 令牌的两个并发请求可以都通过校验并各自写入不同密码，令牌被消费两次。对「攻击者与用户同时使用同一重置链接」不设防。
- **关联**：实施「验证码登录」（见《后续功能备忘》）时必须按 refresh 的原子模式写，否则会把洞放大到 6 位数字凭据上。

### 11. 密码重置令牌有效期 24 小时，文档要求 1 小时【已复现】

- **文档**：《账号后端总规划》`expires_at` 一行写明「验证邮件建议 24 小时，**重置密码建议 1 小时**」。
- **代码**：`auth/auth.go:22` 只有单个 `EmailTokenTTL = 24h`，`handler/auth.go:211-227` 的 `createEmailToken` 不区分 purpose 统一 24h；邮件文案 `mail/mail.go:120` 也写「24 小时内有效」。
- **后果**：账号接管路径上的凭据可用窗口被放大 24 倍。
- **建议**：按 purpose 区分 TTL。

# 第二轮：规划逻辑 / 代码 / 文档 / 安全

第一轮对照的是「规划 vs 代码」。第二轮覆盖四个新维度：规划文档**内部逻辑**、后端与前端**代码本身**、公开**技术文档**的准确性、以及**安全边界**专项。编号自 31 起，与第一轮不重叠。

## P0 新增（本轮已复现）

### 31. 社区对浏览者完全不可用：他人作品的媒体一律 404【已复现；两条独立调查线各自命中】

- **代码**：`server/internal/handler/community.go:408` 把作者素材的 `storageKey` 发给所有浏览者；`server/internal/handler/media.go:421` 的 `findOwned` 强制 `user_id = 当前请求者`，跨用户一律 404；前端 `web/src/pages/community/index.tsx:181-183` 直接 `<img src={mediaUrl(work.storageKey)}>`。
- **后果**：用户 B 打开社区流看用户 A 的作品，请求 `/api/media/image:xxx` 时 uid 是 B、key 属于 A → 404，**全部缩略图与视频裂图**，只有作者本人看得到自己的作品。社区功能整体不可用。
- **测试盲区**：`server/internal/handler/site_test.go:179-186` 只断言 JSON 列表，从不解媒体 URL，所以测不出来。
- **注意**：修的时候不能简单放开 `/api/media` 的归属校验——那会同时引入 IDOR 与「上传 Content-Type 完全信任」的存储型 XSS（见第 40 条）。正确做法是给「属于已发布社区作品的 key」单独一条只读放行分支，或签发只读社区媒体令牌。

### 32. 免费试用计数是先查后加，可并发超发【已复现；两条独立调查线各自命中；真环境实测复现】

- **代码**：`server/internal/service/request.go:27-45`，函数注释写着「**原子**占用一次免费额度」，实现却是 `usageWithin`（普通 SELECT）后再 `AddUsage`（无条件 `value = value + 1`），没有行锁、没有条件更新、没有 `RowsAffected` 判定。
- **真环境实测复现（测试站，实测数据）**：`usage_records.free_image_trials` 在 3 条并发请求下从 **2 涨到 5**，而上限是 3（`service/quota.go:24`）——即实际只剩 1 次却放行了 3 次，**超发 2 次**。三条请求的 `created_at` 落在同一毫秒（`09:26:27.566 / .567 / .567`）。触发路径是前端多图节点的一次生成会并发发出多个请求，不需要人工构造并发。
- **对照证据**：同一代码库的 `service/credit.go:318` 与 `service/orders.go:216` 都用了 `clause.Locking{Strength: "UPDATE"}`，唯独 `ConsumeFreeTrial` 没有——正确写法就在同仓内，属遗漏而非无先例。
- **后果**：已验邮箱账号先取 N 个 quote，再并发提交生成，N 个事务都读到「计数未满」并各自 +1 全部放行。视频路径更严重——视频的并发判断（`handler/ai.go:663-671`）发生在 `beginRequest` **之前**，而任务行是之后才落库（`ai.go:683`），且视频路径没有 `slots.acquire`（只有 image/audio/text 有，见 `ai.go:191/516/886`），所以视频的超发倍数不被槽位限制。
- **建议**：改成单条条件更新（`UPDATE … SET value = value + 1 WHERE … AND value < ?` 后判 `RowsAffected`），或对 usage 行加 `FOR UPDATE`（照 `credit.go:318` 的写法）；视频的并发判断与建任务合并。注意这与第一轮第 4、5 条是不同层面的问题，修了那两条这条仍在；与第四轮第 124 条（失败不退还）是同一个计数器的两个方向，建议同批修。

### 33. 注销到期后媒体原件永久残留，社区作品仍留在公开流【已复现；两条独立调查线各自命中】

- **代码**：`server/internal/service/deletion.go:110-111` 的注释写「磁盘对象由保留期清理任务回收」，但它紧接着就在同一事务里 `Delete(&model.MediaFile{})`；而 `server/internal/service/cleanup.go:58` 的 `Reclaim` 正是按 `media_files WHERE user_id = ?` 扫描——行已被删，永远扫不到。`storage.Storage` 接口（`server/internal/storage/storage.go:22-33`）也没有 List 方法，全仓无对象清单扫描。定时任务里只有订单超时、隔离区清理、匿名化三项（`server/cmd/server/main.go:415-444`）。
- **后果**：用户的图片/视频字节永久占用磁盘与 S3 费用，与「注销即删除」的承诺相悖；其社区作品也不会被下架（`deletion.go` 未处理 `community_works`），继续出现在公开流与用户主页，但指向已删素材——前端裂图。
- **建议**：删除行之前先按 `object_path` 逐个 `storage.Delete`；匿名化时一并下架 `community_works`；补一个基于对象清单的孤儿 GC。

### 34. `starttls` 模式下发信实际走未认证连接【已复现】

- **代码**：`server/internal/mail/mail.go:90-99` 建立连接、`StartTLS`、`client.Auth(auth)` 一气呵成，但第 101 行真正发送用的是 `smtp.SendMail(addr, **nil**, …)`——第二个参数是 `auth`，传的是 `nil`。`smtp.SendMail` 内部会**另开一条连接**且不做 AUTH，前面那条已认证的连接只被 `defer client.Close()` 关掉。
- **后果**：`MAIL_SECURITY=starttls` 且 SMTP 服务器要求认证时（生产常见），验证邮件与重置密码邮件被服务器拒收；失败只落一条 slog。用户既收不到验证邮件，也无法自助重置密码——注册与找回两条链路同时断掉。
- **附带**：`mail.go:42-47` 的 `go func` 发送无并发上限，`smtp.Dial` 无超时，SMTP 黑洞时会堆积 goroutine 与连接。
- **建议**：复用已认证连接发送（用 `client.Mail/Rcpt/Data`），或把 auth 传给 `SendMail`；补 dial 超时与并发上限。

### 35. 邀请返利无任何防刷【已复现】

- **代码**：`server/internal/handler/activity.go:191-264` 的 `BindInvite` 只校验：开关已开、邀请码存在、不是自己、没绑定过。**没有**邮箱已验证校验、没有账号时长限制、没有风控评分、没有每日预算（对照 `account.go:253-267` 的免费领取有 `RiskScore` + `FREE_GRANT_DAILY_BUDGET_MICROS`）。路由（`server/cmd/server/main.go:308`）对任何登录用户开放。
- **后果**：注册限流是 10 次/小时/IP，批量注册后用每个新号调一次 `/activity/invite/bind`，主号即到账 `InviteRewardMicros`（默认 100000 微元）。单 IP 每小时可稳定换取约 1 元等价点数，用代理池则无上限，且这些点数是可直接消费的生成额度。
- **建议**：绑定要求被邀请人邮箱已验证 + 注册时长窗口 + 与免费领取共用同一套风控与每日预算。

第三轮不再按领域找 bug，而是换成六个不同视角审同一套东西：**架构决策、对抗式证伪、发布就绪度、端到端用户旅程、数据与运维、合规与隐私**。

## 发布门禁裁决（release-governor）：**不可发布**

判据是项目自己定义的开放条件（公开注册 / 开放充值 / 平台模型入口必须等 Phase 4+5 与合规事项全部通过）。

**第 83 条（高）｜合规门禁与代码默认值方向相反**：`server/internal/config/config.go:126` 的 `REGISTRATION_ENABLED` **默认 `true`**，而 `MODERATION_ENABLED` 默认 `false`（`:144`）；登录页注册开关在站点设置未注入时回落到该默认值（`server/internal/handler/auth.go:49-54`）。`deploy/env.prod.example` 正是「开注册 + 关审核」的组合。也就是说，**按模板部署即公开注册**，而项目自己的规则要求在备案、条款法务确认、人工复核值守全部完成前不得开放。代码里没有任何「合规未完成则拒绝启动」的检查（`config.go:212-268` 全表无此条）。

其余两条门禁：审核总开关两头堵——不开则合规门禁未履行，开了则视频功能对已付费用户不可用（第 3 条）；充值渠道装配是 fail-safe 的（不配置就不上架），但一旦开启即违反前置（第 4、5、7、32、35 条）。

**回滚能力**：只有「换回上一个镜像」这一层成立。迁移是裸 `AutoMigrate`（`server/internal/db/db.go:50-51`，无版本表、无 down），定时备份未实施、恢复从未演练，点数流水、已发放补偿、已匿名化账号、已删隔离原件、`CREDENTIAL_MASTER_KEY` 丢失后的渠道密钥**都是单向门**。

# 第四轮：测试环境部署后的实测发现

测试环境（`https://sim-art.youc.online`）部署完成后的第一轮真实链路实测。与前三轮不同，本节条目的证据来自真环境数据，不是静态阅读推断。

### 124. 失败的生成会永久消耗一次免费试用【已复现，真环境数据】

- **现象**：用免费试用发起生成，请求失败（本例为 502「该模型没有绑定平台渠道」），免费试用计数**不退还**。
- **证据**：`usage_records.free_image_trials = 2`，而 `ai_requests` 只有两条——`gpt-image-1` 的 `failed`（`final_cost_micros = 0`，未产生任何上游调用成本）与 `gpt-image-2` 的 `succeeded`。失败的那条同样占用了 1 次。
- **机制**：`handler/ai.go:1224` 在免费试用模式下由 `ConsumeFreeTrial` 直接加计数，返回的 `ReserveResult{UsedFreeTrial: true}` **不产生任何点数流水**；失败路径 `service/request.go:98` 的 `MarkFailed` → `Refund` 只按 `consume_transaction_ids` 退点数，试用单没有流水，`consumeIDs` 为空后直接 return（`request.go:111-114`），计数无处可退。`service/request.go:26` 的注释「计数只增不减」是有意设计，但它针对的是「删除生成历史不返还」；**失败退还是未被覆盖的场景**。
- **影响**：任何失败（上游 5xx、超时、未绑定渠道、进程重启收敛）都会吃掉一次试用。每人仅 3 次，三次失败即耗尽。与文档承诺的「先扣后生成、失败原桶退还」不一致——点数退了，试用没退。
- **修复方向**：`ai_requests` 增加「本次使用了免费试用」的可判定字段（或从 `pricing_snapshot` 的 `billingMode` 推导），`Refund` 在该字段为真时对同一 metric 做 `AddUsage(-1)`，并保证重复退还只生效一次。
- **严重度**：P2。不涉及资金与数据安全，但直接消耗免费用户的可用次数，且与已承诺行为不符。
