项目整体结构：

```text
web/                    浏览器端主应用
canvas-agent/           本机 Canvas Agent、MCP、Codex/Claude 桥接
plugins/canvas/         画布节点插件、SDK、官方插件
plugins/infinite-canvas Codex App 插件
docs/                   文档站与开发计划
```

核心架构是：

```text
浏览器 web
 ├─ Zustand 管理画布、素材、配置、Agent 状态
 ├─ IndexedDB/localforage 保存画布、媒体、生成记录、提示词缓存
 ├─ 直接请求用户配置的 OpenAI 兼容接口
 └─ 可选连接本机 Canvas Agent

Canvas Agent
 ├─ Express HTTP + SSE
 ├─ MCP Server
 ├─ Codex app-server
 └─ Claude Code CLI Adapter
```

目前最重要的事实是：项目现在还没有 `server/` 后端，仍然是纯前端本地模式。账号、云端同步、支付、平台模型计费等内容都只是规划，还没有真正实现。

我对几个核心模块的理解如下：

- `web/src/pages/canvas/`：画布页面和画布编辑器。
- `web/src/components/canvas/`：节点、连线、工具栏、缩放、生成面板等。
- `web/src/stores/canvas/`：画布项目和插件状态。
- `web/src/lib/canvas/`：节点工厂、几何计算、Agent 操作、插件加载、资源引用等纯逻辑。
- `web/src/services/api/`：图片、视频、音频、提示词和本地 Agent 请求。
- `web/src/services/image-storage.ts`、`file-storage.ts`：浏览器 IndexedDB 媒体文件存储。
- `canvas-agent/src/canvas/`：画布快照、SSE 会话和 MCP 工具。
- `canvas-agent/src/agent/`：Codex 会话、事件、历史、消息元数据和 Skill。
- `plugins/canvas/`：通过 ESM 动态加载的画布节点插件，插件运行在主页面内，没有 iframe 隔离。

当前计划是五期后端演进：

1. Phase 1：账号、邮箱验证、登录、刷新令牌、基础风控。
2. Phase 2：登录用户的画布、素材、生成记录和媒体资源服务端化，凭据加密托管。
3. Phase 3：存储配额、双桶点数账本、支付和管理后台。
4. Phase 4：平台模型由后端转发、报价、预扣、失败退款；用户自定义渠道继续浏览器直连。
5. Phase 5：内容审核、隔离存储、人工复核和上线合规门禁。

这个计划的关键设计是：

- 匿名用户继续使用纯本地模式。
- 登录用户使用服务端资源接口。
- 用户自己的 API Key 不经过平台后端转发。
- 平台模型的 Key 只存在服务端。
- 每个阶段必须通过自动化测试、人工验收和数据对账后才能进入下一阶段。
- 当前 `todo` 主要是 Claude Agent SDK、Skill 资源管理，以及整套账号后端。

当前主要风险和待验收范围集中在：

- Canvas 多图生成、缩放、选择和平移。
- Agent 的 MCP 初始化、流式消息、历史恢复、多标签页隔离。
- Agent 消息元数据、附件、Skill 和画布引用的持久化。
- 插件系统的运行安全。
- 国际化、主题和弹层样式。
- 本地存储清理与生成历史引用关系。
- 后续账号后端与现有本地数据模型之间的迁移边界。

另外，当前 `web` 还没有测试脚本，后端 `server/` 也不存在，因此规划里的 `bun run test`、`go test ./...` 等阶段门禁暂时还不能执行。

做得比较好的地方：

- `web/`、`server/`、`canvas-agent/` 分层合理，不需要拆成两个仓库。
- 五期按账号、数据、计费、AI、审核递进，依赖关系清楚。
- 匿名本地模式与登录云端模式通过 `services/data/` 隔离，方向正确。
- 平台模型走后端，用户自定义渠道继续直连，能避免 SSRF。
- 双桶点数、价格快照、报价 token、幂等和审核隔离区，这些关键意识是对的。
- 现有前端确实是全量 localforage 状态，例如 [use-canvas-store.ts](./web/src/stores/canvas/use-canvas-store.ts) 和 [use-asset-store.ts](./web/src/stores/use-asset-store.ts)，所以资源化改造是必要的。

必须先修的几个问题：

1. 不要把 `AutoMigrate` 当成生产数据库方案。

当前 [Phase 1](./docs/content/docs/progress/account-backend-phase1.zh-CN.mdx) 和总规划都依赖 `AutoMigrate`。它适合本地开发，不适合五期持续演进的正式数据库。

建议：

- 本地开发可以保留 `AutoMigrate`。
- 测试、预发布、生产使用版本化 migration。
- 每一期的表结构、索引、字段删除都必须有明确版本。

2. 支付订单字段设计需要重做。

当前使用 `provider_order_id` 同时承担订单匹配和幂等，但支付宝、微信通常同时存在：

- 本站商户订单号
- 支付渠道交易号

而文档的回调已经出现 `providerOrderID` 和 `outTradeNo` 两种字段，但数据库没有明确保存 `outTradeNo`。见 [Phase 3 支付回调](./docs/content/docs/progress/account-backend-phase3.zh-CN.mdx)。

建议拆成：

- `merchant_order_no`：本站生成，唯一，回调首先用它找订单。
- `provider_transaction_id`：渠道返回，按 `provider` 唯一。
- `payment_events`：保存已验签的回调事件，避免“回调先到、订单还没提交”时丢单。
- `POST /api/orders` 必须支持幂等 key，避免用户重复点击生成多笔订单。

3. 对象存储和 MySQL 不存在真正的同一事务。

文档多处写“数据库事务回滚即可”，但对象存储写入无法参加 MySQL 事务：

- 文件已写入，对应数据库事务失败，会产生孤儿文件。
- 数据库已占用配额，进程在写文件前崩溃，会产生配额假占用。
- 审核隔离区转正式存储也有同样问题。

建议给媒体增加状态，例如：

`uploading → quarantined → ready → deleting → deleted`

再配合幂等操作和后台 reconciliation 扫描。这个问题在 [Phase 2 媒体存储](./docs/content/docs/progress/account-backend-phase2.zh-CN.mdx) 和 [Phase 5 审核](./docs/content/docs/progress/account-backend-phase5.zh-CN.mdx) 中都必须明确。

4. AI 扣点状态还不够表达异常情况。

当前 `AIRequest` 只有 `running/succeeded/failed/refunded`，但实际会出现：

- 上游已经接受请求，本站随后断电。
- 视频任务已创建，但轮询进程崩溃。
- 结果已生成，但保存对象存储失败。
- 客户端断开，但服务端仍在执行。
- 上游状态未知，不能贸然退款。

建议把“请求状态”和“扣费状态”分开，至少支持：

`reserved → submitted → succeeded / failed / unknown → refunded / settled`

另外，所有收费的图片、视频、语音接口都应该强制 `idempotencyKey`，不能允许缺省。详见 [Phase 4 AI 转发](./docs/content/docs/progress/account-backend-phase4.zh-CN.mdx)。

5. 媒体 Cookie 的描述有技术错误。

文档说 `ic_media` Cookie“只对 GET 和 HEAD 生效”，但 Cookie 本身不能限制 HTTP 方法。设置了 `Path=/api/media` 后，PUT、DELETE 请求也会携带它。

因此必须在后端明确：

- GET/HEAD 可以接受 `scope=media` Cookie。
- PUT/DELETE 必须要求 access token。
- 状态修改接口增加 CSRF/Origin 校验。
- 管理员角色不能只信 JWT 中的旧 `role`，管理员降权后应立即失效或重新查库。

这部分见 [Phase 1 令牌策略](./docs/content/docs/progress/account-backend-phase1.zh-CN.mdx)。

6. 用户 API Key 目前并没有真正做到“服务端独占”。

当前 [config-file.ts](./web/src/services/config-file.ts) 会导出完整 `AiConfig`，其中包含 API Key；`use-config-store.ts` 也会持久化完整配置。

所以当前方案的真实含义是：

> API Key 服务端加密保存，但登录后仍会以明文返回给浏览器，并可能继续保存在浏览器本地。

这可以接受，但文档要说准确。更推荐：

- 登录态的 API Key 只放内存。
- 页面刷新后重新从服务端读取。
- 配置导出默认不包含 API Key。
- 匿名模式继续允许本地保存，因为它本来就是本地模式。

7. 路由规划前后存在冲突。

总规划要求匿名用户继续使用画布，但 [Phase 1 路由表](./docs/content/docs/progress/account-backend-phase1.zh-CN.mdx) 又写“其余业务路由全部 `RequireAuth`”。

建议最终明确：

- 匿名可访问：首页、画布、图片、视频、素材、提示词、配置。
- 必须登录：个人中心、云端数据、充值、平台模型、管理后台。
- `canvas-agent` 保持本机独立链路。

8. 第三期范围太大。

第三期同时包含：

- 点数账本
- 配额
- 支付
- 清理任务
- 模型目录
- 折扣活动
- 管理后台
- 个人中心
- 充值页

建议拆成：

- Phase 3A：点数、权益、配额。
- Phase 3B：支付和订单。
- Phase 3C：模型目录、运营后台、清理任务。

这样资金功能可以先单独验收，不会被后台页面和清理任务拖住。

框架层面我建议最终固定成：

```text
server/
  cmd/server/
  internal/
    handler/
    service/
    repository/
    model/
    middleware/
    provider/
    payment/
    moderation/
    storage/
    config/
```

其中 `repository/` 需要在文档里补齐。现在 Phase 2 提到了 repository，但目录结构没有统一说明。

最终判断：架构路线正确，尤其是单仓库、匿名/登录双模式、平台模型后端转发和双桶账本这几个核心决策可以保留。真正需要优先修的是数据库迁移、支付订单幂等、对象存储一致性、AI 异常状态、Cookie 权限和 API Key 持久化策略。

目前只是审查，没有修改代码或文档。
