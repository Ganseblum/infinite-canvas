# 账号体系与后端服务规划

本文档规划在无限画布上增加一套「登录后可用的多用户系统」：新增一个 Go 后端服务，提供登录注册、数据云端同步、媒体对象存储与用户权益，通过 Docker 部署在自有服务器上。

改造后**全站功能登录后使用**：未登录只能访问登录与注册页面，业务页面对匿名访问者不再开放。AI 能力只使用服务端配置的渠道，用户不再自行填写 Key 与 baseUrl，也不存在免登录的本地模式。

本文档只描述方案，不包含实现代码。

## 现状

当前项目**没有任何后端服务**。

- `web/` 是 Vite + React 19 + Ant Design + Tailwind + Zustand 的纯静态 SPA，构建产物 `web/dist` 由 nginx 托管。
- `Dockerfile` 是两阶段构建，运行镜像只有 nginx，没有服务端进程。`vercel.json` 是静态 SPA 部署，`render.yaml` 复用同一个镜像。
- 业务数据全部在浏览器：画布、素材、插件走 IndexedDB（localforage），AI 配置、WebDAV 凭据、主题走 localStorage。
- AI 请求由浏览器直连用户自己配置的 OpenAI 兼容接口，中间不经过任何服务器。
- 跨设备同步依赖用户自备的 WebDAV 服务器。
- `canvas-agent/` 是运行在**用户本机**的 Express + MCP 桥接进程，监听 `127.0.0.1:17371`，用于连接 Codex / Claude Code 操作画布。它是单人本机工具，不是后端服务，也没有数据库。

登录注册功能**完全不存在**。`web/src/stores/use-user-store.ts` 只是一个空壳，`user` 恒为 `null`，仅有一个 `clearSession`。`web/src/router.tsx` 中八条业务路由全部无鉴权守卫。

## 目标

- 提供注册登录，**全站功能登录后使用**：云端存储、平台预设模型与点数计费都以登录为前提，未登录访问任何业务页面都被引导到登录页。
- 登录用户的画布、素材、生图记录、视频记录在服务端持久化，换设备登录后自动恢复，包含图片与视频原文件。
- AI 渠道全部由服务端配置与管理，用户不接触任何 API Key 与 baseUrl，原有的自定义渠道、自定义模型与自定义脚本一并移除。
- 提供档位与配额体系，按存储容量、单文件大小与媒体保留期限制资源占用。
- 全部 AI 请求经后端转发，用户通过在线支付购买点数，生成在服务端按点数计量扣减。
- 站内生成与上传链路的输入与产物经内容审核，满足面向中国大陆运营的合规要求。
- 全套服务通过 Docker Compose 部署在自有服务器上，媒体走 S3 兼容对象存储。

## 目标追踪与执行规则

这套后端不是五个互相独立的功能包，而是一条按依赖逐步闭环的交付链。每个阶段只能在前一阶段通过验收后开始，不能用“代码基本写完”代替阶段完成。

| 阶段 | 核心目标 | 必须产出的可验证结果 | 禁止提前开放的能力 |
| --- | --- | --- | --- |
| Phase 1 | 建立可信账号身份和邮件链路 | 注册、验证、登录、会话刷新、找回密码、免费赠送资格判定均可审计 | 云端数据、充值、平台模型 |
| Phase 2 | 让登录用户的数据和媒体以服务端为权威 | 两台设备能按资源接口读取同一份画布、素材、生成记录和媒体 | 总量计费、充值、平台模型 |
| Phase 3 | 建立可对账的权益、存储配额和支付基础 | 双桶余额与流水逐桶相等，支付只到账一次，降档和清理可演练 | 对外充值入口，直到 Phase 4 同批上线 |
| Phase 4 | 让平台模型调用可计量、可扣点、可退还 | 平台 Key 不出服务端，报价与实扣一致，失败原桶退还，直连实现与自定义渠道删除 | 对外开放注册，直到 Phase 5 和合规前置完成 |
| Phase 5 | 在服务端可达链路建立内容安全闭环 | 输入、参考图、产物和上传按规则审核，后台可追溯、复核和补偿 | 未完成审核与备案时的公开运营 |

### 每个阶段的执行闭环

每个 Phase 都按同一套顺序推进：

1. **确认基线。** 对照总规划、上一阶段验收记录和当前源码，列出本阶段允许修改的边界；发现文档与源码不一致时先修计划，不带着冲突开始编码。
2. **按纵向切片实现。** 优先打通一条最小完整链路，再扩展同类能力。例如 Phase 2 先跑通单张画布的列表、详情、保存和冲突，再复制到素材与生成记录，避免三条半成品链路并行。
3. **任务级验证。** 每个任务完成后立即运行对应单元或集成测试，不把所有问题留到阶段末一起排查。
4. **阶段门禁。** 完成该 Phase 文档中的自动化检查、人工验收、数据不变量和安全检查；任何一项未通过都保持本阶段，不进入下一期。
5. **记录结果。** 把已实现且待用户确认的行为写入 `pending-test.zh-CN.mdx`，从 `todo.zh-CN.mdx` 移除已完成范围，并在 `CHANGELOG.md` 的 `Unreleased` 归纳用户可感知变化。

### 如何判断已经偏离目标

出现任一情况就视为偏离，不以“以后再补”为理由继续扩大改动：

- 为了省事把 access token 写进 `localStorage`，或让平台渠道 Key 出现在浏览器、响应体和日志中。
- 业务路由缺了 `RequireAuth`，或继续把业务全量数据当作本地权威，页面绕过统一数据层直接混用 localforage 与远端 API。
- 余额可以不经过流水直接修改，支付回调可能重复到账，报价逻辑与实际扣点逻辑各写一份。
- 任何形式的用户自带 Key、自定义 baseUrl 或自定义脚本重新出现在产品里，包括「过渡期先留着」「只读不写」这类变体。
- 内容审核只做前端拦截、审核原文被长期保存，或者宣称范围超出站内生成与上传的链路已被审核。
- 为尚未确认的多实例、订阅、退款、迁移或多云需求提前引入复杂抽象，导致当前阶段无法闭环。

### 纠偏流程

1. 立即暂停当前切片，不继续叠加依赖它的新代码。
2. 用一个最小复现、失败测试、SQL 对账或网络抓包确认偏离是实现问题还是计划冲突。
3. 以本总规划的关键决策和当前 Phase 的完成定义为准，删除越界实现或修正文档；不能同时满足时必须回到总规划重新决策。
4. 修复后重跑当前任务测试、该阶段受影响的回归集和上一阶段关键冒烟用例。
5. 在阶段执行记录中写清“偏离信号、根因、修改、复验结果”；同类问题再次出现时补充到 `AGENTS.md` 的可执行规则。

### 全局质量门禁

- 后端至少通过 `go test ./...`，涉及 MySQL、支付、对象存储或外部服务的路径还要有对应集成测试。
- 前端至少通过 `bun run typecheck`、`bun run test` 和与本阶段相关的浏览器人工验收。
- 数据库不变量、安全边界、幂等和并发行为必须通过专门用例验证，不能只验正常页面流程。
- 阶段验收必须保留证据：命令结果、关键接口响应、SQL 对账结果或截图；只有文字结论不算通过。
- 任何跳过项都要写明原因、风险、负责人和补验条件；存在阻断级跳过项时不得进入下一 Phase。

## 已确认的关键决策

| 决策项 | 结论 | 影响 |
| --- | --- | --- |
| 第三方 AI API Key | 只存平台自己的渠道 Key，AES-GCM 加密，主密钥走环境变量；用户不配置任何 Key | 用户侧不再存在第三方凭据，服务端只保管平台渠道密钥；`SECURITY.md` 必须同步说明 |
| 是否保留免登录模式 | 不保留，全站功能登录后使用 | 前端业务路由统一包 `RequireAuth`，未登录只能访问登录注册页；数据层只有服务端一套实现，浏览器 IndexedDB 不再承担业务数据存储；Vercel 纯静态部署随之失效，完整能力只支持 Docker 自部署 |
| 面向地区与合规 | 以中国大陆为主 | 审核选开源方案（图片 NSFWJS、文本 Detoxify，第五期接入），支付只做支付宝与微信、币种只做 CNY；算法备案与大模型服务备案是上线前置事项，必须在对外开放注册之前完成，具体流程由法务确认 |
| 媒体文件同步范围 | 登录用户（即全部用户）媒体全量上云，图片与视频原文件都同步 | 体验最完整；对象存储的容量与出网流量成本自行承担，需要配额兜底 |
| 对象存储 | S3 兼容，`STORAGE_DRIVER` 在 `local` 与 `s3` 之间切换 | 云端优先 Cloudflare R2（出网流量免费），大陆访问速度实测不可接受则退到阿里云 OSS + CDN；读走 302 重定向到预签名 URL，写仍经后端代理；本地磁盘驱动保留给开发与私有化部署 |
| WebDAV 同步 | 直接移除 | 只保留云端同步一条路径，删除 `webdav-sync.ts` 及配置页 UI、国际化文案与配置导出字段 |
| 注册策略 | 邮箱必填并完成验证 | 任何人都能注册，但邮箱验证只是基础门槛；免费赠送还要经过账号、IP、设备和活动领取记录的联合风控 |
| 邮箱验证与找回密码 | 两者都做，SMTP 可替换 | 当前小体量部署先使用 QQ 邮箱 SMTP；后端只依赖通用 SMTP 配置，后续可切换腾讯云、阿里云或其他事务邮件服务 |
| 管理后台 | 第三期实现轻量版 | 在本项目内新增 `/admin` 路由，覆盖用户列表、点数增减、用量查看与封禁，模型目录与充值档位配置也随第三期交付；第四期补上平台渠道管理，第五期补上审核记录与人工复核 |
| 档位配额 | 免费、付费、日落三档 | 免费 50 MB 存储、单文件 20 MB、媒体保留 7 天；付费 1 GB、200 MB、15 天；日落档 200 MB、200 MB、7 天，只在降档后的 60 天宽限期内出现，不可购买 |
| 付费形态 | 只卖点数，双桶记账加付费权益有效期 | 点数分 `purchased` 与 `granted` 两桶，付费身份判定为 `purchased_micros > 0 OR paid_until > now()`；充值把 `paid_until` 往后推 `entitlement_days`，赠送与签到只进 `granted` 桶、不产生付费身份；仍然没有 subscriptions 表 |
| 免费生成额度 | free 档给一次性的 3 张图片与 1 个视频，两个计数器互不占用 | 只覆盖被锁定的最便宜参数组合，参数超出即改走点数分支而不是报错；模型侧由 `model_catalog.free_trial_eligible` 限制范围；不每日重置；领取资格单独记录并做多维风控 |
| AI 请求链路 | 全部经后端转发，不存在浏览器直连上游的路径 | 平台渠道 Key 只存服务端，点数在服务端扣减；用户自定义渠道、自定义模型与自定义脚本整体移除，模型能力差异全部由 `model_catalog.constraints` 表达 |
| 模型目录 | 由后台维护，前端按目录动态渲染参数表单 | 前端不再靠关键词猜能力、不再硬编码分辨率与时长；模型只能来自平台目录，用户自定义模型随自定义渠道一起移除 |
| 媒体保留期 | 全部媒体按最后触达时间计时，超期清理 | 活跃项目不会被回收，长期无人问津的媒体到期释放存储；到期前 2 天预警并提供导出入口 |
| 内容审核 | 单独作为第五期，接开源方案：图片 NSFWJS、文本 Detoxify | 用户必须登录，生成与上传全部经过服务端，输入与产物全链路可审；合规口径可以覆盖站内全部生成与上传链路 |
| 支付渠道 | 支付宝与微信，只做 CNY | v1 不接 Stripe，也不支持退款；需要商户资质与公网可达的回调地址，回调必须验签且幂等 |
| 账号注销 | 自助申请加 7 天冷静期，到期匿名化并软删除业务数据 | 面向中国大陆的付费服务必须有账号注销入口，这是开放注册前的合规前置项，与算法备案同属上线门禁；订单与点数流水按财务要求保留但脱敏，余额不随注销退现，与「不退款」条款一致 |

### 配额的能力边界

存储配额是**硬约束**，媒体必须经过后端才能落盘，服务端在写入前校验，无法绕过。

生成消耗同样是**硬约束**。点数是用户花真金白银买的，扣不准就等于卖了一个算不清账的东西，因此全部 AI 请求都经 Go 后端转发：平台的第三方 Key 只存在服务端，浏览器根本拿不到，实际调用了几次、用了什么参数完全由服务端掌握，扣点在转发链路里同步完成。这条链路就是第四期要做的事。

不存在需要绕开这条链路的第二路径。早期方案曾考虑保留用户自带 Key 的直连渠道，现在明确取消：一是因为直连路径上的调用服务端看不见，点数与用量的口径会在两条链路之间永远说不清；二是因为服务端看不到的生成链路无法审核，与内容合规的目标冲突；三是因为同时维护「可计量的平台链路」和「不可计量的用户链路」两套前端调用、两套错误处理与两套参数约束，复杂度远超收益。用户不再能配置任何 Key 与 baseUrl，模型只能来自平台目录，产品文案因此可以把点数消耗描述成确定的、不可绕过的计量，这是收费成立的前提。

### 点数与付费身份

单位先定死：**1 点 = 1 微元 = 0.000001 元，充值按 1:1 到账**，充 10 元就是 10,000,000 点。全部金额与点数一律 `int64`，任何位置都不允许浮点参与运算。用户界面同时展示点数与人民币，例如 `500,000 点（¥0.50）`，用户既能核对余额变化，也不用自行换算。

平台模型必须提供可读的**价格矩阵**，不能只在生成后给出一笔总扣款。图片按模型支持的分辨率、质量与数量展示，例如 1K、2K、4K 各多少点和多少元；视频按分辨率与时长形成二维矩阵，例如 480p/5 秒、480p/10 秒、720p/5 秒、720p/10 秒分别多少钱。后台编辑结构化价格矩阵，生成页突出当前选中组合，并允许展开查看完整价格表。

基础价格之上支持独立的**限时折扣规则**。管理员可以给整个模型、指定分辨率、指定时长或完整参数组合设置折扣与生效区间，例如整个模型 9 折、全部 720p 8 折、全部 10 秒 8.5 折，或者只给 720p/10 秒设置 7 折。折扣不叠加：匹配参数最多的规则优先，参数数相同时按显式 `priority` 选择；同一具体度和优先级存在冲突时拒绝保存。这样完整组合可覆盖单参数折扣，单参数折扣可覆盖整模型折扣，最终价格只有一个确定答案。

参数变化时前端防抖调用 `POST /api/ai/quote`。服务端返回原价、命中的折扣、折后价、人民币展示值、是否走免费额度、余额是否足够、差额和短期签名 `quoteToken`。点击生成必须携带该 token；后端先验证参数与报价一致，再在事务中原子占用免费次数或预扣折后点数，成功后才调用上游。报价有效期不得晚于促销结束时间；基础价格、折扣规则或免费资格变化时返回 `QUOTE_STALE`，要求用户按最新价格重新确认，不能静默恢复原价或改成更高价格生成。

**账本分双桶。** `purchased` 桶只装用户花钱买来的点数，`granted` 桶装赠送——签到、充值包里的赠送部分、管理员补偿都进这里。扣减时先扣 `granted` 再扣 `purchased`，让用户先花掉不用付钱的那部分。

分桶是为了回答一个单桶模型答不了的问题：**这个用户到底付过费没有。** 「余额大于零即付费」在有赠送的那一刻就失效了——给新用户送一点体验额度，他立刻变成「付费用户」，拿到 1 GB 存储和 15 天保留期，而平台一分钱没收到。付费身份因此改判为 **`purchased_micros > 0 OR paid_until > now()`**，赠送来源无论多少都不产生付费身份。

`paid_until` 解决的是另一半问题：充过值的用户把点数花光之后是不是立刻变回免费档。如果只看 `purchased_micros > 0`，花光的那一刻档位就翻转，上午充值下午用完就被降档清理，观感等同于耍赖。因此每次充值把 `paid_until` 从当前时刻往后推 `entitlement_days`（默认 30 天，可按充值档位单独覆盖），这段时间内无论余额是否归零都保持付费档。

**这仍然不是订阅制。** `paid_until` 只是一个到期时间戳，过期不触发任何动作：没有定时任务、没有自动续费、没有账期与宽限续订、没有扣款失败重试，也没有 `subscriptions` 表。判定档位时现算一次比较，过期用户的下一次请求自然落回免费档。订阅制真正贵的从来不是那张表，而是围绕它的一整套状态机，这里一样都不引入。

档位翻转的后果与原方案一致，只是多了一档缓冲。降档不删任何数据，但已用存储很可能已经超过新档位的上限，此时账号进入**只读模式**：可以浏览、导出、删除，不能再上传新媒体。曾经付费过的用户先落 **`sunset` 日落档**（200 MB 存储、单文件 200 MB、保留 7 天）并宽限 60 天，之后才落到 `free` 的 50 MB。这一档是免费档从 500 MB 降到 50 MB 之后被逼出来的：付费用户手里攒下几百 MB 数据是常态，直接砸到 50 MB 意味着「点数一用完就删掉大半资产」从边缘情况变成每一次付费流失的必经路径——那不是配额设计，那是把流失用户批量变成投诉用户。宽限期内发邮件提醒，用户可以充值恢复，也可以自行清理；60 天后仍然超额的，从最旧的媒体开始清理，直到回到配额之内。

**v1 不支持退款**，这一条要写进服务条款：点数一经充值不退，`orders.status` 的 `refunded` 枚举保留但不启用。理由是点数一旦被消费，上游成本就已经真实发生，而部分消费后的退款需要一整套按比例结算、扣回赠送、回滚付费身份的逻辑，当前规模不值得为它承担这份复杂度与对账风险。注意它和生成失败的整笔退还不是一回事：后者是同一笔交易内部的冲正，写 `type = refund` 流水，不涉及真实资金。

### 免费生成额度

免费档给两个**独立**的一次性计数器：可以生成 3 张图片，**并且**可以生成 1 个视频，两者互不占用，用完就没有，**不每日重置**。

不每日重置是算出来的结论，不是保守。开放注册下每日重置意味着单个账号的年化敞口是一次性额度的 365 倍，而注册成本接近于零，等于把「换个邮箱就能一直白嫖」做成一条稳定管道；一次性额度的敞口是「注册量 × 一次」，量级差一个数量级以上，真被刷时也只是一次性损失而不是持续出血。分成两个计数器而不是一个通用次数，是因为图片与视频的上游成本差一到两个数量级：共用一个计数器，要么让一次视频把额度全部吃光，要么把图片额度压到没有体验价值。

额度只覆盖**被锁定的最便宜参数组合**：图片限 `n = 1` + 该模型最小尺寸 + 默认质量；视频限 480p + 该模型 `constraints.duration` 里的最小正值 + 无音轨 + 无参考图。参数超出锁定组合时**不报错，直接改走点数分支**——试用额度的目的是让人看到效果，不是给人一个必须先读懂规则才能用的功能，弹一句「免费额度不支持这个尺寸」只会让新用户在第一次生成时就流失。前端要做的只是提前显示这一次是走额度还是扣点，判定口径以服务端为准。

还需要 `model_catalog.free_trial_eligible` 一列来限制模型范围。锁死参数只压住了单次成本的一部分，模型之间的单价差异更大，没有这一列就等于允许新用户拿试用额度去打目录里最贵的那个模型——而那恰恰是所有人都会做的选择。这一列默认为 false，新上架的模型不会自动进入试用范围，否则每次上架一个更贵的模型都在无声地扩大敞口。

付费侧仍然纯按点数，两种口径不混用：不存在「按次折算成点数」的中间态，也不会出现同一次生成一半走额度一半走余额。判定顺序是先看模型是否 `free_trial_eligible` 且本次参数落在锁定组合内，再看对应计数器是否还有剩余，两个条件同时成立才走额度，否则一律走点数。

### 媒体保留期与到期清理

清理范围是**全部媒体，包括画布正在引用的**。这一点和常见做法不同，值得先解释：如果只清理孤儿文件，那么用户只要把图片挂在某张画布上就能永久占用存储，保留期形同虚设。

但「画布里的图片会被删掉」听起来像是会毁掉用户的项目，所以计时方式必须配套。一个媒体文件的**最后触达时间**取所有引用它的画布 `updated_at`、素材 `updated_at`、生成记录 `created_at` 里的最大值，只要有任何一处被动过，计时就重新开始；超过所属档位的 `retention_days`（免费与日落档 7 天，付费档 15 天）才进入清理。结果是活跃项目永远不会被回收，只有真正放着不管、既没打开过画布也没碰过素材的媒体才会到期。

实现上不新增 `expires_at` 列。到期时间是一个会被多张表的写入不断刷新的派生值，落成列就得在每次画布保存、素材更新、生成写入时同步维护，写放大且极容易漏掉一处。改为清理任务扫描时现算，并与第三期的孤儿文件回收合并成同一个扫描任务，两者都遍历三张业务表的 MySQL `JSON` 字段解析引用关系。

到期前必须预警：到期前 2 天发邮件，同时在站内给出提示，并提供一键导出入口，让用户能把要留的东西先拿走。没有预警的自动删除等同于事故。

### 开放注册与全量媒体同步的成本风险

这两个决策叠加后仍然存在成本敞口，但配额调整之后量级已经完全不同：免费档 50 MB 存储，100 个注册用户的理论峰值是 5 GB，而不是原先的 500 GB。这个数字在任何一家对象存储上都近似于免费，**容量已经不再是需要提前担心的事**。

成本焦点因此从磁盘转到**出网流量**。画布类应用的读放大很高：一张画布打开一次就要拉几十张图，用户来回切换、多设备同步、分享出去被别人打开，每一次都是一次出网。容量是一次性的，流量是按次累加的，几百 GB 的月出网在按流量计费的对象存储上足以超过存储费本身一个数量级。这正是云端优先选 Cloudflare R2 的原因——它的出网流量免费，直接把这项主要成本归零。R2 在中国大陆的实际访问速度需要实测，不可接受时退到阿里云 OSS + CDN，那时流量费重新成为第一大项，必须配套流量告警与预算上限。

量级下降不等于防线可以撤。以下几条全部保留：

- 注册接口按 IP 与邮箱域名维度限流，避免脚本批量注册。
- **邮箱验证通过前不允许上传媒体文件**，把未验证账号的存储占用压到零。
- 存储配额与单文件上限在文件写入前校验，超额直接拒绝而不是先写后算。
- 提供长期不活跃账号的清理策略，作为兜底手段。
- 媒体按档位的保留期到期清理，把「注册后传满配额就再也不管」这种静态占用变成有期限的占用，用量不再随注册量单调累加，而是会随不活跃账号的到期自然回落。

在此之上新增一条方向完全相反的敞口：**免费生成额度是真金白银的上游调用成本。** 存储只是占空间，一次免费生成是平台已经向上游付过钱的。3 张图加 1 个视频的一次性额度乘上注册量就是这项支出的上限，所以它必须和注册限流、邮箱验证绑在一起看——能压住注册量才压得住这笔钱。`FREE_TRIAL_ENABLED` 是被刷时的紧急阀门，和 `REGISTRATION_ENABLED` 一样属于必须提前留好的开关。

存储容量仍应按「预期注册量 × 免费配额」的一定比例预留并配置水位告警，只是基数小了一个量级；真正需要盯住的告警项换成了出网流量与免费额度的日消耗。

## 仓库形态：留在本仓库，新增 `server/` 顶层目录

**结论：不新开仓库，在当前仓库新增 `server/` 目录。**

本仓库已经是多包结构，`web/`（前端）、`canvas-agent/`（本机 Node 服务）、`plugins/`（画布插件）、`docs/`（文档站）各自独立，新增 `server/` 与既有组织方式完全一致。

选择单仓库的三个理由：

1. **前后端契约耦合紧。** 画布、素材、生成记录的字段结构由前端类型定义（`CanvasProject`、`Asset` 等）与后端表结构共同承担，改一个字段两侧都要跟着动。同一个仓库里一次改动就能同时更新两侧，拆成两个仓库需要额外的版本协调和契约同步机制，成本远大于收益。
2. **部署编排需要放在一起。** Docker Compose 要同时编排前端、后端、数据库三个服务，`nginx.conf` 要反代 `/api`，这些配置天然属于同一份部署描述。
3. **服务端渠道配置与计费已经与上游定位分叉。** 上游 `basketikun/infinite-canvas` 是 MIT 开源的纯本地工具，本次改造把它变成登录后使用的多用户服务，新增账号、服务端配置的 AI 渠道、对象存储与点数计费，本就不打算再向上游合并。因此「拆仓库便于同步上游」这个理由不成立。

需要配套注意的是：`server/` 里不要提交任何真实密钥或生产配置，全部走环境变量与 `.env`（已在 `.dockerignore` 忽略）；README 中标注本仓库为私有化分叉版本，说明与上游的差异。

如果后续确实需要保留向上游合并的能力，替代方案是后端独立成仓、前端改动收敛到少数文件——但登录态与数据分发层会侵入路由、请求层、配置页、顶栏等多处，很难收敛，不推荐。

## 技术选型

| 用途 | 选型 | 理由 |
| --- | --- | --- |
| HTTP 框架 | Gin | 生态成熟、文档充足，路由与中间件写法简洁 |
| ORM | GORM + AutoMigrate | 项目尚未上线，不需要迁移脚本，AutoMigrate 建表最省代码 |
| 数据库 | MySQL 8.0+ | 使用原生 JSON 字段保存画布与素材数据；标签改为关联表，避免依赖 PostgreSQL 数组与 GIN 索引 |
| 鉴权 | golang-jwt/jwt v5 | access token + refresh token 双令牌 |
| 密码哈希 | golang.org/x/crypto/bcrypt | 标准做法，无需自行设计 |
| 凭据加密 | 标准库 crypto/aes + cipher.GCM | 无需引入第三方加密库 |
| 对象存储 | S3 兼容（云端 Cloudflare R2，可退阿里云 OSS），保留本地磁盘驱动 | 画布类应用的主要成本是出网流量而不是容量，R2 出网免费直接把这项归零；用 `aws-sdk-go-v2` 一套代码对接所有 S3 兼容服务，私有化部署仍可切回磁盘卷 |
| 内容审核 | 开源自托管：图片 NSFWJS、文本 Detoxify，视频抽帧复用 NSFWJS | 零调用费用、数据不出服务器；provider 接口保持可替换，若监管要求有资质服务商再单独立项更换，第五期接入 |
| 支付渠道 | 各渠道官方 Go SDK | 下单参数与回调验签由 SDK 处理，签名逻辑绝不手写 |
| AI 转发 | 标准库 net/http | 上游调用与 SSE 逐块刷出靠 `http.Flusher` 就够，各家协议的差异交给 `internal/provider` 里的适配实现，不需要额外框架 |

遵循项目规范：通用能力一律使用成熟稳定的库，不手写协议、加密、日期等底层实现。

## 数据模型

### 账号相关

**users** — 用户主表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | char(36) | UUID 主键 |
| `email` | varchar | 唯一，登录标识 |
| `username` | varchar | 唯一，登录标识 |
| `password_hash` | varchar | bcrypt 哈希 |
| `display_name` | varchar | 展示名 |
| `avatar_url` | varchar | 头像 |
| `role` | varchar | `user` / `admin`，管理后台鉴权依据 |
| `status` | varchar | `active` / `disabled`，封禁用 |
| `email_verified_at` | datetime(3) | 邮箱验证时间，为空表示未验证 |
| `created_at` / `updated_at` | datetime(3) | UTC 时间 |

未验证邮箱的账号可以登录并浏览，但**不允许上传媒体文件或使用平台免费生成额度**，这是开放注册下控制存储和上游调用成本的基础约束。邮箱验证不是唯一的防刷依据，免费赠送还要经过独立的领取记录与风险判断。

**账号注销走「冷静期 + 匿名化」，不做物理删除。** `status` 增加 `pending_deletion`：申请注销后账号立即禁止新的生成与充值，但允许登录浏览和导出，7 天内可随时撤销；到期由后台任务在同一事务里把 `display_name`、`avatar_url` 置空，`email` 与 `username` 改写为 `deleted-{id}@invalid` 这类不可登录的占位值并保留唯一性，密码哈希清空，撤销全部 refresh token，业务表（画布、素材、生成记录）按用户维度软删除，媒体交给既有的保留期清理自然回收。`credit_transactions` 与 `orders` 是财务凭证，保留原金额但把与身份的直接关联降为不可逆的用户 id 引用。注销后同一邮箱可重新注册，是新账号而不是恢复。冷静期给 7 天是因为误注销与「注销躲避封禁」都需要一个可撤销窗口，太短起不到冷静作用，太长会放大「占用邮箱占位」的滥用面；具体天数可按运营经验调整，机制不变。

**free_grant_claims** — 免费赠送领取记录

| 字段 | 类型 | 说明 |

| 字段 | 类型 | 说明 |

### 业务数据

画布、素材、生成记录各自独立成表，一行一个业务对象，而不是把一整个域打包成一个 JSON 大对象存进去。这样列表页能分页、能按标题搜索、能交给数据库排序，乐观锁也只锁到单条记录。每张业务表都带 `deleted_at` 做软删除，因此不需要单独的删除标记表。

**canvases** — 画布

| 字段 | 类型 | 说明 |

| `id` | char(36) | UUID 主键 |

**media_files** — 媒体文件索引

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | char(36) | UUID 主键 |
| `user_id` | char(36) | 外键 |
| `storage_key` | varchar | 形如 `image:xxx` / `video:xxx`，与前端一致 |
| `object_path` | varchar | 对象存储中的实际路径 |
| `mime_type` | varchar | |
| `bytes` | bigint | 文件大小 |

`(user_id, storage_key)` 唯一。业务表里存的是 `storage_key`，二进制内容与实际落盘路径由这张表统一管理，存储用量统计也从这里聚合。

两张表的 `moderation_status` **第二期就加，不等第五期**。审核逻辑当然是第五期的事，但建表时多一列的成本几乎为零，而在一张已经装着真实数据的表上加列要同时考虑回填、并发写入与默认值语义，成本高一个数量级。第五期之前所有写入一律填 `skipped`，含义是「这条数据产生时审核链路还不存在」，而不是「审核通过」——这个区分在事后追溯时很重要，不能用 `passed` 当占位。

### 权益相关

**plans** — 档位定义

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar | `free` / `paid` / `sunset` |
| `name` | varchar | 展示名 |
| `storage_bytes` | bigint | 存储总配额 |
| `max_file_bytes` | bigint | 单文件上限 |
| `retention_days` | int | 媒体保留天数 |
| `free_image_trials` | int | 一次性免费图片生成次数 |
| `free_video_trials` | int | 一次性免费视频生成次数 |

初始化时写入三行默认数据：

| id | 名称 | 存储配额 | 单文件上限 | 媒体保留期 | 免费图片 | 免费视频 |
| --- | --- | --- | --- | --- | --- | --- |
| `free` | 免费 | 50 MB | 20 MB | 7 天 | 3 | 1 |
| `paid` | 付费 | 1 GB | 200 MB | 15 天 | 0 | 0 |
| `sunset` | 日落 | 200 MB | 200 MB | 7 天 | 0 | 0 |

免费额度落成 `free_image_trials` 与 `free_video_trials` 两列，而不是一个通用 `JSON` 次数：它们是互不相干的计数器，可直接参与 SQL 判断。这两列只定义上限，已用数量按 `(user_id, metric)` 记在 `usage_records`。

`sunset` 不是卖给用户的档位，它只出现在降档路径上，因此不进 `/api/plans` 的对外列表，也不可购买。把它做成一行档位定义而不是在代码里硬编码一组降档参数，是为了让「日落期能存多少、留多久」和另外两档一样可配、可查、可在管理后台改。

这张表不再记录每日生成次数——生成消耗的是点数，免费额度是一次性试用而不是周期配额。它也不表示「用户买了哪个套餐」，用户与档位的关系由付费身份现算推导：

- `purchased_micros > 0 OR paid_until > now()` → `paid`
- 否则 `paid_until` 非空且 `paid_until + 60 天 > now()` → `sunset`
- 其余 → `free`

日落档因此不需要任何新列，也不需要一个「降档时间」字段：`paid_until` 已经精确记录了付费权益结束的时刻，宽限期从它往后数 60 天即可。这也意味着降档不是一个需要被触发的事件，没有定时任务、没有状态迁移，只是同一个表达式在不同时刻算出了不同结果。因此仍然没有 subscriptions 表，也不存在订阅关系需要维护。

**credits** — 点数余额，双桶

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `user_id` | char(36) | UUID 主键兼外键，一个用户一行 |
| `purchased_micros` | bigint | 充值买来的点数余额，不允许为负 |
| `granted_micros` | bigint | 赠送得来的点数余额，不允许为负 |
| `paid_until` | datetime(3) | 付费权益到期时间，可空 |
| `updated_at` | datetime(3) | UTC 时间 |

**不再单独存一个 `balance` 总额列**：它等于两桶之和，多存一份就多一个可能与两桶不一致的「真相」，而对外展示时现算一次加法的成本可以忽略。扣减一律先扣 `granted` 再扣 `purchased`，跨桶时两桶的更新必须在同一个事务里完成。

**credit_transactions** — 点数流水

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | char(36) | UUID 主键 |
| `user_id` | char(36) | 外键，索引 |
| `type` | varchar | `purchase` / `consume` / `refund` / `grant` / `expire` |
| `bucket` | varchar | `purchased` / `granted`，这一笔动的是哪个桶 |
| `amount_micros` | bigint | 正数为增、负数为减，单位微元 |
| `balance_after_micros` | bigint | 本次变动后**该桶**的余额 |
| `ref_type` | varchar | `order` / `generation` / `admin` / `checkin` |
| `ref_id` | varchar | 关联对象的 id |
| `refund_of_transaction_id` | char(36) | 退款指向的消费流水，可空且唯一 |
| `note` | varchar | 备注 |
| `created_at` | datetime(3) | 索引，游标分页用 |

点数流水单独成表而不是只留余额字段，是因为收费系统必须可对账：用户问「我的点数为什么少了」，产品必须能逐条列出来源。`balance_after_micros` 是刻意的冗余，出问题时不用从头累加就能定位到是哪一笔开始算错。余额与流水的写入必须在同一个事务里，否则迟早会出现「扣了余额没有流水」或者反过来的情况，而这类数据一旦错了就无法自动修复。

`bucket` 让对账等式按桶分别成立：`credits.purchased_micros` 等于该用户全部 `bucket = purchased` 的 `amount_micros` 之和，`granted` 同理。没有这一列，一次跨桶扣减就只能记成一条金额合并的流水，事后无法还原是从哪个桶扣走的，双桶会退化成「只在余额上分家、在账上说不清」的伪结构。因此**跨桶扣减写成两条流水**，同一事务、同一 `ref_id`。

`ref_type` 现在就预留 `checkin` 取值。签到本期不上线，但它的落点必须是 `granted` 桶，这一点在结构上先定死——等到真要做的时候再决定，很容易为了省事直接进 `purchased`，那等于把每个签到用户都变成付费用户。

**credit_packages** — 充值档位

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar | 主键 |
| `name` | varchar | 展示名 |
| `price_micros` | bigint | 售价，微元；到账进 `purchased` 桶的点数与它 1:1 相等 |
| `bonus_micros` | bigint | 赠送点数，进 `granted` 桶 |
| `entitlement_days` | int | 本档位延长的付费权益天数，为空时取 `ENTITLEMENT_DAYS` |
| `currency` | varchar | 币种，当前只有 `CNY` |
| `enabled` | bool | 是否上架 |
| `sort` | int | 排序 |

原来的 `credits` 列删掉了：充值 1:1 到账，进 `purchased` 桶的点数恒等于 `price_micros`，再存一遍只会制造两个数对不上的机会。`price_cents` 也换成 `price_micros`，全表统一到一个单位；提交给支付渠道时再换算成分，因此后台保存时要校验价格是 10000 微元的整数倍（即整分），不给「三厘五」这种收不了款的定价留口子。`entitlement_days` 放在档位上而不是只用全局常量，是为了让大额档位能给更长的权益期——这是一个促销杠杆，写死成全局值就用不上了。

**orders** — 支付订单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | char(36) | UUID 主键 |
| `user_id` | char(36) | 外键 |
| `provider` | varchar | `alipay` / `wechat` |
| `provider_order_id` | varchar | 渠道侧订单号，唯一 |
| `package_id` | varchar | 外键，指向 credit_packages |
| `price_micros` | bigint | 实付金额快照，内部统一使用微元 |
| `currency` | varchar | 币种，当前只有 `CNY` |
| `purchased_micros` | bigint | 本单进 `purchased` 桶的点数快照 |
| `granted_micros` | bigint | 本单进 `granted` 桶的赠送点数快照 |
| `entitlement_days` | int | 本单延长的付费权益天数快照 |
| `status` | varchar | `pending` / `paid` / `failed` / `refunded`（保留枚举，v1 不启用） |
| `paid_at` | datetime(3) | 支付完成时间，可空 |
| `created_at` / `updated_at` | datetime(3) | UTC 时间 |

订单快照必须保留 `price_micros`、两个桶的到账金额和权益天数，回调时不反查 `credit_packages`。内部账本和订单统一用微元，创建支付单和校验回调时再把 `price_micros` 换算成渠道要求的分；后台只允许保存 10000 微元的整数倍，避免产生渠道无法收取的金额。

`provider_order_id` 唯一是回调幂等的地基：同一笔支付重复回调时，第二次会被唯一索引直接挡住，不可能重复加点。渠道普遍会重试回调，这是常态而不是异常路径。

**usage_records** — 用量计数，按 `(user_id, metric, period)` 唯一，`period` 只有 `total`。它服务三个 metric：`storage_bytes`、`free_image_trials` 与 `free_video_trials`。存储要在每次上传前校验，而 `SUM(bytes)` 会随文件数增长逐渐变慢，放在上传热路径上不合适，计数器是这里的必要妥协；两个免费额度同理——判定发生在每次生成之前，而且它们是一次性的，用计数器比从 `generations` 回溯统计更直接，也不会被历史数据的变动影响（用户删掉生成记录不应该退回免费额度，回溯统计会）。除此之外的生成次数仍然不进这张表，「今天生成了多少张」这类展示数字直接从 `generations` 数出来，扣费以点数流水为准。

### 模型目录

**model_catalog** — 平台模型目录

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `name` | varchar | 模型标识，调用上游接口时实际传的值 |
| `display_name` | varchar | 展示名 |
| `capability` | varchar | `image` / `video` / `text` / `audio` |
| `provider` | varchar | 归属渠道 |
| `constraints` | json | 参数约束，形如 `{ sizes: [], aspectRatios: [], durations: [], qualities: [], modes: [], maxCount: n, maxEdge: n, sizeStep: n, supportsAudio: bool, supportsWatermark: bool, maxReferenceImages: n }`；数组元素统一为 `{ value, label? }` 结构——`value` 是传给上游与服务端校验的实际值（如 `1k`、`1440`、`"16:9"`），`label` 是用户端展示名（缺省回退为 `value` 的格式化展示）；比例的 `value` 统一为 `宽:高` 整数对（如 `"5:4"`），前端由它换算 W×H，不要求用户手写字符串。预设值与自定义值同层参与价格矩阵校验与白名单校验 |
| `credit_cost` | json | 精确参数价格矩阵，包含计价维度、每个参数组合的 `cost_micros` 与版本号 |
| `free_trial_eligible` | bool | 是否允许被免费生成额度使用，默认 false |
| `enabled` | bool | 是否对用户可见 |
| `sort` | int | 排序 |
| `created_at` / `updated_at` | datetime(3) | |

这张表要解决的是当前前端的三处硬伤：模型能力靠 `use-config-store` 里的 `guessCapability` 按名字关键词猜；分辨率与最大边长这类参数是 `image.ts` 里的 `QUALITY_BASE`、`IMAGE_MAX_EDGE` 等全局硬编码，对所有模型一视同仁；系统压根不知道某个具体模型支持哪些尺寸、比例或时长，用户只能试——选了不支持的组合，要等上游接口报错才知道。

`constraints` 与 `credit_cost` 使用 MySQL `JSON`，因为不同能力的约束与计价维度不同。`credit_cost` 不使用容易产生匹配优先级歧义的加法和乘法规则，而保存精确组合：图片按 `resolution`、`quality` 给出单张价格，再乘 `n`；视频按 `resolution`、`duration` 精确匹配；对话与语音可使用无参数固定价。后台保存时必须验证 `constraints` 的全部可选组合都有唯一价格，缺价、重复价或多余组合都拒绝保存。

`constraints` 的取值分两层：**预设值**与**自定义值**。现有前端已经支持自定义参数——视频分辨率可手填任意 p 值、图片宽高可手填（16 像素步进）、视频秒数为 4–30 连续滑杆——这些行为保留，约束配置必须能表达它们而不是只给固定档位。因此 `sizes`、`aspectRatios`、`durations` 既接受预设值（`1k`、`16:9`、`10`），也接受自定义值（`1440`、`5:4`、`17`）；管理员在后台用预设多选加自定义输入框配置，自定义值与预设值同层参与价格矩阵校验（每个自定义组合同样必须有唯一价格）与第四期的白名单校验。后台录入交互：自定义值通过「添加」弹层输入并带格式校验（像素为正整数、比例为宽高两个独立数字输入框、p 值为正整数），确认后成为可删除的标签；标签悬浮显示实际存储的 `value`。边界类约束（图片最长边上限、尺寸步进、数量上限、视频秒数范围、智能时长支持与否、配音与水印支持与否）同样进入 `constraints`，前端用它替代 `IMAGE_MAX_EDGE`、`DIMENSION_STEP`、`VIDEO_SECONDS_MIN/MAX` 等全局硬编码。

**分辨率档位与实际像素的换算规则必须明确**：图片与视频的参数体系不同，必须分开表达，对齐现有前端的两套面板。图片侧：`quality`（auto/high/medium/low）是渲染质量档位，与像素无关；`sizes`（`1k`/`2k`/`4k`/`auto`）是**短边基准档位**，实际 W×H 由档位 × 比例换算（沿用现有 `imageSizePresets` 换算表：`1k` 在 1:1 下为 1024×1024、16:9 下为 1536×864；`2k` 在 16:9 下为 2048×1152；`4k` 在 16:9 下为 3840×2160），换算结果受 `maxEdge` 与 `sizeStep`（16 像素步进）约束，W×H 也可由用户直接手填覆盖。视频侧：`resolutions`（`480`/`720`/`1080` + 任意自定义 p 值）是**垂直像素基准**，16:9 下分别为 854×480、1280×720、1920×1080，实际 W×H = p 值 × 比例换算（宽度取偶数），同样可手填覆盖；`durations` 是连续秒数区间（默认 4–30，前端渲染为滑杆）而非离散档位，`-1` 表示支持智能时长；`modes` 为 `frames`（首尾帧）/ `reference`（全能参考）；`supportsAudio`、`supportsWatermark` 对应配音与水印开关。档位 `value` 存档位标识，前端按 `constraints` 换算出每个组合的实际宽高并展示给用户；换算表由服务端随 `/api/models` 下发（进入 `constraints` 或独立字段），避免前端再硬编码。用户与管理员在界面上看到的任何分辨率选项都应能查到它对应的实际像素，不允许只有档位名没有像素语义。

`free_trial_eligible` 反过来必须是一个可查询的布尔列而不是塞进 `constraints`：免费额度的判定在生成热路径上，需要它参与 SQL 与索引条件，也需要管理后台能一眼列出「当前哪些模型在试用范围内」。默认 false 是刻意的——新上架的模型不自动进入试用范围，否则每次上架一个更贵的模型都在无声地放大免费敞口。

**model_price_promotions** — 模型限时折扣

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | char(36) | UUID 主键 |
| `model_id` | char(36) | 平台模型 id，索引 |
| `name` | varchar | 活动名称 |
| `match_params` | json | 匹配参数；空对象表示整模型，支持模型 `constraints` 中的计价维度 |
| `discount_bps` | int | 折扣系数，基点制；8000 表示 8 折，范围 1-9999 |
| `priority` | int | 同一具体度的显式优先级，值越大越优先 |
| `version` | int | 每次修改递增，报价凭证绑定该版本 |
| `starts_at` / `ends_at` | datetime(3) | 生效区间，`starts_at < ends_at` |
| `status` | varchar | `draft` / `scheduled` / `active` / `ended` / `disabled` |
| `created_at` / `updated_at` | datetime(3) | UTC 时间 |

折后价使用纯整数计算：`ceil(base_cost_micros * discount_bps / 10000)`。不允许 0 折，免费活动继续走已有免费额度体系，不能用折扣规则绕开领取风控和预算。`match_params` 的键必须属于模型价格矩阵的 `dimensions`，值必须在 `constraints` 内；折扣只改变价格，不得扩大模型支持的参数范围。

同一模型的候选规则按“`match_params` 键数量倒序、`priority` 倒序”选择第一条。后台保存时如果时间区间重叠、具体度相同、优先级相同且存在可同时命中的规则，直接拒绝并要求管理员调整优先级；运行时不靠创建时间或数据库返回顺序碰运气。

促销活动按生命周期管理，不物理删除：`draft` 只对管理员可见，`scheduled` 等待 `starts_at`，`active` 在有效时间内生效，`ended` 到达 `ends_at` 后只读，`disabled` 由管理员提前停用。活动进入 `scheduled` 后修改匹配条件、折扣或时间必须递增 `version`，已经签发的报价全部失效；已经 `active` 的活动不允许直接覆盖原记录，修改必须生成新版本并保留旧版本快照，方便解释历史扣款。运营误配时先停用活动，再重新创建修正版，不通过直接改库恢复。

增加 `PRICING_PROMOTION_ENABLED` 全局开关。关闭后新报价只返回基础价格，所有旧的折扣报价凭证返回 `QUOTE_STALE`；该开关只影响折扣，不影响基础价格、免费额度与登录。关闭或恢复开关都必须写管理审计日志并触发价格缓存失效。

促销记录不得硬删除。管理员创建、修改、启用、停用和全局关闭操作都写入 `admin_audit_logs`，审计内容包含操作者、请求 id、目标活动、旧版本摘要、新版本摘要和原因；审计日志不保存 API Key、原始提示词或媒体内容。

## API 设计

统一前缀 `/api`，由 nginx 同源反代，避免跨域。除注册登录与支付回调外全部需要 `Authorization: Bearer <accessToken>`；支付回调由渠道服务器发起，拿不到用户令牌，改用签名校验替代鉴权。

响应失败一律包一层 `error.code`，全项目唯一的错误码总表在[第一期](第一期-账号体系与邮件链路.md)的「错误码」一节，每个 code 标注启用期；前端按同一张表登记 `apiErrors.*` 文案并分层提示，机制同样定义在第一期。本节及各期接口定义里出现的错误码都应能在总表里找到，新增时先回总表登记。

### 媒体文件

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| HEAD | `/api/media/{storageKey}` | 查询是否存在及大小、校验和 |
| GET | `/api/media/{storageKey}` | 302 重定向到预签名 URL；本地磁盘驱动下直接回流二进制 |
| PUT | `/api/media/{storageKey}` | 上传，经后端代理流式转发到对象存储，写入前校验配额与邮箱验证状态 |
| DELETE | `/api/media/{storageKey}` | 删除 |

媒体走独立的二进制接口，业务对象里只存 `storageKey`。前端拿到画布或素材后按需取文件，不与 JSON 主体一起传输。

**`GET /api/media/{storageKey}` 要设计成能直接塞进 `<img src>` 的普通 URL**，而不是让前端下载 Blob 再转 ObjectURL。这一点值得强调，因为它能直接删掉前端现有的一整套机制：目前 `image-storage.ts` 和 `file-storage.ts` 各维护一个模块级的 `storageKey → ObjectURL` Map，打开画布时批量把所有图片解成 ObjectURL，而这个 Map 永不驱逐，用户在画布间来回切换内存就一直涨。改成直连 URL 之后，浏览器 HTTP 缓存接管一切，那两个 Map、批量 hydration 的异步逻辑、以及随之而来的泄漏问题全部消失。

这里有一个必须解决的冲突：第一期把 access token 定为只存内存、refresh token 放在 `Path=/api/auth` 的 httpOnly cookie 里，而 `<img src>` 发出的请求既带不上内存里的 token，也够不到那个受限路径的 cookie。

解法是**登录与刷新时额外下发一个只读媒体 cookie**，属性为 `HttpOnly; Secure; SameSite=Lax; Path=/api/media`，与 refresh token 同周期轮换。它的权限被刻意限制到最小：只能读当前用户自己的媒体文件，不能调任何业务接口。这样即使被窃取，损失也远小于 access token 泄漏——后者能调用全部业务接口、驱动平台的 Key 生成并消耗点数。

上传仍然走带 `Authorization` 头的正常请求，这个 cookie 只对 `GET` 和 `HEAD` 生效。不要为了省事把它做成通用会话 cookie，那等于把第一期的令牌设计推翻。

#### 读路径：302 重定向到预签名 URL

`GET /api/media/{storageKey}` 的实现是**校验身份与归属之后 302 到对象存储的预签名 URL**，二进制不经过后端，省掉一份出网带宽和一份内存拷贝。预签名的两个参数必须成对设计：**签发时间对齐到整点，有效期等于 2 × 对齐粒度**（默认 1 小时对齐、2 小时有效）。对齐是为了让同一小时内所有请求拿到的是**同一个 URL**，浏览器与 CDN 才有共同的缓存键可命中——不对齐的话每次请求都签出一个新 URL，缓存命中率直接归零，等于白做重定向。有效期取对齐粒度的两倍，是为了让每个 URL 在下一个对齐点到来时仍有整整一个粒度的余量，避免「整点前一秒签出来的 URL 一秒后就过期」。

**302 响应自身的 `Cache-Control` 只能是 `private, max-age={预签名剩余秒数 - 60}`。** 这是整条读路径最危险的地方，值得写死在实现里并配一条测试。如果照着「媒体是不可变内容」的直觉给这条重定向加上 `immutable` 或一年 `max-age`，浏览器会把重定向连同里面的签名一起缓存下来；两小时后签名过期，而请求根本不会再回到服务端重签，表现就是全站图片在某个时刻集体裂开、刷新无效、只能清缓存。一年 `immutable` 是要写在**对象自己的元数据**上的——那份缓存策略属于预签名 URL 指向的那个对象，不属于指向它的这条重定向。减去的 60 秒是时钟偏移与在途请求的安全边界。

预签名 URL 本身不带 cookie，也带不到对象存储的域名上，这正好是我们要的：媒体 cookie 的授权范围到「换取一次重定向」为止，真正的读授权由那个短期 URL 承担，两者的有效窗口都很短。

**写路径继续走后端代理流式转发，v1 不做预签名直传。** 直传能省掉后端一次转发，但配额校验与 sha256 都必须发生在写路径上：直传之后再回调补记，中间就有一个「文件已经落进桶里但还没记账」的窗口，而这个窗口正是刷爆配额最省事的入口。等转发真的成为瓶颈再说，v1 不为一份还不存在的性能收益放弃一道硬约束。

本地磁盘驱动不做重定向，由后端直接回流二进制，这样开发环境与私有化部署不需要任何 S3 服务也能跑通全链路。

| GET | `/api/credits` | 双桶余额、`paidUntil` 与最近流水摘要 |
| GET | `/api/credits/transactions?cursor=&bucket=` | 流水游标分页，可按桶筛选 |

流水和生成记录一样是只增的历史流，因此同样用游标分页而不是页码分页。余额单独开一个 `/api/credits` 而不是并进 `/api/me`，是因为它在生成过程中会实时变化，前端需要能高频单独刷新；`/api/me` 还带着用户资料与档位信息，没必要跟着一起重取。余额按桶分别返回而不是只给一个总数——用户需要知道自己手上哪部分是买来的、哪部分是送的，因为只有前者与付费身份相关，而这正是「我明明还有点数为什么被降档」这个问题的答案。

### 支付与订单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/credit-packages` | 充值档位列表，只返回已上架的 |
| POST | `/api/orders` | 创建订单，请求体 `{ packageId, provider }`，返回对应渠道的支付参数 |
| GET | `/api/orders?cursor=` | 订单列表，游标分页 |
| POST | `/api/orders/{id}/cancel` | 取消待支付订单 |
| POST | `/api/payments/webhook/{provider}` | 支付回调，公开访问但必须验签且幂等 |

`POST /api/orders` 只创建本地订单并返回支付参数，点数不在这一步到账。到账只发生在回调确认支付成功之后，且写订单状态、加两个桶的余额、推 `paid_until`、写点数流水这几件事必须在同一个事务里完成。到账要拆成两条流水：`purchased_micros` 进 `purchased` 桶，`granted_micros` 进 `granted` 桶，两条都用同一个 `ref_id` 指向订单。`paid_until` 取 `max(当前值, now()) + entitlement_days`——从当前值往后叠，才不会让还在权益期内的用户因为再充一次反而缩短了到期时间。

只有支付宝与微信两个渠道，币种只有 CNY，v1 不接 Stripe 也不做外币。订单不支持退款，`refunded` 状态保留但不会被任何代码路径写入。

回调接口是整个后端唯一一个不带 `Authorization` 的写接口，它的两道防线要写死在实现里。**验签**交给各渠道官方 SDK，签名不通过直接拒绝，绝不能因为「订单号看起来像是我们的」就放行。**幂等**由 `orders.provider_order_id` 唯一索引加订单状态机保证，只允许 `pending → paid` 这一次跃迁，重复回调返回成功但不做任何写入。

### 模型目录

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/models` | 平台模型目录，含 `constraints`、基础价格矩阵与当前折扣展示信息 |

前端在生成页初始化时拉取目录并按模型动态渲染参数表单和完整价格矩阵。当前有效折扣按每个组合计算后展示原价、折后价、折扣标识和结束时间；目录只用于即时展示，最终确认价格以 `/api/ai/quote` 为准，因为活动时钟、实时余额、免费资格和版本只有服务端能准确判断。

### AI 请求转发

第四期新增，全部要求登录。这是全站唯一的 AI 调用路径，不存在任何绕过它直连上游的方式。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/ai/quote` | 返回当前组合的原价、折扣、折后价、人民币金额、免费资格、余额差额和短期报价凭证 |
| POST | `/api/ai/images/generations` | 图片生成，文生图与图生图共用一个入口 |
| POST | `/api/ai/videos/generations` | 视频生成，只创建异步任务并返回 `taskId` |
| GET | `/api/ai/videos/tasks/{id}` | 查询视频任务的状态与产物 |
| POST | `/api/ai/audio/speech` | 语音合成 |
| POST | `/api/ai/chat/completions` | 对话补全，SSE 流式 |

`/api/ai/quote` 使用与真实预扣相同的基础价格和折扣解析器。它本身是纯查询，不占余额、不消耗免费次数；响应中的 HMAC 签名 `quoteToken` 固定模型、参数哈希、计费模式、原价、折后价、基础价格版本、命中的活动 id 与活动版本。普通报价最长 5 分钟；命中活动时取“5 分钟后”和 `ends_at` 中更早的时间。真实生成重新解析当前活动，活动开始、结束、停用、修改或更具体规则生效导致当前价格与 token 不一致时返回 `QUOTE_STALE`；即使新价格更低也要求重新确认，不能按旧原价多扣。

路径贴着 OpenAI 兼容协议的形状，但**请求体与响应体都不是上游的原样透传**。请求按能力定义自己的字段，参考图传 `storageKey` 而不是 base64；响应固定给出本次花费（扣了多少点，或标明走的是免费额度）与 `storageKey` 形式的产物，各家上游那些字段名、信封、`b64_json` 与 `url` 的差异全部收敛在服务端。`/api/ai/chat/completions` 同理，它是一套自有事件流而不是上游 SSE 的透传，后端逐块 flush，不能等上游返回完再一次性吐出来，否则画布里的助手对话会从流式变成整段弹出，体验直接倒退。

因此前端要新增 `web/src/services/api/ai.ts` 承载这六个接口，并把 `image.ts`、`video.ts`、`audio.ts` 里的直连实现整体删除：所有模型都来自平台目录、都走 `ai.ts`，`model-plugin.ts` 自定义脚本与用户渠道的模型编解码（`channelId::modelName`）一并移除。视频从「本地轮询上游」改成「轮询本站的任务查询接口」。浏览器从此不持有任何 API Key，也碰不到任何上游域名。

扣点顺序是**先扣后生成、失败退还**：转发前按模型的 `credit_cost` 与本次参数算出点数，在一个事务里校验余额、按「先 `granted` 后 `purchased`」扣减、写消费流水（跨桶则两条），余额不足直接返回 402；上游失败或超时按被扣金额整笔退还到原桶，并写 `type = refund` 流水。不做「按实际结果补差」——第三期只暴露 `Reserve` 与 `Refund` 两个方法，本来就没有补差能力，多一条结算路径也就多一种对不上账的可能。这条链路的一致性是第四期最需要反复测的地方。

在扣点之前先判免费额度：模型 `free_trial_eligible` 且本次参数落在锁定组合内、对应计数器仍有剩余，就走额度、递增 `usage_records` 的计数、不产生点数流水；任一条件不满足就直接走点数分支，不报错。

**对话与语音按次固定价 ¥0.02（20000 点）**，不按 token 计。对话的输入长度在扣费时刻是已知的，输出长度不是，按 token 计就必须先按上限预扣、再按实际用量退差——那恰好推翻了本期「不做按实际结果补差」的决定，多出来的那条结算路径带来的对账风险远大于定价精度的收益。固定价的代价是长对话被低估、短对话被高估，在这两类调用的单次成本都远低于图片与视频的前提下，这个误差可以接受。

### 管理后台

全部要求 `role = admin`，由独立中间件校验，不能只靠前端隐藏入口。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/users` | 用户列表，支持分页、关键字搜索与状态筛选 |
| PATCH | `/api/admin/users/{id}` | 修改状态（封禁/解封） |
| POST | `/api/admin/users/{id}/password` | 管理员重置用户密码 |
| POST | `/api/admin/users/{id}/credits` | 管理员增减用户点数，请求体必须显式带 `bucket` |
| GET | `/api/admin/users/{id}/usage` | 查看单个用户的存储占用与生成用量 |
| GET/POST/PATCH/DELETE | `/api/admin/models` | 模型目录的增删改查 |
| GET/POST/PATCH/DELETE | `/api/admin/channels` | 平台上游渠道管理，Key 只写不读，第四期新增 |
| GET/POST/PATCH | `/api/admin/model-promotions` | 模型折扣活动查询、新增、修改与停用 |
| GET/POST/PATCH | `/api/admin/credit-packages` | 充值档位的查询、新增与修改 |
| GET | `/api/admin/orders` | 订单列表，支持按状态与用户筛选 |
| GET | `/api/admin/stats` | 总览：用户数、存储总量、当日生成量 |

档位不再由管理员分配，因此 `PATCH /api/admin/users/{id}` 只改状态。要给用户点数就走 `POST /api/admin/users/{id}/credits`——它必须写一条 `type = grant` 的流水，和改用户状态不是同一类操作，所以单独开接口而不是塞进 PATCH。

这个接口的请求体**必须显式指定 `bucket`，不给默认值**。默认在这里是有害的：默认进 `granted`，线下收款后的人工补单就不产生付费身份，用户付了钱却拿不到付费档；默认进 `purchased`，一次善意补偿就把用户变成付费用户，白送 1 GB 存储和 15 天保留期。规则是运营赠送与误判补偿一律进 `granted`，只有确实收到过钱的补单才进 `purchased`，两者都要求填 `note` 说明来由。

充值档位只有查询、新增与修改，没有删除。下架用 `enabled` 字段完成；已经有订单指向的档位一旦物理删除，历史订单就再也说不清用户当初买的是什么。

### 内容审核（第五期）

审核不新增任何用户侧接口。它是内联在既有写路径里的一道校验：`/api/ai/*` 在转发前审提示词与参考图、在产物落盘前审产物，`PUT /api/media` 在入盘前审文件，结论写进 `generations.moderation_status` 与 `media_files.moderation_status`。前端读原有字段即可，不需要为「查审核结果」单开一个轮询接口。

管理侧新增三个：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/moderation/records` | 审核记录列表，按结论、命中标签、用户与时间筛选 |
| PATCH | `/api/admin/moderation/records/{id}` | 人工复核，改判结论并记录操作人 |
| GET | `/api/admin/moderation/stats` | 命中率与标签分布，用于判断策略过松还是过严 |

人工改判**不退点数**，补偿走 `POST /api/admin/users/{id}/credits` 写一条 `bucket = granted` 的 `type = grant` 流水。这不是抠门：产物被判不通过时上游的钱已经花掉了，如果误判可以退点，「生成违规内容 → 申诉 → 退点」就成了一条稳定的免费算力管道，而甄别申诉真假的成本远高于补偿本身。用赠送桶补偿还有一个附带好处——它不会把一个从没付过费的用户变成付费身份。

## 数据方案：服务端权威的资源化模型

最初的方案打算直接复用现有 WebDAV 同步的 domain manifest 契约：把 canvas、assets、image-workbench、video-workbench 四个域各自打包成一个 JSON 整体上传下载，客户端用 `mergeById` 合并，再补一张删除标记表填上缺失的删除语义。它的吸引力完全在于工作量——`web/src/services/app-sync.ts` 里真正与 WebDAV 绑定的只有上传下载两个函数，换掉传输层就能跑起来。

**这个方案已经被否决。** 它把「省下一部分前端工作量」排在了「架构长期可用」之前，而省下的工作量很快会以更贵的形式还回来：

1. **整域一坨 JSONB 无法查询。** 列表页想拿到画布列表，就必须把整个域拉下来，动辄几 MB，翻页、按标题搜索、按更新时间排序只能在前端内存里做。
2. **生成记录本质是只增的历史流。** 用「合并」去处理一条只追加不修改的日志流本来就别扭，而且用户攒到几千条之后每次打开工作台都要全量拉取，这个代价不可接受。
3. **revision 锁的粒度太粗。** 乐观锁加在整个域上，意味着两台设备改的是**不同**的画布也会撞车，用户无法理解为什么编辑 A 画布会被提示与 B 画布冲突。
4. **删除需要额外机制。** manifest 模型下必须专门建一张 tombstone 表记录删除，并在每次合并时按它过滤；资源化之后每行一个 `deleted_at` 就解决了。
5. **数据对外不可查。** 管理后台想看某个用户有多少画布、占了多少空间，未来任何一个 API 客户端想读一条记录，都得先把整域 JSON 拉下来自己解析。

因此数据层改为**服务端权威的资源化 REST 模型**：每张画布、每个素材、每条生成记录都是数据库里的一行，前端不再持有全量副本，而是按需向服务端请求。

**服务端是唯一权威。** 客户端不再做合并。写入直接落到服务端，读取以服务端返回为准。前端内存里的数据是服务端数据的一份视图，而不是需要与之对账的另一份副本。

**按需加载，列表与详情分离。** 列表接口只返回摘要字段，不含 `data`；打开某张画布时才请求详情。生成记录用游标分页，只拉当前这一页。用户攒多少数据，与首屏加载多少数据不再挂钩。

**乐观锁下放到单条记录。** `revision` 存在每一行画布上，`PUT /api/canvases/{id}` 必须带上客户端读到的 `revision`，服务端比对不一致就返回 409 `REVISION_CONFLICT`。改不同画布的两台设备互不干扰，只有真正同时编辑同一张画布才会冲突，冲突提示也能明确指到具体是哪一张。

**软删除替代删除标记。** 删除就是写 `deleted_at`，列表查询默认过滤掉。没有 tombstone 表，也不存在「本地删了远端又带回来」这个合并 bug——在这个模型里它根本不会发生。

代价要说清楚：**前端数据层的改动比原方案大得多。** 现有 store 是「启动时把整个域从 IndexedDB 读进内存」的模式，要改成「列表按页拉、详情按需拉、编辑后防抖回写」。`app-sync.ts` 那套合并逻辑不再复用，直接删除。这部分工作量是实打实增加的，换来的是一个能分页、能搜索、能被管理后台和未来任何客户端直接查询的数据层。

**这套模型没有本地形态。** 全站功能登录后使用，数据权威只有服务端一处，前端不再需要「同一份契约、local 与 remote 两套实现、按登录态分发」的设计。页面与 store 直接依赖 API 客户端与 react-query，浏览器 IndexedDB 不再保存任何业务数据。

仍要写死一条实现约束：**登录、退出与切换账号时必须清空 react-query 缓存与全部内存 store。** 不清空的后果不是缓存效率问题而是数据泄露——退出登录后缓存不失效，上一个用户的画布列表会直接出现在下一个用户眼前，而这两次渲染在代码上看起来完全一样，本地自测几乎不可能发现。

### 删除文件

| 路径 | 原因 |
| --- | --- |
| `web/src/services/webdav-sync.ts` | WebDAV 同步整体移除，由服务端存储取代 |
| `web/src/services/app-sync.ts` | 整域打包、`mergeById` 合并、资产 hydrate 全部随模型作废；其中的客户端媒体垃圾回收随本地媒体缓存一起删除，孤儿回收由服务端负责 |
| `web/src/services/api/model-plugin.ts` | 用户自定义脚本随自定义渠道一起移除；模型调用方式由平台通过 `constraints` 与服务端 provider 保证 |
| `web/src/lib/seedance-video.ts` 及 `image.ts` / `video.ts` / `audio.ts` 内的全部直连协议实现 | 第四期统一切到 `/api/ai/*` 后没有调用方，直连上游的前端代码全部退场 |

删除 `app-sync.ts` 是资源化带来的直接结果：合并语义整体上移到服务端，客户端不再需要「本地一份、远端一份、算出第三份」的流程。原方案把这个文件当成最大的复用资产，现在它是要清理的负债。垃圾回收也不再有存身之处——前端不持有全量数据，客户端 GC 无从判断引用关系；媒体由服务端按保留期与孤儿扫描统一回收。

`vercel.json` 与 `web/vercel.json` **随全登录方案一并移除**。纯静态部署无法提供登录与后端 API，这份部署形态随之失效；项目只支持 Docker 自部署，`render.yaml` 同步调整或移除。

移除 WebDAV 是一次牵连性改动，除了删文件本身，还要清掉 `use-config-store` 的 `webdav` 字段、`config-file.ts` 的导出字段、配置页 UI，以及两个语言包里的 `config.webdav.*` 文案。建议在第二期数据资源化跑通并验收之后再执行删除，避免中间态既没有 WebDAV 也没有可用的云端存储。

## 部署编排

`docker-compose.yml` 从单容器改为三服务：

```txt
app   nginx + 前端静态产物，对外暴露 3000
api   Go 后端，仅内网暴露 8080
db    MySQL 8.0（`mysql:8.0`），仅内网暴露 3306
```

数据卷：`mysqldata` 持久化数据库；`media` 卷只在 `STORAGE_DRIVER=local` 时使用，切到 `s3` 之后媒体不落本机磁盘，这个卷可以不挂。`mysqldata` 卷**必须有数据库备份**：点数余额与流水是资金凭证，不能只依赖单机卷。备份策略（频率、保留份数、存放位置）由部署方按自身条件确定，文档只约定底线——定期备份且至少演练过一次从备份恢复，没有验证过恢复的备份不算备份。`db` 的初始账号、密码与库名由 `MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_DATABASE` 和 `MYSQL_ROOT_PASSWORD` 提供，健康检查使用 `mysqladmin ping`，`api` 要等它通过之后再启动。

`nginx.conf` 增加反代，前端与后端同源，无需处理 CORS：

```txt
location /api/media/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    client_max_body_size 200m;
}

location /api/ {
    proxy_pass http://api:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    client_max_body_size 2m;
}
```

**`proxy_pass` 不能带任何 URI 部分**，这是这份配置里最容易踩的坑。写成 `http://api:8080/` 时，nginx 会把 location 匹配到的 `/api/` 剥掉再转发，`/api/auth/login` 到后端就成了 `/auth/login`；而本文档所有接口都写作 `/api/...`，后端也统一注册在 `r.Group("/api")` 下，照字面实现会全线 404。不带尾斜杠则路径原样透传，和后端的路由前缀严格对齐。

体积上限必须拆成两档。200MB 只给 `/api/media/`，其余 API 限制为 2MB；否则画布 `data` 的 MySQL `JSON` 也能提交 200MB 并撑大数据库。免费档 20MB 的更严格限制由后端按派生档位校验。

后端所需环境变量写入 `server/.env.example`：

| 变量 | 说明 |
| --- | --- |
| `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE` / `MYSQL_ROOT_PASSWORD` | `db` 服务的初始账号、密码、库名与 root 密码，同时供 MySQL 健康检查使用 |
| `DATABASE_URL` | MySQL 连接串，取值必须与上面数据库变量一致 |
| `PORT` | 后端监听端口，缺省 8080，改了要同步 nginx 的 `proxy_pass` 与 compose 的健康检查 |
| `JWT_SECRET` | 访问令牌签名密钥 |
| `CREDENTIAL_MASTER_KEY` | 凭据 AES-GCM 主密钥，32 字节；第四期的平台渠道 Key 复用同一把，不再引入第二把密钥 |
| `STORAGE_DRIVER` | 媒体存储驱动，`local` 或 `s3`；`local` 落 `MEDIA_ROOT` 指向的卷，`s3` 走下面一组变量 |
| `MEDIA_ROOT` | 本地驱动的落盘路径，对应 `media` 卷；`STORAGE_DRIVER=s3` 时不使用 |
| `S3_ENDPOINT` | S3 兼容服务的接入地址，R2 与 OSS 都要显式配置，不依赖 SDK 的默认域名推断 |
| `S3_REGION` | 区域标识，R2 固定填 `auto` |
| `S3_BUCKET` | 桶名，必须是私有桶 |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | 访问密钥，权限只给这一个桶的读写，不要复用账号主密钥 |
| `S3_FORCE_PATH_STYLE` | 是否用路径风格寻址，MinIO 与部分自建服务需要设为 true |
| `S3_PRESIGN_ALIGN` | 预签名签发时间的对齐粒度，缺省 1h |
| `S3_PRESIGN_TTL` | 预签名有效期，缺省 2h；必须等于 2 × `S3_PRESIGN_ALIGN`，启动时校验，不满足直接启动失败 |
| `ENTITLEMENT_DAYS` | 充值默认延长的付费权益天数，缺省 30；充值档位上的 `entitlement_days` 可以覆盖它 |
| `FREE_TRIAL_ENABLED` | 免费生成额度总开关，默认开启；被刷时可立即关闭，已用计数不清零 |
| `MODERATION_ENABLED` | 内容审核总开关，第五期新增；对外开放注册前必须为开启 |
| `MODERATION_NSFWJS_ENDPOINT` / `MODERATION_DETOXIFY_ENDPOINT` | NSFWJS 与 Detoxify 推理服务地址 |
| `MODERATION_FAIL_MODE` | 审核服务不可用时的处置策略，`reject` 或 `allow`，必须显式配置，不给缺省值 |
| `APP_BASE_URL` | 站点外网地址，用于拼接邮件里的验证与重置链接 |
| `SMTP_HOST` / `SMTP_PORT` | 邮件服务器地址与端口 |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | 邮件服务账号 |
| `SMTP_FROM` | 发件人地址 |
| `SMTP_SECURITY` | `ssl` 或 `starttls`；QQ 邮箱当前建议 `smtp.qq.com:465` + `ssl`，后续替换邮件服务时只改配置 |
| `REGISTRATION_ENABLED` | 注册总开关，默认开启，出问题时可紧急关闭 |
| `FREE_GRANT_ENABLED` | 免费赠送总开关，默认开启；被刷时关闭赠送但不影响已有账号登录 |
| `FREE_GRANT_CAMPAIGN_ID` | 当前免费赠送活动标识，用于按活动幂等领取 |
| `FREE_GRANT_DAILY_BUDGET_MICROS` | 每日免费赠送预算上限，达到后停止发放新的赠送 |
| `FREE_GRANT_RISK_THRESHOLD` | 风险评分阈值，达到后拒绝或转人工处理 |
| `PRICING_PROMOTION_ENABLED` | 限时折扣总开关；关闭后新报价只使用基础价格，折扣报价全部失效 |
| `ALIPAY_*` / `WECHATPAY_*` | 支付宝与微信的商户号、密钥与回调地址，未配置的渠道自动不上架 |

`MODERATION_FAIL_MODE` 刻意不给缺省值。审核服务挂掉时是「宁可拦错也不放过」还是「宁可放过也不挡住用户」，这是一个业务与合规的取舍，不该由框架替谁做决定；不写就启动失败，逼部署方明确表态一次，比默认放行之后在事故里才发现要好得多。

平台预设模型的上游地址与 Key **不走环境变量**。第四期新建 `platform_channels` 表存放每个渠道的 `BaseURL`、AES-GCM 加密后的 `Payload`（明文是上游 API Key）、`Priority` 与 `Enabled`，加解密复用 `CREDENTIAL_MASTER_KEY`，管理入口是 `/api/admin/channels`，请求按 `Priority` 顺序取第一个可用渠道并在失败时切到下一个。之所以放表里，是因为换 Key、加备用渠道、临时停用某个上游都不该需要改配置重启容器，而多渠道故障转移本来就不是一对环境变量能表达的。

媒体保留期没有单独的开关变量。清不清理由所属档位的 `retention_days` 决定，验证期间想先只扫描不删除，用第三期「先做成管理后台按需触发，在单个用户上验证正确后再挂定时任务」的做法即可，不需要再加一个全局总开关。

对象存储有两条必须写进**部署检查清单**的项。第一条是**桶必须保持私有**：Cloudflare R2 的 `r2.dev` 开发域名一旦启用，整个桶立刻变成公开可读，本文档所有预签名与鉴权设计当场归零——而这个开关就在控制台一个很容易被顺手点开的位置，上线前要实测一次匿名直接访问确实被拒。第二条是**上线前实测一次目标地区的访问速度**：R2 出网免费是选它的主要理由，但如果在中国大陆的实际下载速度不可接受，这个理由不足以抵消体验损失，届时退到阿里云 OSS + CDN，代价是流量费重新成为第一大成本项，需要同步配置流量告警与预算上限。

`APP_BASE_URL` 配错会直接导致验证邮件里的链接不可用，部署时需要重点核对。当前小体量部署可以使用 QQ 邮箱 SMTP，例如 `SMTP_HOST=smtp.qq.com`、`SMTP_PORT=465`、`SMTP_SECURITY=ssl`；`SMTP_PASSWORD` 填 QQ 邮箱生成的授权码，不填邮箱登录密码。后端只依赖通用 SMTP 配置，不在代码中绑定 QQ，后续可切换其他事务邮件服务。SMTP 全部变量为空时后端应启动失败并给出明确报错，而不是静默地发不出邮件。

支付回调地址必须公网可达，且要能被各渠道的服务器直接访问——纯内网部署无法完成支付闭环，这一点要在部署文档里写明。两个支付渠道相互独立，只配其中一个也能跑，未配置的渠道在 `/api/credit-packages` 与下单接口里自动不可选，而不是让用户点进去才失败。

`render.yaml` 目前是单镜像静态部署，改造后不再适用，需一并调整或移除。

## 安全设计

- 密码用 bcrypt 哈希存储，不可逆。
- refresh token 只存哈希，泄露数据库也无法直接使用；改密码时撤销该用户全部其他令牌。
- 第三方 AI 凭据只用平台自己的渠道 Key，AES-GCM 加密，主密钥从环境变量读取，不进数据库、不进仓库。表结构预留 `key_version` 支持后续轮换。用户侧不存在任何需要托管的 Key。
- 上传接口必须校验 `storage_key` 格式并限定在当前用户命名空间下，防止路径穿越与越权读取他人文件。
- 预签名 URL 的授权范围收到最小：**单个对象、只读、有效期等于 2 × 对齐粒度**（默认 2 小时），绝不签桶级或前缀级的 URL。它一旦签发就脱离了我们的控制——URL 本身就是凭据，任何拿到它的人在有效期内都能读到那个对象，所以窗口要短、范围要窄，并且不能出现在日志与错误信息里。
- 对象存储桶必须保持私有。Cloudflare R2 的 `r2.dev` 公开域名一旦启用即等于整桶公开，所有预签名与鉴权当场作废；这条要进部署检查清单并在上线前实测。
- 内容审核服务的 AccessKey 与其他业务密钥同级保管，只走环境变量、不进数据库也不进仓库。调用审核服务的出网请求不允许把用户令牌或平台 AI Key 一并带出去。
- **审核记录只存内容哈希、命中标签与服务商返回的结论摘要，不存原始文本与图片。** 存原文等于把违规内容在自己库里再存一份，既扩大了泄露面，也让日后的数据清理变成一件需要逐条判断的事。需要复现某条判定时用哈希去关联原对象，原对象该删照样删。
- 邮件令牌只存哈希，明文仅出现在邮件链接中，且必须一次性使用并设置较短有效期。
- 找回密码接口无论邮箱是否存在都返回成功，避免通过响应差异枚举已注册账号。
- 管理接口由独立的 `role = admin` 中间件校验，绝不能只靠前端隐藏入口。首个管理员通过环境变量或初始化命令创建，不开放自助提权。
- 平台自己的第三方 Key 加密存放在 `platform_channels` 表里，解密只发生在发起上游请求的那一刻，明文只在 `internal/service/upstream.go` 与 `internal/provider` 内部停留，不进缓存，任何情况下不出现在响应体、错误信息或日志里；转发响应还要过滤掉上游可能回显的鉴权头。
- 支付回调是唯一的公开写接口，必须先验签再处理，同时限制请求体大小与处理频率，避免它成为压垮后端或伪造订单的入口。
- AI 转发接口按用户维度限流。拿到一个已鉴权身份就能驱动平台的 Key 打上游，余额校验管的是花多少钱，限流管的是打多快，两者缺一不可。
- 服务端只持有平台自己的上游密钥，不持有任何用户密钥，责任边界比「托管用户凭据」的早期方案小得多。`SECURITY.md` 与 `docs/content/docs/support/security.mdx` 必须说明平台 Key 的存储方式、加密算法与风险边界，并补充支付密钥的保管方式。

### 开放注册带来的额外攻击面

公开注册意味着任何人都能拿到一个已鉴权身份，防护重点从「拦住陌生人」变成「限制单个账号能消耗多少资源」：

- 注册与发信接口按 IP 和邮箱维度双重限流，防止批量注册与邮件轰炸。
- 邮箱验证通过前禁止上传媒体，未验证账号无法占用存储。
- 邮箱验证通过前禁止领取平台免费赠送；邮箱验证只是基础门槛，不是唯一身份证明。
- 免费赠送按 `campaign_id` 记录领取结果，至少以 `(user_id, campaign_id)` 幂等；邮箱哈希、IP 网段哈希和设备哈希参与风险评分，不能只依赖其中一个维度。
- 免费赠送使用独立预算、风险阈值和紧急开关；达到预算或风险阈值时停止发放，不影响正常登录与已有权益。
- 存储配额、单文件上限与点数余额在操作前校验，超额或余额不足直接拒绝。
- 平台模型的转发接口按用户限流，新注册账号不因为「已登录」就能无限制驱动平台 Key。
- 免费生成额度是一次性的，且只对锁定参数组合与 `free_trial_eligible` 的模型生效，把「注册即可白嫖」的单账号上限压到一个确定的小数。
- `REGISTRATION_ENABLED` 与 `FREE_TRIAL_ENABLED` 作为紧急开关，被刷时可立即关闭注册或免费额度。
- `FREE_GRANT_ENABLED`、`FREE_GRANT_DAILY_BUDGET_MICROS` 与 `FREE_GRANT_RISK_THRESHOLD` 作为免费赠送的独立控制项；关闭赠送不应误伤已注册用户的登录和已有权益。

## 分期实施计划

每期都有一份中文执行计划，精确到文件职责、实施顺序、接口出入参、偏离判定、纠偏动作与验收清单：[第一期](第一期-账号体系与邮件链路.md)、[第二期](第二期-数据资源化与对象存储.md)、[第三期](第三期-点数计费与管理后台.md)、[第四期](第四期-AI请求后端转发与点数计量.md)、[第五期](第五期-内容审核与人工复核.md)。

### 第一期：账号体系与邮件链路

后端搭建 `server/` 骨架，实现 users、refresh_tokens、email_tokens 与 `free_grant_claims` 表，注册登录登出刷新改密码、`/api/me`、鉴权中间件，接入可配置 SMTP 完成邮箱验证与找回密码，并给注册、发信和免费赠送领取接口加上限流与风险判断。当前部署使用 QQ SMTP 配置示例，代码不得绑定 QQ 专用逻辑。

前端新增统一 client、`use-auth-store`、登录注册页、邮件验证与密码重置两个落地页、顶栏用户菜单与国际化文案。**全部业务路由包 `RequireAuth`**——全站功能登录后使用是本次改造的产品形态，这一期就把守卫布好，未登录访问任何业务页面都重定向到登录页并携带回跳地址。

部署上完成三服务编排、`/api` 反代与 `client_max_body_size` 放开。

因为选择了开放注册，邮箱验证不能推迟到后面的阶段——它是限制未验证账号占用存储和领取免费赠送的基础前提，必须和账号体系一起交付；但免费赠送还必须经过独立领取记录和多维风控。

验收标准：全新环境起容器后可注册并收到验证邮件，点击链接完成验证；可登录、刷新令牌、登出；忘记密码能收到重置邮件并成功改密；未验证账号不能上传媒体或领取免费赠送；同一账号重复领取同一活动只成功一次，命中风险阈值或活动预算后拒绝赠送；未登录访问画布、素材等任何业务页面都被重定向到登录页，登录成功后回到原路径。

### 第二期：数据资源化与对象存储

后端实现 canvases、assets、generations、media_files 四张表与对应的资源接口，含分页列表、游标分页、单条乐观锁与软删除；`internal/storage` 一次做成接口加 `local`、`s3` 两份实现，读路径的 302 重定向与对齐预签名、写路径的代理转发都在这一期定型。`generations` 与 `media_files` 的 `moderation_status` 列现在就建好，本期一律写 `skipped`。

前端按「服务端是唯一权威」改造：画布、素材、生成历史三处 store 去掉 `persist` 与全量加载，改为 react-query 按需拉取与防抖回写；浏览器 IndexedDB 不再保存业务数据，媒体展示直接用 `/api/media/{key}`。删除 `app-sync.ts` 与客户端媒体垃圾回收，孤儿回收改由服务端负责。上传接口加上「未验证邮箱禁止上传」的约束。

数据资源化验收通过后，再执行 WebDAV 的整体移除。

这一期是全期里前端改动最重的一期，重点不在接口本身，而在数据加载时机与缓存策略的改造，排期时要留出余量。

验收标准：A 设备创建画布并生成图片，B 设备登录同一账号后能看到完整画布与图片原文件；A 设备删除画布后 B 设备刷新列表不会再看到它；画布列表能分页、能按标题搜索，且列表响应体不含 `data`；两台设备同时编辑同一张画布时，后保存的一方收到 409 而不是静默覆盖；未验证邮箱的账号上传被拒绝；退出登录后不会看到上一个账号的任何数据（react-query 缓存与 store 已清空）；`STORAGE_DRIVER` 在 `local` 与 `s3` 之间切换后，上传与显示都正常，且 302 响应的 `Cache-Control` 不含 `immutable`。

### 第三期：档位、点数账本与管理后台

实现 plans、usage_records 与配额校验，写入 free、paid、sunset 三档默认数据，`/api/me` 返回当前档位、存储用量、双桶余额、`paidUntil` 与免费额度剩余次数，前端个人中心展示，上传前做存储配额与单文件上限拦截，降档路径按付费身份现算并落 `sunset`。

同期实现点数与支付的账本侧：credits（双桶加 `paid_until`）、credit_transactions（带 `bucket`、金额以微元计）、credit_packages、orders 四张表，充值档位、下单、订单列表与取消，以及两个渠道的回调验签与幂等处理，前端新增 `/billing` 充值与流水页。免费额度的档位定义与计数器也在这一期建好，但真正的消耗判定要等第四期——在那之前没有任何东西会消耗它。

同期实现媒体保留期清理：按最后触达时间现算过期，与孤儿文件回收合并成同一个扫描任务，到期前 2 天发预警邮件、站内提示并提供一键导出入口。

同期实现模型目录与价格体系：`model_catalog`（含 `free_trial_eligible`）、`/api/models` 与管理后台的模型增删改查、参数价格矩阵与限时折扣活动，为第四期的报价与转发提供唯一事实来源。

同期实现账号注销闭环：自助申请、冷静期撤销、到期匿名化与业务数据软删除（详见「账号相关」一节），作为开放注册前的合规前置项。

同期实现管理后台：`/admin` 路由与 `RequireAdmin` 守卫，用户列表、封禁解封、点数增减、订单查询、充值档位配置、用量查看与总览统计。

需要清醒认识的是，这一期结束时点数只是一个能充值、能查账的余额，还没有任何东西会消耗它。因此在第四期上线之前不要对外开放充值入口，否则等于卖一个暂时兑现不了的东西。

验收标准：超出存储配额或单文件上限时上传被拒绝并给出明确提示；用户能完成一次真实支付并看到 `purchased` 桶余额与 `paid_until` 正确增加、赠送部分进 `granted` 桶且两条流水都在，同一笔支付重复回调不会重复加点，取消后的订单再回调也不会加点；只有 `granted` 余额的账号不被判为付费用户；充值后把点数花光但仍在权益期内的账号保持付费档，权益到期后落 `sunset` 而不是直接落 `free`；对任意用户按桶验证 `SUM(amount_micros)` 等于对应桶的余额；超过保留期且长期未触达的媒体被清理，而近期编辑过的画布所引用的媒体不受影响，清理前 2 天能收到预警邮件；管理员能在后台查到任意用户的存储占用与两桶余额并按指定桶手工增减点数，非管理员访问 `/admin` 与管理接口均被拒绝；账号注销能完成申请、冷静期撤销与到期匿名化的全流程，注销后原邮箱重新注册得到的是全新账号。

### 第四期：AI 请求后端转发与点数计量

沿用第三期建好的 `model_catalog`（含 `free_trial_eligible`）与 `/api/models`，本期为其补上渠道绑定列，把模型能力、参数约束与计费规则接入转发链路；管理后台补上平台渠道的增删改查。后端新增 `internal/provider` 与 `internal/service/upstream.go`，以及 `/api/ai/*` 转发接口与 `/api/ai/quote` 预估接口（视频改为异步任务，创建与查询各占一个），实现三种上游协议的适配与 SSE 流式转发；平台渠道的 Key 加密存在 `platform_channels` 表里，由 `/api/admin/channels` 管理并支持按优先级故障转移。前端新增 `web/src/services/api/ai.ts` 作为唯一的生成调用路径，`image.ts`、`video.ts`、`audio.ts` 保留签名、内部全部改为调用 `ai.ts`，直连协议实现、自定义脚本（`model-plugin.ts`）与本地 AI 渠道配置整体删除，参数表单按 `constraints` 动态渲染。扣点在转发链路里完成：先判免费额度，不适用则先扣后生成、失败整笔退还；对话与语音按次固定价。

这一期和第三期的点数体系是同一件事的两面。第三期解决「怎么把点数卖出去」，第四期解决「点数怎么被消耗掉」；缺了后者，前者卖的就是一个无法计量、也无法兑现的东西。这也是它必须紧接着第三期做、不能无限期后排的原因。

它同时是整个收费模型的技术地基。平台 Key 只有放在服务端，扣点才可能准确；只有扣点准确，点数才敢作为商品出售。「全部生成走服务端渠道、按点数计量」这条商业规则也在这一期落地，浏览器里从此不存在任何 API Key 与上游域名。

验收标准：使用平台预设模型生成图片、视频与语音都能成功，点数按模型的计费规则正确扣减并留下流水；新账号在锁定参数下能用掉 3 张图与 1 个视频的免费额度且不产生点数流水，第 4 张图自动改走点数而不是报错，把参数调出锁定组合时同样直接走点数；`free_trial_eligible = false` 的模型拿不到免费额度；`/api/ai/quote` 的返回与实际扣费逐项一致；画布里的助手对话是逐字流式输出而不是整段返回；余额不足时生成入口被拦截并提示充值；上游报错或超时时点数不被扣掉，已预扣的能退回原桶并留下退还流水；浏览器网络面板里看不到任何第三方域名、API Key 与直连请求；配置页没有任何渠道、Key 或脚本入口；模型参数表单只展示该模型 `constraints` 支持的选项，不支持的组合直接禁用。

### 第五期：内容审核

接入开源审核方案（图片 NSFWJS、文本 Detoxify，视频抽帧复用 NSFWJS），在写路径上落审核：`/api/ai/*` 转发前审提示词与参考图、产物落盘前审产物，`PUT /api/media` 在入盘前审文件。结论写进第二期就建好的 `moderation_status` 列，管理后台新增审核记录列表、人工复核与命中统计。审核记录只存内容哈希、命中标签与服务商返回的摘要，不存原始文本与图片。

**这一期必须在对外开放注册之前完成。** 这和第三期「第四期上线之前不要对外开放充值入口」是同一类的硬约束，不是排期建议：面向中国大陆运营、允许任何人注册、又能调用平台的生成能力，三者同时成立而没有审核，是一个不能承担的合规敞口。算法备案与大模型服务备案同属上线前置事项，同样要在开放注册前完成，具体流程由法务确认。

要提前说清楚的是**审核的覆盖口径**。全部生成走服务端转发、全部上传走 `PUT /api/media`，所以站内的输入与产物都在服务端手里，全链路可审，合规口径可以覆盖站内全部生成与上传。范围之外的只有一件事情：用户在自己的第三方工具里如何使用导出的内容，那不经过本站，也不属于本站能承诺的部分。前端可以在输入框上做一层提示性拦截以减少无谓的上游调用，但它运行在用户可以随意修改的环境里，**只能当提示，绝不能当合规依据**——服务端那一道校验一次都不能省。

**产物审核命中扣点不退。** 上游的钱在产物生成出来的那一刻已经真实付掉了，审核只决定这份产物能不能留下。如果不通过就退点，等价于开出一条「用违规提示词免费打算力」的路径，而这条路径不需要任何技术门槛就能被反复利用。误判的补偿走 `type = grant` 的人工补偿，不复用 refund 路径——两者在账上是不同性质的事，混用会让退款金额里混进一部分从来没有对应过真实资金的补偿。这条规则必须提前写进服务条款与生成页提示，不能等用户被扣了点之后才在客服口径里解释。

验收标准：平台模型的违规提示词在转发前被拦下并给出明确原因；违规产物不落盘、生成记录标记为 `rejected` 且点数不退还；用户上传的违规参考图或素材在入盘时被拦下；审核服务不可用时按 `MODERATION_FAIL_MODE` 的显式配置处置并告警，没有配置时启动失败；审核记录里查不到任何原始文本或图片；管理员能改判结论并通过 `granted` 桶补偿完成一次误判处理。

## 影响与破坏性变更

- **取消免登录模式**，全站功能登录后使用，未登录访问任何业务页面都被重定向到登录页。数据层只有服务端一套实现，浏览器 IndexedDB 不再保存业务数据。
- **用户自定义 AI 渠道整体移除**。用户不再能配置任何 API Key、baseUrl 与自定义模型，`model-plugin.ts` 自定义脚本一并删除；模型只能来自平台目录，本机此前配置的渠道在第四期切换后失效。愿意自带 Key 的用户不再是本产品的服务对象。
- **本地已有数据不会自动上云。** 注册登录之后，本机已有的画布与素材不会自动出现在云端账号里。这一条与「登录只是多了一份备份」的直觉相反，是最容易招来投诉的一处，界面上必须显式说明；用户可以先用现有的画布导出功能导出 zip，登录后再通过导入入口带上去。
- **WebDAV 同步整体移除**，原先依赖 WebDAV 做跨设备同步的用法不再支持，改由服务端统一存储。
- **前端数据层大改**，画布、素材、生成记录全部改为服务端按需加载，store 不再持有全量数据，依赖这些 store 直接读全量列表的组件都要跟着调整；`app-sync.ts` 的合并逻辑与媒体缓存层整体废弃，不再复用。
- **离线能力移除。** 数据权威在服务端，断网后既读不到未缓存的画布，也保存不了修改，产品文案要说清楚。
- **Vercel 静态部署不再可用**，纯静态部署无法提供登录与后端 API，完整能力只支持 Docker 自部署。
- **媒体改由 S3 兼容对象存储承载**，读路径是 302 重定向到预签名 URL 而不是后端直出二进制。部署方需要准备一个私有桶与一对只授权该桶的密钥；`STORAGE_DRIVER=local` 仍可退回磁盘卷；用 R2 时必须确认 `r2.dev` 公开域名没有被启用。
- **新增 SMTP 依赖**，没有可用邮件服务时注册流程无法完成。
- **新增支付渠道依赖**，需要支付宝或微信的商户资质与密钥，且回调地址必须公网可达，纯内网部署无法完成支付闭环。
- **v1 不支持退款**，点数一经充值不退，需写进服务条款；`orders.status` 的 `refunded` 枚举保留但不启用。
- **AI 请求链路收敛为一条**，全部经后端转发，前端不再直连任何上游；模型能力与参数约束全部来自平台目录，不再有「自己填接口就能用」的自由度。
- **平台承担全部第三方调用成本**，每次生成都直接产生真金白银的成本。计费规则配错或扣点链路有洞，亏的是平台的钱。
- **付费权益到期会自动降档**，付费用户在 `paid_until` 过期且购买余额归零后先落 `sunset` 日落档（200 MB、保留 7 天）并宽限 60 天，之后落到免费档的 50 MB；已用存储超过新档位上限时进入只读模式，宽限期结束仍超额的从最旧的媒体开始清理。这是产品行为而不是故障，必须在界面和邮件里说清楚。
- **媒体不再永久保留**，所有媒体按档位的保留期计时（免费与日落档 7 天、付费档 15 天），长期未触达的会被清理。这与「上传即永久保存」的直觉相反，是本次改动里最需要提前告知用户的一条。
- **审核不通过的生成同样消耗点数。** 上游成本在产物生成时已经发生，审核只决定它能不能留下；误判走人工补偿而不是退款。这条要同时写进服务条款与生成页提示。
- **项目定位从纯本地工具变为登录后使用的多用户服务**，`AGENTS.md` 中「外部服务请求统一放在 `web/src/services/api/`，由浏览器前端直连，不假设存在项目后端」这条规则必须修订：AI 请求统一走后端转发，业务数据的读写统一走资源客户端与 react-query 而不是各自直接调 localforage。
- 项目尚未上线，不做旧数据迁移。本机浏览器里已有的 IndexedDB 数据保留原样但不再是产品的一部分，不会在首次登录时被自动搬到云端账号。
- `canvas-agent` 不受影响，仍然是连接 `127.0.0.1:17371` 的本机工具，与多用户后端是两条独立链路。

## 实施时需要重点盯的风险

方案层面的决策已经全部敲定，以下是落地过程中最容易出问题的地方。

**客户端垃圾回收必须整块删除，不能迁移。** 现有的 `cleanupImages` 与 `cleanupUnusedMedia` 通过扫描「全部素材加全部画布」来判断哪些媒体没人引用，然后删掉孤儿文件。这套逻辑成立的前提是前端手里有全量数据——而按需加载恰好推翻了这个前提，改造后前端只持有当前打开的那一张画布，在这个前提下运行的客户端 GC 会把其它画布正在引用的图片当成孤儿删掉，这是本方案唯一可能直接造成数据丢失的地方。

既然全站登录后使用、媒体缓存层整体删除，这段逻辑就没有任何存身之处：没有「匿名态需要它」的例外，不做 `local/` 迁移，不做多态实现，连同 `image-storage.ts`、`file-storage.ts` 一起删干净，并用验收清单确认 `cleanupImages`、`cleanupUnusedImages`、`cleanupUnusedMedia` 三个名字全局无残留。孤儿媒体回收改为服务端职责。

**服务端的孤儿文件回收可以留到第三期。** 它与存储用量重算、媒体保留期都需要扫描三张业务表的 MySQL `JSON` 字段，三者共用同一次扫描。顺带记录一个既存 bug 供参照：旧 `cleanupUnusedMedia` 收集引用时漏扫了两个生成日志库，只存在于视频历史里的媒体会被误判为孤儿——这个函数随 GC 一起删除，问题自然消失，但说明「前端判断引用关系」这条路本身不可靠。

**支付回调的幂等与时序。** 渠道会重试回调，也可能乱序到达，甚至可能在用户已经手动取消订单之后才到。加点必须以 `orders.provider_order_id` 唯一索引加订单状态机为准，只允许 `pending → paid` 这一次跃迁，重复回调返回成功但不做任何写入。订单状态、两个桶的余额、`paid_until` 与两条点数流水必须在同一个事务里写完，任何一处失败都整体回滚——回调半成功比回调完全失败难查得多，而且用户会直接感知为「钱付了点没到」。还要处理「回调先于下单响应到达」这种情况：下单事务尚未提交时回调查不到订单，需要有重试或延迟处理机制，不能直接当成非法请求丢掉。

**点数扣减与生成结果的一致性。** 这是第四期最容易出事的地方，两个方向都会出问题：扣了点但生成失败，用户会认为平台在骗钱；生成成功但没扣到点，亏的是平台。可靠的做法是转发前按 `credit_cost` 扣减并记消费流水（跨桶则两条），失败时整笔退还到原来的桶，退还同样写 `type = refund` 流水，而不是直接改余额——余额可以事后重算，流水不行。不要做「按实际结果补差」：第三期只提供 `Reserve` 与 `Refund` 两个方法，一次生成要么扣成、要么整笔退回，多一条结算路径只会多一种对不上账的可能。视频生成这类耗时长、可能异步出结果的场景要特别小心：请求已经发出但连接断了，点数到底扣不扣，必须有明确结论并在实现里写死，而不是听天由命。

**平台下架模型的存量引用。** 用户的历史生成记录甚至画布节点里可能还引用着已经从目录下架的模型——读取历史时不能因为目录里查不到就报错或渲染成空白。下架只应影响新的生成请求，不应破坏历史内容的展示。

**成本失控，但失控点已经换了地方。** 配额降到 50 MB 之后容量不再是问题，真正需要盯的是**出网流量**与**免费生成额度**：前者随读放大增长，后者随注册量增长，两者都不会体现在磁盘水位上。配额校验仍然必须在文件写入前完成，不能先落盘再统计；邮箱验证前禁止上传这条约束不能省略；流量与免费额度的日消耗告警要和存储水位告警一起配好，`FREE_TRIAL_ENABLED` 与 `REGISTRATION_ENABLED` 两个阀门要确认真的能一键关掉，而不是只写在文档里。

**预签名 URL 的缓存与过期。** 这条已经在 API 一节写清了规则，之所以在风险里再提一次，是因为它的错误形态极具欺骗性：给 302 响应加上长缓存在开发和测试期间完全正常，问题要等到预签名过期的那两个小时之后才出现，届时表现是全站图片突然集体裂开、刷新无效、服务端日志里干干净净没有任何请求。上线前要专门验一次：拿到 302 响应检查 `Cache-Control` 不含 `immutable`、`max-age` 小于预签名剩余时间，再把系统时间往后推过有效期确认浏览器会重新回源。

**账号切换时的缓存隔离。** 数据权威在服务端，但 react-query 缓存与内存 store 里仍然存着上一个账号的数据。登录、退出、切换账号三个时刻都必须清空缓存与 store，否则下一个账号会在极短的时间窗口里看到上一个账号的画布列表——这在代码上看起来完全正常，本地自测几乎不可能发现，要作为专项用例测试。

**审核链路的三处边界。** 一是**性能**：审核是一次同步的外部调用，串在生成与上传的关键路径上，超时设置与降级策略必须显式配置（`MODERATION_FAIL_MODE`），不能让审核服务的抖动直接变成产品不可用。二是**误判**：命中不通过但扣点不退，这条规则本身没问题，但如果误判率高到需要频繁人工补偿，那是策略阈值该调而不是靠客服兜，命中统计接口就是用来发现这一点的。三是**对外表述的准确性**：站内生成与上传全链路可审可以写进合规口径，但不要顺手扩大成「用户的全部内容均经审核」——用户导出后的使用、用户设备本地的内容不经过本站，那不是本站能承诺的部分。

**保留期清理的误删风险。** 清理范围包含画布正在引用的媒体，这意味着最后触达时间一旦算错就是直接删用户的图。上线前必须先跑一段只扫描不删除的观察期，把「将被清理」的清单打出来人工核对；预警邮件和站内提示要确认真的发得出去；清理动作本身建议先软删除再延迟物理删除，留出可恢复的窗口。

**邮件送达率。** 自建 SMTP 很容易被判为垃圾邮件，导致用户收不到验证邮件而无法完成注册。建议使用成熟的邮件服务商，并在注册后的界面上明确提示「没收到可以重发」，同时提供重发入口。

**前端按需加载的改造深度。** 这是本方案里最容易被低估的一块。现有代码默认「数据已经全在内存里」，很多地方直接遍历全量列表；改成按需加载后，加载态、空态、分页边界、详情未就绪时的渲染都要逐处处理。建议先把画布跑通形成范式，再套用到素材与生成记录，不要三块并行改。

**乐观锁的冲突体验。** 单条记录级的 `revision` 把冲突范围缩到了最小，但同一张画布在两台设备上同时编辑仍会产生 409。前端必须给出明确的处理路径——提示冲突、拉取最新版本、让用户决定，而不是静默覆盖或直接丢弃用户当前的编辑。

**防抖保存的边界情况。** 画布编辑靠防抖回写，要处理好关闭页面、切换画布、网络失败这几种情况下的未保存内容，否则用户会遇到「改了但没存上」。保存失败必须有可见反馈和重试入口。

**WebDAV 移除的牵连范围。** 它同时涉及 store 字段、配置导出、配置页 UI 和两个语言包，删除时容易漏掉一处导致类型报错或界面残留。务必等第二期数据资源化验收通过后再动手。

**首个管理员的创建方式。** 需要在部署文档里写清楚，否则会出现「后台建好了但没人能登进去」的情况。
