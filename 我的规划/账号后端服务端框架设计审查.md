# 账号后端服务端框架设计审查

本文档是对[账号后端总规划](账号后端总规划.md)及第一期到第五期执行计划的服务端框架审查。审查对象是当前分支 `codex/account-backend-plan`（`9f57791`，代码基线 `d213a74` / v0.18.0），并合并了 `项目对话记录.md` 中此前一轮审查的结论。

本文只做核验，不改任何规划结论。每条判断都给出当前仓库中的文件与行号依据；无法由现有材料确认的事项全部列为「待决策」，不做推断。

## 一、版本与分支现状

### 1.1 三个 main 的实际状态

| 引用 | 提交 | `VERSION` | 实际状态 |
| --- | --- | --- | --- |
| `upstream/main` | `d213a74` | v0.18.0 | fork 源头最新版本，已 fetch 到本地 |
| 本地 `main` | `d213a74` | v0.18.0 | 与源头完全一致，当前跟踪 `upstream/main` |
| `origin/main` | `616630b` | v0.15.1 | 落后源头一个版本，含 5 个早期规划文档提交，与 `main` 已分叉 |
| `codex/account-backend-plan` | `9f57791` | v0.18.0 | 源头 + 1 个文档提交，已推送 `origin/codex/account-backend-plan` |

补充事实：

- 归档 tag `archive/account-backend-plan-2026-09-11` 存在，保留旧规划线。
- `origin/main` 不是本地 `main` 的祖先（`git merge-base --is-ancestor` 判定为否），即两条线已经分叉，不是简单的落后。
- 当前分支相对源头只改了文档：`git diff upstream/main..HEAD` 共 16 个文件，其中 14 个在 `docs/`，另加 `README.md` 与 `CHANGELOG.md`，没有 `web/`、`canvas-agent/`、`plugins/` 的任何改动。

### 1.2 回答「fork 源头和当前分支一样吗」

代码一样，文档不一样：

- 两边代码都是 v0.18.0（`d213a74`），当前分支没有落后、没有代码分叉。
- 当前分支比源头多 1 个纯文档提交（账号后端规划、项目结构、Fork 维护约定）。
- `origin/main` 不是当前有效基线：它是 v0.15.1 加上另一条规划文档线，既落后源头，也落后当前分支。

### 1.3 与 Fork 约定文档的差异

`docs/content/docs/development/Fork同步与部署约定.md:16` 定义 `main` 为「唯一的长期稳定集成分支，包含最新源头代码和已经接受的本 Fork 改动」，`:25-33` 的同步流程是 merge `upstream/main` 后 `git push origin main`。

实际状态是本地 `main` 跟踪 `upstream/main`、不含任何规划；`origin/main` 停在 v0.15.1 且已分叉。约定与现状不一致，处理方式见待决策项 D1。

## 二、总体结论

框架方向合理，但现状不能直接进入编码。理由：

- 分层、数据模型、计费账本、媒体读路径、安全边界和阶段门禁都有明确设计，关键决策在规划文档 `账号后端总规划.md` 与各期执行计划中已闭环。
- 有 2 处文档自相矛盾必须先修：第一期路由守卫（3.7）、媒体读路径缓存（4.1）。
- 有 4 处设计缺口需要补齐或明确接受：支付订单号与回调时序（3.2）、对象存储与数据库一致性（3.3）、AI 请求异常终态（3.4）、登录态 API Key 持久化（3.6）。
- 另有 2 处排期与门禁问题：第三期体量（3.8）、前端测试门禁（4.3）。
- 上一轮对话中提出的并发扣点、视频任务表缺失、多实例假设三点，经本轮核验已在文档中覆盖，本文件正式撤回（4.5）。

### 3.1 AutoMigrate

现状：规划与第一期到第三期都依赖 `AutoMigrate` 建表（`账号后端总规划.md:216`、`:256`；`第一期-账号体系与邮件链路.md:173`、`:183`；`第二期-数据资源化与对象存储.md:156`、`:229`；`第三期-点数计费与管理后台.md:122`），并且 `第二期-数据资源化与对象存储.md:675` 明确写了「项目尚未上线，没有需要保留的线上数据，后端只要 `AutoMigrate` 建表即可，不需要迁移脚本」。

判定：这是当前阶段的显式决策，不是遗漏；风险不在开发期，而在首次对外发布并产生真实用户数据之后，删列、改名、改索引这类结构变更 `AutoMigrate` 处理不了。处理方式见 D6。

### 3.2 支付订单字段与回调时序

现状：

- 订单模型只有 `ProviderOrderID`（`第三期-点数计费与管理后台.md:185`），文档未定义商户订单号列。
- 回调解析结果里出现了 `outTradeNo`（`第三期-点数计费与管理后台.md:490`），但没有写它映射到哪个字段、回调用什么键查订单。
- 幂等依据是 `provider_order_id`（`第三期-点数计费与管理后台.md:589`、`账号后端总规划.md:725`、`:1117`）。
- 总规划承认「回调先于下单响应到达」需要重试或延迟处理（`账号后端总规划.md:1117`），但第三期执行计划没有给出机制（全文没有 `payment_events` 之类的落表）。
- 建单接口目前只有 10 单/小时的限流（`第三期-点数计费与管理后台.md:484`），没有下单幂等 key。
- 有超时订单主动查渠道的兜底（`第三期-点数计费与管理后台.md:604`）。

判定：部分成立。需要明确 `outTradeNo` 与 `orders.id` 的关系、回调查找键，以及「查不到订单」的重试或落表策略。处理方式见 D5。

### 3.3 对象存储与 MySQL 一致性

现状：

- 第三期写「校验与写入必须在同一事务内，先占用后写盘，失败则回滚计数」（`第三期-点数计费与管理后台.md:533`），但数据库事务回滚不了已经写入对象存储或本地磁盘的文件。
- `media_files` 没有对象状态列，删除是硬删除（`第二期-数据资源化与对象存储.md:199-211`、`:223`）。
- 文档承认计数可能漂移，提供人工「重算存储用量」入口（`第三期-点数计费与管理后台.md:344`）。
- 审核路径有隔离区、TTL 和幂等重试（`第五期-内容审核与人工复核.md:121`、`:129`），并且自己把「状态与文件不一致」列为阻断级故障（`第五期-内容审核与人工复核.md:107`），但普通上传路径没有对应状态机。

判定：成立。至少要明确补偿策略（对象状态列 + 对账扫描），或显式接受人工重算这一兜底。处理方式见 D4。

### 3.4 AI 请求异常状态

现状：

- `AIRequest.Status` 取值是 `running | succeeded | failed | refunded`（`第四期-AI请求后端转发与点数计量.md:665`），`RefundPending` 只覆盖「退款写库失败」（`第四期-AI请求后端转发与点数计量.md:447`）。
- 视频任务有 `AITask` 表和启动恢复轮询（`第四期-AI请求后端转发与点数计量.md:306`、`:577`、`:679`）。
- `ai_requests` 没有对应的启动对账或超时收敛，进程在请求进行中崩溃后，记录会停在 `running`，预扣点数没有结论。
- `idempotencyKey` 被明确设计为可选（`第四期-AI请求后端转发与点数计量.md:479`），与项目对话记录中建议的「强制幂等」相反，这是已经写明的决策而不是遗漏。

判定：部分成立。需要补 `running` 请求的终态与对账规则，或者明确接受人工处理。处理方式见 D3、D8。

### 3.5 媒体 Cookie

现状：项目对话记录指出的问题在当前文档里已经落地解决：

- 中间件规则写死为 `GET` 与 `HEAD` 接受 `ic_media` cookie 或 Bearer，`PUT` 与 `DELETE` 只接受 Bearer（`第二期-数据资源化与对象存储.md:481`）。
- 上传始终走带 `Authorization` 头的请求（`第二期-数据资源化与对象存储.md:485`）。
- CSRF 策略是 `SameSite=Lax` 加 refresh 只接受 POST，明确不引入 CSRF token（`第一期-账号体系与邮件链路.md:152`）。
- 第一期的「只对 GET 与 HEAD 生效」（`第一期-账号体系与邮件链路.md:156`）是设计意图，第二期已给出实现规则。

判定：已覆盖，不需要按项目对话记录的原意修改，最多把第一期的措辞对齐第二期。

### 3.6 登录态 API Key 持久化

现状：

- 配置 store 用 zustand `persist` 持久化整个 `AiConfig`（`web/src/stores/use-config-store.ts:3`、`:207`），`AiConfig` 与 `ModelChannel` 都直接包含 `apiKey` 字段（`web/src/stores/use-config-store.ts:22`、`:30`、`:32`）。

判定：成立。文档需要写清登录态 Key 的持久化策略与导出脱敏规则，见 D2。

### 3.7 路由守卫冲突

## 四、本轮核验新增发现

### 4.1 媒体读路径与缓存描述矛盾（优先修）

同一接口在三处写法不一致：

- 总规划：`GET /api/media/{storageKey}` 是「302 重定向到预签名 URL；本地磁盘驱动下直接回流二进制」（`账号后端总规划.md:666`），并且 302 响应自身的 `Cache-Control` 只能是 `private, max-age={剩余秒数 - 60}`，绝不能加 `immutable`（`账号后端总规划.md:684`），本地驱动直接回流（`:690`）。
- 第二期任务表：明确写「302 预签名读取」（`第二期-数据资源化与对象存储.md:47`）。
- 第二期接口表和缓存段落：写的是「返回二进制流，带 `ETag` 与 `Cache-Control: private, max-age=31536000, immutable`」（`第二期-数据资源化与对象存储.md:459`、`:567`），没有按驱动区分。

风险：如果实现者按第二期接口表的字面意思，把一年 `immutable` 加到 S3 驱动的 302 响应上，就是总规划 `:684` 明确警告过的故障形态——浏览器缓存住带签名的重定向，签名过期后再也不回源，全站图片集体裂开。如果第二期的本意是「本地驱动直出二进制时用 `immutable`」，则需要按驱动拆成两行写清楚。

### 4.2 模型目录与充值档位的归属矛盾

- 总规划：模型目录与充值档位配置在第四期补上（`账号后端总规划.md:98`），第四期新增 `model_catalog` 表（`:1062`）；第三期管理后台只列了充值档位配置（`:1054`），同一份文档里 `:98` 与 `:1054` 本身也不一致。
- 第三期执行计划：模型目录、价格矩阵、促销和 `/api/models` 已经在第三期建设（`第三期-点数计费与管理后台.md:14`、`:205`、`:498`），任务 6 也包含模型目录（`:44`）。
- 第四期执行计划：把 `model_catalog` 当作第三期已交付的前置条件（`第四期-AI请求后端转发与点数计量.md:8`、`:93`）。

判定：分期执行计划已经把模型目录前移到第三期，总规划的对应段落未同步。需要确定以哪一份为准，并统一 `plan:98` 与 `plan:1054`。

### 4.3 前端测试门禁与现状不符

总规划要求前端至少通过 `bun run typecheck`、`bun run test`（`账号后端总规划.md:81`），但 `web/package.json:6-13` 只有 `dev`、`build`、`typecheck`、`start`、`format`、`format:check`，没有 `test` 脚本；`canvas-agent/package.json:19` 才有测试脚本。当前门禁里的 `bun run test` 无法执行。

### 4.4 术语不一致：repository

见 3.9。统一为 service 直连即可，不需要新增目录。

### 4.5 上一轮结论撤回

以下三点在上一轮对话中被提出，本轮核验确认文档已覆盖，予以撤回：

- 并发扣点原语：第三期已写「在事务中锁定该用户的 `credits` 行」（`第三期-点数计费与管理后台.md:156`）与 `Reserve` 在事务中锁定余额（`:304`）。
- 视频任务状态落点：第四期有 `AITask` 表、服务端主动轮询与启动恢复、平台链路不再使用 `PATCH /api/generations/{id}`（`第四期-AI请求后端转发与点数计量.md:306`、`:577`、`:679`）。
- 多实例假设：文档显式限定单实例，并记录扩容触发条件（`第一期-账号体系与邮件链路.md:60`、`:167`；`第四期-AI请求后端转发与点数计量.md:24`、`:62`）。

## 八、2026-09-12 设计变更注记

用户在本次审查后拍板了两个方向性变更，本节的核验结论凡与之冲突的，以本注记为准：

1. **取消免登录模式，全站功能登录后使用。** 全部业务路由包 `RequireAuth`，数据层只有服务端一套实现，浏览器 IndexedDB 不再保存业务数据。据此：
   - 3.7「路由守卫冲突」的修复方向反转：保留 `RequireAuth` 全覆盖的写法，撤销第一期中「业务路由匿名可访问」的纠偏行（该行已在本次修订中改为相反语义）。
   - 低优先级观察项中「前端垃圾回收迁移到 `services/data/local/`」不再成立：GC 连同媒体缓存层整体删除，孤儿回收由服务端负责。
2. **取消用户自定义渠道与用户凭据托管，AI 渠道全部由服务端配置。** 模型只能来自 `model_catalog`，浏览器不持有任何 Key、baseUrl 与自定义脚本。据此：
   - 3.6「登录态 API Key 持久化」的暴露面随用户凭据一起消失；`user_credentials` 表、`/api/credentials` 接口与第二期凭据托管章节已从文档中移除，AES-GCM 能力挪到第四期为 `platform_channels` 服务。
   - D2「登录态 API Key 持久化与导出」已决策关闭：不存在登录态用户 Key，无需制定持久化与脱敏规则；第四期删除 `use-config-store` 的渠道字段与 `config-file.ts` 的 AI 配置导出。
   - 第四期由「平台模型转发 + 用户渠道直连」双路径改为单一路径，`::` 渠道编解码、`model-plugin.ts`、`seedance-video.ts` 与全部直连协议实现随期删除。
   - 第五期审核覆盖面从「平台链路可审、用户直连只能拦上传、匿名不可达」收敛为「站内生成与上传全链路可审」，对外合规口径相应改写。
