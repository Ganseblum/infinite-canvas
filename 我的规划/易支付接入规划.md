# 易支付接入规划

本文档规划在第四期已交付的支付体系上新增易支付（EasyPay，彩虹易支付协议）通道。订单状态机、点数账本、报价预扣与回调幂等全部沿用现有实现，只新增一个渠道适配。

## 背景与结论

- 现有渠道只有支付宝（PC 网页支付）与微信（Native 扫码），都需要企业商户资质与公网回调域名，测试期无法真实跑通。
- 易支付是聚合通道，个人/小体量也能开通，且该协议被大量站点使用，接入成本低，适合测试与早期收款。
- 已只读调研同机部署的 sub2api（`/opt/sub2api`，LGPL-3.0）：其易支付实现包含页面跳转、API 下单、查单与退款。**本规划只参考公开协议，自行实现，不复制其代码。**
- 首期只做支付宝（用户当前易支付通道支持支付宝），协议同时支持微信，保留 `type` 映射配置，后续可开。

## 协议摘要

### 1. 页面跳转下单（首期采用）

浏览器跳转 `{apiBase}/submit.php?...`，参数：

| 参数 | 说明 |
| --- | --- |
| `pid` | 商户 ID |
| `type` | 支付方式，如 `alipay`、`wxpay` |
| `out_trade_no` | 我方订单号，即 `orders.id` |
| `notify_url` | 异步通知地址 |
| `return_url` | 支付完成后的浏览器回跳地址 |
| `name` | 商品名，取充值档位名称 |
| `money` | 金额，元，两位小数字符串（如 `1.00`） |
| `cid` | 可选，通道 ID；不同支付方式对应不同通道 |
| `device` | 可选，`mobile` 表示手机端 |
| `sign` / `sign_type` | 签名与签名方式，固定 `MD5` |

### 2. 签名算法

- 剔除 `sign`、`sign_type` 与空值后，参数按 key 的 ASCII 升序排列；
- 拼接为 `k1=v1&k2=v2...`，**末尾直接追加商户密钥**（不加 `&key=`）；
- 取 `MD5` 小写十六进制。

验签必须用常量时间比较（`crypto/hmac.Equal`），比较前对回调参数先做 URL 解码（`url.ParseQuery` 已解码，不重复解码）。

### 3. 异步通知

- 易支付以 GET/POST 把参数回调到 `notify_url`，验签通过且 `trade_status == TRADE_SUCCESS` 视为支付成功；
- 必须校验 `out_trade_no` 与 `money`（金额必须与订单快照一致），不一致拒绝并记日志；
- 处理成功后响应体固定输出 `success`（不换行），否则易支付会按策略重试；
- 重复通知靠现有 `provider_order_id` 唯一索引与订单状态判断幂等。

### 4. 查单（超时订单兜底）

`POST {apiBase}/api.php`，参数 `act=order`、`pid`、`key`（商户密钥）、`out_trade_no`；返回 JSON 中的 `trade_status` / `status` / `money` / `trade_no` 形态在不同易支付实现间略有差异，解析要同时兼容顶层与 `data` 嵌套两种结构。

### 5. API 下单（首期不做，留作后续）

`POST {apiBase}/mapi.php` 返回 `payurl` / `payurl2` / `qrcode`，可做站内二维码。首期统一走收银台跳转，减少一个失败面。

## 服务端改动

| 文件 | 改动 |
| --- | --- |
| `server/internal/payment/easypay.go` | 新增 Provider：`Name()` 返回 `easypay`；`CreatePayment` 生成 `submit.php` 跳转 URL（`Params.Type = redirect`）；`VerifyAndParse` 验签并解析回调；`QueryOrder` 走 `api.php`；`PaidAmountMicros` 解析元字符串为微元 |
| `server/internal/payment/payment.go` | 现有方法签名都不用改；若采纳下面关于回调响应的建议，则新增一个 `AckResponse()` 并在支付宝、微信两个既有 Provider 上实现 |
| `server/internal/config/config.go` | 新增 `EASYPAY_*` 环境变量解析与校验 |
| `server/internal/service/payment_registry.go` | `EASYPAY_PID` 配置存在时注册渠道，未配置自动不上架 |
| `server/internal/handler/order.go` | 两处必改。① 下单校验从硬编码 `alipay` / `wechat` 改为 `registry.Has(provider)`（第 43 行）。② 回调成功响应（第 216-223 行）目前按渠道名 switch，`easypay` 会落到 `default` 分支返回 200 空 body，而协议要求响应体恰好是 `success`——不改的话订单照常入账、但网关判定通知失败并持续重推，属静默故障，验收项 5 也过不了。 |
| `.env.example` / `deploy/env.test.example` / `deploy/env.prod.example` | 补充变量与说明 |
| `docker-compose.yml` / `docker-compose.local.yml` | api 容器用 `${VAR:-}` **逐项枚举**环境变量且没有 `env_file:`，只改 env 文件不生效，必须把 `EASYPAY_*` 加进 `environment:` 列表。本地 compose 连现有 `ALIPAY_*` / `WECHATPAY_*` 都还没补，本地联调时一并加。 |

回调地址复用现有路由：`/api/payments/webhook/easypay`（`server/cmd/server/main.go:356` 的 `:provider` 通配），与支付宝、微信同层。

> 关于 ② 的改法建议：不要只加一个 `case "easypay"`。`server/internal/payment/payment.go` 的包注释写着「handler 只认这里统一后的结构，**接一个新渠道不应该改到 handler**」，而现在这个 switch 恰好违反该意图，逼着每个新渠道都回 handler 加分支。把响应格式下沉到 `Provider` 接口（例如 `AckResponse() (contentType, body string)`），handler 只负责调用，既修掉这次的问题，也让下一个渠道不再踩同一个坑。

## 环境变量

| 变量 | 必填 | 说明 |
| --- | --- | --- |
| `EASYPAY_API_BASE` | 是 | 网关地址，如 `https://pay.example.com`，代码自动去掉尾斜杠与 `/submit.php`、`/mapi.php`、`/api.php` 后缀 |
| `EASYPAY_PID` | 是 | 商户 ID |
| `EASYPAY_KEY` | 是 | 商户密钥，仅服务端保存，禁止出现在日志与响应中 |
| `EASYPAY_TYPE` | 否 | 支付方式，默认 `alipay`；支持 `wxpay` |
| `EASYPAY_ALIPAY_CID` / `EASYPAY_WECHAT_CID` | 否 | 对应通道 ID，网关要求区分通道时填写 |
| `EASYPAY_RETURN_URL` | 是 | 支付完成后的浏览器回跳地址（充值页）。协议要求 `return_url`，而现有回跳配置只有支付宝专用的 `ALIPAY_RETURN_URL`（`server/internal/service/payment_registry.go:26`），需要新增对应变量 |
| `PAYMENT_NOTIFY_URL` | 生产必须 | 已是现有变量（`server/internal/config/config.go:133`），必须公网可达，指向正式/测试各自域名。代码在留空时会回退为 `APP_BASE_URL` + `/api/payments/webhook`（第 243-244 行），但**生产环境必须显式设置**，不要依赖回退值，注册渠道时还会再拼上 `/{provider}` |

测试与正式环境各自独立配置，互不复用密钥。

## 前端改动

- `web/src/services/api/orders.ts`：`PaymentProvider` 增加 `"easypay"`。
- `web/src/i18n/locales/zh-CN.ts` / `en-US.ts`：`billing.providers` 增加易支付文案。
- `web/src/pages/billing/index.tsx`：可选渠道已从 `packages.providers` 动态渲染，渠道本身无需改动。默认值是硬编码的 `alipay`（第 32 行），仅当它不在 `availableProviders` 里时才回退到 `availableProviders[0]`（第 75-79 行）。首期「alipay + easypay」的部署下默认渠道仍是支付宝，确定；但一旦**已配置渠道 ≥2 个且不含 `alipay`**，回退结果就由 `PaymentRegistry.Names()` 的 map 迭代顺序（`server/internal/service/payment_registry.go:67-73`，无排序）决定，不稳定。若要稳定默认渠道，需在注册表里固定顺序或在接口里显式返回 `defaultProvider`。
- `web/src/pages/billing/components/payment-modal.tsx`：**需要确认，不能按「无需改动」处理**。订单轮询只在 `payment.type === "qrcode"` 时启动（第 25 行定义 `isQrcode`、第 41 行的 `enabled` 条件），易支付走 `redirect`，当前只有手动「刷新」和「打开支付页」两个按钮，没有回跳落地或自动轮询——用户付完回到充值页若不点刷新，看不到到账状态。要么补 redirect 的回跳检测/轮询，要么明确接受手动刷新这一体验。
- `web/src/pages/admin/orders/index.tsx`：订单筛选渠道选项增加易支付。

## 安全与对账

- 金额一律以订单快照 `price_micros` 为准，回调金额不匹配直接拒绝并记日志，绝不按回调金额入账。
- **现有金额校验有个短路口子要一并补上**：`server/internal/service/orders.go:197`（查单路径同 `:269`）写的是 `PriceMicros != 0 && PriceMicros != order.PriceMicros`，即**回调金额解析为 0 时整个判断被跳过、直接按本地快照到账**。易支付的 `money` 是字符串，解析失败或字段缺失时若 `PaidAmountMicros` 返回 0 就会静默放行。实现时必须让「解析不出金额」返回错误而不是 0，或把该处改成无条件比对。
- 签名失败返回 400 `INVALID_SIGNATURE`；`EASYPAY_KEY` 不落日志、不进错误信息。查单接口把密钥放在请求参数里（`act=order&key=...`），实现时禁止记录完整 URL 或原始错误响应体，否则密钥会随日志外泄。
- 通知处理与订单状态更新在事务内完成，重复通知不重复加点（现有机制）。
- 超过 30 分钟的待支付订单由现有扫描任务查上游状态后再决定置为失败，查单接口对易支付不可用时保持待支付，不误杀。
- 网关地址强制 `https`（本地联调例外，仅测试环境）。

## 验收清单（测试环境）

1. 充值档位页出现易支付渠道，下单后浏览器跳转到易支付收银台。
2. 支付完成后异步通知到 `sim-art.youc.online`，点数按订单快照入账，订单状态与流水正确。
3. 伪造 `sign` 回调返回 400，余额与订单不变。
4. 金额不匹配的回调被拒绝并留下日志。
5. 同一笔支付重复通知只入账一次，第二次仍返回**裸文本 `success`（不换行、非 JSON）**——这条同时验证回调响应格式的改造是否到位。
6. 未支付订单超过 30 分钟后，查单确认未支付才置失败；网关不可用时订单保持待支付。
7. 手机浏览器下单可正常跳转与回跳；回跳后无需手动刷新即可看到到账状态（若决定保留手动刷新，需在此项注明并确认可接受）。
8. 后台订单筛选可按易支付过滤。

## 风险与边界

- **聚合通道风险**：易支付为第三方聚合，存在资金冻结、延迟结算、服务方失联与合规风险；上线前需向用户明示支付服务由第三方提供。长期正式收款仍建议办理支付宝/微信官方商户资质。
- **v1 不支持退款**：与现有决策一致，不实现易支付退款接口；失败生成的整笔退还仍走站内点数冲正，不涉及真实资金。
- 金额只支持两位小数（整分），与现有「后台价格必须是 10000 微元整数倍」的校验一致。
- 不实现部分退款、分账、对账单拉取；对账先以查单接口为准。

## 实施顺序

1. 配置解析与 Provider 骨架（含签名与验签单元测试、金额解析测试；**金额解析失败必须返回错误，不能返回 0**）。
2. 注册渠道 + `order.go` 两处改造（下单校验 + 回调响应格式）。
3. 回调与查单联调（测试环境），确认回调响应体是裸 `success`（可用 `curl -i` 直接看原始响应，不要只看前端是否到账）。
4. 前端渠道展示、`payment-modal` 的 redirect 到账确认方式、后台筛选。
5. 测试：`server/internal/handler/billing_test.go` 与 `server/internal/service/orders_test.go` 里的 `fakeProvider.Name()` 固定为 `alipay`，回调响应分支没有端到端用例；新增渠道要补「回调响应体格式」与「验签失败返回 400」两个用例。
6. 文档更新：`.env.example`、`deploy/README.md`（支付配置一节）、`CHANGELOG.md`、`pending-test.mdx` 验收项，以及枚举了支付渠道的 `docs/content/docs/overview/features.mdx` / `features.zh-CN.mdx` 与 `我的规划/Fork同步与部署约定.md`。
