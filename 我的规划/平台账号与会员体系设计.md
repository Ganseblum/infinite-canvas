# 平台账号与会员体系设计（未上线，一步到位方案）

背景：趁未上线，把「多产品共用账号」一步到位做掉。用户在优刻注册一次，画布、blog、办公套件通用；后台管理与会员机制随之重构。本文档回答三个核心问题：架构怎么拆、充值套餐怎么算、空间怎么管。

## 一、业界调研摘要

| 产品 | 身份 | 会员 | 通用货币 | 空间 |
| --- | --- | --- | --- | --- |
| Google | 统一 Google 账号 | Google One 订阅 | 无 | **全家共享池**（Drive/Gmail/Photos 共用一个配额） |
| Adobe | 统一 Adobe ID | Creative Cloud 订阅 | **generative credits**（全应用通用，按功能扣不同量） | 共享云存储池 |
| Apple | Apple ID | Apple One 打包订阅 | 无 | iCloud 共享池（可家人共享） |
| Microsoft 365 | 统一账号 | 按人订阅 | Copilot 额度方向 | OneDrive 共享池 |
| JetBrains | 统一账号 | 按产品或全家桶订阅 | 无 | 无 |
| 国内 AI 生成平台（即梦/可灵等） | 手机号统一账号 | 会员分档送积分与特权 | **积分平台内通用**，图片/视频扣不同量 | 各产品独立居多 |

**结论**：身份统一是共识；成熟形态是「账号中心 + 权益中心」，产品只做消耗。会员 = 订阅权益层；货币 = 通用积分池（流水带产品维度）；空间 = 平台共享池 + 分产品占用明细（Google/Adobe/Apple 全是这个模式，没有一家让用户在产品间自己划配额）。

## 二、目标架构：模块化单体，不提前拆微服务

一个 Go 进程内分四个平台域（同库、表级隔离、代码按域收口），画布作为第一个业务域接入：

| 域 | 职责 | 关键表 |
| --- | --- | --- |
| identity | 身份：注册/邮箱验证/找回/注销/会话，未来的 OIDC Provider | platform_users、sessions |
| membership | 会员订阅：档位、周期、权益快照 | membership_plans、membership_subscriptions |
| billing | 平台点数：账本、充值套餐、订单、回调 | credit_accounts、credit_transactions（带 product 维度）、credit_packages、orders |
| storage | 空间：配额、占用记账、回收 | storage_accounts、storage_usage（带 product 维度） |

- 画布业务域（现有 handler/service 的其余部分）改为引用 `platform_user_id`；媒体记账、生成扣费全部带 `product="youc-canvas"`。
- 域间调用是**进程内函数调用**，不是 HTTP——不为了「架构好看」提前上微服务。等第二个产品用不同技术栈时，identity/billing/storage 三个域接口已收口，拆服务是搬运不是重写。
- 数据库：单库分域即可；不建第二个 MySQL。

## 三、会员与计费：充值套餐的答案

**套餐拆成两张表，钱进一个池子：**

1. **平台会员（订阅制）**：优刻会员 = 平台身份的订阅，分免费/标准/专业。权益 = 空间上限、生成并发、专属功能开关、每月赠送点数。会员状态全产品生效——买一次会员，画布和未来产品的会员权益同时生效。
2. **平台点数（预付货币）**：一个余额、全产品消耗。账本流水带 `product` 维度（这笔消耗发生在画布还是 blog），对账时可按产品拆分。充值套餐 = 点数包（可做「充点数送会员时长」的促销组合）。
3. **产品定价留在产品内**：图片模型的价格矩阵仍是画布的概念，blog 将来的 AI 写作价是 blog 的概念；消耗时按 `product + spec` 从平台余额扣。

现有代码的映射：`credit_packages` 拆为 `membership_plans` + `credit_packages`；`orders` 保留（带套餐类型）；`credits` 双桶与 `credit_transactions` 随账本进 billing 域；「free/paid/sunset 档位派生」改为会员订阅状态驱动。

**免费试用**改为平台新人礼：注册即赠（图片 3 次/视频 1 次的口径平移），领取、风控、每日预算逻辑随迁到 identity/billing 收口——防刷在一个地方做，不用每个产品各防一遍。

## 四、空间管理：共享池 + 分产品明细

采用 Google One / Adobe / iCloud 的模式：

- **一个平台空间账户，总配额由会员档位决定**；画布媒体、blog 附件、办公文档都从同一个池扣。
- 记账两层：`storage_usage(product, bytes)` 分产品明细 + `storage_accounts` 总账。用户界面展示「总空间 + 各产品占用」。
- 配额校验收口为 storage 域的统一 API（507/READ_ONLY 语义保留），产品业务不再各自查配额——上传前预检、写后复核的逻辑挪到平台域一次实现。
- 清理与保留期：保留期策略按产品自定义（画布的「最后触达 + N 天回收」保留），回收释放回同一个池。
- **不做按产品分配配额**：让用户在产品间自己划份额是反体验的，业界无一采用。

## 五、后台管理改造点

- 「用户」升级为平台用户：列表展示身份 + 各产品本地档案有无；封禁/注销在平台层生效于全产品。
- 新增「会员管理」模块（订阅查询、权益调整、会员补偿）；「充值档位」模块随套餐拆分改为会员套餐 + 点数包两页。
- 订单、点数调整、审计不变；流水与用量页增加 product 筛选。
- 空间维度进「用户详情」与总览卡片（总池占用、分产品占用）。

## 六、迁移路径（三步，未上线所以无数据迁移包袱，测试库直接重建）

| 步骤 | 内容 | 预估 |
| --- | --- | --- |
| M1 身份先行 | 新建 identity 域：platform_users 剥离业务字段；auth 接口路径与响应形状不变（画布前端零改动）；画布业务表挂 platform_user_id | 2-3 天 |
| M2 权益中心化 | membership / billing / storage 三域建表；画布的档位派生、扣费、配额预检改为调平台域（进程内）；免费新人礼迁移 | 3-5 天 |
| M3 OIDC Provider | authorize/token/userinfo/jwks 四端点 + 产品接入注册表（client_id/secret）；admin 会员管理模块 | 2-3 天 |

每步独立可验收；M1/M2 落地后画布行为应与现状完全一致（回归点：登录、充值、生成扣费、配额 507、注销）。

## 七、需要拍板的决策表

| 决策 | 选项 | 建议 |
| --- | --- | --- |
| 空间 | 平台共享池 / 各产品配额 | **共享池**（业界一致，体验最好） |
| 会员 | 平台会员 / 各产品会员 | **平台会员**（一次订阅全产品权益） |
| 点数 | 共享余额 / 各产品钱包 | **共享余额**（流水带 product 维度） |
| 免费试用 | 平台新人礼 / 产品各自发放 | **平台新人礼**（风控收口） |
| 套餐 | 会员订阅 + 点数包两张表 | **是**（不再一张表混装） |
| 服务形态 | 模块化单体 / 拆 identity 独立服务 | **先单体**，接口按域收口 |
| blog/办公的计费 | 免费订阅制 / 也扣平台点数 | 先免费订阅制，需要扣点时零改造（billing 已带 product 维度） |

## 八、明确不做

- 不做跨产品共享登录 Cookie（红线延续：根域 Cookie = 任何子域 XSS 全站沦陷）。
- 不提前拆微服务、不建第二个数据库。
- 不给产品间做「配额划拨」类功能。
- 不在 M3 之前动 OIDC：blog 立项前登录链路保持现状，避免无消费方的抽象。
