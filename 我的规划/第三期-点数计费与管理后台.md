# 第三期执行计划：点数计费与管理后台

本文档是[账号后端总规划](账号后端总规划.md)第三期的中文执行计划。前置条件是[第一期](第一期-账号体系与邮件链路.md)与[第二期](第二期-数据资源化与对象存储.md)已交付并通过验收。

## 范围界定

### 本期要做

双桶点数账本（`purchased` 与 `granted`）、流水、原桶退还和逐桶对账不变量，充值档位与支付订单、支付回调、`paid_until` 付费权益、三档配额与存储校验、`usage_records` 存储及一次性试用计数、平台模型目录、参数价格矩阵与限时折扣活动、媒体保留期清理与孤儿文件回收、账号注销闭环（申请、冷静期撤销、到期匿名化）、个人中心、充值页与 `/admin` 管理后台。

### 本期不做

**实际的生成扣点与免费试用消耗。** 两者发生在第四期的 AI 请求转发接口里。本期只把账本、余额、流水、免费试用计数和原桶退还机制建好，并暴露供第四期调用的内部方法。本期部署上线后不会自行出现 `consume` 流水，余额变化只来自充值、第一期已批准赠送的入账和管理员手工调整。

订阅制、自动续费、发票、退款自助申请。原方案里的两档订阅套餐已经整体作废，`subscriptions` 表在本期删除。

## 阶段目标与完成定义

本期目标是建立“任何权益变化都有来源、任何余额都能重算、任何支付都只到账一次”的财务与配额基础。完成不等于充值页能显示数字，而是双桶账本、订单状态机、档位派生、存储计数和清理任务都能在并发与故障下保持不变量。

| 目标 | 完成定义 | 主要证据 |
| --- | --- | --- |
| 双桶账本可对账 | `purchased`、`granted` 分别等于对应流水之和，跨桶消费和原桶退还可解释 | SQL 对账与并发测试 |
| 付费身份不被赠送污染 | 只有购买余额或有效 `paid_until` 产生付费档，赠送余额再多也不产生付费身份 | 档位矩阵测试 |
| 支付只到账一次 | 验签、金额校验、订单跃迁、两桶入账和权益延期在同一事务 | 重复、乱序和故障注入测试 |
| 配额为硬约束 | 上传前按派生档位检查单文件、总量和只读态，计数可重算 | 并发上传与重算测试 |
| 清理可预演可恢复 | 先扫描后执行，按用户隔离，预警后软删除并延迟物理删除 | dry-run 清单与恢复演练 |
| 管理操作可审计 | 点数调整必须指定桶和说明，封禁、清理、模型和档位操作可追踪 | 后台权限与审计记录 |

## 阶段检查与纠偏

| 偏离信号 | 说明 | 立即纠偏 |
| --- | --- | --- |
| 代码仍读取或写入 `credits.balance` | 单桶旧设计残留 | 暂停支付联调，统一改为双桶并补逐桶对账测试 |
| `granted` 余额让用户进入 `paid` | 赠送污染付费身份 | 档位解析收口到一个 service，禁止页面和 SQL 自行判断 |
| 使用 PostgreSQL 部分索引语法 | MySQL 8.0 无法创建 | 改为可空 `refund_of_transaction_id` 唯一索引，普通流水保持 NULL |
| 回调 handler 直接改余额 | 绕过账本和事务 | 只允许 order service 调 credit service，回调层只验签和解析 |
| 清理任务直接物理删除 | 一次误判就不可恢复 | 先 dry-run 和软删除，观察期后异步物理删除 |
| 前端按本地目录规则计算最终价格 | Phase 4 会产生展示与实扣漂移 | 本期只展示估算，最终报价统一预留 `/api/ai/quote` |
| Phase 4 未完成就公开充值 | 用户购买的点数没有消费闭环 | 隐藏入口并关闭下单开关，等 Phase 4 同批发布 |

出现账本差异时立即关闭下单、管理员点数调整和平台模型开关；保留查询和导出。用流水重算定位首条差异，禁止直接把余额手工改成“看起来正确”。修复后要重放导致差异的并发或回调场景，并对全用户重新对账。

## 阶段门禁

- 自动化：双桶账本、档位矩阵、支付状态机、配额并发、清理 dry-run 和管理权限测试通过。
- 财务：逐用户逐桶对账为零差异；订单金额和到账快照一致；重复回调不新增任何余额或流水。
- 数据：`usage_records.storage_bytes` 与媒体有效记录求和一致，试用计数只能增加且删除历史不返还。
- 安全：支付必须用官方 SDK 验签，密钥不入库、不进日志；管理接口全部由后端鉴权。
- 发布：本期可以先部署内部验证，但充值入口必须和 Phase 4 消费链路同时开放。

## 先说清楚：存储与生成次数都是硬约束

原方案在这里写的是「存储是硬约束、生成次数是软约束」，理由是 AI 请求由浏览器直连用户自己配置的第三方渠道、完全不经过本项目后端，服务端无法感知用户实际生成了多少次，只能依赖前端上报，技术上可以绕过。**这个结论现在全部不再成立**，因为规划已经新增第四期，把 AI 请求改成由 Go 后端转发。

**存储是硬约束。** 所有媒体文件必须经过 `PUT /api/media/{storageKey}` 才能落盘，服务端在写入前校验总量与余额状态，超额直接拒绝。这条路径没有绕过的可能。

**生成次数同样是硬约束。** 第四期之后密钥只存在于服务端、浏览器完全接触不到，用户想生成就必须走后端转发，而转发接口在发出请求前先扣点。没有点数就没有请求，不存在「改前端代码绕过计费」这条路。

所以本期的点数余额可以在产品文案里当成真实限制来描述，不需要再加「技术上可被绕过」这类免责说明。代价是**生成的计量能力依赖第四期的转发接口**：本期把账本、余额、流水和退还机制建好，但没有任何地方会调用扣点，实际消耗要等第四期上线才会发生。这个先后关系在下面的「点数扣减的一致性」里还会再讲一遍，因为它是本期最容易被误读的地方。

## 档位与点数模型

### 档位定义取代订阅套餐

`plans` 表的语义从「订阅套餐」变成「档位定义」，只描述存储侧的三个上限，不再带任何生成次数字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | varchar 主键 | `free`、`paid` 或 `sunset` |
| `name` | varchar | 展示名 |
| `storage_bytes` | bigint | 存储总量上限 |
| `max_file_bytes` | bigint | 单文件大小上限，第二期已在用 |
| `retention_days` | int | 媒体保留天数，见下面的保留期一节 |

三档的取值：

| 档位 | storage_bytes | max_file_bytes | retention_days |
| --- | --- | --- | --- |
| `free` | 50 MB（52428800） | 20 MB（20971520） | 7 |
| `paid` | 1 GB（1073741824） | 200 MB（209715200） | 15 |
| `sunset` | 200 MB（209715200） | 200 MB（209715200） | 7 |

第一期的 `SeedPlans` 写入的是旧版档位字段，本期统一为 `free`、`paid` 与 `sunset` 三档定义，并删除 `daily_images`、`daily_videos` 等旧字段。项目尚未上线，直接改模型与 seed 即可，不写迁移脚本，不做旧字段兼容。

`daily_images` 与 `daily_videos` 之所以删掉，是因为「每天多少张」这种一刀切的计数根本描述不了真实成本：同样是一次图片生成，不同模型、不同尺寸、不同质量之间的成本能差几十倍，视频更是按秒计价。这些差异用点数表达是自然的，用张数表达只能取一个所有人都不满意的折中值。

`subscriptions` 表整个删除。`paid_until` 只是充值附带的固定权益截止时间，不产生自动续费、账期、扣款失败重试或订阅状态机。

### 付费身份与降档路径

档位只通过一个服务端解析器现算，所有接口、清理任务和管理列表都复用它：

- `purchased_micros > 0 OR paid_until > now()`：`paid`。
- 否则 `paid_until` 非空且 `paid_until + 60 天 > now()`：`sunset`。
- 其余：`free`。

`granted_micros` 不参与付费身份。这样新用户拿到赠送点数后仍是免费档；用户花完购买点数但仍在权益期内继续保持付费档；权益结束后先进入 60 天日落期，再落免费档。

只读只作用于媒体上传：当实际存储超过当前派生档位的上限时，可以浏览、编辑画布结构、重命名、删除和导出，但不能上传新媒体。日落期结束后仍超出免费上限的账号，从最后触达时间最早的媒体开始清理，直到回到 50 MB，而不是删除全部数据。任意充值都按 `max(paid_until, now()) + entitlement_days` 延长权益并立即重新计算档位。

## 数据模型

本期新增四组表，全部按第一二期的写法用 GORM 模型定义、`AutoMigrate` 建表。

### 点数余额与流水

```go
type Credit struct {
    UserID          uuid.UUID  `gorm:"type:char(36);primaryKey"`
    PurchasedMicros int64      `gorm:"not null;default:0"`
    GrantedMicros   int64      `gorm:"not null;default:0"`
    PaidUntil       *time.Time `gorm:"type:datetime(3)"`
    UpdatedAt       time.Time
}

type CreditTransaction struct {
    ID                    uuid.UUID  `gorm:"type:char(36);primaryKey"`
    UserID                uuid.UUID  `gorm:"type:char(36);index;not null"`
    Bucket                string     `gorm:"type:varchar(16);not null"` // purchased | granted
    Type                  string     `gorm:"type:varchar(16);not null"` // purchase | consume | refund | grant | expire
    AmountMicros          int64      `gorm:"not null"`
    BalanceAfterMicros    int64      `gorm:"not null"` // 当前桶写入后的余额
    RefType               string     `gorm:"type:varchar(16)"`
    RefID                 string     `gorm:"type:varchar(64);index"`
    RefundOfTransactionID *uuid.UUID `gorm:"type:char(36);uniqueIndex"`
    Note                  string     `gorm:"type:varchar(200)"`
    CreatedAt             time.Time  `gorm:"type:datetime(3);index"`
}
```

MySQL 8.0 不支持 PostgreSQL 风格的部分唯一索引，因此退款幂等通过可空的 `refund_of_transaction_id` 实现：普通流水为 `NULL`，退款流水指向被冲正的消费流水；MySQL 唯一索引允许多行 `NULL`，但同一个非空消费 id 只能出现一次。跨桶消费会生成两条消费流水，退款时也分别指向并退回各自原桶。

`credits` 一个用户一行。第三期上线时为已有用户补零值行，并把创建动作加入后续注册事务；不要等第一次充值才建，否则每个读余额的地方都要处理“行不存在”。

整套账本有两条必须永远成立的不变量：`credits.purchased_micros` 等于该用户 `bucket = purchased` 的 `amount_micros` 之和，`credits.granted_micros` 等于 `bucket = granted` 的对应之和。任何改桶余额的路径都必须在同一事务写流水，禁止裸 UPDATE。

扣减顺序固定为先 `granted`、后 `purchased`。在事务中锁定该用户的 `credits` 行，计算两个桶各扣多少，校验总余额后更新两桶并按实际涉及的桶写一到两条消费流水；不能用两条彼此独立的 UPDATE，否则跨桶扣减可能只成功一半。

```sql
SELECT purchased_micros, granted_micros
FROM credits WHERE user_id = ? FOR UPDATE;
```

总余额不足时不更新任何桶、不写流水，返回 402 `INSUFFICIENT_CREDITS`。`balance_after_micros` 记录当前流水所属桶写入后的余额，不记录两桶合计。

`expire`（点数过期）本期不启用，先把枚举值留好，避免以后加类型时又要动一遍校验白名单和前端文案表。

### 充值档位与订单

```go
type CreditPackage struct {
    ID              string `gorm:"primaryKey;type:varchar(32)"`
    Name            string `gorm:"type:varchar(80);not null"`
    PriceMicros     int64  `gorm:"not null"`
    BonusMicros     int64  `gorm:"not null;default:0"`
    EntitlementDays int    `gorm:"not null;default:30"`
    Currency        string `gorm:"type:varchar(8);not null;default:CNY"`
    Enabled         bool   `gorm:"not null;default:true"`
    Sort            int    `gorm:"not null;default:0"`
}

type Order struct {
    ID              uuid.UUID  `gorm:"type:char(36);primaryKey"`
    UserID          uuid.UUID  `gorm:"type:char(36);index;not null"`
    Provider        string     `gorm:"type:varchar(16);not null"` // alipay | wechat
    ProviderOrderID *string    `gorm:"type:varchar(128);uniqueIndex"`
    PackageID       string     `gorm:"type:varchar(32);not null"`
    PriceMicros     int64      `gorm:"not null"`
    Currency        string     `gorm:"type:varchar(8);not null"`
    PurchasedMicros int64      `gorm:"not null"`
    GrantedMicros   int64      `gorm:"not null"`
    EntitlementDays int        `gorm:"not null"`
    Status          string     `gorm:"type:varchar(16);not null;default:pending"` // pending | paid | failed | refunded
    PaidAt          *time.Time
    CreatedAt       time.Time
    UpdatedAt       time.Time
}
```

价格、购买桶点数、赠送桶点数和权益天数在建单时从 `credit_packages` **快照**到订单行，到账时不回查档位表。`purchased_micros` 与 `price_micros` 1:1，`bonus_micros` 进入 `granted` 桶；提交支付渠道时再把微元换算成分，并要求价格是 10000 微元的整数倍。

`provider_order_id` 的唯一索引是回调幂等的基础设施。建单时若第三方还没返回单号，字段留 `NULL`——唯一索引对 `NULL` 不生效，但**空串会互相冲突**，第二个待支付订单会直接插不进去。因此字段类型必须是 `*string` 而不是 `string`，GORM 下用零值字符串是很容易踩进去的坑。

索引：`(user_id, created_at desc)` 服务用户侧订单列表，`(status, created_at)` 服务超时订单的扫描清理。

### 平台模型目录

```go
type ModelCatalog struct {
    ID          uuid.UUID      `gorm:"type:char(36);primaryKey"`
    Name        string         `gorm:"type:varchar(120);not null"`
    DisplayName string         `gorm:"type:varchar(120);not null"`
    Capability  string         `gorm:"type:varchar(16);not null"` // image | video | text | audio
    Provider    string         `gorm:"type:varchar(60);not null"`
    Constraints datatypes.JSON `gorm:"type:json"`
    CreditCost  datatypes.JSON `gorm:"type:json"`
    FreeTrialEligible bool     `gorm:"not null;default:false;index"`
    Enabled     bool           `gorm:"not null;default:true"`
    Sort        int            `gorm:"not null;default:0"`
    CreatedAt   time.Time
    UpdatedAt   time.Time
}

type ModelPricePromotion struct {
    ID          uuid.UUID      `gorm:"type:char(36);primaryKey"`
    ModelID     uuid.UUID      `gorm:"type:char(36);not null;index"`
    Name        string         `gorm:"type:varchar(120);not null"`
    MatchParams datatypes.JSON `gorm:"type:json;not null"`
    DiscountBPS int            `gorm:"not null"` // 8000 = 8 折
    Priority    int            `gorm:"not null;default:0"`
    Version     int            `gorm:"not null;default:1"`
    Status      string         `gorm:"type:varchar(16);not null;default:draft"` // draft | scheduled | active | ended | disabled
    StartsAt    time.Time      `gorm:"type:datetime(3);not null"`
    EndsAt      time.Time      `gorm:"type:datetime(3);not null"`
    CreatedAt   time.Time
    UpdatedAt   time.Time
}
```

`name` 是发给第三方接口的模型标识，`display_name` 是给用户看的名字，两者必须分开：渠道换了模型 id 而产品名不变的情况很常见，混成一个字段就得改用户可见的文案。

`constraints` 描述这个模型接受哪些参数。这份键集由本期定义，第四期的转发接口拿同一份键做服务端白名单校验，**两边必须逐字一致**，任何一侧改键名都会让另一侧读不到：

```json
{
  "size": ["1024x1024", "1536x1024", "1024x1536"],
  "quality": ["low", "medium", "high"],
  "n": { "max": 4 },
  "duration": [4, 6, 8],
  "resolution": ["480p", "720p", "1080p"],
  "ratio": ["16:9", "9:16", "1:1"],
  "features": ["mask", "referenceImage"]
}
```

键名一律用单数，与请求体里的参数名逐个对应，服务端校验时就不需要再维护一张「参数名到约束键名」的映射表。数组型的键是取值白名单，做精确匹配；对象型的键是范围约束，目前只有 `n` 一个，`max` 给出单次最多生成几个产物；`features` 是能力开关的字符串数组，`mask` 表示支持蒙版、`referenceImage` 表示支持参考图，这类能力没有取值可枚举，塞进一个数组比给每种能力单开一个布尔键要省事得多。

不适用的键直接省略，前端按「键在不在」决定渲染哪些控件，不写模型名的硬编码分支。

`credit_cost` 描述精确参数价格矩阵。图片按分辨率、质量配置单张价格，最终乘 `n`；视频按分辨率与时长逐项配置：

```json
{
  "version": 1,
  "dimensions": ["resolution", "duration"],
  "prices": [
    { "params": { "resolution": "480p", "duration": 5 }, "costMicros": 500000 },
    { "params": { "resolution": "480p", "duration": 10 }, "costMicros": 900000 },
    { "params": { "resolution": "720p", "duration": 5 }, "costMicros": 1000000 },
    { "params": { "resolution": "720p", "duration": 10 }, "costMicros": 1800000 }
  ]
}
```

上面的金额仅用于说明结构，不是正式定价。价格矩阵的 `dimensions` 必须是该模型 `constraints` 键的子集：图片模型如果用 `size` 表示 1K/2K/4K，就配置 `dimensions: ["size", "quality"]`；如果某家模型明确用 `resolution`，则约束和请求也统一使用 `resolution`。`n` 不进矩阵，按单张价格做整数乘法。视频统一用 `resolution` 与 `duration`，后台保存时验证笛卡尔积全部有且只有一个价格。

折扣不改写 `credit_cost` 基础矩阵，单独存进 `model_price_promotions`。空 `match_params` 匹配整模型；`{"resolution":"720p"}` 匹配全部 720p；`{"duration":10}` 匹配全部 10 秒；`{"resolution":"720p","duration":10}` 只匹配该组合。折扣系数使用 `discount_bps`，例如 8000 表示按原价 80% 收取，最终微元向上取整。

多条活动同时有效时不叠加折扣：先选 `match_params` 键最多的规则，再选 `priority` 最大的规则。后台不允许存在同一时间段内可同时命中、具体度和优先级又完全相同的规则；命中这种冲突的保存请求返回 409 `PROMOTION_CONFLICT`，管理后台把冲突的既有规则列表展示出来，让管理员去调整那一条，而不是只给一句「保存失败」。价格解析器返回基础价格、命中活动和折后价格，Phase 4 的报价与真实预扣共用这一实现。

两个 `JSON` 字段不拆成列，是因为不同能力的参数维度完全不同；计价发生在应用层。图片价格矩阵使用模型实际声明的尺寸字段（`size` 或 `resolution`），视频使用模型声明的 `resolution` 与 `duration`，不能在目录层强行改名。`free_trial_eligible` 必须是独立布尔列并默认 false，因为它在生成热路径和后台筛选中需要直接查询，新模型不能自动进入免费范围。

这张表是前端唯一的模型来源：`/api/models` 返回什么，用户就只能选什么，不存在与之并列的用户自定义模型。第四期的转发接口拿同一份 `constraints` 做服务端校验，本期把键集定下来之后两侧都不能再单独改名。渠道的指向关系（一个模型走哪些上游渠道）本期不建，留给第四期引入 `platform_channels` 时补 `channel_ids` 绑定列——本期目录只回答「有哪些模型、怎么计价」，不回答「请求打到哪个上游」。

## 点数扣减的一致性

扣点和生成结果必须一致，这是本期最容易写错的地方，单独讲清楚。

顺序只有两种选择。**先生成后扣**看起来对用户更友好，只在成功后收费，但失败率一高就会漏扣：转发超时、流式中断、进程重启，任何一处丢掉扣点动作，这次生成的成本就白付了，而这类失败在 AI 接口上并不罕见。**先扣后生成**则可能多扣，但多扣是可以退的。

本期采用**先扣后生成、失败自动退还**。判断依据是两类错误的可恢复性不同：漏扣不可恢复，算力已经消耗掉了，事后没有任何办法追回；多扣可恢复，退一笔就行。宁可走多扣退还的路径，也不要走漏扣的路径。

**退还必须走流水并回到原桶。** 每条退款写 `refund_of_transaction_id` 指向被冲正的消费流水，不能直接增加余额，也不能把购买桶消费退进赠送桶。唯一索引保证同一消费流水最多退款一次。

供第四期调用的内部方法就两个：

```go
// 先扣 granted、再扣 purchased，返回实际产生的消费流水
func (s *CreditService) Reserve(ctx context.Context, userID uuid.UUID, amountMicros int64, refID string) ([]CreditTransaction, error)

// 按消费流水逐条退回原桶，靠 refund_of_transaction_id 唯一索引保证幂等
func (s *CreditService) Refund(ctx context.Context, userID uuid.UUID, consumes []uuid.UUID, note string) error
```

`Reserve` 在一个事务中锁定余额、扣桶并写流水；`Refund` 直接尝试插入退款流水，撞上 `refund_of_transaction_id` 唯一冲突视为已经退过。不要先查后写，避免并发双退。

**本期不会产生任何 `type=consume` 的流水**，因为没有任何地方调用 `Reserve`——实际扣减发生在第四期的转发接口里。本期只把这两个方法、账本表和对账不变量建好，并用管理后台的手工增减点数（`type=grant`）验证账本正确。读到这里不要以为本期上线后点数就会自动消耗。

## 用量统计

### 存储与一次性试用使用计数器

`usage_records` 按 `(user_id, metric, period)` 唯一，`period` 本期固定为 `total`。

| metric | period 形态 | 更新时机 |
| --- | --- | --- |
| `storage_bytes` | `total` | 文件上传成功时增加，删除时减少 |
| `free_image_trials` | `total` | 第四期成功占用一次免费图片额度时增加，只增不减 |
| `free_video_trials` | `total` | 第四期成功占用一次免费视频额度时增加，只增不减 |

之所以存储不像生成次数那样实时 `SUM`，是因为它要在**每次上传前**校验，而 `SUM(bytes)` 会随文件数增长逐渐变慢，放在上传热路径上不合适。计数器是这里的必要妥协。

`storage_bytes` 由服务端自己维护，不接受客户端上报。增减必须与 `media_files` 的写入放在同一个事务里，否则并发上传会导致计数漂移。

### 生成次数从生成记录统计，扣费以点数流水为准

这一节要说清楚两套数字的关系，否则很容易在前端把它们混用。

`generations` 表仍然是生成历史的权威来源，「今日生成了多少张」这类**展示用**的数字直接从表里数出来，不需要独立计数器：

```sql
SELECT count(*) FROM generations
WHERE user_id = ? AND kind = ? AND deleted_at IS NULL
  AND created_at >= UTC_DATE()
```

`(user_id, kind, created_at desc)` 索引第二期已经建好，这个查询很便宜。日期按 UTC 算，避免跨时区用户看到的「今日」和服务端不一致。

但**扣费依据不是这张表，而是 `credit_transactions`**。两者记录的是不同性质的事实：`generations` 记录「生成了什么」，是业务历史，用户可以软删除；`credit_transactions` 记录「花了多少点」，是财务事实，永不删除。用户删掉一条生成记录，历史里少一条，已经花掉的点数不会退回来。

因此不要用“生成条数 × 单价”反推消耗。唯一财务对账口径是两个桶分别等于各自流水之和；免费试用则只和 `usage_records` 的一次性计数及领取资格核对，删除生成历史不返还试用。

### 存储用量的自愈

计数与实际占用长期运行后可能出现偏差，例如异常中断的上传。提供一个重算入口：管理后台的用户详情页放一个「重算存储用量」按钮，触发对该用户 `media_files` 的 `SUM(bytes)` 全量统计并覆盖计数。不做定时任务，按需触发即可。

## 媒体保留期与孤儿文件回收

### 保留期按最后触达时间续期

清理范围是**全部媒体，包括画布正在引用的**。这一点必须在产品文案和充值页写清楚，否则用户会以为「只要还挂在画布上就永远不会被删」，等到文件消失才发现不是。

计时方式是这里的关键设计：不是从上传时间起算固定寿命，而是**按最后触达时间续期**。一个媒体的最后触达时间等于所有引用它的画布 `updated_at`、素材 `updated_at`、生成记录 `created_at` 里的最大值；没有任何引用时退化为 `media_files.created_at`。超过所属档位的 `retention_days` 才进入清理范围。

这样设计的效果是：用户还在用的项目，每次自动保存都会把它引用的全部媒体的寿命续上；只有真正被冷落了几周、一次都没打开过的项目才会被清理。按上传时间算固定寿命则会把用户天天在编辑的老项目误删，那是不可接受的。

**不新增 `expires_at` 列。** 加一列意味着每次画布保存、素材更新、生成记录写入都要回头更新它引用的全部媒体行，写放大严重，而且一旦某条路径漏更新就会误删用户还在用的文件。清理任务扫描时现算即可——扫描是低频后台作业，多几个 join 完全无所谓，而误删是不可逆的。

到期前 2 天发邮件加站内预警，列出将被清理的媒体数量与总大小，并提供一键导出入口（复用现有的画布导出）。预警按用户维度发送而不是按文件维度，同一用户 7 天内不重复发，用第一期发信限流那套计数器控制即可，不需要为此新增表。

### 保留期清理与孤儿回收合并为一个扫描任务

孤儿文件回收是第二期遗留给本期的工作。第二期删掉了客户端的垃圾回收（它依赖「前端持有全量数据」这个已经不成立的前提，留着会误删其它画布正在引用的图片），但没有实现服务端的替代品，所以在本期之前，用户删掉画布后其引用的媒体会一直留在磁盘上。这不影响任何人的数据，只是占空间，因此推迟是安全的。

它和保留期清理的输入完全一样，都要扫 `canvases`、`assets`、`generations` 三张表的 `JSON` 字段收集还被引用的 `storage_key`，因此合并成同一个扫描任务。

1. 在 `media_files` 里存在但没有任何引用的 `storage_key`，即孤儿，直接删。
2. 有引用但最后触达时间已超过 `retention_days` 的，即过期媒体，删。

分两次扫是纯粹的浪费，更重要的是两套引用收集逻辑早晚会不一致，届时同一个文件在一个任务里算孤儿、在另一个任务里算有效，排查起来非常痛苦。

两个必须注意的点。**判断引用时不能漏掉软删除的记录**——`deleted_at` 不为空的画布仍可能是用户想恢复的，它引用的文件不该被当成孤儿删掉；软删除记录的 `updated_at` 同样参与最后触达时间的计算，所以一张软删除后再没动过的画布，其独占的媒体会在保留期后随过期清理一起消失，不需要为软删除单独定义一套保留期。**回收要按用户隔离**，绝不能做成全局扫描后统一删除，一旦引用收集逻辑有 bug，影响面就是全部用户而不是一个。

日落期满的降档清理复用同一个任务，只是排序和终止条件不同：按最后触达时间从旧到新删，删到该用户 `storage_bytes` 落回 `free` 档上限以内即停止，不是删光。

建议先做成管理后台按需触发的动作，在单个用户上验证正确后再挂定时任务。清理完成后顺带重算一次该用户的存储用量。

**不给 `media_files` 增加「对象存在性」状态列，也不做定时全量对账。** 对象存储与 MySQL 之间的事务一致性在 v1 的部署规模下不值得引入双写状态机，接受的兜底是三层：上传失败不留半截文件（临时文件 rename）、清理与回收都在扫描后先软删除、存储用量可随时全量重算。出现用量对不上或孤儿告警时走人工核对与重算，等问题真实出现、量级撑出需求了，再把对象生命周期对账立项。

## 接口

### 错误码补充

沿用第一期的错误码总表，本期启用或新增的条目：

| HTTP | code | 触发场景 |
| --- | --- | --- |
| 402 | `INSUFFICIENT_CREDITS` | 余额不足以支付本次请求（第三期起预扣场景）；管理员把余额扣成负数同样拒绝 |
| 403 | `READ_ONLY` | 只读态下执行写操作（上传、生成入口）；与 402 分开——「没余额」和「超额只读」的引导方向不同，混用一个码前端就没法区分该提示充值还是清理 |
| 403 | `ACCOUNT_PENDING_DELETION` | 注销冷静期内调用生成或下单（登记见第一期，本期启用） |
| 409 | `ORDER_ALREADY_PAID` | 取消一个已支付的订单 |
| 409 | `PROMOTION_CONFLICT` | 保存折扣活动时与既有规则存在可同时命中且具体度、优先级完全相同的冲突 |
| 409 | `DELETION_NOT_PENDING` | 未处于注销冷静期时调用撤销注销（登记见第一期，本期启用） |
| 400 | `INVALID_SIGNATURE` | 支付回调验签失败 |

价格矩阵与 `constraints` 的问题不单独设码：缺价、重复价、多余组合、键不在白名单一律 400 `VALIDATION_FAILED` 附 `fields`，管理后台表单按字段渲染错误。

第二期的 507 `STORAGE_QUOTA_EXCEEDED` 继续沿用。上传接口先解析当前档位与只读态，再校验本次上传后的总量；响应带当前档位、已用量和上限，让前端正确提示充值或清理。

### 用量、档位与点数

**GET `/api/me`** 在第一期的基础上增加 `credits` 与 `usage`，`plan` 换成新的档位结构：

```json
{
  "user": { "...": "..." },
  "plan": { "id": "paid", "name": "付费档", "storageBytes": 1073741824, "maxFileBytes": 209715200, "retentionDays": 15 },
  "credits": { "purchasedMicros": 1000000, "grantedMicros": 280000, "totalMicros": 1280000, "paidUntil": "..." },
  "usage": { "storageBytes": 1234567, "freeImageTrialsUsed": 1, "freeVideoTrialsUsed": 0 },
  "mediaExpiry": { "nearestAt": "2026-09-20T00:00:00Z", "expiringCount": 3 },
  "deletion": { "status": "none", "scheduledAt": null },
  "readOnly": false,
  "graceEndsAt": null
}
```

`mediaExpiry` 是服务端按「最后触达时间 + 档位保留期」现算出的最近一批到期媒体，`expiringCount` 只统计未来 2 天内到期的数量，供前端渲染到期预警条；没有将到期的媒体时 `nearestAt` 为 `null`。`deletion` 反映注销冷静期状态，前端据此展示撤销入口。

`plan` 里不再有每日额度字段。`plan.id` 由统一档位解析器根据 `purchasedMicros` 与 `paidUntil` 实时判定，`grantedMicros` 不产生付费身份。

`readOnly` 与 `graceEndsAt` 是服务端算好的派生字段。判定规则虽然只有两个条件，但让前端各自实现一遍必然出现口径不一致，而这个口径直接决定用户看到的是「充值」还是「清理文件」。

`usage` 里的生成次数只用于展示，不参与任何拦截判断。

### 点数与流水

**GET `/api/credits`** 需登录，返回双桶余额、权益截止时间与最近流水摘要：

```json
{
  "purchasedMicros": 1000000,
  "grantedMicros": 280000,
  "totalMicros": 1280000,
  "paidUntil": "...",
  "recent": [
    { "id": "t1...", "bucket": "purchased", "type": "purchase", "amountMicros": 1000000, "balanceAfterMicros": 1000000, "refType": "order", "refId": "o1...", "note": "标准包", "createdAt": "..." }
  ]
}
```

`recent` 固定返回最近 5 条，供个人中心的余额卡片直接渲染，省掉一次分页请求。

错误：`UNAUTHORIZED`。

**GET `/api/credits/transactions?cursor=&size=&type=`** 游标分页，形状与第二期的生成记录一致：

```json
{
  "items": [
    { "id": "t2...", "bucket": "granted", "type": "consume", "amountMicros": -20000, "balanceAfterMicros": 260000, "refType": "generation", "refId": "g1...", "note": "GPT Image · hd", "createdAt": "..." }
  ],
  "nextCursor": "eyJ0..."
}
```

`cursor` 是 `base64url(created_at 的 RFC3339Nano 形式 + "|" + id)`，对客户端不透明，解不出来返回 `VALIDATION_FAILED`。`size` 缺省 20、上限 100。`type` 可选，按流水类型筛选，不在枚举内返回 `VALIDATION_FAILED`。

用游标而不是页码的理由与生成记录相同：流水是只增历史流，`COUNT(*)` 会随时间线性变慢，而新流水插在头部会让 offset 分页出现重复项和漏项。

流水**只读，没有任何写接口**。所有写入都由服务端在业务事务里完成，前端没有任何途径能伪造一条记录。

错误：`UNAUTHORIZED`、`VALIDATION_FAILED`。

### 充值档位与订单

**GET `/api/credit-packages`** 需登录，返回 `enabled = true` 的档位，按 `sort` 升序：

```json
{
  "items": [
    { "id": "standard", "name": "标准包", "priceMicros": 30000000, "purchasedMicros": 30000000, "bonusMicros": 1000000, "entitlementDays": 30, "currency": "CNY" }
  ]
}
```

错误：`UNAUTHORIZED`。

**POST `/api/orders`** 请求 `{ "packageId": "standard", "provider": "alipay" }`，成功 201：

```json
{
  "order": { "id": "o1...", "packageId": "standard", "priceMicros": 30000000, "currency": "CNY", "purchasedMicros": 30000000, "grantedMicros": 1000000, "entitlementDays": 30, "status": "pending", "createdAt": "..." },
  "payment": { "type": "qrcode", "payload": "https://qr.alipay.com/..." }
}
```

订单分别快照购买桶、赠送桶和权益天数，不存一个无法解释来源的合计点数字段。

`payment.type` 取 `qrcode`、`redirect`、`clientSecret`，前端据此决定渲染二维码、跳转还是拉起渠道 SDK。三个渠道的形态差异全部收敛在这一个字段里，前端不写 `if (provider === "alipay")` 这类分支。

错误：`VALIDATION_FAILED`（档位不存在或已下架、`provider` 不在枚举内）、`UNAUTHORIZED`、`RATE_LIMITED`（同用户 10 单/小时，防止刷出大量垃圾待支付订单）。

**GET `/api/orders?cursor=&size=&status=`** 游标分页返回当前用户的订单，形状与流水列表一致，`items` 里是订单对象。错误：`UNAUTHORIZED`、`VALIDATION_FAILED`（游标无法解码或 `status` 不在枚举内）。

**POST `/api/orders/{id}/cancel`** 取消待支付订单，成功 200 返回更新后的订单。只有 `pending` 状态能取消。

错误：`NOT_FOUND`（订单不存在，**或订单不属于当前用户**——与第二期一致，跨用户访问返回 404 而不是 403）、`ORDER_ALREADY_PAID`。

### 支付回调

**POST `/api/payments/webhook/{provider}`** 公开路由，不走 `RequireAuth`，但**必须验签**。

请求体是各渠道自己的格式，不做统一约定。每个渠道一个适配函数，把原始报文验签并解析成统一的 `{ providerOrderID, outTradeNo, priceMicros, status }` 再进入同一套处理流程；只有调用渠道 SDK 时才把 `priceMicros` 换算为分。

两个单号的语义要写死：**`outTradeNo` 就是本站的 `orders.id`**，下单时作为商户订单号传给渠道，回调时用它定位订单行；**`providerOrderID` 是渠道侧自己的交易号**，落 `provider_order_id` 列并靠它的唯一索引做幂等。适配函数绝不能用渠道交易号反查订单——它只负责记录，定位永远走我方订单号。

响应格式**按渠道要求返回**，支付宝要 `success` 纯文本，微信要固定结构的 JSON，Stripe 只看 2xx。这一处不能套用项目统一的错误响应格式，否则渠道会判定回调失败并持续重试。

错误：`INVALID_SIGNATURE`（400）、`NOT_FOUND`（本地找不到对应订单）。**验签失败一律拒绝**，不提供任何跳过验签的开关或环境变量，调试用渠道自己的沙箱环境。

`NOT_FOUND` 返回非成功响应，让渠道按自身策略重试——这同时就是「回调先于下单响应到达」的处理机制：下单事务尚未提交时回调查不到订单，渠道稍后重推，重推时订单已在；配合下面「超时订单要清理」一节里支付前主动查询的兜底，回调整体丢失也不会漏到账。不为此建延迟重放表，渠道重试加主动查询已经覆盖。

到账的具体处理逻辑与幂等保证见下面的「支付实现要点」，那一节的五条都是硬性要求。

### 账号注销

**POST `/api/me/deletion`** 需登录，请求体 `{ "password": "..." }`。校验密码后把账号置为 `pending_deletion` 并预约 7 天后的匿名化任务，返回 200 与 `{ "scheduledAt": "..." }`。效果立即生效：生成与下单被 403 `ACCOUNT_PENDING_DELETION` 拦截，浏览、导出、删除自己的数据不受限。重复调用幂等，返回同一个 `scheduledAt`，不重置倒计时。错误：401 `INVALID_CREDENTIALS`（密码错误，不泄露其他信息）、409 `DELETION_NOT_PENDING` 不会出现在这里（重复申请按幂等成功处理）。

**POST `/api/me/deletion/cancel`** 需登录，无请求体。仅当 `deletion.status === "pending"` 时有效，账号恢复 `active` 并取消匿名化任务，返回 200；未处于冷静期时返回 409 `DELETION_NOT_PENDING`。

匿名化到期由后台任务执行（与超时订单扫描同一类定时任务），把账号置 `disabled`、写入占位邮箱与用户名、清空密码哈希、撤销全部 refresh token、软删除该用户全部业务数据。`/api/me` 的 `deletion` 字段（状态与 `scheduledAt`）随每次返回携带，前端不需要单独的状态查询接口。

### 模型目录

**GET `/api/models?capability=`** 需登录，返回 `enabled = true` 的模型，按 `sort` 升序，`capability` 可选：

```json
{
  "items": [
    {
      "id": "m1...",
      "name": "gpt-image-1",
      "displayName": "GPT Image",
      "capability": "image",
      "provider": "openai",
      "constraints": { "size": ["1024x1024", "1536x1024"], "quality": ["low", "medium", "high"], "n": { "max": 4 }, "features": ["referenceImage"] },

```

错误：`UNAUTHORIZED`、`VALIDATION_FAILED`（`capability` 不在枚举内）。

### 上传接口增加总量校验

第二期已有的 `PUT /api/media/{storageKey}` 增加两条校验，顺序不能颠倒：

1. 实际用量超过当前派生档位上限时返回 402 `INSUFFICIENT_CREDITS`，响应体带当前 `planId` 与日落期结束时间；只有付费权益有效才恢复 `paid` 上限。
2. 当前 `storage_bytes` 加上本次文件大小超过所属档位的 `storage_bytes`，返回 507 `STORAGE_QUOTA_EXCEEDED`，响应体带 `{ "used": ..., "limit": ... }`。

校验与写入必须在同一事务内，先占用后写盘，失败则回滚计数。

全部路由挂在 `/api/admin` 下，由独立的 `RequireAdmin` 中间件校验 `role = admin`。中间件要在 `RequireAuth` 之后执行，非管理员返回 403 `FORBIDDEN`。

用户列表响应：

```json
{ "items": [ { "id": "...", "email": "...", "username": "...", "role": "user", "status": "active", "emailVerified": true, "planId": "paid", "purchasedMicros": 1000000, "grantedMicros": 280000, "paidUntil": "...", "storageBytes": 123, "createdAt": "..." } ], "total": 128, "page": 1, "size": 20 }
```

两个列表接口的分页参数直接沿用第二期给业务资源定的那套约定，不另立一份：`page` 从 1 开始、缺省 1，`size` 缺省 20、上限 100，越界返回 `VALIDATION_FAILED`；`sort` 走白名单枚举再映射到列名，不能把参数拼进 SQL，前缀 `-` 表示倒序，两个接口都缺省 `-createdAt`，不在白名单内返回 `VALIDATION_FAILED`。`/api/admin/users` 的白名单是 `createdAt`、`purchasedMicros`、`grantedMicros`、`storageBytes`；`/api/admin/orders` 的白名单是 `createdAt`、`priceMicros`。管理后台必须明确显示两个点数桶，不再出现“余额”这种无法说明来源的单一排序字段。

`planId` 不是 `users` 表上的列，筛选与展示必须复用统一档位表达式：购买桶非零或权益未过期为 `paid`，权益过期 60 天内为 `sunset`，其余为 `free`。列表里的两个桶与存储用量通过一次 join 取齐，不能逐行查询。

全部管理接口的公共错误：`UNAUTHORIZED`（未登录）、`FORBIDDEN`（非管理员）、`NOT_FOUND`（用户或资源不存在）、`VALIDATION_FAILED`（参数不合法），下面只列各接口特有的部分。

`PATCH /api/admin/users/{id}` 不允许改 `planId`。档位由购买桶和 `paid_until` 派生；线下收款补单必须明确进入 `purchased` 桶并按规则延长权益，普通补偿进入 `granted` 桶且不升档。

**POST `/api/admin/users/{id}/credits`** 请求 `{ "bucket": "granted", "amountMicros": 500000, "note": "客服补偿" }`，金额正增负减，成功返回两个桶的新余额。`bucket` 和 `note` 都必填。

必须写入指定桶的 `type=grant` 流水，`ref_type=admin`、`ref_id` 为管理员 id。禁止直接改任一桶；指定桶扣到负数时返回 402。

**DELETE `/api/admin/models/{id}`** 是硬删除，但只允许删从未被使用过的模型；已经产生过流水的模型只能置 `enabled = false`。流水的 `note` 里存了模型名，删掉目录行不会让历史流水失去可读性，但把用户正在用的模型删掉，会让前端下拉里的选中项凭空消失。

`credit_packages` 只提供 GET、POST、PATCH，**没有 DELETE**：订单行引用了 `package_id`，删掉档位会让历史订单查不到来源。下架用 `enabled = false`。

### 封禁的即时生效

把用户改成 `disabled` 后，其已签发的 access token 在 15 分钟内仍然有效。必须同时**撤销该用户全部 refresh token**，这样最多 15 分钟后就会因无法刷新而彻底掉线。

如果要求立即生效，需要在鉴权中间件里每次查库确认用户状态，代价是每个请求多一次查询。本期采用撤销令牌的方案，在管理后台的操作提示里说明「最多 15 分钟后完全生效」。

## 支付实现要点

支付是本期唯一一处「出错会直接造成资金差错」的地方，下面五条都不是可选项。

**回调必须幂等。** 同一个 `provider_order_id` 重复回调只能到账一次。渠道会因为超时、网络抖动、主动重推等原因重复发送同一个回调，这是常态而不是异常。保证方式是订单表的唯一约束加状态机：到账时用一条带条件的 UPDATE 完成状态跃迁。

```sql
UPDATE orders SET status = 'paid', paid_at = now(), updated_at = now()
WHERE id = $1 AND status = 'pending'
```

影响行数为 1 才继续加点数，为 0 说明这一单已经处理过，**直接返回成功响应给渠道，不要报错**——返回错误会让渠道认为回调失败并无限重试。

**到账必须是一个事务。** 更新订单状态、增加两个桶、延长 `paid_until`、写对应流水必须一起提交，任何一步失败整体回滚。

**不要信任回调里的金额。** 到账桶金额与权益天数取本地订单快照，回调金额只和 `price_micros` 换算后的渠道金额比较；不一致时拒绝到账并记录错误，绝不能覆盖本地记录。

**验签失败一律拒绝。** 不提供 `SKIP_SIGNATURE_VERIFY` 之类的开关，也不因为「本地调试不方便」临时放宽——伪造回调等于凭空造钱，这是整条支付链路上唯一一个能被外部直接攻击的入口。各渠道的公钥或密钥从环境变量读取，缺失时启动失败并明确报错，写法与第一期校验 SMTP 变量一致。

**超时订单要清理。** `pending` 订单超过 30 分钟未支付即置为 `failed`，用一个每 5 分钟跑一次的后台任务扫描 `(status, created_at)` 索引。置失败前必须先向渠道**主动查一次真实状态**，不能只看本地时间就判失败：用户可能在最后一秒付款而回调还在路上，直接置失败就会出现「钱付了、订单是 failed、点数没到」的差错。查到已支付的走正常到账流程，这条主动查询同时也是回调整体丢失时的兜底。

`admin_audit_logs` 至少包含 `id`、`actor_user_id`、`action`、`target_type`、`target_id`、`request_id`、`before_summary`、`after_summary`、`reason`、`created_at`。版本摘要只保存脱敏后的价格、折扣、状态和版本，不保存 API Key、提示词、媒体内容或完整用户凭据；审计记录只能追加，不能通过业务接口修改或删除。

```go
type Provider interface {
    CreatePayment(ctx context.Context, order *model.Order) (*PaymentParams, error)
    VerifyAndParse(ctx context.Context, r *http.Request) (*CallbackResult, error)
    QueryOrder(ctx context.Context, order *model.Order) (*CallbackResult, error)
}
```

配额与档位逻辑集中在 `service/quota.go`，不要散落在 handler 里，否则第二期的上传接口和本期的用量查询会出现两份不一致的判断。

## 前端改造

### 个人中心 `web/src/pages/profile/index.tsx`

在第一期的资料与改密码基础上，增加当前档位、点数余额、存储用量进度条与最近 5 条流水。存储用量用 Ant Design 的 `Progress`，接近上限时变色提示。

处于只读态时在页面顶部放一条 Alert，写明宽限期截止时间、到期后会清理什么、以及充值和导出两个入口。这条提示不能用 `message` 弹一下就消失，它需要一直在——用户很可能是几天后才回来看的。

`mediaExpiry.nearestAt` 落在未来 2 天内时，页面顶部同样放一条常驻 Alert：「有 N 个媒体将在 X 后因长期未使用被清理」，附一键导出入口。画布列表页顶部复用同一个查询（`/api/me` 已带数据）渲染同一条预警，两处共用一个私有程度高的全局 hook（`use-media-expiry`）即可，不要各写一份倒计时逻辑。

页面底部放「危险区」：注销账号入口。点击后弹确认 Modal，写清三件事——余额不退、冷静期 7 天内可撤销、到期后数据清理且不可恢复——要求输入密码确认后调 `POST /api/me/deletion`。冷静期内（`deletion.status === "pending"`）这条 Alert 显示截止时间与「撤销注销」按钮，点撤销调 cancel 接口并刷新 `/api/me`。

### 充值与订单 `web/src/pages/billing/`

档位卡片列表加订单历史两块。点击档位调 `POST /api/orders`，按 `payment.type` 渲染：`qrcode` 弹二维码 Modal，`redirect` 跳转，`clientSecret` 拉起渠道 SDK。

支付完成的感知**不能只靠回调**，因为回调打到的是服务端，前端并不知道。二维码 Modal 打开期间轮询订单详情，直到状态变成 `paid` 或用户关闭弹窗，轮询间隔 3 秒、最多 10 分钟。到账后让 `/api/me` 与 `/api/credits` 的 react-query 查询失效，余额和档位自动刷新，不要手写同步逻辑。按项目既有约定，轮询定时器要在 effect 的 cleanup 里清理干净。

轮询达到 10 分钟上限仍不是 `paid` 时，明确停止轮询并提示「支付确认可能有延迟；若你已完成支付，点数会自动到账，可稍后刷新查看」，**不要**把订单标成失败、也不要让用户重新下单——渠道回调或主动查询晚到时订单仍会正常到账，前端抢先判失败只会制造客诉。订单列表里的状态徽标只有 `pending / paid / failed` 三种，与后端枚举一一对应，不自创「处理中」之类的前端态。

订单列表用 `useInfiniteQuery` 配 `nextCursor`，与生成记录同一套写法。

### 生成入口的点数拦截

生成前可以用 `/api/me` 的 `totalMicros` 做即时 UI 提示，但最终是否走免费额度、扣多少点以第四期 `/api/ai/quote` 和真实请求的同一服务端逻辑为准。

但要写清楚：**本期的前端拦截只是体验优化，真正的扣点在第四期的转发接口里。** 前端算出的预估价只用于展示「本次消耗 N 点」，不要据此在本地扣减任何数字，也不要在生成后自己往流水里写东西——流水根本没有写接口。

原来读 `plan.dailyImages` 与 `usage.imageGenerateToday` 做拦截的代码要整块删除，不要留成两套配额判断并存。

涉及位置是 `web/src/pages/image/index.tsx`、`web/src/pages/video/index.tsx`，以及画布内的生成逻辑 `web/src/components/canvas/canvas-node-generation.ts`。三处都要接，不要漏掉画布内生成。

### 模型选择与动态表单

模型下拉的数据源改为 `GET /api/models`，参数表单**按 `constraints` 动态渲染**，不在前端硬编码每个模型支持哪些尺寸。

渲染规则就是看键在不在：有 `size` 或 `ratio` 就渲染对应选择器，有 `duration` 就渲染时长选择，有 `quality` 就渲染质量选择，有 `resolution` 就渲染分辨率选择，有 `n` 就渲染生成数量输入并把 `n.max` 作为上限，`features` 里含 `referenceImage` 才显示参考图上传、含 `mask` 才显示蒙版入口，键不存在就不渲染该控件。

切换模型时要校验当前已选参数在新模型的 `constraints` 里是否仍然合法，不合法就回落到第一个可选值。漏掉这一步会出现「换了模型但尺寸还是上一个模型独有的值」，一直到第四期的转发接口才报错，用户完全看不懂。

生成页既展示当前组合的 `N 点（¥X.XX）`，也提供“查看价格表”：图片按 1K/2K/4K、质量列出，视频用分辨率为行、时长为列展示。参数变化时先根据目录矩阵即时更新，再防抖请求服务端报价覆盖显示；未拿到有效报价凭证时生成按钮不可提交。

平台模型与第二期用户自带渠道的模型要在 UI 上分开，不要混进同一个下拉——两者的计费主体完全不同，一个花点数，一个花用户自己的第三方额度，混在一起用户根本不知道这一次生成花的是谁的钱。

### 上传超额与只读态的处理

媒体上传遇到 507 `STORAGE_QUOTA_EXCEEDED` 或 402 `INSUFFICIENT_CREDITS` 时，**不要让整个保存操作失败**。画布、素材、生成记录本身的元数据体量很小，应当照常写入服务端，只是其中引用的媒体文件缺失。

这个区分很重要：如果因为一张图超额就让整张画布保存失败，用户的编辑成果会直接丢掉。正确做法是元数据先落库，上传失败的 `storageKey` 收集起来统一提示。两个错误码的引导方向不同，文案要分开：507 引导去清理文件，402 引导去充值并说明宽限期还剩多久。

### 管理后台 `web/src/pages/admin/`

四个页面：`users/`、`models/`、`credit-packages/`、`orders/`。

按项目既有约定组织：页面私有组件放各自目录的 `components/` 下，不要放到共享目录；表格配色、卡片阴影、深浅主题分支统一在 `web/src/lib/app-theme.ts` 配置，页面组件里不写 `dark ? ... : ...` 这类判断。

列表统一用 Ant Design `Table` 配 `@ant-design/pro-components`（项目已有依赖），支持搜索、筛选、分页。用户页的行操作包含封禁解封、增减点数、重置密码、触发清理扫描、查看详情。

模型页支持新增、编辑、上下架，`constraints` 与 `credit_cost` 两个 `JSON` 字段使用受控表单，不做裸 JSON 文本框。模型详情增加“折扣活动”区域，可选择整模型、一个参数或多个参数组合，设置折扣、开始结束时间和优先级，并实时预览受影响的价格矩阵。已排期活动进入 `scheduled` 后不能覆盖编辑，修改必须保存为新版本；活动支持停用但不删除，后台显示当前状态和历史版本。键集变更必须同时修改后端校验、后台表单、促销匹配和生成页动态渲染。

### 路由与守卫

`/admin` 下各页挂在 `RequireAuth` 内层再包一个 `RequireAdmin`，非管理员重定向到首页而不是登录页。`/billing` 只需要 `RequireAuth`。顶栏用户下拉在 `role === "admin"` 时多出「管理后台」入口，所有登录用户都多出「充值」入口并显示当前余额。

前端隐藏入口只是体验优化，**真正的权限判断在后端中间件**，两者都要做。

### 国际化

在 `zh-CN.ts` 与 `en-US.ts` 同步新增 `admin.*`、`billing.*`、`credits.*` 三段，保持两个文件对称。原有 `quota.*` 里关于每日生成次数的文案要删除，不要留着不用。

## 验收清单

点数账本：

- 管理后台向 `granted` 桶增加 500,000 点后，只有 `granted_micros` 增加，流水带正确 `bucket`、`amount_micros` 与 `balance_after_micros`，档位仍为 `free`。
- 对任意用户分别执行 `SUM(amount_micros)` 并按 `bucket` 分组，结果始终等于 `credits` 两个桶；充值、赠送、跨桶扣减和退还后重复验证。
- 管理员扣减指定桶到负数被拒绝，两个桶和流水都不变。
- 并发发起多次跨桶扣减，最终不超扣，也不出现只扣一个桶的半事务。
- 流水没有任何写接口，前端无法伪造记录。
- 第一阶段已批准的同一赠送活动重放多次只向 `granted` 桶入账一次，不产生付费身份。
- 本期部署上线后不会自动产生生成用 `type=consume` 流水，直到第四期接入平台模型转发。

扣点失败退还：

- 让一次 Reserve 同时消耗 `granted` 与 `purchased`，再 Refund 后两个桶分别回到原值，并产生两条指向原消费流水的退款记录。
- 对同一消费流水连续 Refund 两次，第二次因 `refund_of_transaction_id` 唯一约束按成功幂等处理，只退款一次。
- 总余额不足时 Reserve 返回错误且不改变任何桶、不产生流水。

支付与订单：

- 订单快照包含 `priceMicros`、`purchasedMicros`、`grantedMicros` 与 `entitlementDays`；管理员修改档位后，已创建订单快照不变。
- 同一个 `provider_order_id` 重复回调只到账一次，购买和赠送各写一条对应桶流水，第二次仍返回渠道要求的成功响应。
- 伪造签名的回调返回 400 `INVALID_SIGNATURE`，订单状态与余额都不变。
- 回调金额与本地 `price_micros` 换算值不一致时拒绝到账，日志有 error 记录。
- 在到账事务中人为让写流水失败，订单状态回滚为 `pending`、余额不变，重推回调能正常到账。
- 取消已支付的订单返回 409 `ORDER_ALREADY_PAID`；用另一个账号的订单 id 调取消返回 404。
- 待支付订单超过 30 分钟被置为 `failed`，且置失败前向渠道主动查过一次真实状态；把渠道状态构造成已支付时，该订单转为正常到账而不是 `failed`。
- 连续充值两次时 `paid_until` 从原截止时间继续延长，不会从当前时间重算导致权益缩短。

账号注销：

- 申请注销需要校验密码，重复申请幂等；申请后立即无法生成与充值，但能登录浏览和导出。
- 冷静期内撤销后账号恢复 `active`，一切功能正常，匿名化任务不再处理该账号。
- 人工把冷静期调短（或直接推进过期时间）后，匿名化任务把 `display_name`、`avatar_url` 清空，`email` 与 `username` 变成不可登录的占位值，refresh token 全部失效，业务表按用户软删除。
- 注销后用原邮箱重新注册是新账号：没有旧画布、没有旧余额、免费赠送按新账号风控。
- `credit_transactions` 与 `orders` 的金额保留可读，但无法通过任何接口反查出注销前身份。

档位与只读：

- 只有 `granted` 余额的新用户仍为 `free`，能在 50 MB 上限内正常上传。
- 充值后 `/api/me` 的 `plan.id` 立刻变成 `paid`，`storageBytes`、`maxFileBytes`、`retentionDays` 同步变大，全程不需要管理员操作。
- 购买桶耗尽但 `paid_until` 未到时仍为 `paid`；权益到期后进入 `sunset`，60 天结束后才进入 `free`。
- 当前用量超过派生档位上限时 `readOnly` 为 true，媒体上传被拒；浏览、结构编辑、删除和导出仍可用。
- 只读态下仍能浏览画布、编辑画布结构、重命名、删除数据、导出 zip。
- 只读用户充值后立刻恢复 `paid` 上限和上传能力。
- 存储接近上限时上传被拒绝，返回 507 `STORAGE_QUOTA_EXCEEDED` 且响应体含 `used` 与 `limit`。
- 并发上传多个文件后，`usage.storageBytes` 与 `media_files` 的 `SUM(bytes)` 一致。
- 「重算存储用量」能修正人为改坏的计数。
- 全库与全前端代码里都不再出现 `subscriptions`、`dailyImages`、`dailyVideos`。

保留期与清理：

- 删除一张画布后触发清理扫描，它独占的图片从磁盘消失、存储用量下降；被其它画布或素材共用的图片**不会**被删。
- 一个媒体只被一张画布引用时，把该画布的 `updated_at` 改到 `retention_days` 之前，扫描后该媒体被清理；重新编辑一次画布让 `updated_at` 刷新，同一个媒体不再被清理，验证按最后触达时间续期生效。
- 软删除但仍在保留期内的画布，其引用的媒体不会被清理。
- 同一次扫描同时产出孤儿与过期两个结果集，日志里能看到两者分别清理了多少个文件、多少字节。
- 日落期满的降档清理按最后触达时间从旧到新删，删到 `storage_bytes` 落回 `free` 上限即停止，不会把用户媒体删光。
- 到期前 2 天收到预警邮件与站内提示，提示里有可用的一键导出入口，同一用户不会每天重复收到。

模型目录：

- 管理员新增一个模型后，前端生成页的下拉里立刻出现，参数表单按 `constraints` 渲染出对应控件。
- 从某个模型的 `constraints` 里去掉 `quality` 后，前端不再渲染质量选择器，其余控件不受影响。
- 切换模型时不合法的已选参数自动回落到第一个可选值，不会把上一个模型独有的取值带过去。
- 图片价格表能展示 1K/2K/4K 与质量组合的点数和人民币；视频价格表以分辨率为行、时长为列展示全部合法组合。
- 选择 480p/5 秒、480p/10 秒、720p/5 秒等不同组合时，生成按钮旁的当前价格立即变化，且不存在合法参数却没有价格的情况。
- 后台拒绝保存缺少组合、重复组合、负价格或包含 `constraints` 外参数的价格矩阵。
- 创建整模型 9 折后，所有组合显示相同折扣；再创建 720p 8 折后，720p 使用 8 折，其余仍为 9 折。
- 同时创建 10 秒 8.5 折和 720p/10 秒 7 折后，720p/10 秒只命中 7 折，不叠加其他活动。
- 后台拒绝无效折扣、结束时间不晚于开始时间、`match_params` 不在模型约束内，以及时间重叠且具体度与优先级相同的冲突规则。
- 停用或修改活动后版本递增，生成页价格矩阵刷新，历史基础价格不被改写。
- 活动到达 `starts_at` 或 `ends_at` 后，前端依据 `nextPricingChangeAt` 自动刷新完整价格矩阵，不需要用户手工刷新页面。
- 活动进入 `scheduled` 后修改会生成新版本，旧版本和对应审计记录仍可查询，不能直接覆盖历史活动。
- 关闭 `PRICING_PROMOTION_ENABLED` 后所有新报价回到基础价，旧折扣 token 全部失效；恢复开关后仍需重新报价，不能复用旧 token。
- 管理员停用活动、修改活动和切换全局开关都能按 request id 查询审计记录。
- 已产生过流水的模型无法硬删除，只能下架；下架后前端下拉里消失，历史流水仍能读出模型名。
- 充值档位没有删除入口，下架后 `GET /api/credit-packages` 不再返回，但历史订单仍能查到来源档位。
- 平台模型与用户自带渠道的模型在界面上分开展示，能一眼看出这次生成花的是点数还是自己的第三方额度。

管理后台：

- 管理员能按邮箱、状态与 `planId` 筛选用户，列表展示购买桶、赠送桶、`paidUntil`、当前档位和存储用量。
- 封禁用户后其 refresh token 全部失效，最多 15 分钟后完全掉线。
- 管理员重置用户密码后，该用户全部设备被踢下线。
- **非管理员账号直接请求 `/api/admin/users`、`/api/admin/models`、`/api/admin/credit-packages`、`/api/admin/orders` 一律返回 403**，即使前端入口被隐藏也拦得住。
- 非管理员访问 `/admin` 下任意路由被重定向到首页。
- 订单列表能按状态、渠道、用户筛选，能看到每单对应的点数与到账时间。
- 模型页用受控表单编辑 `constraints`、价格矩阵和限时折扣，可预览整模型、分辨率、时长与完整组合折后的价格。

一致性：

- 管理后台与充值页在深色与浅色主题下配色正常，且没有在页面组件里写主题分支。
- `bun run typecheck` 通过，两个语言包 key 结构对称。
